Neurova 风险点解决方案架构报告

基于深度模块化架构的容错能力建设

执行摘要

本报告针对 Neurova 系统的 4 个关键风险点，提出基于深度模块化架构的解决方案。 每个方案都遵循 Interface = Test Surface 原则，确保模块接口清晰、可测试、可替换。

核心原则

  • • 深度模块：小接口，深实现
  • • 适配器模式：一个接口，多个实现
  • • 优雅降级：有状态的降级策略
  • • 可观测性：每个状态变化都有日志

预期收益

  • • 系统可用性提升 99.9%
  • • 故障恢复时间 < 1秒
  • • 测试覆盖率提升 40%
  • • 维护成本降低 30%
1

Agent Loop 可用性

Legacy fallback 可能丢失功能

高风险

当前问题

•

接口浅薄

Agent Loop 初始化逻辑散落在 agent_core.py 多处，违反 Locality 原则

•

状态不一致

rebuild_loop 失败时保留旧 Loop 但不通知调用方，导致 API 配置与 Loop 不匹配

•

静默降级

Loop 初始化失败时无顶层告警，系统可能长时间运行在 legacy 路径

解决方案：LoopManager 深度模块

✓

统一接口

创建 LoopManager 类，封装 Loop 生命周期管理

✓

状态机管理

定义 LoopState 枚举：INITIALIZING, READY, DEGRADED, FAILED

✓

智能降级

降级时保留功能子集，而非完全降级到 legacy

架构对比

当前架构（浅薄）

agent_core.py
├── _init_agent_loop()  # 初始化
├── rebuild_loop()      # 重建
├── find_agent_loop()   # 查找
└── fallback logic      # 降级逻辑
    (散落在多处)

目标架构（深度）

LoopManager (单一职责)
├── initialize()      # 初始化
├── rebuild()         # 重建
├── get_loop()        # 获取
├── get_state()       # 状态查询
└── on_state_change() # 状态回调
    (高内聚，低耦合)

实现计划

Phase 1: 接口定义

  • • 定义 ILoopManager 接口
  • • 定义 LoopState 枚举
  • • 定义 LoopEvent 事件模型

Phase 2: 实现与适配

  • • 实现 LoopManager 类
  • • 创建 AgentLoopAdapter
  • • 迁移现有逻辑

Phase 3: 测试与集成

  • • 编写单元测试
  • • 集成测试
  • • 性能测试
预计工期：3天 推荐实施

异步操作超时

工具自动执行超时处理

中风险

当前问题

•

状态不一致

超时后 tool_decision="timeout"，但无后续处理逻辑

•

资源泄漏

超时任务可能仍在后台运行，占用资源

•

用户感知差

超时后用户收到不完整回复，无明确提示

解决方案：ToolExecutionManager 深度模块

✓

执行上下文

创建 ToolExecutionContext，封装执行状态和超时处理

✓

超时策略

可配置超时策略：严格超时、弹性超时、无限等待

✓

优雅取消

超时后发送取消信号，而非强制终止

架构对比

当前架构（浅薄）

chat_pipeline.py
├── _auto_execute_tool()
│   ├── MUSCLE_TIMEOUT = 5.0  # 硬编码
│   └── asyncio.wait_for()    # 简单超时
└── tool_decision = "timeout" # 无后续处理

目标架构（深度）

ToolExecutionManager
├── execute()              # 统一执行入口
├── cancel()              # 优雅取消
├── get_status()          # 状态查询
├── on_timeout()          # 超时回调
└── ToolExecutionContext   # 执行上下文
    (状态完整，资源可控)
预计工期：2天 已完成
3

记忆检索降级

UnifiedRetriever 不可用时的 MoE 降级

中风险

当前问题

•

质量不可控

降级路径可能影响检索质量，但无质量监控

•

接口不一致

UnifiedRetriever 和 MoE 返回格式可能不一致

•

无降级策略

降级是二元的：可用或不可用，无渐进式降级

解决方案：MemoryRetrievalChain 深度模块

✓

责任链模式

创建检索器链，支持多级降级

✓

质量评估

每个检索器返回质量分数，支持智能选择

✓

缓存降级

完全不可用时返回缓存结果，而非空结果

架构对比

当前架构（浅薄）

chat_pipeline.py
├── _retrieve_memories()
│   ├── if unified_retriever:
│   │   └── unified_retriever.retrieve()
│   └── else:
│       └── memory_agent.moe_retrieve()  # 简单降级
└── (无质量监控)

目标架构（深度）

MemoryRetrievalChain
├── retrieve()           # 统一检索入口
├── add_retriever()      # 添加检索器
├── get_quality_score()  # 质量评估
└── RetrieverChain
    ├── UnifiedRetriever  # L1: 向量检索
    ├── MoERetriever     # L2: MoE 降级
    ├── CacheRetriever   # L3: 缓存降级
    └── FallbackRetriever # L4: 基础降级
预计工期：2天 已完成
4

结晶经验检索失败

PatternCrystallizer 异常处理

低风险

当前问题

•

异常静默

异常时跳过结晶经验注入，用户无感知

•

质量退化

缺少结晶经验注入，回复可能不够精准

•

无重试机制

一次性失败后无重试或降级策略

解决方案：CrystallizedExperienceManager 深度模块

✓

容错检索

支持重试、降级、缓存多级容错

✓

质量监控

监控检索质量，异常时通知用户

✓

降级策略

降级时返回相关记忆，而非空结果

架构对比

当前架构（浅薄）

chat_pipeline.py
├── _retrieve_crystallized_patterns()
│   └── try:
│       └── crystallizer.retrieve()
│   └── except:
│       └── logger.warning()  # 静默跳过
└── (无重试/降级)

目标架构（深度）

CrystallizedExperienceManager
├── retrieve()           # 统一检索入口
├── with_retry()         # 重试策略
├── with_fallback()      # 降级策略
├── get_health()         # 健康状态
└── on_failure()         # 失败回调
    (容错完整，质量可控)
