## 1. P0-2 · 安卓 WS 心跳双缺陷

**根因（三层，逐层实证）**：
1. `MobileWsChannel.kt:121` 心跳发**裸文本 `"ping"`**——后端 `mobile_pairing.py:1401`
   `json.loads(data)` 只吃 JSON，抛 `Expecting value: line 1 column 1` 后进
   `except Exception` 拆线。即客户端每 30s 亲手杀掉自己的连接。
2. `:122-124` 发完 ping **不看 pong**，`delay(10s)` 后无条件 `close(1006)`——
   即使后端正常回 pong 也拆线；拆线后走 RECONNECT 退避，反复直至 GIVE_UP。
3. **红灯实测揭出的更深一层**：`1006` 是 RFC6455 保留码，OkHttp 发送侧
   `WebSocketProtocol.validateCloseCode` 直接抛
   `IllegalArgumentException: Code 1006 is reserved and may not be used`
   ——原实现的 `close(1006)` **从未成功发出过**，心跳协程首拍超时即崩死
   （SupervisorJob 下静默），连接成僵尸：无心跳、无拆线、无重连触发。

**修复点（文件:行，修复后行号）**：
- `Mobile/android-native/app/src/main/java/top/neurova/mobile/core/net/MobileWsChannel.kt:128-149`
  `startHeartbeat()`：改发 `{"type":"ping"}` JSON 帧（复用 sendFrame）；发前置
  `awaitingPong=true`，`delay(pongTimeoutMs)` 后**仅当标记仍为真**才拆线；
  拆线码改线上合法的 `1000 (reason="pong-timeout")`，仍走传输层重连档（策略等价）。
- `MobileWsChannel.kt:196-199` `onMessage`：删除永假的 `text == "pong"` 裸文本判断，
  `when` 增加 `"pong" -> awaitingPong.set(false)` 分支（后端 pong 是 JSON 帧）。
- `MobileWsChannel.kt:89-93` `connect()`：新增 `manualClosed` 终态守卫——手动关闭后
  挂起的重连协程不得借 connect() 复活通道（MobileWsClosePolicy「manual 恒终态」的
  执行点；也是测试 tearDown 挂起的一条根因）。
- `MobileWsChannel.kt:35-37` 构造参数新增 `heartbeatIntervalMs/pongTimeoutMs`
  （默认值=生产常量 HEARTBEAT_MS/PONG_TIMEOUT_MS，生产行为不变；测试注入短周期，
  行为路径与生产同一份，非绕过装配点）。
- `app/build.gradle.kts` + `gradle/libs.versions.toml`：新增 `mockwebserver`
  （4.12.0，与 okhttp 同版本）testImplementation。

**红灯证据**（先红后绿，实测输出）：
- 首跑（仅加注入参数、缺陷原样）：`MobileWsChannelHeartbeatTest` 3 用例 2 失败——
  `heartbeatFrameIsJsonPingNotBareText`：`心跳周期内服务端未收到任何帧`；
  `silentPongStillTimesOutWithClose1006`：`expected:<1006> but was:<null>`。
  （gradle `:app:testDebugUnitTest --tests ...MobileWsChannelHeartbeatTest`，BUILD FAILED）
- 中间态（帧契约已修、拆线码未改）：stderr 实证
  `Exception in thread "DefaultDispatcher-worker-1" java.lang.IllegalArgumentException:
  Code 1006 is reserved and may not be used at okhttp3.internal.ws.WebSocketProtocol.validateCloseCode`
  （MobileWsChannel.kt:137，即原 close(1006) 行）——上 fissure 3 的直接证据。

**绿灯证据**：
- 修复后同套件 3/3 通过：`heartbeatFrameIsJsonPingNotBareText`（服务端收到的首帧是
  JSON 且 type=ping）、`connectionSurvivesHeartbeatCycleWhenPongArrives`（pong 往返
  跑满两个心跳周期 state 恒 AUTHED、零 close 码）、`silentPongStillTimesOutAndCloses`
  （pong 静默时按期收到 close 码 1000）。
- 全量：`gradlew :app:testDebugUnitTest` BUILD SUCCESSFUL，14 套 60 用例 0 失败。

**live-verify（真链路）**：

`mobile_pairing.router`（真 WS 面 + 真配对流：generate→confirm 铸真 connect_ticket，
Authorization: Bearer 握手），websockets 客户端实测：
- `[PASS] JSON ping → JSON pong — {'type': 'pong', 'timestamp': 1794844382.53}`

- `[PASS] 裸文本 ping 被拆线 — ConnectionClosed code=abnormal`（后端日志同步出现
  `WebSocket error: Expecting value: line 1 column 1 (char 0)`——修复前安卓端
  每 30s 触发的正是这个）

**遗留移交**：无阻塞遗留。备查：MockWebServer 对 websocket 升级连接的

## 2. P1-37 · PairingConfirmed 死模型删除

**grep 复核（删除前现量）**：`Mobile/android-native` 全目录 `PairingConfirmed`
仅 `app/src/main/java/top/neurova/mobile/core/model/Contracts.kt:115` 定义处 1 次命中，
**零消费方**。其 `@SerialName("ws_token")` 与后端 confirm 真实响应
（`connect_ticket`）不符，属臆写形状的孤儿模型。

**对比结论（教义第 7 条）**：真实解耦事实源是
`core/protocol/PairingWire.kt` 的 `ConfirmedWire`（`connect_ticket` 必填），
其契约测试 `PairingWireTest.confirmWireDecodesRealBackendPayload` 已钉住后端真实
响应形状；PairingConfirmed 无独有字段、无消费方，无可取之处 → 直接退役，不接线。

**修复点**：删除 `Contracts.kt` 中 `PairingConfirmed`（9 行，含前导空行）。

**验证**：删除后 `gradlew :app:testDebugUnitTest` 全量 BUILD SUCCESSFUL（60 用例
0 失败）——编译期即证明零引用。

**同根因命中点扫查**：注意区分——鸿蒙 ArkTS 侧存在**同名** `PairingConfirmed`
（`Mobile/harmony/entry/src/main/ets/libs/types/index.ets:335`），但那是**活码**：
`MobilePairingApi.ets` 的 confirm 链路在用且已做 `connect_ticket→wsToken` 映射。
与安卓 Kotlin 侧死模型非同一事物，属 S4/S8 域，本批未触碰。

**遗留移交**：无。
