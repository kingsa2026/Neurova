## 1. 现状（2026-09-11 实测锚点）

### 1.1 执行模型

- 任务调度用 **APScheduler BackgroundScheduler**（`scheduler.py:794`），executors 配置 `ThreadPoolExecutor(10)` + `ProcessPoolExecutor(5)`（`:791`）。
- 所有任务经 `_add_to_scheduler` 注册到 `add_job(func=self._execute_task_wrapper, ...)`（`:860`），**未指定 executor** → 全部走默认线程池。
- `_execute_task_wrapper`（`:992-1009`）：**每个 job 在线程池 worker 线程上新建一个事件循环**（`asyncio.new_event_loop()`）→ `run_until_complete(execute_task(...))` → `run_until_complete(drain_pending_retries())` → `loop.close()`。

### 1.2 重试链与循环的耦合（2026-09-11 台账 #7 修复后的形态）

- 失败重试由 `_handle_retry` spawn 独立任务（`_pending_retry_tasks` 持引用 + done_callback discard），任务跑在**发起它的那个 job 循环**上。
- `drain_pending_retries` 在循环关闭前显式等整条重试链收口（否则重试任务随 `loop.close()` 被销毁）；`stop()` 时 `_cancel_pending_retries` 取消未决重试。

### 1.3 两个休眠事实（重构时需一并处置）

- **AsyncIOScheduler 是死声明**：`:616` 声明 `self._scheduler`，全文件无实例化——双调度器并存只是表象，实际只有 BackgroundScheduler 在跑。
- **ProcessPoolExecutor 配置了但从未使用**：`add_job` 无 `executor=` 参数，processpool 池空转（5 个进程的配置纯属摆设）。

## 2. 问题定性（为什么立项）

| # | 问题 | 量级 |
|---|---|---|
| P1 | 每 job 新建/销毁事件循环的固定开销（loop 创建、selector 初始化、线程栈上下文） | 每 job 毫秒级；高频 interval 任务下持续累积 |
| P2 | 重试链生命周期被绑死在发起 job 的循环上：drain 语义要求 job 线程等整条链（含 `2**n` 退避 sleep）跑完才释放线程——**重试等待期占用线程池工作线程**，10 线程池在多个长退避重试并发时可能饿死 | 与台账 #1 修复前的"饿死调度池"同构，现被 max_attempts 封顶缓解但未消除 |
| P3 | 循环内无跨 job 共享：job 间无法复用连接池/后台任务（未来 ASGI 生命周期整合、Lifespan 钩子均被 per-job loop 阻断） | 架构扩展性 |
| P4 | `run_until_complete` 嵌套面：wrapper 在 APScheduler 线程上自建循环，与主应用事件循环（uvicorn）彻底隔离——将来想在任务里调用主循环资源（如 `agent.chat`）必须跨循环桥接 | 演进阻力 |

**非问题（不要顺手改）**：per-job 循环的隔离性本身是正确行为（job 异常不互相污染循环状态）；当前 drain+封顶语义经 23 用例验证是正确的。

## 3. 目标与非目标

**目标**
1. 单例常驻后台事件循环线程（daemon，懒启动，参照 `neurova_recall.py:32-77` `_get_recall_loop()` 已落地的同型实现——线程存活判据防竞态）。
2. `_execute_task_wrapper` 改为 `asyncio.run_coroutine_threadsafe(self.execute_task(...), shared_loop)` 提交 + `future.result()` 等待（保留 APScheduler 的超时/事件监听语义）。
3. 重试任务直接 spawn 在共享循环上，**job 提交即返回、不再 drain**——线程池 worker 只承担提交与结果等待，重试等待期不占工作线程（消灭 P2）。
4. `stop()` 收口：cancel 未决重试 + 关闭共享循环（`shutdown_recall_loop()` 同型）。
5. 删除死声明 AsyncIOScheduler 与空转 ProcessPool 配置（或显式启用，二选一，立项评审定）。

**非目标**
- 不改 execute_task 本体的任何业务语义（状态机、事件发射、历史记录、_running_executions）。
- 不动 ProcessPool 语义（若确认启用才扩展）。
- 不引入新依赖。

## 4. 方案草案（分三阶段，每阶段独立可验收）

### 阶段 1：共享循环基建（1 天）
- 新增 `_get_scheduler_loop()` / `_shutdown_scheduler_loop()`（模块级或类级单例，仿 recall 实现）。
- `_execute_task_wrapper` 切换提交式；`drain_pending_retries` 降级为 stop() 专用收口（job 路径不再调用）。
- 验收：既有 23 个 scheduler 测试全绿（retry_propagation 的 4 处 `await drain_pending_retries()` 断言需随新契约调整为等待 future——语义等价替换，不得削弱）。

### 阶段 2：重试线程释放（0.5 天）
- 重试任务改挂共享循环，job 不等待；新增并发测试：3 个长退避重试并发时 ThreadPoolExecutor 无等待占满（红→绿）。
- 验收：max_attempts 封顶/退避序列/终态日志三断言不变。

### 阶段 3：清理（0.5 天）
- 删 AsyncIOScheduler 死声明；ProcessPool 配置处置；`stop()` 时序测试（cancel → drain → loop close 顺序）。
- 全量回归：tests/unit/agent/ + tests/unit/api/ + tests/unit/core/ 基线差分零新增。

## 5. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 共享循环被阻塞协程卡死（历史教训：event loop 内同步 IO 全家桶） | execute_task 链路的同步重活已有 to_thread 下沉约定；立项验收加"共享循环心跳"探针测试 |
| 重试任务逃逸（future.result 不等了，异常无人收割） | `_pending_retry_tasks` 引用集 + done_callback 内 logger.exception 收割（multi_model_client._pending_tasks 同型） |
| stop 时序：先 cancel 后 close 的窗口竞态 | `_shutdown_scheduler_loop` 先 cancel 全部 pending 再 stop/close，重试三例锁存 |
| 与 uvicorn 主循环的 Future 跨界误用 | 约定：共享循环只服务调度域，主循环资源经既有桥接模式（参照 mobile WS `run_coroutine_threadsafe` 先例） |
| Windows 句柄（WAL 连接在任务链中打开） | 关闭链已含 memory_manager._persist_conn（B-1 轮修复），共享循环 close 前置 drain 保留 |

## 6. 验收标准（全部满足才算完成）

## 8. v2 科学化修订方案（2026-09-11 主线评审，取代 §4 实施序，§5/§6 继续有效）

> 修订动机：§4 是"已选定共享循环后怎么分阶段做"；科学化修订回答三个此前未回答的问题——**P1/P2 到底多大（度量）？共享循环是不是最优解（多方案打分）？怎么保证切换安全且可回滚（实验协议）？**

### 8.1 Phase 0：度量先行（0.5 天，零行为变更，数据驱动 go/no-go）

先量化，避免为不存在的问题做架构手术：

- **M1 loop 开销微基准**：基准脚本对比 `new_event_loop + run_until_complete + close` vs `run_coroutine_threadsafe` 提交的每 job 开销（n≥1000，报 P50/P95）。**P1 门槛**：若共享循环改善 < 0.2ms/job 且调度域实际 job 频率 < 1/min，P1 降级为"可忽略"。
- **M2 重试并发遥测**：`_handle_retry` spawn 处加计数器（pending 数、在途退避秒数分布）+ 线程池占用探针（活跃 worker / 总数）；测试回放 N=10 并发长退避 + 72h 生产遥测。**P2 门槛**：观察期 pending 重试峰值 ≥ 5，且出现 misfire/coalesce 类饥饿信号，才维持 P2 高优先级。
- 产出 `docs/B7基线度量报告.md`，给出两个 go/no-go：**数据不支持 → 方案降级为 D（维持现状+仅保留遥测），2 天工作量免掉**。

### 8.2 多方案决策矩阵（用 Phase 0 数据打分，不预设结论）

| 方案 | P1 | P2 | P3/P4 | 风险 | 工作量 | 备注 |

> **✅ 选型结论（2026-09-11 Phase 0 实测，详见 docs/B7基线度量报告.md）**：M1 显示 P1 绝对节省仅 0.25ms/job（比值 8 倍但真实频率下占比 <0.05% CPU）→ P1 不足以支付方案 A 的全量改造风险；M2 确定性回放实锤 P2（legacy：10 并发重试链占满 10 worker 7 秒、短任务排队最长达整链时长 7.0s；shared：10ms 级）。**选定方案 B（仅重试出循环）**，`NEUROVA_SCHEDULER_EXEC_MODE = legacy|shared` 双路径 + 等价性协议实施；方案 A 的基建设计保留本节，待 P3/P4（ASGI 生命周期整合/任务内调主循环资源）出现硬需求时按 §8.3 协议升级。

### 8.3 实验化推进协议（选型 A 或 B 通用）

1. **特征化测试先钉行为**：重构前把 23 个既有用例 + wrapper 可观测行为（execution_started/completed 事件序列、`_running_executions` 生命周期、history 顺序、异常包装）固化为 characterization 套件——**先在现状代码下全绿**，重构全程在该安全网下进行。
2. **特性开关**：`NEUROVA_SCHEDULER_EXEC_MODE = legacy | shared`（env，默认 legacy），两路径并存一个发布周期；kill switch = 改 env 重启，秒级回滚。
3. **等价性协议**：同一确定性任务集（固定 cron 序列 + 固定失败注入脚本）在两模式各跑一遍，diff 执行轨迹（事件序列/history 顺序/重试次数/退避间隔）——逐帧一致才判等价。
4. **不变量测试（property 风格）**：调度循环线程数 ≤ 1；`stop()` 后 pending=0；worker 占用是活跃 job 数的函数而非重试链深度的函数；单 job 异常不污染循环状态。
5. **可观测性**：loop submit 延迟、job 执行时长分布、pending 重试数、共享循环心跳探针（历史教训：事件循环内同步 IO 卡死必须可探测）——接入 core/metrics。
6. **金丝雀与退役**：开关切 shared 观察 48h 指标 → 默认值翻转 → legacy 路径保留一个版本后删除。

**Phase 2 产出（G1/G2 证据）**：
