## 一、P0（数据丢失 / 账号接管 / 治理失效）

### SEC-P0-1 治理白名单/审批端点完全无鉴权 ✅实测
- `neurova/api/endpoints/governance.py:86,93,109,121,142,152,212,250,261,279`
- `_governance_admin_dep = require_admin()` 在 :21 已创建但除 /settings 外全部端点未挂。
- **实测**：无 token `POST /api/v1/governance/whitelist` → `code:0` 成功创建白名单条目。
- 后果：未认证者可添加白名单使危险工具免治理放行；可批准待审批请求（:193 以 `skip_governance=True` 重放执行任意工具）。
- 修法：全部端点补 `Depends(_governance_admin_dep)`。

### SEC-P0-2 WebSocket /ws 无鉴权可驱动 agent ✅实测
- `console.py:1366-1395`：`_manager.connect` 直接 accept，无 token 校验；`chat` 分支调 `agent.chat`。
- **实测**：无 token WebSocket 握手返回 101（切换协议成功）。
- 后果：未认证者可消耗 LLM 配额、写会话（且写入的会话 user_id 为空 → 全员可见，与 SEC-P1-2 形成越权闭环）。
- 修法：握手校验 JWT，拒绝时 `close(code=4401)`。

### SEC-P0-3 auth.py 硬编码管理员恢复密码（后门）
- `auth.py:47` `MASTER_RECOVERY_PASSWORD = "nerovamakehard"`（原文 "nerovamakehappy"）；消费点 :245-294。
- 常量随源码/打包产物分发 → 任何拿到包的人可重置 admin 密码接管账号。限流只防爆破。
- 修法：删除常量，改环境变量或首启随机生成打印到控制台。

### SEC-P0-4 agent 删除/切换/宪法端点无鉴权 ✅实测（可达性）
- `agent.py:443`(DELETE)、:557(switch)、:594(constitution)、:616(decision)、:652(rebuild-loop)。
- **实测**：无 token `DELETE /agents/xxx` 返回 404（资源不存在）而非 401——端点无鉴权直接可达。
- 后果：`DELETE` 连带 `shutil.rmtree` 工作区与记忆数据，永久丢失；decision 可无限制驱动 LLM。
- 修法：补 `get_current_user` + owner_user_id 归属校验（:333 已持久化 owner 但从未消费）。

### DATA-P0-5 窗口化渲染下标错位 → 删除/编辑错消息（前端，双端数据丢失）✅代码实锤
- `ChatPage.vue:132`（模板 `v-for="(msg, idx) in renderedMessages"`）+ `:1398`（renderedMessages = `messages.slice(renderStart,…)` 相对下标）vs `:1767/1723`（`messages.value[idx]` 绝对下标）。
- 触发：会话超 90 条（WINDOW+BUFFER）且上滚扩窗后（renderStart>0）操作任何消息。
- 后果：删除轮次删错轮——本地 splice 错位 + 后端按错 timestamp 删（**双端数据丢失**）；搜索命中比较 `idx===msgSearchCursor` 语义错误。
- 修法：模板传 `renderStart + i` 作为绝对下标，key 用消息唯一键。

### SUB-P0-6 会话损坏文件 → 非重入锁同线程重入死锁
- `session_manager.py:256-257`（`_quarantine_broken_file` 内 `with lock:`）vs 持锁调用方 `:379/:944/:985/:1031`。
- 触发：任一损坏的 session JSON + 对该会话的下一次写操作（隔离逻辑在持锁路径内再次取同一把非重入 Lock）。
- 后果：线程永久死锁且持锁，该会话所有写入永久阻塞。S4 修复时已意识到 Lock 不可重入（:285 注释）但漏了这条重入路径。
- 修法：文件锁改 `RLock`，或隔离函数加 "已持锁" 参数。

### SEC-P0-7 console 会话端点 user_id 恒 "anonymous"（越权+看不到自己会话）
- `console.py:90-91`（`_get_user_id` 读 `request.state.user_id`，全仓无任何中间件赋值）→ 恒 "anonymous"；影响 :637,655,682,699,729,803,815,827,849,914,1039,1090,1147 十余个端点。
- 后果：越权校验（anonymous==anonymous）形同虚设；JWT 建的会话在 /chat/sessions 被过滤规则隐藏。
- 修法：`_get_user_id` 改从 JWT 依赖取身份（与 /chat :392 同源）。

## 二、P1（核心功能失效 / 数据静默丢失）

### LLM-P1-1 切模型后 `AgentLLMClient.model` 仍是旧值（rebuild_loop 只修了一半）⚠️与本次已修 bug 同源
- `agent_core.py:126-137`（`self.model` 构造时冻结）、:992-999（rebuild_loop 只回填 loop.llm_client，而 chat 路径经 `AgentLLMClient.chat` 用的是 `self.model`）。
- 三条切换路径（chat 手动切换/多模态路由/POST /model/switch）只调 rebuild_loop，从不更新 `agent.llm_client.model` → 请求仍路由旧模型；且 config 已指向新模型导致 `model != current_model` 判断失效，永远卡死。
- 修法：rebuild_loop 成功后同步 `self.llm_client.model/provider_id`，或 chat 动态读 config。

### LLM-P1-2 流式 usage 永远丢失：空 choices 的最终 chunk 被 continue 丢弃 ✅代码实锤
- `llm_client.py:347-349`（chat_stream）、:464-466（chat_stream_async）：`if not chunk.choices: continue` 在读取 `chunk.usage` 之前；而 :341/:456 显式请求了 `stream_options.include_usage=True`（usage 附带在空 choices 的末 chunk）。
- 后果：流式 token 恒靠估算或记 0，TokenBudgetGate 永不触发。
- 修法：usage 提取移到 choices 判断之前。

### AGENT-P1-3 Adaptive Retrieval 整链静默失效：`llm.chat()` 未 await
- `chat_pipeline.py:1355`（_decompose_query）、:1371（_rewrite_query）：`resp = llm.chat([...])` 拿到的是 coroutine，`resp.content` 恒空 → 二次检索永不执行 + 每轮泄漏协程。与本次修复的 rebuild_loop 同类 bug。
- 修法：两处加 `await`。

### AGENT-P1-4 EKB 经验检索拿不到 agent_id → 跨 Agent 经验互串
- `chat_pipeline.py:1435`：`getattr(self._agent, "agent_id", "")` —— Agent 实例无此属性（在 `self.config.agent_id`）→ 恒 None → 检索不过滤 agent，A 的经验注入 B 的 prompt。
- 修法：改 `self.config.agent_id`。

### AGENT-P1-5 共享 Loop 实例的轮次状态被并发请求互踩
- `openai_loop.py:66-74,192-201`：`_tool_rounds/_round_replies/_last_round_calls` 等轮次级状态挂在 agent 级单例 Loop 上；DoomLoopGate 窗口同理。并发对话 A 的 predict_step 重置 B 的计数 → 工具循环不收敛或被误 TERMINATE。
- 修法：轮次状态收进 per-call 上下文对象。

### AGENT-P1-6 `_pending_vision_parts` 挂共享管线实例 → 跨请求图片串线
- `chat_pipeline.py:1018`（写）、:1026-1031（flush）：并发请求图片互串（同 Agent 跨用户时为数据泄漏）；A 异常后残留图挂进 B 的无附件请求。
- 修法：状态移入 ctx。

### SUB-P1-7 session_manager 四个兄弟方法的锁外 RMW 丢数据（S4 修复漏网）
- `session_manager.py:704→735`（save_message 同类已修，但这四处原样）：`save_message` 除外还有 `rename_session :846→851`、`set_session_pinned :893→898`、`set_sessions_sort_order :869→879` —— 锁外读陈旧快照整体写回 → 并发 add_message 时最后一轮对话被静默回滚。
- 修法：read-modify-write 全程持 file_lock，写用 `_write_session_file_unlocked`。

### SUB-P1-8 hf-mirror 下载半截文件永久通过校验
- `tts/model_downloader.py:373-385`：中断留下截断文件，`exists() and size>0` 即跳过重下 → 模型永久损坏且自愈失效。
- 修法：下载到 `.part` 成功后 `os.replace`。

### SUB-P1-9 模型下载 failed/skipped 状态永久卡死
- `tts/download_service.py:61-63`：幂等短路不区分终态 → 重试按钮/换源在进程生命周期内全部无效。
- 修法：仅 pending/downloading 短路。

### FE-P1-10 流式中切会话：usage 记账污染新会话 + 队列消息发进新会话
- `useChat.ts:163-166`（switchSession 不 abort 流不重置 isStreaming）+ `ChatPage.vue:2243`（usage 用事件时刻 sessionId 记账）+ `:2103`（finally drain 用当前 session_id 发送）。
- 修法：switchSession 前 abort；usage/drain 用发起时捕获的 sessionId 快照。

### FE-P1-11 快速切会话无请求序号守卫：旧历史覆盖新会话
- `useChat.ts:163-253`：A 的 history 响应后到覆盖 B 的消息列表 → 后续发送/删除全落错会话。
- 修法：自增请求序号，写入前校验 sessionId 一致。

### FE-P1-12 切会话丢草稿
- `ChatPage.vue:1514-1520` 只 restore 不 save 旧会话草稿（useChatDraft 文档声称会保存）。
- 修法：restore 前先 save 旧会话。

### SEC-P1-13 登出黑名单从不被校验（logout 假成功）
- `auth.py:601-628` 写黑名单，但 `get_current_user`（deps.py:23-59、auth.py:315-347）只 decode 不查 → 登出后 token 在 60 分钟内照常可用；黑名单 set 只增不减。
- 修法：verify_access_token 统一查黑名单（jti + 过期清理）。

### SEC-P1-14 /chat/history 无鉴权可读任意会话 ✅实测（可达）
- `console.py:617-631`：无 get_current_user 且无归属校验，全库扫描匹配 session_id。
- 修法：挂鉴权 + `_find_session_target` 归属校验。

### SUB-P1-15 反思日志状态流转从不落库，重启全部回退 PENDING
- `growth_log.py:234-262`：`_save_entry` 已有 memory_id 时只 update content，metadata（status）从不重写 → 重启后 applied/validated 回退 pending，反思注入每重启断一次。
- 修法：状态流转重写 metadata。

### AGENT-P1-16 async 检索链路同步阻塞事件循环
- `retriever_adapters.py:336-339` → `mem_core.py:141-149`（`run_async_safely` 在运行中的 loop 上 `executor.submit(...).result()` 阻塞）→ MoE 检索期间整个事件循环冻结秒级。
- 修法：`await asyncio.to_thread(...)`。
