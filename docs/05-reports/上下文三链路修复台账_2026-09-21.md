### 根因与改法

`record()` 每行一次 `connect` → 两条 `INSERT` → `commit` → `close`，而池侧 `add_context`
逐条写穿——一次归档调用里 24 条就是 24 个事务。改为"一个常驻连接 + 一次归档调用一个
事务"：台账侧只提供批原语，事务边界由池的 `archiveBatch()` 显式承载，
`orchestrator` 的归档段整段包住。

### 放大视角命中点（教义第 5 条）

- **读路径同批收敛**：常驻连接若只给写用，`recall_evicted` 在长会话下仍每次 connect；
  `search` / `count` / `gc` 一并改走临留连接，实例内 `RLock` 串行（sqlite3 连接对象不可并发）。
  `gc` 的删除 + FTS 对齐改显式事务（关掉隐式 BEGIN 后不包事务会退化成逐条提交，属"没人会发现"的退化）。
- **连接生命周期接线**：常驻连接必须有人释放——`agent_shutdown` 的关闭清单纳入
  `context_orchestrator.context_pool`（与既有的 `_persist_conn` 同根因：不入清单则
  Windows 上关闭/删除 agent 撞 sqlite 句柄残留）。
- **批失败不谎报**：批内失败整批回滚 + 本批条数整批计入 `failed` + `last_error` 点名
  异常类型与消息；`written` 保持 0（写失败不得被记成写成功）。
