### 根因与改法

两条独立的缺陷落在同一个查询函数里：

1. **LIKE 兜底直拼 `f"%{query}%"`**：`%` 与 `_` 是 LIKE 通配符，把用户输入
   变成通配模式（实测库内 3 行时 `%` 命中 3 行、`_` 命中 3 行，真值均为 0）。
2. **长度 <3 的查询也走 MATCH**：trigram 索引不到短查询，强上会得到**假阴性**
   （漏召回比慢更糟）。改前这条看不出来，因为 unicode61 下 MATCH 恰好返回空、
   兜底 LIKE 刚好答对——只看结果输出无法证明分流做对了。

改法：转义、短语包裹、长度分流阈值收口到 `core/sql_like` 一处；台账侧只调用它。

### 放大视角命中点（教义第 5 条）

  `CANDIDATE_LIMIT + 1` 个候选（0.7–2.7 ms），再按"是否触顶"分流。
- **同契约命中点一并收口**：`neurflow` 的 `search_workflows` /
  `search_node_definitions` / `find_subflow_references` 与
  `CognitiveStorageEngine.retrieve` 的 LIKE 兜底同样直拼用户输入——
  一并改走 `likePattern`，各补红→绿用例（改前实测 `%` 把整表拉回）。

- PR：[#123](https://cnb.cool/kingsa2026/neurova/-/pulls/123)（**CI 11/11 全绿，已合入 main**）

- live-verify：`PYTHONPATH=. python tests/manual/context_ledger_fts_rebuild_90.py`

### 根因与改法

`unicode61` 对中文等于无索引（实测中文短语命中 0），而**只改 `tokenize` 参数
不会改已有索引**——必须重建表。重建不能用 `delete-all`（普通 FTS5 非法），
也不能用一次性 `INSERT … SELECT`（长事务整段阻塞写）。

改法：影子表（trigram）+ **分批短事务**回填 + 切换事务（补齐尾批 + `DROP` + `RENAME`），
版本推进到 v2。

### 实施期踩到的三个坑（都写进规格偏离记录）

1. **写面必须走独立连接**：迁移事务（`db_migration` 的 `BEGIN`）在自身连接上
   无法执行 FTS 虚表的 `DROP`/`RENAME`（实测 `database is locked`）。
2. **读取也必须在同一条独立连接上**：迁移连接的读快照**看不到**另一条连接的
   写入——用它读"影子表还差哪些行"会永远取到同一批（实测同批重复插入 →
   `IntegrityError: constraint failed`）。
3. **切换段必须与尾批补齐同事务**：分批循环退出后、切换之前，并发写可能已插入
   新行（内容行在、索引行不在，实测两表差 1 行）。收进同一个 `BEGIN IMMEDIATE` 后
   两表行数严格相等。

### 16.1 B6-6 向量层批量入口（B5 尾巴一）

根因：`UnifiedVectorStore` **从来没有** `encode_batch`，于是
`semantic_drawer.ScoringContext.build` 的 `hasattr(store, "encode_batch")` 恒假
——"批量打分"在 store 这一层从未接上，逐条 `encode` 是唯一路径；且 tfidf 一律
绕过内容寻址缓存（文件头纪律原话："tfidf 词汇表漂移，一律绕过缓存"）。

改法（在向量层修，不在抽屉侧加兜底）：

- `encode_batch(texts)` 是**唯一**批量入口，单条 `encode` 由它派生（不是第二份实现）；
- 入缓存的判据从"后端是不是模型"改为**"向量形态是否稳定"**：tfidf 在词表为空时
  走定维（100）哈希编码，同文本同维度、跨轮不变 → 可缓存；词表被 IDF 填充后向量
  随语料继续漂移 → 判据返回"不稳定"，不入缓存（宁可重算，不可复用形状不一致的向量）；
- 缓存文件从"单指纹、不匹配即整体失效"改为**按指纹分命名空间**：同一进程里
  tfidf 分片与真模型后端并存时不再互相清空（旧格式 `fingerprint`/`entries` 仍能读回）。

实测（`PYTHONPATH=. python tests/manual/context_vector_batch_90.py`，真统一向量仓）：

```

第 1 轮 300 条：真编码 300 次 | 9.6ms
第 2 轮 300 条：真编码 0 次 | 1.4ms      ← 改前两轮各 300 次
池内第 1 轮 draw：真编码 301 次 | 入选 71 条
池内第 2 轮 draw：真编码 0 次 | 入选 71 条
```

红灯 → 绿灯：`9 failed`（`AttributeError: no attribute 'encode_batch'`）→ **9 passed**。

### 16.2 B6-7 归档时刻是读侧唯一时间事实源（B5 尾巴三）

根因：`ContextInput` 有两个时刻字段，`created_at`（归档时刻，写入咽喉落库、召回时
由 `resolveArchivedCreatedAt` 还原）与 `updated_at`（构造时同值、**全仓零写入方**）。
读侧 freshness 打分读的是后者 —— 召回一条 45 天前的归档时它是"本次构造时刻"，
`age_hours = 0` → 退火系数 1.0：**越老的归档越"新鲜"**，相关性打分被系统性抬向旧内容。

改法：读侧排序（`draw` 末尾的稳定排序）与打分（`_calculate_freshness_score`）
共用 `created_at`；第二条时刻定义**删净**（含 `to_dict` 序列化与 auto_tagger 的复制位）。
判据钉"不存在第二次时刻定义"，而不只是"改一行读哪个字段"。


红灯 → 绿灯：`5 failed`（老归档分不低 / 仍有 `updated_at`）→ **5 passed**。

## 18. T-03b 已交付：每轮会话身份接入装配入口（2026-09-24）

工单 §4bis 的残余单，Issue #90 里唯一「用户可感知 + 已实测复现」的缺陷：
**两个普通单聊会话共用同一条折叠摘要**（探针 P2 形状一 = `True`，形状二"两个
协作房间" = `False` —— 键机制本身有效，坏在身份来源）。本节合并两轮接力的交付，
按**合并后**的统一命名（`_resolveTurnSessionId()` / `get_context_health()["turn_identity"]`）
记述。

### 根因（不是"漏传一个参数"）

装配入口**造了第二条身份通道，而三条都空**：

| 环节 | 改前 |
|---|---|
| 构造期身份 | `ContextOrchestrator(a, use_pool=..., auto_tag=...)` 不传 `session_id` |
| 形参入口 | `build_context(chat_collab, chat_room_id)` 无 `session_id` 形参 |
| 轮内赋值 | `_turn_room_id = chat_room_id or (self._session_id or "")`，而 `chat_room_id` **只在协作轮非空** |

三条通道全空 → `_resolve_window_cache_key()` 恒退化为 `"direct"`。

而本轮的会话身份一直存在：`ChatPipeline` 每轮经 `set_request_identity` 把它写进
`core.turn_context` 的 ContextVar，读取契约名就是 `agent.current_session_id`
（后链的幂等键与落盘 session 已在用它）。**没人读它。**

### 同一根因的三个命中点（教义第 5 条，一次做全）

| # | 命中点 | 改前实测 |
|---|---|---|
| A | 折叠摘要缓存键 | `sess_one`/`sess_two` 两轮后键均为 `['direct']`，第二会话视图含第一会话摘要 |
| B | 池归属 → 条目 `metadata["session_id"]` → 持久台账 `session_id` 列 | 三者同值为 `None`；`query()` 本会话优先排序退化、召回会话过滤失效 |
| C | `get_token_budget().used_tokens`（本会话实测快照） | 传 `self._session_id or None` → 退到 agent 级快照 = **别的会话的最近一轮**（实测 2000 vs 本轮真值 1） |

2. **第二命中点同批**（否则半接）：`turn_session` 改走同一份回落链。改前它在

## 21.1 T-10c 前置读数复核：microcompact 的两个门槛在真序列上互相抵消

前轮交接写「`_clear_old_tool_results` 的占位指针**仍恒不触发**」。本轮按真构造面
复核，结论要分两层说 —— **孤立调用可达，真序列上基本不可达**，且原因不是前轮
可能设想的那个。

### 门槛一（已有）：绝对常数

    _clear_old_tool_results: if estimate_window_tokens(window_msgs) <= 8000: return window_msgs

孤立调用确实会触发：6 行 × 3000 字符 → 18053 token，替换 3 次。

### 门槛二（新发现，才是真关卡）：上游窗口裁剪先削掉了输入

`build_context` 的真序列是 **先 `_apply_window_budget`（窗口上限 = 预算 − 信封保留
= 9600 − 1000 = 8600）再 `_clear_old_tool_results`**。而折叠一旦发生，
`compact_window` 就把窗口压到预算的一半以下，**并把 tool 行留成恰好 3 行**
（= `_TOOL_RESULT_KEEP_RECENT`）。于是 microcompact 的两个条件同时失效：

    tool行 chars  折叠?  折叠后token  过8000?  tool行>KEEP?  替换
        3   500  False        1544    False      False      0
        4  2000  False        8057     True       True      1   ← 唯一可达区间
        4  2200   True        6723    False      False      0
        5  2000   True        6123    False      False      0
        6  3000   True        9123     True      False      0   ← 过 8000 但只剩 3 行
       10  1200   True        3725    False      False      0
       20  3000   True        9128     True      False      0
       30  2000   True        6134    False      False      0

可达区间只有"窗口刚好没超 8600、但工具结果总量已过 8000"那一小段
（实测窗口 8057 时替换 1 次）。一旦进入折叠（窗口 6 行 ×3000 即触发），
tool 行被压到 3 行 → `len(tool_positions) <= KEEP` 直接返回，**永不替换**。

### 这不是"bug 没修好"，是判据口径需要重新定义

- `_TOOL_RESULT_KEEP_RECENT = 3` 是**折叠保持**与 **microcompact 保持**两处共用
  的同一个数：折叠把窗口压到这个数就不再压，microcompact 又要求"多于这个数"
  才动手 → 两者在稳态上互相抵消（我称它为**共线**）。工单 §11.4 第 3 条写的
  "首次成为可达路径"在真序列上不成立。
- 所以 T-10c 的正确切入点不是"把 8000 调小"（那是 consumer-only guard 的反面：

  同一个数**——若不是，两者必须各自声明；若是，microcompact 在折叠已发生时
  本就无事可做，它的价值只在"未触发折叠但工具输出已撑满窗口"那一段。
- 该裁定属设计口径（与 §11.4 第 3 条的原文冲突），**需你拍板**。本轮只出读数与
  两个 `KEEP` 共线的证据，不改门槛、不改常量（教义第 2 条：不抹除报错、
  不规避；也不在消费方加兜底）。

## 21.3 T-10c 收口：工具轮载荷进窗口预算判据（计量口径收口为单源）

> 依据：工单 §11.4 第 2 条「`estimate_window_tokens` 的输入集合自此含 tool 行 ——
> 需一条新断言锁住"含工具轮的窗口实测 ≤ 预算"」，以及 §11.6 的具名判据
> `test_tool_rows_counted_in_window_budget`。本批把它落地。

### 根因：判据面只读 `content`，而 T-10b 之后工具轮真载荷在 `tool_calls` 里

`WindowTokenMeter._contentOf` 只取 `message["content"]` 字符串。

T-10b 让 `get_recent_model_context()` 把会话台账的 `metadata.tool_calls` 还原成
provider 合法的 `assistant.tool_calls` 之后，这份载荷**会真发给模型** ——
`arguments` 是协议原文串（JSON），对 `run_code` / `write_file` 这类工具，
参数本体就是调用参数的绝大部分。但它是 `content` 以外的字段，**不进任何窗口判据**。

同一批消息因此有两个计量结果（真构造面实测，`_tool_turn_window(8, 3000)`）：

```
判据侧 estimate_window_tokens = 85      ← 折叠 / microcompact / 召回额度都按它判
展示侧 composition.total      = 10321
                                差 10236 token（121×）
```

后果不是"面板数字不准"，而是**判据空判**：cap=8600 时判据读到 85 → 判"没超预算"
→ 零折叠、零占位，而真 prompt 早已越过模型窗口。工单 §11.4 第 2 条要锁的那条
断言，改前在含工具轮的形状上恒真（判据读的是不含工具载荷的假读数）。

同批实测的第二处：`content` 为多模态分段 list 时，计量对 list 做字符类别正则匹配
直接抛 `TypeError` —— **判据面等于没有多模态口径**，多模态轮完全不受预算管辖。

### 两处各算一份 = 平行体系（修复教义第 6 条）

展示侧 `composition._measure_messages` 自己算了一份"含 `tool_calls`、含多模态分段"
的口径（`json.dumps(tool_calls)` + 图像段固定 800），判据侧另一份（只读 `content`）。
两处各写一遍即"同一契约两份实现"，本次收口为**单源派生**：

    window_compactor.messagePayloadTokens(message, estimator=None)
      = 文本内容｜多模态分段（text 段按文本、image_url 段按 IMAGE_PART_TOKENS）
        + tool_calls 协议原文串（json.dumps）

- 判据侧 `WindowTokenMeter.one()` 走它（整窗 `total()` 由 `one()` 求和，仍是单源）；
- 展示侧 `composition` 走它，**删净**自带的 `tool_calls` / `image_url` 分支（−17 行）；
- 图像段计价常量 `IMAGE_PART_TOKENS = 800` 收口到该模块（原数在展示侧就地写死）；
- 退役 `_contentOf`（派生收口后无消费方，留下即第二份口径的入口）。

## 23. T-11a：折叠改分代，旧摘要降一层而非被覆盖（2026-09-25）

工单 §0.4 第 13 步、§12.4 的第一张子票。本票是 T-11 全族的地基：T-11b 的
`level` / `covers` 索引、T-11c 的分辨率装配器都以"存在多代节点"为前提。

### 根因（不是"少存一份摘要"）

折叠摘要在改前是**一个字符串**：`cache["summary"] = compaction.summary`。
每轮折叠原地覆盖上一轮，于是：

- 全部被压缩的历史**永远只塌成一个节点**。实测（真 `build_context` 连续多轮）：
  池内 `ContextSource.SUMMARY` 节点数 **0**，摘要只活在 `_window_compaction_cache`
  这个进程内易失的字符串里；
- **分辨率梯度（§12.1 C2）在数据上不可能存在** —— 只有一个层，就谈不上
  "越远的位置分辨率越低"；
- **层即索引（C4）无从落地** —— 没有多节点，就没有可解析的 `covers` 可供下钻。
  工单 §12.5 第 2 条把这个形态直接列为假实现（"只保留最后一层却声称轨迹全在"）。

### 改法：代际栈 + 单一写入点

新增 `_advanceFoldGeneration(slot, summary)`，是代际栈的**唯一写入点**：

- 新摘要入栈顶（`level` = 1，最细分辨率档）；
- 栈内既有节点**文本原样**降一层（`level` + 1）—— 不就地改写（T-04 的纪律同样
  适用于摘要层）；
- 既有的每一代原样保留，**一档都不丢**（代际栈不设上限，工单 §12.1）；
- `slot["summary"]` / `slot["level"]` 保留为**栈顶投影**：既有读侧（防抖判定、
  静态摘桩沿用、手动压缩回执）据此**逐字不变**，本票不改变它们的语义。

**自动折叠与手动 `/compact` 共用这一处**（教义第 6 条）：改前两处各写一遍
`cache["summary"] = ...`，是同一契约的两份实现 —— 只改一处，另一处会静默
继续覆盖（本票的红灯之一就钉在这一点上）。

读数落 `get_context_health()["fold_layers"]`：`levels`（栈深）/
`demoted`（累计降层数）/ `last_summary_chars`（无 `truncated`，见 §23.1）。
与同面 `turn_identity` / `microcompact` 同为"最近一次 + 累计量"口径，
**不另造逐会话第二份读数**（折叠缓存本就按会话分槽）。

### 23.1 对工单 §12.1「档数不设上限」的偏离**已按裁定撤销**（2026-09-25 订正）

**原偏离（已撤销）**：本票交付时给进程内代际栈设了上限
`_MAX_FOLD_GENERATIONS = 5`，理由写成"进程内易失状态不可只增"。

**裁定**：负责人 2026-09-25 回「删掉上限」。上限已删（`= None`，保留为可断言的
显式契约），工单 §12.1 原话自此**不再有偏离记录**。

**原理由为什么不成立**（订正，不是让步）：代际栈**不是只增容器** —— 每轮折叠是
"+1 新代 / 既有代各降一层"的**等量代换**，深度恒等于活代数，本身有界；真正随
会话时长累加的只有 `fold_layers` 里的**计数**（原 `demoted` / `truncated`），
而计数不占内存、正是读数的意义。上限的真实代价是把当时最深的一档**丢弃**，
而"轨迹越长档数自然增长"（§12.1）正是分辨率梯度成立的前提 —— 旧上限等于
§12.5 第 2 条（"只保留最后一层却声称轨迹全在"）的轻量版，而读数与视图都不能
自证丢了什么。

**同批收口**：`truncated` 读数字段一并退役（单源口径）—— 无上限即永不可能截断，
留一个恒 0 的字段就是谎报面（协作红线：不留断点）。判据已改写而不删断言：
`test_generation_stack_keeps_every_generation`（原 `test_generation_stack_is_bounded_and_counted`）
同强度地钉住"没有一代既不活也不被记账"。

**证据**：红 → 绿 `3 failed → 8 passed`（红输出含
`代际栈深度 5 != 摘要调用次数 8`）；live-verify 跑满 8 轮后

## 24. T-11b：层节点索引（池内 SUMMARY 节点带 covers，解析率 0、跨重启读得回）（2026-09-25）

工单 §0.4 第 14 步、§12.4 的第二张子票。T-11a 让折叠**分代**了，本票让"代"成为
**可寻址的索引** —— T-11d 的下钻与 T-11c 的装配器都以它为前提。

### 根因（不是"少写两个字段"）

T-11a 的代际栈只活在 `_window_compaction_cache`（进程内易失）：池内
`ContextSource.SUMMARY` 节点数实测 **0**。于是工单 §12.1 的 **C4 层即索引**
在数据上不成立：没有 `covers`，下钻无从知道一个摘要覆盖了哪些原文条目；
进程内缓存一重启即空，"整个轨迹可寻址"没有落点。

### 改法（三处同批，缺一条索引就是假的）

1. **写入**：折叠推进时把**这一代**经 `ContextPool.archive_summary` 写进池
   （池的唯一写入咽喉 → 自动继承 T-02 的作用域，教义第 5 条）；
2. **派生**：新模块 `neurova/context/fold_index.py` 是 covers 的**唯一**派生
   （写入侧 `buildCovers`）与解析（读取侧 `parseCovers`）处。covers 的 hash
   取自**本轮新覆盖**那一批（折叠缓存 `covered` 集合里刚追加的那批 = 工单 §12.3
   说的"复用 T-03 激活的 `covered` 集合"），轮次 id 复用 `assign_turn_ids`
   （与归档侧同源：另起一份"第几条算一轮"的算法会让 turn 区间与归档归属对不上）；
3. **读取**：`ContextPool.summaryLayers()` 是索引的**唯一读面**（常驻 + 台账持久
   两源合并、按内容 hash 去重、档号在此派生），读数 `foldIndexHealth()` 并进
   `get_context_health()["fold_index"]`（生产读者 = /metrics 的既有快照面，
   不新开端点）。覆盖闭合的反例数（`uncovered`）也在读面算，判据源是编排器
   从折叠缓存取出的已覆盖全集（`_foldedHashes()`）——池**不另存**一份。

### 与工单 §12.4 原话的一处偏离（如实记录，改工单原话见 §0.4 第 14 步）

§12.4 原话是"SUMMARY metadata 增 `level` + `covers`"。实现存的键是 `fold_seq`
（该次折叠的**层序**，不可变事实），**档号由读面派生**（最新一档恒 1，越早越大）。

理由：档号随新代产生**整体下移**。写进归档实体就要每次折叠就地改写已归档节点
（与 T-04「归档实体永不原地改写」正面冲突），而且每写一次那一刻它都确实是最新
一档 → 每一代都被写成 `level=1`，档号退化成恒 1 的谎报面。层序是事实，档号是
它的确定性函数——一份事实，一处派生。

## 25. T-11d：确定性下钻（摘要行内联 covers_ref，按引用取回被覆盖原文）（2026-09-25）

工单 §0.4 第 15 步、§12.4 的第三张子票。T-11b 让索引**存在**了，本票让索引
**被读**——把工单 §12.0 承诺 A（任何已归档内容都存在一条确定性回取路径）从
"数据上说得通"变成"模型真取得到的"。

### 25.1 根因（不是"少一个工具"）

索引写进去之后，整条链路上**没有任何消费方**，三处断点各自成立：

1. **视图侧无引用**：摘要行（`[早期对话摘要] …`）是一段纯文本，模型读到摘要却
   没有任何确定性寻址手段，只能退回 `recall_history(query=…)` 的**相关性门槛
   碰运气**——工单 §12.5 第 3 条明列此为假实现（"门槛不保证取得到"）；
2. **索引侧无直取面**：`covers` 的 hash 列表只能整体取出，没有"按 hash 取若干条"
   的读路径；写了没人读的字段正是红线段禁止的断点形态；
3. **两个指纹域不通**（本票最值钱的一段，由跨重启判据咬出）：台账去重用的是
   `contentDigest(content)` —— **纯内容**哈希；而 `covers` 里存的是池内容指纹
   `ContextInput.compute_hash(source, content)` —— **带来源域**。两个值不相等，
   于是即使索引齐全，重启后按 covers hash 去台账里查也**必然全员落空**：
   索引与原文从来对不上，"任取一档摘要都能取回原文"在跨重启形态下不成立。

判据先红在现象上（`fold:2` 解析不了 / `drilldown` 不存在），实现后红在**第 3 条**
上（重启后取回 0 条），最后修到根因（池指纹落独立列 + 直取面按它建索引）。

### 25.2 改法（一条寻址口径，五处接线同批）

1. **引用单点派生/解析**（`fold_index.renderCoversRef` / `parseCoversRef`）：
   语法 `covers_ref=fold:<层序>@<会话身份>`。**档号不入引用**——它随新代产生整体
   下移（T-11b 已就此偏离过 §12.4 原话），写进引用会在下一次折叠后指向别的档；
   层序是不可变事实，才是可长期寻址的键。与 `_tool_placeholder` 的 `call=` 指针
   同纪律：地址由生产它的那一处给，消费方只解析，不猜；
2. **视图内联**（`orchestrator._inlineCoversRef`）：引用挂在摘要行尾部，会话身份取
   `_resolveWindowCacheKey()` —— **与折叠缓存槽同一个键**。这不是巧合而是必需：
   引用里的会话 = 索引里的会话 = 缓存槽身份，三处同取一条回落链（T-03b）；
   各取一份就会出现"引用指 A、索引只有 B"的静默落空。放在有 LLM 摘要与只有静态桩
   两条分支的**汇合处**——否则"摘要行有引用"只在摘要成功时才成立（那是运气，不是契约）；
3. **池直取面**（`ContextPool.drilldown`）：引用 → `summaryLayers()`（唯一索引读面）
   → 该档 covers → 常驻 `entriesByHash` + 台账 `rowsByPoolHashes` 双源直取 →
   `_allowedRecallItems` 作用域闸门（与视图路径、`recall_evicted` **同源**）。
   全程只有一条寻址口径：本方法不解析引用语法、不重算 covers；
4. **池指纹落列**（台账 **v3** 迁移）：新增 `pool_hash` 列 + `idx_pool_hash`。
   写入侧 `_writeArchived` 把 `ContextInput.hash` **原样**落库（不二次哈希）；
   v3 之前的真实归档由 `_backfillPoolHash` 按 metadata 的来源域**确定性回算**
   （与写入侧同一份派生）——不回填等于把历史归档排除在下钻之外。本列**不建唯一
   索引**：同一段文本在两个来源域下是两条不同归档，唯一约束会把跨域条目误合并；
5. **工具面**（`recall_context_span`）：schema + 分派表 + 治理故障放行白名单 +
   并行安全声明 + per-tool 超时 + 元检索名单，六处一次接齐（教义第 5 条：
   一个断链被点名后，同契约的全部消费方一并处理）。执行体**无退化路径**——
   取不到就点名 `RefUnparsable` / `LayerAbsent` / `SourceMissing` / `ScopeFiltered`
   并附本会话现有档位，让模型能自行纠正引用，而不是盲重试。

### 25.3 判据与主链一致（写死字面量的断言改取单一事实源）

台账版本号从 v2 增到 v3，三个既有判据（`test_fresh_ledger_lands_at_latest`、
`test_legacy_db_migrates_to_latest`、`test_tokenizerIsTrigramAfterMigration`）
因**写死 `== 2`** 而红。红的不是它们要守的判据（"库有版本号纪律且落到最新"），
只是散落在用例里的第二个数字。故新增单源 `db_migration.latest_version(域)`，
三处改从它取值——**判据语义一字未改**，链长不再需要人肉同步（这与 v2 交付时

同理，`test_context_pool_retention_contract` 的台账替身补上 `item_hash` 形参：

## 26. T-11e：折叠 rollup 后台化（关键路径每轮 ≤1 次摘要调用）（2026-09-25）

工单 §0.4 第 16 步、§12.4 的第四张子票。判据源：§12.7 判据 6（成本上界）
与 §12.6 的回退等式。

### 根因（不是"少一次重试"）

判据 6 要求「每轮新增摘要 LLM 调用 ≤ 1 次（rollup 走后台）」。改前该上界被
**失败形状**打穿：`compact_window` 的收敛保证是「摘要失败 → 丢最旧一条重试
（上限 `_SUMMARY_MAX_RETRIES` = 3）」，而编排器的折叠路径把整段重试**与**递进
折叠循环（`ratio` 每轮 +0.1 再摘要一次）一并放在关键路径上。

实测（真 `build_context`，30 条长消息，摘要器恒失败）：

```
改前：单轮发起 4 次摘要 LLM 调用（1 首试 + 3 重试）
改后：1 次
```

失败越多、调用越多 —— 正是判据 6 要挡住的曲线。

### 改法：成本入参 + 后台 worker（不是二选一，两个都要）

1. **成本入参**（`window_compactor.compact_window`）：新增 `summary_max_retries`
   与 `summary_call_budget` 两个入参，**默认值维持既有语义**（零行为变化），
   折叠路径显式给 `0` / `1`。压缩器对**直接**调用者的收敛保证一字不改 ——
   `tests/unit/context/test_window_compact_convergence.py` 锁的就是它，本票必须
   让它继续绿。
2. **后台补做**（新模块 `context/fold_rollup.py`）：`ContextRollupWorker` 是失败
   批次补做的**唯一**落点。它**持有并 await 自己的任务** —— 工单 §12.5 第 4 条
   把 `asyncio.ensure_future` 发后不管列为假实现（现成反例
   `openai_loop.py:492/555`：异常无人 await），故异常在此记账成 `last_error`
   （点名类型与消息），不逃逸、不静默。
3. **失败不写**：worker 只在摘要成功时回调 `_commitRollupSummary`，因此"失败不
   推进覆盖账"由**调用点位置**保证，不靠调用方自觉（与 T-05 同族，别把假账带
   回来）。失败时视图沿用既有静态折叠桩语义。
4. **有界**：同会话在飞 ≤1、全局在飞 ≤4；超出的派发被丢弃并计 `dropped`（可见）。
   无界队列会让会话越长堆积越多，与 T-07"持久层不可只增"的纪律同理。
5. **单一事实源**：提交点与热路径逐字同源（`covered` / `last_count` / 代际推进）；
   派发时带上**那一刻**的窗口条数 —— 后台跑完时窗口早已前移，用当时的条数会把
   期间新增的消息一并谎报为已覆盖。
6. **读数**：`get_context_health()["fold_rollup"]`
   （`dispatched / succeeded / failed / in_flight / dropped / last_error`），
   生产读者 = /metrics 既有抓取面（不新开端点）。取数取自 worker 本体，编排器不
   另记一份。
7. **回退开关** `NEUROVA_CONTEXT_ROLLUP=0`：不装配 worker，行为等价于本票之前。

## 27. T-11c：分辨率装配器（视图按距离 1:4:16 几何退避装多档概览）（2026-09-25）

工单 §0.4 第 17 步、§12.4 的第五张子票，也是 **T-11 族的收口单**。判据源：
§12.1 C2（梯度）、§12.0 B（概览梯度常驻）、§12.7 判据 1、2 与探针 **P15**。

### 27.1 根因（不是"视图里少一行摘要"）

T-11a/b/d/e 交出的是**数据**：代际栈、池内层节点（带 `covers`）、可解析引用、
后台 rollup。而**视图装配器**这一环从没改过 —— `build_context` 把
`compact_window` 产出的那一行摘要（= 代际栈顶）拼进 `context` 就结束了。

实测（真 `build_context` 连跑 6 轮，budget 1200）：**池内 6 档层节点、视图 1 行摘要**。

```
池内层节点 6 档, 摘要调用 6
  level=1 seq=6 turn=[1, 13] hashes=13 tokens=9
  ...
  level=6 seq=1 turn=[1, 8]  hashes=8  tokens=9
--- 视图里的 system 行（摘要相关）---
  [早期对话摘要] 第6代摘要：覆盖 13 条     ← 只有栈顶这一代
```

于是 §12.1 的 C2 在数据上不成立 —— 只有一代，谈不上"越远的位置分辨率越低"
（§12.0 B），判据 1 / 2 与 P15 全红。

### 27.2 改了什么

**新增 `context/fold_resolution.py`：阶梯的单点出处。** 档位预算、可行档数、
按预算截断三件事只在这里定义一次 —— 装配器只做"取索引 → 问阶梯 → 拼行"，
读侧（读数、探针）也从同一处取档位预算。各写一份几何比就是第二份事实源。

- 档间比 = `GEO_RATIO = 4`（1 : 4 : 16 的相邻比）。**方向**：近档预算大、远档小
  （规格的数列按距离升序读即为 1 : 4 : 16）。理由见工单 §12.4 偏离记录第 1 条。
- 深度 `k` 的阶梯总预算 = `region × (1 + 1/4 + …) < 4/3 × region`，对任意 `k` 成立
  —— 故"档数不设上限"（§12.1）与视图预算有限不冲突：**索引**不设上限，**视图**
  按预算装前 `k` 档，装不下的深档计入 `dropped_levels`（可见），且它们仍可由
  `covers_ref` 确定性下钻（T-11d）。
- 概览区额度 = 窗口预算 − 尾部原文实占（不足地板时取地板），故阶梯总量恒 ≤ 窗口预算。

**装配器落点**：`orchestrator._assembleResolutionLadder`，接在 `_inlineCoversRef`
之后（唯一的概览区出口）。**替掉**那一行摘要而不是在它后面再补：池索引已含栈顶
那一代的原文（`archive_summary` 存的是同一个字符串），留着旧行再加索引行会让同一档
在视图里出现两次。索引取不到时**原样返回** —— 那时视图里那行静态折叠桩是诚实的
降级面。每档引用**由装配器自己渲染**（引用属于该档；拿栈顶那一份挂全部档位就是
第二份寻址口径）。行序**由远及近**：位置序必须在视图里显式成立。

读数落 `get_context_health()["fold_resolution"]`（`enabled` / `levels` /
`dropped_levels` / `budget_ratio` / `level_budgets` / `truncated_chars` /
`last_error`），生产读者 = /metrics 的既有快照面，**不新开端点**。

回退开关 `NEUROVA_CONTEXT_FOLD_RESOLUTION=0`：**刻意不复用** T-11e 的
`NEUROVA_CONTEXT_ROLLUP` —— 那是"rollup 走不走后台"，这是"视图装不装多档"。

### 27.3 同批在根因处修掉的跨会话缺陷（本票最值钱的一段）

**我在 A/B 时被咬出来的，不是本票引入的，但是本票让它从"潜伏"变成"实际泄漏"。**

根因在 T-11b 的索引读面：**`fold_seq`（层序）是会话内的事实**（每个会话各从 1
起算），而台账库按 `(user, agent)` 分库、同一个库文件里躺着该 agent **全部会话**
的 SUMMARY 行。T-11b 的实现把两源并成一个列表后，用**全局**最大层序派生档号：

- 新会话的第一代（层序 1）被别的会话/历史行推到档号 21；
- 而档号 1 落到**别的会话**那一行上。

改前这个缺陷是**潜伏的**（索引写进归档、没人按档号取用，所以判据都没碰到）。
本票的装配器一按档号装配，它当场变成**跨会话摘要注入视图** —— P1-1 / T-03 同族的
泄漏。A/B 实测：`test_two_direct_sessions_do_not_share_fold_summary` 等 **4 条既有
用例由绿转红**（基线全绿，故不能算预存失败）。

修法（不在报错处加判空，按教义第 1 条收口契约）：

1. `ContextPool._projectLayers` **按 `session_id` 分组派生档号** —— 跨会话比较层序
   本身没有意义；
2. 装配器只取本会话的档（判据取 `pool.session_id`，即写入侧打标的**同一个值**，
   不另算一份身份）；
3. `drilldown` 的引用里的会话必须与档的会话一致 —— 只按层序取时，两个会话都从 1
   起算会命中外会话的档（引用语法里本来就有会话身份，此前解析了却被丢弃）。

### 33.3 判据 7（前缀命中率）——两处契约面断点，不是"少接一根线"

工单 §12.7 判据 7 与裁决 D3 都写明「不用估算口径自证」。读侧通路看着是现成的
（`composition` 有 `provider_usage` 形参、也实现了"优先采信
`prompt_tokens_details.cached_tokens`"），实测两处断点**都在契约面**：

**① 形状分裂。** 生产链路能拿到的唯一真值是 `usage_accounting.last_call()` 的
**归一** payload（`multi_model_client._extract_cache_tokens` 已把 OpenAI 与
Anthropic 两形合并到这一处）：

```
{'prompt_tokens': 1000, 'cache_read_tokens': 800, 'cache_write_tokens': 0, ...}
```

而 `composition` 只认**原始供应商形**。把生产真值原样喂进去，读数如实落在
`cache_source='none'` / `cache_hit_rate=None` —— **真值在手却读不出来**。

**② 生产从不喂。** `measure_composition(...)` 在 `chat_pipeline` 的调用点
不传 `provider_usage`（实测 `neurova/` 下该形参只有定义、零生产实参）。
面板命中率永远只能是 `prefix_estimate` —— 那正是判据 7 明禁的估算口径自证。
