# MOSS TTS 按需加载 + 超时释放可行性分析（2026-09-08）

> 结论先行：**可行，且收益比原估大一个量级**。实测模型真实增量是
> **+3.4GB RSS**（非磁盘 728MB），shutdown 后 **-98% 全还 OS**，热重载
> **6.9s**。但冷启动延迟是硬代价，推荐"按需 + TTL 释放 + edge-tts 顶班"
> 方案（见 §四 C），复用现有 fallback 机制，无新增协议。

## 一、实测依据（全生命周期探针，干净子进程，即用即删）

| 阶段 | RSS | 线程 | 耗时 |
|------|-----|------|------|
| 基线 | 43MB | 24 | — |
| 首次 initialize（5 个 ONNX 会话） | **3496MB** | 42 | **12.7s** |
| 合成一句 | 3506MB | 43 | 1.03s |
| shutdown + gc | **92MB** | 28 | — |
| 重载 initialize（OS 缓存热） | 1470MB | 43 | **6.9s** |
| 终态释放 | 98MB | 28 | — |

三个决定性事实：

1. **内存真还**：shutdown 置空 5 个会话 + gc 后 RSS 3496→92MB，ORT 竞技场随
   会话销毁归还 OS，"超时即释放"在内存机制上完全成立。
2. **重载不算贵**：热缓存 6.9s、冷启动 12.7s。且重载稳态（1470MB）比首载
   （3496MB）低一半——首载含一次性开销，释放-重载循环后的稳态反而更省。
3. **合成会话正常**：释放前后合成均产出正常 WAV（65KB/57KB，RTF 正常），
   说明重建后的会话与首载无差异。

## 二、放大视角：MOSS 生命周期全链盘点（改动前必读）

系统里有**三个 TTSManager 实例**，各自独立持 `_engines` 缓存——按需/释放
机制必须覆盖全矩阵，否则只省到三分之一：

| 实例 | 创建点 | 初始化时机 | 消费方 |
|------|--------|-----------|--------|
| 全局 `app_state.tts_manager` | `api/app.py:426` | **启动即载**（`app.py:677`） | VoiceEngine 统一层 → `/synthesize`、`/synthesize-stream` |
| per-agent `a.tts_manager` | `agent_core.py:617`（工作区模型路径） | **懒**（`tool_executor.py:3051` 用时 initialize） | `tts_synthesize` 工具 |
| `voice_pipeline._tts_manager` | `voice_pipeline.py:111` | **从不 initialize** | `voice_pipeline.py:242` 直接 synthesize |

已存在的可复用机制：

- **懒初始化先例**：`tool_executor.py:3051-3052`
  `if not manager.is_initialized: await manager.initialize()` —— 用时加载
  模式在库内已被验证，工具路径天然就是按需的。
- **请求中途初始化引擎的先例**：`manager.py` `_fallback_synthesize` /
  `synthesize_stream` 的候选循环里本来就会 `_initialize_engine`——fallback
  机制天然支持"运行时把引擎换进来/换出去"。
- **`shutdown()` 双层已就绪**：`MOSSNanTTS.shutdown()`（moss_nano.py:922）置空
  全部 5 会话；`TTSManager.shutdown()`（manager.py:311）清 `_engines` 缓存。
- **MIME 随引擎动态**：`manager.get_audio_media_type` 按当前引擎取
  （moss=wav / edge=mpeg），`/synthesize-stream` 端点透传——引擎切换对前端
  blob 播放天然兼容，无需前端改动。

必须处理的耦合点（现状会挡路）：

1. **`app.py:703` VoiceEngine[TTS] 的创建被 `is_initialized` 门控**——defer
   初始化后该门控恒 False，统一层不会被建，端点走旧降级分支。须改为无条件
   创建（`is_available()` 本来就是动态属性，门控多余）。
2. **`/synthesize-stream`（audio.py:240 起）把 manager 的异步生成器持到流
   结束**——流进行中释放会把 sessions 置 None，下一个 `session.run()`
   抛错 → 流截断（manager 层 except 会吞掉不 500，但音频缺尾巴）。需要
   in-flight 守卫（见 §五）。
3. **`moss_nano.shutdown()` 漏清 `self._sp`（sentencepiece）、`_manifest`、
   `_builtin_prompt_codes`**——体积小（MB 级），但按需释放语义上应一并置空，
   下次 initialize 重载。
4. **per-agent 双载风险**：`agent_core.py:617` 用工作区模型路径
   （`agent_workspaces/{id}/models/tts/`），该目录当前不存在 → per-agent
   initialize moss 必失败 → fallback edge **掩盖了真实意图**；一旦有人把
   模型放进工作区，就会双载 3.4GB×N。按需机制落地时应顺带处理（引擎级
   单例共享或显式禁止 per-agent moss）。
5. **`voice_pipeline.py:242` 是疑似预存死路径**：该 manager 从不 initialize，
   `synthesize` 恒返回 `b""`（manager.synthesize 的未初始化契约）。本次不修，
   登记；按需机制落地后此路径会被 `_ensure_ready` 顺带治好。

## 三、方案对比

| 方案 | 思路 | 内存收益 | 代价/风险 | 判定 |
|------|------|----------|-----------|------|
| A 维持现状 | 启动即载、常驻 | 0 | 3.4GB 常驻 | 语音重度用户可接受，非语音部署浪费 |
| B 完全按需 + TTL 释放（简单版） | 请求时同步 initialize；空闲 TTL 后 shutdown 丢缓存 | 空闲期 **-3.4GB** | 每次冷启首句 +7~13s；流中释放竞态 | 可行但 UX 粗糙 |
| **C 按需 + TTL 释放 + edge 顶班（推荐）** | 释放后当前引擎切 edge-tts（轻量已缓存）；moss 后台预载，就绪换回链顶 | 空闲期 **-3.4GB** | 本次语音暂时降级为 edge 音色；需 in-flight 守卫 | **收益/复杂度最优** |
| D 进程外推理服务 | 子进程承载 moss，主进程按需 RPC | 主进程 -3.4GB | IPC/流式/生命周期全套新协议，改动大 | 过度设计，不建议 |

## 四、推荐方案 C 的实施设计

### 4.1 行为定义

- **按需**：任何 `synthesize / synthesize_stream` 入口先
  `_ensure_ready()`——当前引擎可用直接用；不可用按 fallback 链初始化
  （复用 `_initialize_with_fallback`，实例缓存防重复加载）。
- **TTL 释放**：manager 持 `_last_used_ts`；后台协程每 60s 检查，
  `now - _last_used_ts > ttl` 且 `_active_requests == 0` 且当前引擎是
  moss → 释放（shutdown + `_engines.pop`）→ 当前引擎切 fallback 链中
  下一个轻量引擎（edge-tts），`_initialized=True` 保持服务可用。
- **顶班换回**：释放后首个请求由 edge 立即合成（零等待）；同时后台触发
  moss 预载，就绪且无进行中请求时 `_engine` 换回 moss（链顶竞争语义）。
  保守档可改成"下个请求同步等 moss 重载"（+6.9s 一次），由配置选择。
- **配置面**：`TTSConfig` 增 `lazy_release: bool = False`、
  `release_ttl_sec: int = 600`；env 兜底 `NEUROVA_TTS_LAZY_RELEASE=1`。
  默认关——行为默认不变，显式开启才生效（与 P0 八件套 env 门控惯例一致）。

### 4.2 改动点清单（全部落 manager 层，引擎与端点零改动）

| 位置 | 改动 |
|------|------|
| `neurova/tts/manager.py` | `_ensure_ready()`、`_active_requests` 计数、`_last_used_ts`、TTL 协程、`_release_heavy_engine()`、后台预载任务 |
| `neurova/api/app.py:675-677` | `lazy_release` 开启时跳过启动 initialize（仅创建 manager） |
| `neurova/api/app.py:703` | VoiceEngine[TTS] 创建去掉 `is_initialized` 门控 |
| `neurova/tts/moss_nano.py:922` | shutdown 补清 `_sp/_manifest/_builtin_prompt_codes` |
| `neurova/agent_core.py:617` | per-agent manager 透传同一份 lazy 配置（或禁止 per-agent moss，登记 §二-4） |
| 测试 | `tests/unit/tts/`：懒初始化触发、TTL 释放（假时钟）、`_active_requests>0` 不释放、释放后 MIME 随 edge、释放后重载合成正常 |

### 4.3 守卫与竞态（必须全做）

1. **in-flight 计数**：`synthesize` 与 `synthesize_stream` 的生成器体进入
   +1 / finally -1；计数 >0 时 TTL 释放跳过本轮（下轮再查）。
2. **释放与预载互斥**：`asyncio.Lock` 保护"释放/换回/预载"三个动作，
   防止后台预载与 TTL 判定互相踩。
3. **moss 内部锁不升级**：`moss_nano._lock`（threading.Lock，moss_nano.py:209,
   799, 886）只串行化推理，释放走 manager 层，不碰引擎锁——避免
   threading.Lock 在事件循环里长阻塞。
4. **切换期 MIME**：释放后 `audio_media_type` 跟随 edge=mpeg；流式端点已在
   生成器启动时取值，切换动作只在无活动请求时发生，无撕裂窗口。

## 五、风险与未知

- **首句降级**：idle 释放后第一句是 edge 音色（方案 C 语义），若用户对
  moss 音色敏感，用保守档（同步等 6.9s）或前端开启自动语音时预热。
- **ORT 首载一次性开销（3.4GB vs 重载 1.5GB 的差值）**：差值大概率是 arena
  初始预留与一次性探测缓冲，重载稳态即真实常驻水位；生产观察以重载后为准。
- **线程残留**：探针 shutdown 后线程 28 vs 基线 24（+4 残留，非 18 全退），
  ORT 线程池线程对象延迟回收所致，内存已还，无实际影响；登记不处理。
- **多 agent 并发 TTS**：per-agent manager 若同开 moss，双载风险见 §二-4，
  落地时必须二选一收口。

## 六、验收方法

1. `NEUROVA_TTS_LAZY_RELEASE=1` 启动 → 启动日志无 "TTS engine ready: moss-nano"，
   进程 Private 比基线低 ~3GB。
2. 首次合成：默认走 edge（无等待）；后台数秒后日志出现 moss 换回。
3. 强制 moss 合成一句后静置 `release_ttl_sec` → 日志 "MOSSNanTTS 已关闭"，
   Private 回落 GB 级。
4. 流式合成进行中人为触发 TTL → 流不截断，释放延后到流结束。
5. 回归：`tests/unit/tts/` 全绿 + 前端自动语音（useStreamTTS 句级流水线）
   实测一遍播放正常（MIME wav/mpeg 混合场景）。
