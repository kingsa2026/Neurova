## 1. 用户看到的现象与真实死因

Issue #236 附的构建链接指到 `cnb-8dk-1k3c7a0e0`。该构建**不是门禁**：

```
流水线: cnb-8dk-1k3c7a0e0-001 (status: error)
失败 Stage: 真撞顶：强制多轮工具调用 + maxTurns=1
错误信息: Agent aborted: reached maxTurns limit (1)
```

`maxTurns=1` 是**刻意压到 1 的探针**——它要自证「平台在撞顶时刻注入哪些事实变量」
（`CNB_PIPELINE_STATUS` / `CNB_BUILD_FAILED_MSG`），即 Issue #158 批的判据来源。
探针按设计撞顶并被平台中止，收尾接力 Stage（`cnb:trigger → api_trigger_npc_handoff`）
随之被判真并成功。**这条流水线的红与仓库代码、与 `main.push` 的十个门禁都无关**，
它只是「配额触发的正常收官」在一个探针上的复现。

## 2. 真正需要修的是另一件事：配额被自己的判据钳住

同一批会话在 main 线上把配额从 200 调到 500，CI 门禁
（`tests/unit/test_ci_npc_config_guard.py`）立刻把 500 判非法并钳回 200 ——
红灯原文：

```
TestTurnBudgetMultiplierIsNotAReachableSpinCeiling::test_declared_budget_exceeds_the_measured_interrupt_ceiling
E   AssertionError: 现行配额上限 200 不高于实测掐断轮数 251

...::test_budget_leaves_room_for_repeated_topouts
E   AssertionError: 现行配额 200 未超过「一次 2h 会话可容纳的 203 轮」
E   assert 200 > 203
```

### 根因（类别错误，不是阈值没调好）

旧判据要求 `maxTurns ≤ 2h ÷ SECONDS_PER_TURN(35.3s) ≈ 203 轮`。这个算式把
两件**不同源**的事相除：

| 量 | 实际来源 | 说明 |
|---|---|---|
| 被除数 2h | **平台**对 `npc:go` **会话**的墙钟硬限 | 约束的是整轮会话 |
| 除数 35.3s | **本仓**可优化的单轮均摊耗时 | 会随优化单调下降 |

后果有三层，缺一层都不足以解释这个数值为什么必须重写：

1. **前提不成立**：平台并不按「轮数 × 单轮耗时」计费墙钟。真撞顶探针
   `cnb-8dk-1k3c7a0e0` 的读数是 **1 轮 / 2428ms** 正常 abort；多轮会话只受
   `npc:go.timeout`（每次工具执行 20m）与流水线 20h 上限约束（见 `.cnb.yml` 注释）。
2. **方向是反的**：单轮越快，`2h ÷ 单轮` 越大，表面上"可用轮数变多"，
   但该值同时是**上钳**——它把配额压到"预算刚好够一次会话跑完"，
   于是"跑满 → 收尾接力 → 再跑满"这条设计内的链条在合法域里只剩一轮。
   配额若**低于**实测掐断轮数，撞顶就永远是"被平台外部掐断"（无告警、无收尾，
   worktree 里已改未提交的成果随容器一起丢），而不是"配额触发的正常收官"。
3. **连自己的读数都够不着**：实测 `cnb-f1c-1k31garu5` 是 251 轮 / 7262s、
   `cnb-m48-1k33grbms` 是 207 轮 / 7300s，两次都**被外部掐断**；
   而上钳给的是 203 轮 —— 判据给出的"合法上界"比"实际会发生的轮数"还低。

## 3. 修法（教义第 1 条：改根因，不改症状）

| # | 改动 | 落点 |
|---|------|------|
| 1 | 删掉「2h ÷ 单轮耗时」的上钳；上限只反映 `$` 兜底挂载点的**现行声明值**（下钳 `MIN_TURNS`，防非法值被洗白） | `tests/unit/test_ci_npc_config_guard.py` 的 `maxTurnsCeiling()` |
| 2 | 算式改为**读数函数** `spinCeilingReading(cost_per_turn)`，成本口径由调用点显式给出；重新做成钳位即红 | 同上 |
| 3 | 新增独立判据：配额必须**高于**实测掐断轮数（251 / 207），且必须高于当前单轮成本下的会话容纳读数 | `TestTurnBudgetMultiplierIsNotAReachableSpinCeiling` |
| 4 | 配额现值单源化：`.cnb.yml` 两处 `maxTurns: 500`，`.cnb/settings.yml` 三个角色的「现行 N 轮」读数随之对齐；两处漂移即红 | `TestDeclaredBudgetIsSingleSourcedIntoThePersonas` |
| 5 | `.cnb.yml` 的「轮次上界」注释段重写：写明"配额 ≠ 2h 反推值"，并附两类实测读数 | `.cnb.yml` 的 `$` 段 |

**净 LOC 去向**：产品代码 0 行；`.cnb.yml` 注释净增约 +8 行（新增两类实测读数的
理由记录，按教义第 2 条逐条列明）；`.cnb/settings.yml` 三处、各改 1 字符；
判据侧净增约 +120 行（两条新判据 + 两个新常量），并删除旧判据
`test_max_turns_leaves_room_under_platform_hard_limit`（它守的正是被证伪的钳位）
及其常量 `MAX_TURNS_BUDGET` / `AFFORDABLE_TURNS`（教义第 6 条：删净第二份定义）。

## 6. 同批修掉的第二处根因：叙述性提及被当成悬空路径引用（CI 两例红）

本批 CI 的 `unit-tests-py311` 跑出两例红，均落在
`tests/unit/test_archive_nav_impact_guard.py`：

```
FAILED ...TestPointerEntriesAreProjectInitiated::test_summary_block_matches_scanner
  AssertionError: 台账的筛选摘要与扫描器输出不一致
  - 空引用共 **1867** 条 …
  + 空引用共 **1866** 条 …

FAILED ...TestMachineBlocksHaveAGenerator::test_writer_is_idempotent_on_the_shipped_ledger
  AssertionError: 台账与生成器已不同步：把生成结果写回后正文仍会变。
```

**根因不在台账，也不在本批新增的第 4 节正文措辞**，而在扫描器的**入账门槛**：
`scripts/scan_docs_refs.py::scanFile` 把任意被反引号包住、后缀落在 `PATH_SUFFIXES`
里的字符串一律登记为路径引用。`PATH_SUFFIXES` 含 `js` / `ts` / `json`，于是
**平台侧**校验器 `validate.js`（`cnb` CLI 的一部分，**不在本仓**）被登记，
判定「源已删除」，计入归档层悬空引用 —— 台账机器区是从扫描器生成的，
立刻从 1866 漂到 1867，而台账正文里的 1866 是上一轮生成物，于是两例红同时成立。

**修法（教义第 1 条：改根因，不手改生成物）**：入账门槛收口为
`codeSpanNamesARepoLocation(ref, byBasename)` —— 行内码只有**在表达仓库内位置**时
才算路径引用：带目录分隔符（`context/fold_resolution.py`），或**全仓同名有命中**
（`fold_resolution.py`）。零命中的裸文件名是**叙述性提及**，不入账。
判定与可达性解析仍只走同一份 `resolveTarget`，此处只调门槛，不另造解析。

**这不是为一篇文档开的豁免**：同一判据修掉一批既存误报 ——
`restart_neurova.bat` / `pytest.ini` / `memory-enhancement.ts` /
`TokenConsumptionChart.vue` 这类「旧方案里提过的组件名」，此前全被登记成
「源已删除」。
