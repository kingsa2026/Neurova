## 1. 现象与实测读数（不是推测）

Issue #306 的评论里，用户 @ 了**本仓在册角色** `@kingsa2026/neurova(DSCoder-max)`。
平台上出现两台构建，且**都停在中转态**，没有一条进入执行：

```
cnb-1ii-1k3jc0fgm-001  pipeline 001                      pending
cnb-tb2-1k3jc0fgm-001  cnb/issue.comment@npc/pipeline-1  pending
```

同一条 Issue 的首条评论（@ 平台内置系统 NPC `CodeBuddy`）留下的状态读数是：

```
cnb/issue.comment@npc/default   error [14.7s]
```

`default` 那一格是**平台默认配置**的流水线；本仓 `.cnb.yml` 的
`$` → `issue.comment@npc` 定义的那几个 stage 名（「构建环境自证：工作区落点可达且与
`$PWD` 同址」/「角色准入：被 @ 的角色名必须在册」/「npc-go 在册角色执行任务」）
**一个都不在里面**。用户读到的「空转」，就是「构建被创建、但跑的不是本仓声明的 Job」。

---

## 2. 根因：本仓 NPC Job 没有自带容器 runtime

平台「自定义 NPC」篇（load-config）：NPC 事件触发时，系统把**系统默认配置**与
**NPC 所属仓库**的 `.cnb.yml` 合并，本仓已定义的事件覆盖默认。

平台系统默认配置里 NPC Job 的容器 runtime 是**按 key 给出**的（`docker.image`）。
合并是 **key 级覆盖**、不是深合并：本仓 Job 声明了 `stages` / `endStages` / `envScript`，
**唯独没有声明 `docker.image`**，于是这一项由平台那一份顶上 —— Job 的实际运行环境
不再由本仓 `.cnb.yml` 决定。这条差异在平台侧与日志里都不响：

- 本仓的解释器探测（`&npc-script-interpreter`）按「镜像只有 node」设计；
- `npc:go` 那一格的实际容器由平台那一份 runtime 决定；
- 而配置里看不到任何痕迹 —— 同一根因下「看得见的配置」与「跑起来的配置」分叉。

`@CodeBuddy` 那台是**另一件事**，不是同一个根因：它是平台内置系统 NPC，
「NPC 所属仓库」是平台的，本仓 `$` 下这套 Job 对它**完全不生效**
（该结论与 `docs/05-reports/npc续跑角色连续性_2026-09-26.md` §1.2 一致，本轮再次印证）。
想让构建落在本仓声明的 Job 上，必须 @ **本仓在册角色**。

---

## 3. 修法（教义第 1 / 5 条）

1. **本仓 NPC Job 自带容器 runtime**：`$` 段共用 Job 体与接力载体两处补
   `docker.image: cnbcool/default-npc:latest`（本仓解释器探测与门禁脚本按该镜像设计）；
2. **放大视角（教义第 5 条）**：同契约的**全部**消费方一次扫清 —— 不只是
   `issue.comment@npc`，`pull_request.comment@npc` 与 `api_trigger_npc_handoff`
   同样补上；判据按「每个 `@npc` 事件下的每个 Job」遍历，而非点名某一条；
3. **判据落地**：新增两支常驻判据（见 §4），把「缺 runtime」变成会红的形态。
