> 方法：先实测运行中进程，再对照代码定位每个字节的来源。所有数字为当场实测，
> 非估算；代码引用均给出 `文件:行号`。结论按收益排序，标注风险与预期收益。
>
> **指标口径（用户拍板）**：只优化**运行内存**；模型文件等硬盘占用不设限、
> 不回收（下载缓存/models 目录/OS 文件缓存随意留）。
>
> **实施状态（2026-09-08 深夜）**：H1 + H2-C 已实施并 live-verify 通过，

## 三、热点定位（按收益排序）

### H1（P0）memory_layer 包 __init__ 急切导入 memory_field → 白拉 torch ≈176MB

- **链路**：`mem_core.init_moe_router`（`neurova/mem_core.py:640-642`）→
  `from ...memory_layer.moe_router import ...` → 触发
  `neurova/cognitive_layers/memory_layer/__init__.py:121-128` 的
  `from .memory_field import ...` → `memory_field.py:18` 模块级 `import torch`。
- **实证**：仅导入 `unified_vector_store` 子模块，torch 即进入 `sys.modules`。
- **要害**：MemoryField（NeRF 记忆场）在运行时**零消费方**——全仓检索
  `get_memory_field / MemoryFieldNetwork( / MemoryFieldTrainer` 仅命中
  `__init__.py` 导出与单测；同包 `volume_renderer.py` 只用 `math` 不依赖 torch。
  也就是说 **176MB 的 torch 是为一个运行时没人用的实验特性进场的**。
- **建议**：`memory_layer/__init__.py` 把 memory_field（及任何 torch 系导出）改
  为 PEP 562 `__getattr__` 惰性导出，包级 API（`from ... import MemoryFieldConfig`）
  完全兼容，单测不动。
- **预期收益**：-176MB（约 -6%），零功能损失。

### H2（P1）MOSS TTS 模型启动即常驻 —— 09-08 深夜实测修正：实际增量是 **+3.4GB**，不是 640MB

- **链路**：`neurova/api/app.py:677` 启动即 `tts_manager.initialize()` →
  `FALLBACK_CHAIN[0]="moss-nano"`（`neurova/tts/manager.py:32`）→
  `MOSSNanTTS` 加载 `models/tts`（磁盘 728MB）进 onnxruntime 多图会话
  （prefill/decode_step/local_frame/codec_decode/codec_encode 共 5 个）。
- **实测（全生命周期探针，干净子进程）**：

  | 阶段 | RSS | 线程 | 耗时 |
  |------|-----|------|------|
  | 基线 | 43MB | 24 | — |
  | 首次 initialize | **3496MB** | 42 | 12.7s |
  | 合成一句 | 3506MB | 43 | 1.03s |
  | shutdown+gc | **92MB（-98%）** | 28 | — |
  | 重载 initialize | 1470MB | 43 | **6.9s**（OS 缓存热） |
  | 终态释放 | 98MB | 28 | — |

  结论：**模型真正占的是 3.4GB（ONNX 权重+arena），不是磁盘 728MB；释放
  机制完全有效（-98% 还 OS）；热重载 6.9s 可接受**。"按需加载+超时释放"
  方案实测可行，详见《MOSS TTS 按需加载可行性分析》(同目录 2026-09-08)。
- 用户实测在用本地 TTS，模型常驻本身是功能成本，但有三处可省：
  1. **arena**：`moss_nano.py:234-237` 的 SessionOptions 只设了优化级别与线程数，
     未关 `enable_cpu_mem_arena`。ORT 内存竞技场默认把释放的内存攥在手里不还
     OS——但 shutdown 后 RSS 实测全还，说明 arena 问题主要影响**运行中碎片**，
     不影响整体释放可行性。
  2. **惰性时机**：可用 `NEUROVA_TTS_DEFER=1` 类 env 门控把 TTS 初始化推迟到
     首次语音请求（代价：首句多一次模型加载延迟），对不用语音的部署省 ~3.4GB。
  3. **实例缓存只增不减**：`manager.py` `self._engines` 缓存所有初始化过的引擎，
     切换引擎后旧模型（实测 3.4GB）永驻。可在切换成功后释放被换下的引擎。
- **预期收益**：非语音部署 defer 模式 **-3.4GB**；语音用户 idle 释放按需重载
  同样 -3.4GB（代价 idle 后首句 +7~13s，可前端预热提示）。

### H3（P1）ONNX embedding 同样未关 arena

- `neurova/embedding/onnx_embedding.py:195-198`：SessionOptions 已设
  `intra/inter=4`（好），但未关 arena。bge-small-zh（models/embedding 274MB）
  是语义检索核心、常驻属必要，arena 策略可与 H2 同批加 env 门控。
- **预期收益**：与 H2 合计计入，单独约 -50~150MB。

### H4（P2）torch CPU 线程池附加成本

- torch 载入后按核数拉起 intraop 线程池（线程+每线程 arena）。**H1 修复后 torch
  完全不进场，此项自动消失**——不建议单独处理。

### H5（P2）49 线程 × 栈保留

- uvicorn 事件循环 + ORT 双会话各 4+4 线程 + 守护线程群。Windows 每线程默认
  1MB 保留（Private 只计 committed 部分），影响中等偏低。ORT 线程已限 4，无
  动作建议，记录在案。

### H6（P2）composition 快照存整轮 messages 引用

- `neurova/context/composition.py:35,184-185`：`_last_composition` /
  `_last_messages` 每 agent 存上一轮完整 messages（渲染截断 200k 字符，但存的是
  原始引用）。规模 = agent 数 × 1 轮（当前 3 个 agent），小头，记录在案，仅在
  agent 数量增长后需加 LRU。

### H7（重要发现）FunASR：已安装、未激活、且一旦激活释放不干净

- **现状（09-08 实测）**：funasr 1.4.13 + modelscope 1.39.1 已装，
  `import funasr` 即 **+437.6MB**（比 torch 本身还大，且 import 即含 torch 链）。
  但 `ASRManager.initialize()` **生产代码零调用**（对比 TTS 在 `app.py:677` 有
  启动调用）——全局 manager 只构造不激活 → `/audio/transcribe` 恒 503
  （audio.py:358 门控）；per-agent 路径（`tool_executor.py:3011`）有懒初始化
  但模型未下载时必失败。**当前进程内存账中 FunASR 贡献 = 0**（从未 import）。
- **若激活，全生命周期实测（干净子进程，含 ModelScope 自动下载 paraformer-zh
  953MB 至 ~/.cache/modelscope）**：

  | 阶段 | RSS | 线程 | 耗时 |
  |------|-----|------|------|
  | 基线 | 24MB | 5 | — |
  | initialize（含下载） | 2666MB | 53 | 10.9s |
  | transcribe（1.5s 正弦波） | 2727MB | — | 0.36s |
  | shutdown + gc | **1411MB（仅还一半）** | 58 | — |
  | 重载（缓存热） | 2824MB | 58 | 4.4s |
  | 终态释放 | **1444MB（残留 ~1GB）** | 58 | — |

- **与 MOSS 的本质差异**：`FunASREngine.shutdown()`（funasr_engine.py:238）置空
  `self._model` 后只回收一半——残留 ≈ 模块底价 455MB（funasr/torch 等已导入
  模块永驻 sys.modules）+ **~1GB 权重未被回收**（≈ paraformer 磁盘 953MB，
  funasr 内部注册表/缓存对模型对象持有引用，`_model=None` 断不掉）。
  **MOSS 的"超时释放"模式照搬到 FunASR 行不通**，须先在 funasr_engine 内
  定位持有链（AutoModel 类级注册/缓存）否则激活即永久多背 ~1GB。
- **另注**：`FunASREngine.__init__` 的 `model_dir` 参数在真实加载路径中未消费
  （`AutoModel(model="paraformer-zh")` 走 ModelScope 远程命名，不经本地目录，
  funasr_engine.py:48,119,177 三处自相矛盾）；`_transcribe_sync` 里
  `asyncio.new_event_loop()`（:218）创建后未关闭/未使用，属小泄漏。
- **建议**：保持 FunASR 不激活（现状=零成本）；若未来要激活本地 ASR，
  先修释放链 + 模型路径三处矛盾，再按 TTS 的 defer/按需模式接入。
