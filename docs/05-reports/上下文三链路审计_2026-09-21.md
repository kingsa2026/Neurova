## 0. 怎么读这份报告

证据标注约定：

- **[实测 P#]** — 探针脚本当轮跑出的数字，可在本机一条命令复现；
- **[行号]** — 通读代码得到的静态事实（调用点/无调用点/常量值）；
- **[外推]** — 由实测值线性推导，**未**在真实规模上测量，不得当证据使用；
- **[假设]** — 因果链尚未证实，只登记为待取证方向。

严重度：

- **P0** = 数据完整性/隔离契约被破坏，或压缩机制对它最该防的内容形态失效；
- **P1** = 功能闭环断裂（写了没人读、读了恒空、跨会话串内容）；
- **P2** = 死线、管理面谎报、口径分裂，需要登记但不直接致障。

一句话结论：**三条链路的骨架都在，承重墙不在。** 决定"该不该压缩"的度量单位对非中文内容低估 20 倍量级；决定"谁能看见召回内容"的隔离闸口在池这一侧根本没有写入口；宣称"永不丢失"的归档池会被视图层就地改写；而真正落盘的那条路（驱逐台账）按当前构造参数不可达。

## 1. 生产默认路径的真实工作机制

默认配置：`enable_context_pool=True`（`agent_core.py:258`）、`enable_auto_tagging=False`（`:259`）、
`NEUROVA_AUTO_COMPACT` 未设=开（`context/orchestrator.py:124`）。

## 2. P0 缺陷

### P0-1 压缩触发判据的度量单位对非中文内容失真 20 倍以上

**根因**：`context/token_estimator.py:52-59` 的 `BALANCED`（"推荐"档）系数为
`chinese_ratio=1.5 / english_word_ratio=0.25 / other_char_ratio=0.1`，
而 `:171-176` 的 word-splitting 分支里 `other_tokens` 恒为 0 —— 即英文/代码/JSON 只按
**空白分词数 × 0.25** 计价，`other_char_ratio` 在这条路径上永不参与。
一个不含空格的长串等于 1 个"词" → 估成 1 token（`:187` 的 `min_tokens=1` 兜住下限）。

**这是决定要不要压缩的那把尺子**：窗口折叠判据（`orchestrator.py:1162`）、
microcompact 门槛（`:1009`）、抽屉召回额度（`:668`）、每条消息开销（`window_compactor.py:13,28`）
全部用它。

**证据**：

- [实测 P11] 12 段英文散文 + 12 段 JSON + 一个 9000 字符无空格块构成的三轮历史：
  `estimate_window_tokens=91`，真 `o200k_base=2075`，**低估 22.8×**；
  预算 45480 → 判据"未超预算" → **折叠消息数 0**，9000 字符块原样进视图。
- [实测 P11-单点] `estimate_tokens("x"*9000)=1`；同长度但带空格的 `"word "*1800` = 450。
- [实测 P8] 同一批文本横向：中文 27 字符 → BALANCED 40 / EXACT 22（高估 1.8×）；
  英文 81 字符 13 词 → BALANCED 3 / EXACT 13 / cl100k 13（**低估 4.3×**）。
- [行号] 设计文档写的是"1 个英文单词 ≈ 1.3 tokens"（`docs/01-architecture/09-context-processing.md:98`），
  实现取了历史 injector 的 0.25 并当作"推荐策略"；`docs/06-bugfix/bugfix-token-estimation.md:188`
  宣称"单一事实源"，实际 EXACT 只被展示面板（`composition.py:32`）采用，判据侧仍是 BALANCED。

**影响**：① 折叠/microcompact 对英文、代码、JSON、URL、base64 形态的工具输出几乎永不触发，
真正兜底的是撞墙后的被动恢复链（`openai_loop`）——即"预算机制是装饰，事故驱动才生效"；
② 抽屉按 `remaining` 放行归档，同一把尺子自证达标，实际 prompt 可达名义额度数倍；
③ 面板（EXACT）与门判（BALANCED）不同源，**从 UI 上看不出超限**；
④ `semantic_drawer.py:154` 截断按"保守 2 char/token"逆推，而同一仓库对中文的口径是 1.5 token/字
（`token_estimator.py:53`）——这条"保守"注释本身自相矛盾，中文条目按它截断会**放进约 3 倍**名义额度的内容。

**放大视角命中点**：所有以 `estimate_tokens`/`estimate_window_tokens` 为判据的位置
（`orchestrator.py:668/1009/1162/1262`、`window_compactor.py:48`、`injector.py:269-276/388`、
`context_pool.py` 写入期 `collector.py:26`、`semantic_drawer.py:142/247-250`）+
第四第五份实现（`anthropic_client.py:168-170`、`gemini_client.py:167-168` 的 `len//4`；
`llm_client.py:871` 的 `int(len*1.5)` 回退；`envelope.py:41` 的 `len/1.5`；
`enhanced_context_builder.py:324-346` 的 `len*0.5`）。

**修复方向（根因处）**：判据侧统一切到已存在的 EXACT（tiktoken o200k，`token_estimator.py:153-157`），
BALANCED 只保留给"没有 tokenizer 时"的回退并在日志里显式降级；`english_word_ratio` 按真机标定重定
（不是照抄 legacy 0.25）；`other_char_ratio` 在 word-splitting 分支要么生效要么删除该字段；
`semantic_drawer.py:154` 的 char/token 逆推改为按同估算器反解。防回归用例：无空格长串、纯英文段、
中英混排三种形态各自的"估算/真值"比值上界断言。

### P0-2 池召回路径的会话作用域隔离恒判 direct（群聊内容泄入单聊）

**根因链**（三处串联，任一处修好都不够）：

1. `agent_core.py:552` 构造 `ContextOrchestrator` **不传 session_id** → `orchestrator.py:102` 恒 None；
   `set_session_id`（`orchestrator.py:185`）在全 `neurova/` 内**零调用点** [行号]（调用只存在于 tests）；
2. `ContextPool` 以 `session_id=None` 构造（`orchestrator.py:171`），于是
   `_inject_isolation_tags` 的条件 `self.session_id is not None`（`context_pool.py:359`）永不成立 →
   chunk 的 `metadata["session_id"]` 从不被写；
3. `_archive_conversation_to_pool` 自身只写 `role/turn_id`（`orchestrator.py:961-978`），
   全仓**没有任何池写入方写 `chat_scope`** —— `chat_scope` 的唯一写入者是记忆侧
   `post_chat_pipeline.py:1074/1081` [行号]。

于是 `orchestrator.py:678-684` 调的 `filter_by_scope` 对池条目走
`memory_scope.scope_from_metadata`：无 `chat_scope` → 回溯 `session_id` 前缀 → 也没有 →
**恒返回 `direct`**（`memory_scope.py:37-44`）。而 `allowed_scopes_for_turn` 在群轮返回
`{direct, room:R}`、单聊轮返回 `{direct}`（`:24-28`）—— 恒 direct 意味着**两个方向全部放行**。

**证据**：

- [实测 P1] 按生产写入形状归档一条"project_roomB 群聊内容"：`chunk.metadata={'role','turn_id','agent_id','user_id'}`；
  单聊轮过滤后保留 **1/1**（应 0/1），他群（roomA）轮保留 **1/1**（应 0/1）。
- [实测 P1-对照] 同一条记忆若带 `chat_scope="room:project_roomB"`，单聊轮保留 **0** 条 ——
  过滤器本身工作正常，坏在池侧没有写入口。

**影响**：`memory_scope.py:4-8` 写死的隔离契约（"群聊记忆绝不泄入单聊""群群隔离"）
对**历史回忆注入**这一路完全失效；泄露的是原文内容（`[历史回忆] 用户: …`，`orchestrator.py:691`），
不是条数统计。读侧参数是对的（`chat_pipeline.py:1530-1531` 正确传 `chat_collab`/`chat_room_id`），
所以这是**写入侧缺字段**，不是判定逻辑写错。

**放大视角命中点**：所有池写入方同样缺 `chat_scope`/`session_id`
（`orchestrator.py:558/566/570/579`、`agent/swarm.py:627-628`（无任何 metadata）、
`voice_context_module.py:221-255`、`api/endpoints/context.py:149/237`、
`neurflow/variable_resolver.py:282`）；`context_pool.py:196` 的 `isolation_key` 同样恒 `:default`。

**修复方向（根因处）**：session 归属必须在**归档那一刻**随内容落进 metadata ——
`ContextOrchestrator` 构造参数不变，但 `build_context` 每轮以 `chat_room_id or ctx.session_id`
把作用域写进池条目（与记忆侧 `scope_tag_for_turn` 同一函数，单源）；
`set_session_id` 要么被真实接线（每轮由 ChatPipeline 调用）要么删除，不留"定义了没人调"的假闸口。
防回归用例必须走生产构造面（`agent_core` 那条调用形状），禁止测试自己手工传 session_id ——
这正是当前 74 个 context 测试没拦住该缺陷的原因（见 §8）。

### P0-3 视图层截断就地改写池内归档原文，并留下 hash 与内容失配

**根因**：`context/collector.py:29-33` 的 `collect()` 返回的是 `self._contexts` 里的**同一批对象引用**
（注释同时声明"归档永不被裁剪"），而 `context/semantic_drawer.py:156-157` 对单条超预算条目执行
`drop.content = truncated; drop.tokens = _est(truncated)` —— 视图层的截断直接写回归档实体。
`pool_models.ContextInput.hash` 是"来源域 + 原文"指纹（`:76-84`），改写 content 后并不重算。

**证据**：[实测 P13] 归档一条 1140 字符中文原文，`drawer.max_tokens=500` 触发截断分支后：
池内现存 **1015** 字符、`被截断=True`、`hash 与内容失配=True`。

**影响**：① 违反池的硬契约"永不丢失"（`context_pool.py:54-60` 第 1 条）——被截掉的部分**没有任何
其他副本**（不像窗口折叠，折叠前已按 turn 归档；截断发生在调取时，源就是它自己）；
② 失配的 hash 让后续真正想归档原文时被 `add_context` 的 hash 去重当作"已存在"跳过
（`context_pool.py:210-231`），**丢失变成不可挽回**；
③ `_by_hash`/`_read_index` 仍持旧 hash，索引与内容从此不一致，`recall_history`/去重/ack 全按旧指纹工作。

**放大视角命中点**：`compress_context`（`:874`）、`dedup`（`:915`）、`clear`（`:888`）也整体重排
`_collector._contexts`，`_rebuild_indexes` 有调用（这三处一致），但它们同为"视图/维护层直接操归档列表"
的同一族写法；`collector._apply_token_budget:38-61` 里另有一份**正确的**截断实现（新建
`ContextInput` 而非改写），只是没有调用方。

**修复方向（根因处）**：截断只能产出视图副本（`dataclasses.replace` + 显式标注 `truncated_from`），
归档实体永不原地改写；若坚持"整条跳过不截断"的原始契约（`semantic_drawer.py:116-117` 注释），
则删除截断分支。两种都可接受，**当前状态是两者混在一起且违反前者**。
防回归用例：draw 之后断言 `pool.get_contexts()[i].content == 原文` 且 `hash` 与 content 自洽。

## 3. P1 缺陷

### P1-1 折叠跨轮缓存没有会话维度：B 会话视图注入 A 会话摘要

`_apply_window_budget` 与 `manual_compact` 的缓存键都是 `self.session_id or "_"`
（`orchestrator.py:1170`、`:1268`），而 session_id 恒 None（见 P0-2）→ 整个 Agent 生命周期内
所有会话共用一个 `_window_compaction_cache` 条目。

**证据**：[实测 P2] 缓存键集合 `['_']`；对会话 A（量子话题）折叠成功后，再对**完全不同**的会话 B
（火星话题）折叠，`summarize` 因防抖（`delta = len(msgs)-last_count = 0 ≤ 4`，`:1176-1177`）
未被调用，B 的窗口首条 = `'[早期对话摘要] 会话A的摘要：用户问的是量子计算'`。

**影响**：跨会话内容串台，且以 system 摘要的权威身份出现（幻觉温床）；防抖判据在切换会话时
必然误判（消息数差与"新消息数"无关）。

**修复方向**：键必须是真 session_id（与 P0-2 同源修）；`set_session_id` 已实现的缓存裁剪
（`:196-202`）随接线一并生效；防抖改用"已覆盖 hash 集合"而不是消息计数 —— 该集合
`cache["covered"]` **已经在维护但全仓无任何读取点**[行号]（只在 `:1170/1211/1268/1295` 出现）。

### P1-2 摘要失败被上层当成"新摘要成功"，据此谎报覆盖

契约错位：`SummarizingCompressor.summarize` 在 LLM 超时/异常/幻觉未过时
`return previous_summary or None`（`summarizing_compressor.py:161/179/189/192/195/198`）——
对池侧 `rollup_overflow_digest` 是合理的幂等 no-op，但对窗口折叠层，返回值非空即被
`window_compactor.py:136-138` 判为"本轮摘要成功"（不再重试），并被 `orchestrator.py:1202-1204`
用来推进 `last_count` 与覆盖 `cache["summary"]`。

**证据**：[实测 P12] LLM 首轮成功、次轮抛错：`llm 调用次数=2`、`摘要文本未变=True`、
`last_count 10→20`。即新增 10 条被记为"已被摘要覆盖"，而那份摘要诞生时它们还在窗口里。

**影响**：后续 `_DELTA_RESUMMARY_MSGS` 防抖期内不再触发摘要，被折叠内容只在视图里留下一个
**与它无关**的旧摘要标题；"零丢失"在归档层成立，但在**摘要层是假账**。

**修复方向（根因处）**：`summarize` 区分两个返回语义——"成功给出新摘要"与"失败"（失败一律 None，
旧摘要由调用方自己持有）；或折叠层显式比对 `previous_summary` 后拒绝记账。
前者是根因，后者是守卫。防回归用例：注入必然失败的 llm_call，断言 `last_count` 不前移。

### P1-3 驱逐台账双端断：写了没人读的路径不可达，读了恒空

- 写入端：`_archive_evicted`（`context_pool.py:535-561`）只有两个调用者 ——
  `_enforce_resident_limit:275` 与 `cleanup_expired:772`。生产构造从不传 `resident_limit`
  （`orchestrator.py:168-177`，默认 None，`:127` 归零），且 `ttl_seconds=0`（`:176`）使
  `cleanup_expired:761-762` 立即返回 0；`cleanup_expired` 本身在 `neurova/` 内**零生产调用点**[行号]。
- 读取端：`recall_evicted`（`:563-620`）被 `tool_executor._execute_recall_history:3107`
  当作"子串模式"召回源暴露给模型。

**证据**：[实测 P5] 生产形状（`ttl_seconds=0`、注入台账 DB、600 条写入）后：
`resident_limit=None`、`cleanup_expired()=0`、内存台账 0 条、台账 DB 查询结果空、
`recall_evicted()` 返回 0 条。

**影响**：① 模型侧 `recall_history(query=…)` 的子串模式**按构造恒空**，而工具文档告诉模型
"可召回被驱逐轮次"（`tool_executor.py:3087-3089`）；② `data/context_ledger/<agent>.db`
每 agent 建库并常驻 FTS/WAL，纯负担；③ `context_pool.py:54-68` 的"回收契约"三条出口在生产里
一条都不通，"回收计数"指标恒 0（`get_retention_stats:305` 自报 `max_size_effective=False`，诚实但无补救）。

**另一层**：池本身**没有任何持久化**——`_collector._contexts` 是进程内 list，
宣称的"永久归档"活不过一次重启（`context_pool.py` 无 save/load 路径）[行号]。

**修复方向**：要么把 `resident_limit`/TTL 真正接线（含 GC 调用方）并让 `recall_evicted` 有数据；
要么把台账 DB、`recall_evicted` 子串模式、`get_eviction_stats` 一并退役，只在文档留痕。
"永久归档"若要成立，需要独立的持久层——这是产品决策，不是 bug 修补（见 §10 决策项 D3）。

### P1-4 调取路径每轮对全池逐条语义编码，成本随规模线性且无缓存

`ContextPool.draw:897-913` 每次都取**全部**常驻条目 → 去重 → `SemanticMatchDrawer.draw`；
抽屉对每条算相关性，向量路径每条编码 1～2 次（`semantic_drawer.py:90` 门槛判定 +
`:99`/`:168` 再算一次总分，非 CONVERSATION 条目被评两次），**嵌入结果不缓存**
（`tokens` 在写入时缓存于 `collector.py:26`，`embedding` 无处可存）。
池按契约只增不减 → 这是设计成对价的热路径。

**证据**：[实测 P14] 200 条常驻、`need` 非空时单轮 `draw=752.3ms`（后端 `UnifiedVectorStore`/ONNX
`bge-small-zh-v1.5`）≈ 3.76ms/条。[外推] 10k 条≈37.6s/轮 —— **未在真实规模测量**，只用于说明量级。

**影响**：长生命周期 Agent 的响应延迟被调取路径单调拖垮；`preload_vector_store`（`:71`）无调用方，
首轮还多付一次模型加载。

**修复方向（根因处）**：归档条目写入时落向量（或落 `models/embedding` 的向量表），
调取用一次矩阵-向量积批算（batch encode），并对 `RELEVANCE_FLOOR` 前置廉价词法粗筛；
`_last_view_hashes`/`mark_hashes_seen` 这类 ack 机制可用来限制候选集而非全池扫描。

- **D3 抽屉额度地板** —— 裁决：地板按模型上下文自适应，取向以**提升前缀缓存命中率优先**。

  （`composition.py:243-249` 已在采）；"命中率优先"意味着倾向跨轮**小而稳定**的召回集合，
  与"多召回更懂你"取向相反。**前置依赖 B1**：尺子未修前按窗口百分比划额度会因 20× 低估而算错。
- **D4 检索文本是否收回信封** —— 裁决：**采用甲案**。范围为 pool 分支的**全部瞬态注入**
  （七处 system 注入位，见前置条件 2），不止字面的"记忆/经验/反思/情感"四类。
  两案代价对照保留在 §10.1 作为决策依据。
  **三条不可省略的前置条件，缺一条则甲案退化为"只换位置"**：

  1. **pool 分支必须接入 `compress_envelope`**。当前该函数只有 `injector.py:879` 一处调用，
     即只活在默认不可达的非 pool 路径（P2-7）。不接入的话，四类内容从 system 行搬进末条
     user 消息后**仍然不受任何 token 预算管辖** —— 现状的窗口预算只覆盖对话消息
     （`orchestrator.py:1061-1080` 只扣 system/developer 前缀，`:1162` 只对窗口判据），
     信封与 user 原文两边都不计。甲案最硬的那条理由（预算管辖）完全依赖此步。
  2. **范围必须一次做全，不留半接**。pool 分支现行的 system 注入位共七处
     （`orchestrator.py:634-657` 记忆/经验/结晶、`:656` 待探索问题、`:686-700` 池召回
     `[历史回忆]`/`[记忆]`/`[经验]`/`[反思]`、`:709-729` `[工具记忆]`、`:731-738` `[情感]`、
     `chat_pipeline.py:1537` growth_lesson 直注）。信封块位已有
     `memories/lessons/experience/reflection/emotion/time`（`envelope.py:31`），
     缺 `<history>`（池召回）与 `<tooling>`（工具记忆/待探索问题）两块；
     建议纪律是"瞬态注入一律入信封，唯一例外是固定前缀"。
     新增块还要定淘汰顺位（`envelope.py:36` `_COMPRESS_DROP_ORDER`）——
     建议 `<history>` 紧跟 `emotion` 之后（它是原文，池内无损可再召回，弃了可再生）。
  3. 联动收益：D5"进视图才记账"在甲案下获得客观判据（`parse_envelope` 能判定条目是否真进视图），
     乙案则需另设定义。

- **D5 反思记账语义** —— 裁决：改为"进视图才记账"。
  影响：需要视图覆盖回写点（`orchestrator.py:1320-1333` 的 ack 集是现成雏形），
  并配"多轮未进视图则降档/出池"的兜底，否则低相关教训永不生效且无退出路径。
  与 `project-reflection-feedback-loop-repair` 的链 B 结论相关，改的是记账语义而非门控开关。

### 10.1 D4 两案代价对照（裁决记录：采纳甲案，2026-09-21）

现状：记忆/经验/结晶/待探索问题/情感以 `system` 行注入在对话窗口**之后**
（`orchestrator.py:634-657`），信封只带 `<time>`（`:763-768`）。

| 维度 | 甲案：四类检索文本收回末条 user 信封 | 乙案：保持 system 行注入 |
|---|---|---|
| 预算管辖 | 进入 `compress_envelope` 确定性淘汰序列（`envelope.py:33-36/142-153`），超预算时按 emotion→reflection→experience→lessons→time 整块弃、memories 尾部行弃 | 这四类在 pool 分支**不受任何 token 预算管辖**：只受条数约束（记忆 limit=10、问题 limit=2），且 P3 后正文不截断 → 唯一无上限注入面 |
| 注入防御 | 落在免疫句覆盖范围内（`envelope.py:23-28`）——外部文档/记忆文本里的指令式内容受语义隔离 | 以 `system` 角色直发，模型权重最高且无免疫覆盖；知识底座已接入外部来源（见知识库事实底座审计），暴露面真实存在 |
| 前缀缓存 | **与乙案等价**：两案动态内容都在窗口之后，击穿面同样只在尾部；前提是不把动态内容前移 | 同左。全仓无显式 `cache_control` 断点，依赖供应商隐式前缀缓存，命中率已在采（`usage_accounting.py:73`、`multi_model_client.py:481`）→ 可实测判定，不必靠论证 |
| token 成本 | 每轮多付免疫句+标签约 20-30 token（B1 修完尺子后重核） | 基线 |
| 可观测/测试 | `test_envelope` 的"两轮 system 字节相等"硬判据在 pool 分支也成立；D5 的"进视图"可用 `parse_envelope` 客观判定 | 该判据只在非 pool 路径成立；"进视图"需另设定义 |
| 改动面 | `orchestrator.py:624-700` 一段装配 + 断言 `[记忆]` system 行的现存用例；对兼容端点而言 system 并入 user 反而降低协议差异风险 | 零改动 |

**裁决：采纳甲案（2026-09-21）。** 决定性理由是"预算管辖"与"注入防御"两条，缓存收益不作为理由（两案等价）。
**代价与红线**：甲案与 B2/B3 触碰 `orchestrator.py:624-700` 同一段，必须同批做；
且落地须满足 §10 D4 条目的前置条件（pool 分支接 `compress_envelope`、七处 system 注入位一次做全、
新增 `<history>`/`<tooling>` 块与淘汰顺位）——否则只是把无预算约束的内容换个位置，
那种半接状态比不改更糟（预算账目更难追）。
