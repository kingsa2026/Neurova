> 承接单：Issue #272（用户诉求：NPC 自动续跑下一轮「无果」）
> 性质：NPC 配置口径修复 + 判据新增（仓内产品代码未改一行）
> 常驻判据：`tests/unit/ci/test_npc_handoff_role_continuity.py`

## 1. 用户看到的现象与真实死因（两条，分开说）

用户先后提了两件事，**它们不是同一条链**：

1. 「子流水线 + 防溢出无果」——上一轮 PR #273 建了四个最高档角色与接力链，
   但自动续跑看起来没有生效。
2. 「根据官方文档再看看怎么实现 NPC 自动续跑下一轮」——想知道平台侧到底怎么开。

真死因有两条，一条是**配置缺陷**（可修），一条是**用错入口**（需换用法）。

### 1.1 配置缺陷：接力落点硬编码了一个**不在册**的角色名

`.cnb.yml` 的接力落点 `api_trigger_npc_handoff` 里，`npc:go.options.role`
此前写死为 `DSCoder`。而 PR #273 把角色改名为
`DSCoder-Red` / `DSCoder-Green` / `DSCoder-Yello` / `DSCoder-Blue` ——
那一批里 `.cnb/settings.yml` 的 `npc.roles` **不再包含** `DSCoder`，
角色名与名单因此成为两份口径（改名漏改不会有任何红，教义第 6 条）。

> 后记（本批）：用户口径已明确「保留 `DSCoder`，共五个在册角色」，
> 故 `DSCoder` 已恢复在册（与四个后缀角色并存）。
> 这**不改变**根修方向 —— 硬编码一个当前在册的名字仍会在下次改名时再断，
> 身份随轮传递（§3.1）才是根修。

平台对 `role` 的解析规则（官方 npc:go 篇）：`role` 需在 `npc.roles` 中定义，
**名字未命中时静默回落平台默认 prompt** —— 不报错、不告警。于是一旦进入接力轮：

- Agent 丢掉本仓人设与修复教义（`AGENTS.md` 的 90+ 处编号引用全部失效）；
- 丢掉角色准入 / 运行期预算 / 交接协议的入口约定；
- 而日志里的样子与「角色解析成功」完全一样。

即：**接力链本身可能是活的，但从第二轮起跑的不是本仓的角色。**

### 1.2 用错入口：`@CodeBuddy` 是**系统 NPC**，不读本仓 `.cnb.yml`

官方 npc.md 明说合并来源是 **NPC 所属仓库的 `.cnb.yml`**：

> NPC 事件触发时，系统通过 include 自动合并**系统默认配置**和**NPC 仓库的 `.cnb.yml`**。
> NPC 仓库中已定义的事件覆盖默认，未定义的事件保留默认行为。

`@CodeBuddy` 是平台内置的系统 NPC，其「NPC 所属仓库」是平台的，不是 `kingsa2026/neurova`。
故本仓 `.cnb.yml` 里那套接力链**对 `@CodeBuddy` 完全不生效**。

构建读数印证（`cnb build get-build-status`）：

```
cnb-q0e-1k3f23m8u  （issue.comment@npc / @CodeBuddy）
  stages: Prepare → npc go → BeforeEnd → DebugDetection → End      ← 平台默认配置
  npc: { name: CodeBuddy }

cnb-9ro-1k3f57fif  （pull_request.comment@npc / @kingsa2026/neurova(DSCoder-max)）
  stages: Prepare → 构建环境自证 → DSCoder 执行任务 → … → 轮数触顶接力   ← 本仓配置
  npc: { slug: kingsa2026/neurova, name: DSCoder-max }
```

**结论**：想要自动续跑，必须用本仓自己的角色（`@kingsa2026/neurova(DSCoder-*)`）。
系统 NPC 走平台默认单步 `npc:go`，仓库侧没有任何挂钩点。

## 2. 平台侧「自动续跑下一轮」到底有没有原生能力

**没有。** 全量文档（`/zh/llms-full.txt`）检索 `续跑 / 下一轮 / 自动开启 / 重新触发`
均无 NPC 续跑原语。可用积木只有两块，本仓的接力链正是它们的组合：

| 积木 | 官方出处 | 作用 |
|------|----------|------|
| `endStages` | 语法手册 | 流水线结束前必然执行，且其成败**不影响**流水线状态 |
| `cnb:trigger` | cnb/trigger.md | 适用**所有事件**，可触发 `api_trigger_*` 自定义事件并传 `env` |

判据取平台在收尾时刻注入的事实（`CNB_PIPELINE_STATUS` / `CNB_BUILD_FAILED_MSG`），
故接力只在「被平台中止而没走完」时发生，正常收官不接力（空轮不烧配额）。

## 3. 修法（教义第 1 / 5 / 6 条）

### 3.1 角色身份**随轮传递**，不再硬编码

只把 `role: DSCoder` 改成某个当前在册的名字不够 —— 角色名会再改名，硬编码就会再断一次。
根修形态是让身份随轮传递：

- 三条评论侧事件的收尾接力：`env` 补 `handoffRole: $CNB_NPC_NAME`
  （`CNB_NPC_NAME` 是平台注入的**当前角色名**，官方「NPC 类变量」篇）；
- 接力落点：`npc:go.options.role: $handoffRole`
  （平台「环境变量」篇：内置任务 `options` 支持变量替换）；
- 落点自己的收尾：`handoffRole: $handoffRole` 继续往下传，链条不断。

### 3.2 为什么没有配置内兜底

平台把**无值变量替换为空串**（环境变量篇：「若 `env_name` 无值，则替换为空字符串」），
且**没有** `${VAR:-default}` 语法。故兜底只能落在**供值侧**：
三条评论侧必须把 `$CNB_NPC_NAME` 供上（本判据钉住「根节点存在」）。

### 3.3 判据（可证伪）

`tests/unit/ci/test_npc_handoff_role_continuity.py` 钉三件事：

- **A 字面量角色必须在册 + 载体不得硬编码**：`.cnb.yml` 里每处
  `npc:go.options.role` 的字面量取值都要在 `npc.roles` 里；
  且载体**不得硬编码任何一个在册名字**（改回任一字面量即红的形态判据）。
- **B 身份随轮传递**：接力的 `cnb:trigger.options.env` 必须带 `handoffRole`，
  且它的根取值必须是 `$CNB_NPC_NAME`，落点自己的收尾必须继续传 `$handoffRole`。
- **C 落点读变量**：落点的 `role` 必须是 `$handoffRole` 形态，不得硬编码角色名。

- **D 名单保留无后缀 `DSCoder`**：`DSCoder` 必须在册（五角色口径），
  且准入脚本对它放行。反向可证伪：从名单摘掉 `DSCoder` → 立刻红（实测 2 failed）。

红灯 → 绿灯实测（本机）：

```
新增 D 判据前:  TestRosterKeepsTheBareDSCoderRole 两条均红（2 failed, 6 passed）
新增 DSCoder 角色后: 8 passed
```

反向锁逐条撤一次，判据均翻转（非恒真壳）：删 `handoffRole` → B 红；
把落点 `role` 写回字面量 → A 红；从名单摘掉 `DSCoder` → D 红。

> 与 main 侧守卫的衔接（PR #276 消解冲突）：main 上一批（PR #275）另有一份
> `tests/unit/ci/test_npc_auto_continue_wiring.py`，与本判据在角色/续跑契约上重叠。
> 冲突解消时按「两个口径各有事实源、不互相打架」收敛：它认「载体 role 为
> 字面量或平台变量两种合法形态」（字的量必须等于 `npc.defaultRole`，
> 变量形态的来源链交本判据判），本判据判随轮传递链的完整性（根为
> `$CNB_NPC_NAME`）与「无后缀 `DSCoder` 在册」。两侧判据咬合，改任一侧漏另一侧即红。

## 5. 未闭环（点名，不静默）

1. `npc:go` 只能在平台侧真实触发，仓内无法端到端 live；等价自证是
   「判据逐条咬合 + `.cnb.yml` 经平台 Schema 可解析（`$handoffRole` 属受支持的
   `options` 变量替换）」。
2. `$handoffRole` 在**接力轮**的真实读数尚无（本轮修复后尚无新的接力构建）。
   下一轮真撞到「平台中止」时应回填：落点 `npc` 段里的 `name` 应为被 @ 的原角色名，
   而不再是 `CodeBuddy` 或空。
3. 系统 NPC `@CodeBuddy` 的续跑能力由平台决定，仓库侧无手段 —— 属**能力边界**，
   非本仓缺陷。若平台后续开放挂钩点，应回填本节。
