# B7 Phase 0 基线度量报告（v2 §8.1）

> 度量日期：2026-09-11；脚本：`scripts/bench_b7_event_loop.py`（可复跑）；解释器：系统 python（3.15.0a7）
> 目的：为方案 A（共享循环提交式）vs B（仅重试出循环）提供数据依据——v2 §8.2 决策矩阵

## M1：每 job 事件循环固定开销（n=1000）

| 场景 | legacy per-job loop P50 | shared loop P50 | 差值 |
|---|---|---|---|
| noop 协程 | 0.288 ms | 0.036 ms | **0.252 ms/job（8 倍比值）** |
| sleep 1ms 负载 | 15.537 ms | 15.551 ms | ≈0（Windows 时钟粒度 ~15.6ms 主导，负载吞没开销） |

**P1 判定**：比值 8 倍超过 0.2ms 门槛，但**绝对节省 0.25ms/job 在真实调度频率下可忽略**（即使 100 job/分钟也只占 0.04% CPU）。按 §8.1 门槛细则：P1 降级为"绝对影响可忽略"。

## M2：10 并发重试链（深度 3，退避 1/2/4s）worker 占用回放

| 模式 | 整链墙钟 | worker 占用峰值 | 短任务提交排队 P50 / max |
|---|---|---|---|
| legacy（重试绑 job 循环 + drain 等整链） | 7.03 s | **10/10 全占满** | 0.13 ms / **7007 ms** |
| shared（重试挂常驻循环，job 即返回） | 0.01 s | 0 | 1.47 ms / 10.24 ms |

**P2 判定**：饥饿机制实锤——10 条重试链使 10 线程池**全满 7 秒**，期间任何新 job（含普通短任务）排队最长达整条链时长；`max_instances/coalesce` 无法缓解（排队发生在 executor 层）。这是 misfire 与调度停摆的直接来源，且 max_attempts 封顶只限制单任务次数、不限制并发任务数。

## 决策（§8.2 矩阵打分）

- **P2 强信号成立**（确定性回放 + 后果量级 = 调度域停摆 N 秒），A 与 B 都能消除。
- **P1 弱信号**（绝对量可忽略）→ 不足以支付方案 A 的全量改造风险（新循环生命周期/Windows 句柄/uvicorn 跨界）。
- **P3/P4**（ASGI 整合、跨循环桥接）当前无近期硬需求，A 的独有收益暂不兑现。
- **选定：方案 B——仅重试出循环**（per-job loop 隔离保留，重试任务提交至调度域常驻循环，drain 语义退役至 stop 收口）。工作量约 1 天；方案 A 的基建部分保留在文档中，待 P3/P4 出现硬需求（如任务内需调用主循环资源）时按 §8.3 协议升级。

## 遗留

- M2 的 72h 生产遥测（真实重试频率分布）随 Phase 3 金丝雀一并观察；本报告的确定性回放已证明机制与量级上界。
- Windows 时钟粒度 ~15.6ms 对 1ms 级 sleep 的放大属已知环境事实（见 memory：Windows 时钟粒度坑），与本次选型无关。
