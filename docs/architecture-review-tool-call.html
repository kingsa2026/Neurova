架构债根源:SkillRegistry 存在两个实现(类 A 和类 B),API 完全不兼容。 调用方(orchestrator / tool_router / chat_pipeline)混用两套 API,导致 12 个断点中至少 4 个(V2-1/V2-2/V2-5/V2-7)围绕此根因。

候选 1 · 统一 SkillRegistry 双实现为 Protocol

Strong

涉及文件

  • neurova/skill_system.py(类 A)
  • neurova/skills/registry.py(类 B)
  • neurova/context/orchestrator.py
  • neurova/tool_layers/tool_router.py
  • neurova/agent/chat_pipeline.py

问题

类 A 用 register(skill) + list_skills(),类 B 用 register_skill(manifest, path) + .skills 返回元组。调用方各自猜测 API,三处静默失败(orchestrator / tool_router / chat_pipeline)。

方案:定义 SkillRegistryProtocol(typing.Protocol),显式声明 skills: Dict[str, Skill]、register(skill)、register_skill(manifest, path=None)、list_skills() 四个方法。两个实现都满足 Protocol,调用方依赖 Protocol 而非具体类。

Before(双实现,API 混用)

orchestrator -> 类A.skills  ❌ AttributeError
tool_router  -> 类B.skills    ❌ 元组未解包
chat_pipeline-> 类B.register_skill ❌ AttributeError
          (3 处静默失败)

After(Protocol 统一 seam)

orchestrator -> Protocol.skills  ✅
tool_router  -> Protocol.skills  ✅
chat_pipeline-> Protocol.register_skill ✅
          (Protocol 保证 API 一致)

收益:Leverage↑ 调用方不再猜测 API;Locality↑ 元组解包逻辑收敛到 Protocol 实现内部;Deletion test 通过(删除 Protocol 后 complexity 重新散布到 N 个调用方)。

候选 2 · ToolRouter 提取 _unpack_skill helper

Worth exploring

涉及文件

  • neurova/tool_layers/tool_router.py(_discover_skill_tools, _resolve_skill_tool)

问题

V2-2 和 V2-7 都在 tool_router.py 内重复实现"如果是元组/列表则取 [0]"的解包逻辑,分散在两个方法中。

方案:提取 _unpack_skill(value) -> Skill 私有 helper,两处调用点共用。

Before(逻辑分散)

# _discover_skill_tools (L210)
if isinstance(skill, (tuple, list)):
    skill = skill[0]

# _resolve_skill_tool (L420)
if isinstance(skill, (tuple, list)):
    skill = skill[0]
# 重复逻辑,易漏改

After(逻辑收敛)

def _unpack_skill(self, value):
    if isinstance(value, (tuple, list)):
        return value[0]
    return value

# 两处调用统一为:
skill = self._unpack_skill(skill)
# 单点修改,Locality↑

收益:Locality↑ 元组解包逻辑单点维护;Testability↑ helper 可独立单测;Deletion test 边缘(helper 删除后逻辑散回两处,但 complexity 不消失,因此是 weak pass)。

候选 3 · 静默 except Exception → logger.exception

Worth exploring

涉及文件

  • neurova/context/orchestrator.py:760
  • neurova/agent/loops/base.py:199
  • neurova/agent/chat_pipeline.py:571

问题

三处关键路径用 except Exception: pass 或 except Exception as e: continue 吞掉异常。V2-1 的 AttributeError 就是被 orchestrator.py:760 静默吞掉,导致 Skill 工具永远不进 LLM tools 列表,且日志无任何痕迹。

方案:将 except Exception 替换为 except Exception: logger.exception("..."),保留控制流(不 re-raise),但确保异常进入日志。

Before(静默吞异常)

try:
    tools = self.skill_registry.skills.items()
except Exception:
    pass  # 静默!无日志

After(可观测)

try:
    tools = self.skill_registry.skills.items()
except Exception:
    logger.exception(
        "Skill 工具加载失败"
    )  # 控制流不变,但可观测

收益:Observability↑ 未来类似 V2-1 的静默失败会立即在日志暴露;改动极小(每处 +1 行);Deletion test 通过(删除 logger.exception 后异常重新消失,debug 成本上升)。

推荐优先执行:最小成本(6 行改动),最高收益(避免未来类似 bug 静默失败)。

候选 4 · ChatPipeline 流式/非流式分支统一

Speculative

涉及文件

  • neurova/agent/chat_pipeline.py:890(stream 分支)
  • neurova/agent/loops/openai_loop.py(predict_step)

问题

V2-6 是 latent bug:predict_step 是 async def,流式分支调用时缺 await 返回 coroutine,非流式分支不触发。任何直接调用 agent.chat(stream=True) 的代码都会 TypeError。

方案:将 stream 决策下沉到 predict_step 内部,统一返回 AsyncIterator。ChatPipeline 不再分支,统一 async for event in await self.loop.predict_step(...)。

Before(分支决策在 Pipeline)

if stream:
    gen = await self.loop.predict_step(stream=True)  # V2-6 修复后
else:
    resp = await self.loop.predict_step(stream=False)
    # 处理 resp...
# 两套处理逻辑,latent bug 温床

After(决策下沉到 Loop)

# predict_step 统一返回 AsyncIterator
async for event in await self.loop.predict_step(...):
    handle(event)
# 单套处理逻辑

收益:Leverage↑ ChatPipeline 不再关心 stream 细节;Locality↑ stream 决策集中在 Loop;但 Deletion test 边缘(改动涉及 Loop 接口变更,影响所有调用方)。

Speculative 警告:改动面较大(~30 行),涉及 Loop 接口变更,可能引发回归。建议在候选 3 之后、有完整流式测试覆盖时再执行。

Top 推荐

优先执行候选 3(静默 except → logger.exception)。理由:

  1. 改动最小(6 行),零回归风险
  2. 直接解决 V2-1 类静默失败的可观测性问题
  3. 无需重构接口,不动现有调用方
  4. 立即提升未来类似 bug 的发现速度

其次执行候选 2(_unpack_skill helper),收敛 V2-2 和 V2-7 的重复逻辑。 候选 1(Protocol)是长期目标但改动较大,建议在候选 3+2 稳定后规划。 候选 4 暂缓,需先补齐流式测试覆盖。
