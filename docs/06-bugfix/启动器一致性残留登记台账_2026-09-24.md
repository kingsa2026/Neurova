## 二、同根因的另一形态：EQP 探针库清单（登记待排期）

`resolve_probe_paths()` 只收**固定路径**下的两个库（数据根默认库、`~/.neurova/audit.db`、
`NEUROVA_DB_PATH`），而真实记忆写在 `agent_workspaces/<agent>/memory/neurova_memories_persist.db`
与 `memory/memory.db`。于是"索引命中基线"覆盖的主要是空库/非记忆库，记忆库那几条
热点查询（`memories_by_agent_desc` 等）在生产形状下常年落在 `not_applicable`。

不在本单扩范围的原因：动态路径收进探针会让探针数量随用户数无界增长，需要先定
"每 agent 还是抽样"的口径——那是独立设计决策，不是修 bug。

实测读数（2026-09-24，接力轮复核，作为后续排期的基线）：

```
resolve_probe_paths() ⇒ ['<数据根>/data/neurova_memory.db', '~/.neurova/audit.db']
其中 neurova_memory.db 五条热点查询**全部** not_applicable（该库连 memories 表都没有），
audit.db 只有 audit_logs 两系可用。仓内 agent_workspaces/ 下没有任何 .db
⇒ 真实记忆写在 agent_workspaces/<agent>/memory/neurova_memories_persist.db，
  探针清单一条都覆盖不到，"记忆库索引命中"这一读数在生产形状下恒为空集。
```

即：该缺失不是"覆盖不全"，而是**覆盖面为 0**——探针看的两个库里没有一个是记忆库。
排期时先定口径，再决定是收 per-agent 还是抽样，不要顺手加 glob（会无界）。
