## 二、同根因的另一形态：EQP 探针库清单（登记待排期）

`resolve_probe_paths()` 只收**固定路径**下的两个库（数据根默认库、`~/.neurova/audit.db`、
`NEUROVA_DB_PATH`），而真实记忆写在 `agent_workspaces/<agent>/memory/neurova_memories_persist.db`
与 `memory/memory.db`。于是"索引命中基线"覆盖的主要是空库/非记忆库，记忆库那几条
热点查询（`memories_by_agent_desc` 等）在生产形状下常年落在 `not_applicable`。

不在本单扩范围的原因：动态路径收进探针会让探针数量随用户数无界增长，需要先定
"每 agent 还是抽样"的口径——那是独立设计决策，不是修 bug。

实测读数（2026-09-24，接力轮复核，作为后续排期的基线）：

```
resolve_probe_paths() ⇒ ['<数据根>/data/neurova_memory.db', '~/.neurova/audit.db']
其中 neurova_memory.db 五条热点查询**全部** not_applicable（该库连 memories 表都没有），
audit.db 只有 audit_logs 两系可用。仓内 agent_workspaces/ 下没有任何 .db
⇒ 真实记忆写在 agent_workspaces/<agent>/memory/neurova_memories_persist.db，
  探针清单一条都覆盖不到，"记忆库索引命中"这一读数在生产形状下恒为空集。
```

即：该缺失不是"覆盖不全"，而是**覆盖面为 0**——探针看的两个库里没有一个是记忆库。
排期时先定口径，再决定是收 per-agent 还是抽样，不要顺手加 glob（会无界）。

## 三、同根因的另一形态：文档里的「仓库条目数」手抄（本单已修两处，余下登记）

与 `.cnb.yml` 头部手抄流水线条数（Issue #231）同一形态：**同一事实的第二份手抄定义**。
导航/纪律事实源在正文里逐字写下全仓内容的条数，而数字与目录实况之间**没有任何机器
判据**，于是各自漂移、且同一时刻互相矛盾。实测（2026-09-25，`main`）：

```
docs/0-index/README.md
  「21 个架构决策记录」   实际 21    一致
  「47 个修复记录」       实际 37    漂移 10
  「模块设计（19 篇）」    实际 21    漂移 2
  「代码评审（3 篇）」     实际 4     漂移 1
  「历史/过时文档 30 篇」  实际 30    一致
  「全仓 97 处引用」   ┐
AGENTS.md             ├ 同一事实的两份手抄，同一时刻两个数
  「被 90+ 处编号引用」 ┘  实际 60 处
```

**已修**（改为不写数字、只描述结构与口径，判据是「不手抄」+「条目仍在」+反向锁）：

- 落点：`docs/0-index/README.md`、`AGENTS.md`；
- 守卫：`tests/unit/test_docs_index_hand_copied_counts.py`（已登记 `scripts/ci/protected_tests.txt`）。

**登记待排期**（同一根因的其余命中点，本单不扩范围）：

- 根 `README.md`：`846 个测试文件（unit 703 / integration 54）`、`42 个 Vitest 测试文件，
  614 条用例`、`neurova/ 约 700 个文件`、`API 接口模块 58 个`。实测同一时刻读数为
  `tests/**/test_*.py` **1792**、`tests/unit` **1637**、`tests/integration` **57**、
  前端 `*.test.ts` **227**。差距很大，说明这些数字自写下起就无人复核。
- `docs/INDEX.md`：`文档总数：约 296 篇`、`真实项目 markdown 约 377 篇` 一类历史盘点。
- `README.md` 的 `846 个测试文件` 同时在两处（统计表 + 目录结构注释），
  与 `.cnb.yml` 头部的两处相反口径是同一种「同文件内互相矛盾」。

排期口径：先定「哪些数字值得留」（能被读者当场复算的才留，否则删），
再决定是删数字还是接一条生成侧；不要顺手把数字改对——改对了下次增删文档仍会漂移。

## 四、存量库的同名覆盖迁移（已闭环 2026-09-25 · ADR 0021）

本单只修了**产生侧**（名字不再撞）；已落盘的存量 manifest 里 `ai_tool` / `general_tool`
这类同名条目仍在，`SkillRegistry` 按 `skill.name` 建键的历史行为未变——这一条已由
**ADR 0021** 承接（名字域 = 身份的函数），三处消费同一份判据
（`neurova/skills/skill_name_domain.py`）：

- 存量库迁移：`SkillService` 打开库时就地收敛并落盘（幂等，落盘失败出声回读）；
- 新写入取名：`_register_metadata` / `install_skill` 新增分支按同一判据取名；
- 运维复算/迁移：`python scripts/diagnostics/skill_name_collisions.py [--apply]`。

**不硬拒**这条纪律照旧（ADR 0019）：迁移改的是名字取值，不改主键、不动血缘，
存量装配不会炸。实测（真库文件 + 真装配链路）：10 条存量条目，迁移前同名覆盖 8 次、
工具面只剩 2 条；迁移后覆盖 0 次、工具面 10 条、身份域全部可取。
