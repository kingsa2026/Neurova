候选 #1：删除 _CHAT_SESSIONS，统一到 SessionManager

Worth exploring

Files

neurova/api/endpoints/console.py:72-94, 144-270
data/console_sessions.json

Problem

Console API 用模块级 Dict + JSON 文件做会话存储，与 Agent 内部用的 SessionManager 完全独立。两份数据不同步，console 历史与 agent 持久化的历史是两套。这是上轮 H-1/H-2 bug 的根因。

Solution

删除 _CHAT_SESSIONS + _SESSIONS_FILE，console 端点改为调用 SessionManager。会话列表用 get_sessions_by_agent(agent_id)，历史用 get_recent_context，发消息由 agent.chat 自动落盘。

Benefits

  • Locality：会话存储集中到一处
  • Leverage：console 与 agent 共享同一历史源
  • 消除 console_sessions.json 与 sessions/ 文件不一致

Before / After

BEFORE（2 套并行存储）
console._CHAT_SESSIONS（内存+JSON）
SessionManager（文件）
→ 数据不同步，H-1/H-2 bug 根因
↓
AFTER（单一存储）
SessionManager（文件）
console API 直接调用
依赖：此候选依赖候选 #3（SessionRepository 接口）先落地，否则 console 端点会直接耦合 SessionManager 具体类。

候选 #2：抽 Pinia store + useChat composable

Worth exploring

Files

NeurUI/src/pages/ChatPage.vue:478-514（14 个 ref/reactive）
NeurUI/src/stores/（无 chat store）
NeurUI/src/composables/（无 useChat）

Problem

ChatPage.vue 把 messages / sessions / currentSessionId / isStreaming 等 14 个状态全放在局部 ref。违反用户规则"建立统一的状态管理库"。无法跨组件共享聊天状态（如顶栏未读数、侧栏会话切换）。

Solution

抽 stores/chat.ts（Pinia store：sessions/currentSessionId/messages）+ composables/useChat.ts（封装 SSE 流式调用、错误处理、UI 提示）。ChatPage.vue 只负责模板渲染。

Benefits

  • Leverage：任意组件读聊天状态
  • Locality：状态变更集中
  • 符合用户规则"统一状态管理库"
  • ChatPage.vue 从 700+ 行瘦身

Before / After

BEFORE（状态散落）
ChatPage.vue × 14 ref
→ 其他组件无法访问
↓
AFTER（store + composable）
useChatStore（Pinia）
useChat（composable）
ChatPage.vue 仅渲染

候选 #3：定义 SessionRepository 接口（统一 seam）

Strong

Files

neurova/session_manager.py:63（SessionManager）
neurova/api/endpoints/console.py:72（_CHAT_SESSIONS）
neurova/sync/session_sync_manager.py:207（SessionSyncManager）
neurova/memory/scripts/init_db.py:76（SQLite 表）

Problem

5 个 adapter 事实满足同一接口（save/load/list/delete session），但无任何 ABC/Protocol。每个 adapter 自己定义方法名和签名（add_message vs set_messages vs create_session），调用方必须知道具体类。Two adapters = real seam，我们有 5 个。

Solution

定义 SessionRepository ABC：save_message / get_history / list_sessions / create_session / delete_session / rename_session。3 个具体 adapter 实现：FileSessionRepository（SessionManager）/ MemorySessionRepository（SessionSyncManager）/ SqliteSessionRepository（新）。Console API 只依赖 ABC。

Benefits

  • The interface is the test surface：可 mock 测试
  • Locality：存储策略变更集中
  • 候选 #1/#5 的前置条件
  • 消除鸭子类型重复

Before / After

BEFORE（5 个具体类，无共享接口）
SessionManager.add_message(agent_id, session_id, user, assistant, ...)
_CHAT_SESSIONS[sid] = {...}
SessionSyncManager.create_session(...)
SQLite sessions 表（孤儿）
agent.conversation_history = []
→ 调用方必须知道具体类
↓
AFTER（统一 seam）
SessionRepository (ABC)
├─ FileSessionRepository
├─ MemorySessionRepository
└─ SqliteSessionRepository
→ 调用方依赖 ABC，可替换
ADR 建议：此候选影响范围大，建议落地时同步写 ADR-0008「SessionRepository 统一接口」，记录 3 个 adapter 的取舍（文件 vs 内存 vs SQLite）。

候选 #5：SessionSyncManager 接入 SessionRepository

Worth exploring

Files

neurova/sync/session_sync_manager.py:207-239, 612-622
neurova/agent/chat_pipeline.py:268-296（_sync_event 调用方）

Problem

SessionSyncManager 维护第 3 套"会话列表+历史"内存镜像（UnifiedSession.history），面向跨渠道广播。与 _CHAT_SESSIONS 并行存在、语义不同、不互通、不与 SessionManager 同步。进程重启即丢。

Solution

SessionSyncManager 实现为 MemorySessionRepository（候选 #3 的 adapter 之一），只做事件广播 + 内存缓存，持久化委托给 FileSessionRepository。ChatPipeline._sync_event 通过 ABC 接口调用。

Benefits

  • 消除第 3 套存储的独立性
  • 跨渠道广播与持久化解耦
  • 依赖候选 #3

Before / After

BEFORE
SessionSyncManager（纯内存，独立）
→ 进程重启即丢，不与文件同步
↓
AFTER
MemorySessionRepository（缓存+广播）
→ 持久化委托 FileSessionRepository

候选 #6：封装 agent.conversation_history

Strong

Files

neurova/agent_core.py:472, 1364（属性定义+重置）
neurova/agent/chat_pipeline.py:348-359（_restore_session_history）

Problem

conversation_history 是 LLM 推理时真实读的"会话状态"，但只是 Agent 实例的普通 list 属性，无封装、无 invariant。_restore_session_history 只在 len(saved) > len(current) 时才覆盖（chat_pipeline.py:357），存在一致性缝隙。Deletion test：删除后 complexity 重新出现在每个读它的步骤（ChatPipeline/PostChatPipeline/LLMRouter）。

Solution

抽 ConversationContext 深度模块：封装 list + invariant（只增不删、role 交替、token 上限）+ restore_from(repository) 方法。Agent 持有 ConversationContext 而非裸 list。

Benefits

  • Locality：上下文 invariant 集中
  • Leverage：LLM 调用方只读不写
  • 消除 _restore_session_history 一致性缝隙
  • token 截断策略集中（目前散落）

Before / After

BEFORE（裸 list 属性）
agent.conversation_history: list
→ ChatPipeline 直接覆盖，无 invariant
↓
AFTER（深度模块）
ConversationContext
→ restore_from(repo) / append() / truncate()

候选 #7：删除 /v1/chat/sessions 死端点

Speculative

Files

neurova/api/endpoints/chat.py:290-317, 330-400
neurova/api/endpoints/__init__.py:190（路由注册）

Problem

GET /v1/chat/sessions 和 POST /v1/chat/sessions 用 hasattr(agent, "session_manager") and hasattr(session_manager, "list_sessions") 守卫，但 SessionManager 没有 list_sessions 方法，守卫永远 False。端点返回空列表 / 不持久化的临时 dict。

Solution

选项 A：删除端点（路由已挂载但瘫痪）。选项 B：补全 SessionManager.list_sessions + create_session(title, user_id)，让端点工作。选项 C：接入候选 #3 的 SessionRepository。

Benefits

  • 选项 A：减少 API 噪音
  • 选项 B/C：提供第 4 套会话 API（与 console 重复）

证据

hasattr 守卫永远 False
if hasattr(agent, "session_manager") and \
   hasattr(session_manager, "list_sessions"):
    # SessionManager 无 list_sessions 方法
    # → 永远不进入此分支
    sessions = session_manager.list_sessions(...)

🏆 Top Recommendation

先做 候选 #3（SessionRepository 接口），因为：

  1. 它是其他候选的前置条件：#1（删 _CHAT_SESSIONS）、#5（SessionSyncManager 接入）、#6（ConversationContext.restore_from）都依赖统一的 SessionRepository seam
  2. Deletion test 通过：删除 SessionRepository 抽象后，complexity 重新出现在 5 个调用方（console / chat.py / sync / agent / chat_pipeline），证明它在 earning its keep
  3. Two adapters = real seam：我们有 5 个 adapter 事实满足同一接口，是强信号
  4. The interface is the test surface：定义 ABC 后，所有存储层可 mock 测试，消除当前"必须真实文件系统"的测试摩擦
