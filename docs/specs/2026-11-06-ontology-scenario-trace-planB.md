# 场景压力测试：方案推荐与经验复用（Agent × Ontology 精准度实例推演）

> 场景：10月10日文档提到小明为客户甲设计了方案A（数据库体量 200M），后续在 A 基础上设计了方案B（数据库体量 400M），客户甲采用了方案B。小红遇到客户丙（需求 400M），问 Agent"该参考哪个方案？能否列举 A 与 B 的差异？"
>
> 定位：这是一个**端到端压力测试**——涉及数值属性匹配、多跳关系遍历、结构化对比三层能力，恰好覆盖检索精准度方案（`2026-11-06-ontology-retrieval-precision-plan.md`）中的三个断桥。本文逐层推演现有管线的真实行为，标注每层"能做什么/不能做什么"，最后给针对性的改进方案。
>
> **推演口径**：以当前 HEAD 代码为事实源（B8–B14 已落格），不假设任何未实现的改进。

---

## §1 数据入库推演（写入面）

### §1.1 文档摄取后什么会变成事实？

10月10日的文档经 `graph_bridge.extract_knowledge_to_graph` 走 LLM 抽取，产出形状取决于抽取 prompt 能引导 LLM 识别出什么：

| 抽取产物 | 形状 | 能否入库 | 备注 |
|---|---|---|---|
| 实体：小明 | `(小明, is_a, person)` | ✅ | person 在 legacyGraphTerms 收编值中 |
| 实体：方案A | `(方案A, is_a, document)` 或 `(方案A, is_a, product)` | ✅ | 取决于 LLM 判断方案是文档还是产品 |
| 实体：方案B | 同上 | ✅ | |
| 实体：客户甲 | `(客户甲, is_a, person)` 或 `(客户甲, is_a, organization)` | ✅ | |
| 关系：小明 designed 方案A | `(小明, designed, 方案A)` | ⚠️ 条件命中 | `designed` 不在 RelationType 枚举中——**除非 LLM 抽取时映射到已有关系或走了 custom 落候选**；B8 候选面已落，未登记关系落候选等审批 |
| 关系：方案B derived_from 方案A | `(方案B, derived_from, 方案A)` | ⚠️ 同上 | `derived_from` 也不在枚举中 |
| 关系：客户甲 adopted 方案B | `(客户甲, adopted, 方案B)` | ⚠️ 同上 | |
| 属性：方案A 体量 200M | `(方案A, has_database_size, "200M")` | ❌ **大概率丢失** | LLM 抽取 prompt 聚焦实体和关系，**数值属性通常留在正文而非结构化为三元组**；即使 LLM 抽出来了，`has_database_size` 未登记 → 落候选 → 审批后才入库 |

### §1.2 关键断点（写入面）

| # | 断点 | 影响 |
|---|---|---|
| W-① | **数值属性没有结构化为 qualifier 事实**——"200M"/"400M"留在文档正文里，抽取 prompt 不引导 LLM 把属性值提取为独立三元组 | 后续检索只能靠文本匹配"400M"字面量，不能按属性结构化过滤 |
| W-② | **关系词（designed/derived_from/adopted）未登记**——B8 候选面会接住它们落候选，但需要管理员审批后才能成为正式关系 | 首次摄取时这些关系全部丢失（落候选不落事实） |
| W-③ | **方案A→方案B 的继承关系无本体表达**——`derived_from`/`extends`/`supersedes` 不是注册表里的关系，即使事实落了库，也没有关系特征（如 transitive）可用 | 无法沿继承链自动遍历 |

## §2 检索推演（读取面）

### §2.1 小红发问后检索管线逐步走

小红输入："客户丙需要 400M 数据库体量，有什么参考方案？"

**Step 1：查询进入 hybrid_search_knowledge（四路 RRF）**

| 路 | 匹配行为 | 方案A 命中？ | 方案B 命中？ |
|---|---|---|---|
| BM25 | 分词后"400M"/"数据库"/"体量"/"参考方案"——"400M" 只在含方案B的文本块中出现；"数据库"/"方案" 在 A 和 B 的文本块都出现 | ⚠️ 部分（"数据库""方案"命中） | ✅ 较强（"400M" 精确命中） |
| FTS5 | 同 BM25 词面 | ⚠️ | ✅ |
| 向量（bge-small-zh） | "400M 数据库体量" 语义上与"数据库体量400M"相近，与"数据库体量200M"也算相近 | ⚠️ 语义相近 | ✅ 更近（"400M"重叠） |
| tfidf 分片 | 词频匹配 | ⚠️ | ✅ |
| 图谱路（weight 0.10） | `graph_walk.walkFromQuery("400M 数据库体量…")` — 锚点靠文本匹配，"400M"不是 subject_key → 可能零锚点或弱锚点 | ❌ 或弱 | ❌ 或弱 |

**RRF 融合后**：方案B 的条目排名大概率高于方案A（因为"400M"字面匹配是强信号）——**但这靠的是 BM25 词面碰撞，不是语义推理**。

**Step 2：排序与过滤**

- 采纳先验：如果之前有人对方案B的内容给过好评 → B 再升
- 推导事实过滤（D-06）：条件类推导事实被过滤（默认关）——本场景不涉及条件类，不受影响
- FactSurface：默认 off → 事实（三元组）不作为检索条目出去——**方案A/B 的结构化属性事实不进 chat 检索**

**Step 3：LLM 收到什么？**

LLM 收到的是**扁平文本块列表**——每个块是文档的一段切片，可能长这样：

```
[chunk 1] "…小明设计了方案A，谈下了客户甲的业务…数据库体量为200M…"
[chunk 2] "…在A方案的基础上设计了方案B…用户数据库的体量为400M…用户最终采用了方案B…"
```

LLM 需要自己从这两段非结构化文本中推断：
- B 的体量（400M）与客户丙的需求匹配
- A 的体量（200M）不匹配
- B 是在 A 基础上设计的（继承关系）
- 差异 = 400M - 200M = 200M（如果 LLM 能做数值减法）

### §2.2 关键断点（读取面）

| # | 断点 | 对本场景的影响 |
|---|---|---|
| R-① | **无数值范围匹配**——"400M"在 BM25 里是词面碰撞不是数值比较；检索系统不知道"400M ≥ 400M"但"200M < 400M" | 方案A 和方案B 都可能命中（都含"方案""数据库"token），排序差异纯靠"400M"是否出现在同 chunk |
| R-② | **无多跳遍历**——从方案B 出发沿 `derived_from` 走到方案A，补齐 A 的属性进上下文 | LLM 只看到检索命中的 chunk，如果 A 的 chunk 和 B 的 chunk 被切到不同位置，**对比信息不全** |
| R-③ | **无结构化属性对比**——LLM 收到的是文本段落，不是 `{方案: A, 体量: 200M}` vs `{方案: B, 体量: 400M}` 的结构化视图 | LLM 需要从非结构化文本中自行提取数值并对比——**出错率高且不可控** |
| R-④ | **推导/观察态不可见**——即使事实在库，LLM 不知道哪些是原始记录哪些是推导的 | 无法在回答中说"根据历史记录，方案B的体量是400M"vs"这是推导出来的" |

## §3 回答质量评估

### §3.1 当前管线会怎么回答？

| 问题维度 | 预期表现 | 置信度 |
|---|---|---|
| **推荐 A 还是 B？** | **大概率推 B**——因为"400M"字面匹配让 B 的 chunk 排名靠前，LLM 从上下文推断 B 更匹配 | ⭐⭐⭐☆☆ 约 70–80%（靠 LLM 推理弥补，非本体保证） |
| **能列举 A/B 差异吗？** | **大概率不完整或出错**——LLM 只拿到文本碎片，需要自行提取两个方案的属性值并做对比；如果 A 和 B 的信息被切到不同 chunk（chunk_size 限制），**对比信息不全** | ⭐☆☆☆☆ 约 30–40% |
| **能说清 B 是在 A 基础上设计的吗？** | **取决于 derived_from 关系是否被抽取并审批**——如果落在候选且未审批，这条关系不在库里，LLM 只能从文本碎片猜 | ⭐⭐☆☆☆ |
| **能说"客户甲最终采用了方案B"吗？** | 同上——adopted 关系是否在库决定了这条信息是否可结构化引用 | ⭐⭐☆☆☆ |

### §3.2 理想回答 vs 现实回答

**理想回答**（本体语义栈全链通后）：

> 根据知识库，方案B最匹配客户丙的需求（数据库体量 400M）。
>
> **推荐方案B**，依据：
> - 方案B 的数据库体量为 **400M**，与客户丙需求精确匹配
> - 方案B 是在方案A 基础上设计的升级版本（derived_from 关系）
> - 客户甲最终采用了方案B（历史采纳记录）
>
> **方案A 与方案B 的差异**：
> | 维度 | 方案A | 方案B |
> |---|---|---|
> | 数据库体量 | 200M | 400M |
> | 状态 | 前置版本（已被 B 取代） | 客户甲采用的最终版本 |
>
> 方案A 的参考价值：作为方案B 的基础版本，如果客户丙后续需求收缩到 200M 以内，可回退参考方案A。

**现实回答**（当前管线）：

> 根据知识库中的信息，方案B 使用了 400M 的数据库体量，与客户丙的需求匹配。方案A 使用了 200M 的数据库体量。
>
> （可能缺失：继承关系、客户采纳记录、结构化对比表格——取决于 LLM 能否从碎片文本中拼凑出这些信息）

## §4 针对性改进方案

### 改进 ①：属性结构化抽取（写入面，解决 W-①）

**问题**：抽取 prompt 不引导 LLM 把数值属性提取为独立三元组——"200M"/"400M"留在正文里。

**方案**：
1. `graph_bridge.extractionPrompt()` 增加**属性抽取指令**：
   - "识别实体/方案的**数值属性和枚举属性**（如体量、金额、等级、状态），每个属性输出一条 `{source: 实体, type: 属性名, target: 属性值}` 的关系"
   - 示例："方案A 数据库体量 200M" → `{source: 方案A, type: has_database_size, target: "200M"}`
2. `has_database_size` 等属性名走 B8 候选面：首次落候选 → 管理员批准 → 成为正式关系术语
3. 批准后的事实带 **qualifier_schema**（v32）：`{"required": [], "allowed": {"unit": "string"}}`——qualifier 里存单位

**落点**：`graph_bridge.py` extractionPrompt + 候选面已有

**效果**：写入后 `(方案A, has_database_size, "200M")` 和 `(方案B, has_database_size, "400M")` 成为结构化事实——检索时可按谓词过滤。

### 改进 ②：qualifier 数值比较（读取面，解决 R-①）

**问题**：检索系统没有数值比较能力——无法做"体量 >= 400M"过滤。

**方案**（两阶段）：
1. **后过滤**（改动最小）：`hybrid_search_knowledge` 返回结果后，如果命中事实带 qualifier 且查询含数值条件，对 qualifier 值做数值比较过滤。需要在查询面暴露 `filter_qualifier` 参数。
2. **条件类数值扩展**（更优雅）：B1 条件类目前只支持字符串 hasValue——增加数值比较原子：`{atom: has_database_size, subject: X, objectConst: "400M", op: ">="}`。这样 `LargeScalePlan = Plan ∩ has_database_size >= 400M` 可以成为条件类，推导自动归入。

**落点**：`rule_engine.py`（扩展限制原子）＋`hybrid.py`（后过滤）或 `rule_engine.py`（条件类数值扩展）。

**效果**：`LargeScalePlan` 条件类下的推导事实恰好是"体量 ≥ 400M"的方案——查询直接命中，不需要 LLM 自己做数值推理。

### 改进 ③：多跳遍历（读取面，解决 R-②）

**问题**：方案B → derived_from → 方案A 这条路径走不通——检索是一跳的。

**方案**：
- 检索命中的种子实体（方案B）→ 沿 `derived_from` 关系走一跳到方案A → A 的属性事实也进结果
- `graph_walk.walkFromQuery` 骨架已有，改为"从检索命中的实体出发"而非"从查询词文本匹配出发"
- 走出的每条补充事实带 `hop_path: [{predicate: "derived_from", direction: "backward"}]`

**落点**：`graph_bridge.py` 或 `graph_walk.py`；knowledge_retriever_adapter 的 `_enrich` 之后插入。

**效果**：方案A 和方案B 的所有结构化属性事实**同时出现在 LLM 上下文中**——LLM 可以直接对比。

### 改进 ④：结构化对比注入（LLM 侧，解决 R-③）

**问题**：LLM 收到扁平文本块，需要自行提取和对比属性。

**方案**：
1. 新模块 `ontology_context_builder.py`：检索结果 → 按本体类型分组 → 结构化注入
2. 对本场景：检索命中包含 `has_database_size` 谓词的事实 → 按主体分组 → 注入为：

```
## 方案属性对比
| 属性 | 方案A | 方案B |
|---|---|---|
| 数据库体量 | 200M | 400M |
| 客户 | 客户甲 | 客户甲（采用） |

## 关系
方案B --derived_from--> 方案A

## 推导标注
（无推导事实）
```

3. LLM 收到这个结构化视图后，**直接输出对比表格**——不需要自行从文本碎片中提取。

**落点**：`neurova/context/ontology_context_builder.py`（新模块）；`chat_pipeline.py` 在 Step2 检索后调用。

### 改进 ⑤：案例推理（case-based reasoning，长期）

**问题**：小红的需求（400M）与客户甲的需求（400M）是**同一参数的相似取值**——系统应自动识别"这是一个相似案例"。

**方案**：
1. 客户丙的需求"400M 数据库体量"作为一条**查询意图**（query intent）——不只是文本匹配，是结构化的属性查询 `{attribute: has_database_size, value: 400M, operator: ">="}`
2. 在 facts 层按 qualifier 数值范围搜索匹配的历史案例
3. 命中的案例（方案B + 客户甲）作为**推荐经验**注入

这个能力超出当前 B 批范围，属于案例推理（CBR）模式——但上面的改进 ①②③④ 落地后，数据层已经为此准备好了结构化事实。

## §7 与检索精准度方案（2026-11-06）的关系

本场景是检索精准度方案三个断桥的具体实例：

| 断桥 | 本场景体现 |
|---|---|
| ① 用户语言→本体术语 | "400M 数据库体量"应映射为 `has_database_size` 谓词的结构化查询——改进 ① 解决 |
| ② 本体语义→检索策略 | "找出匹配 400M 的方案"应触发条件类/数值过滤——改进 ② 解决 |
| ③ 检索结果→LLM 结构化上下文 | 方案A/B 的属性对比应结构化注入——改进 ④ 解决 |

多跳遍历（改进 ③）是检索精准度方案策略 C 的具体实例。
