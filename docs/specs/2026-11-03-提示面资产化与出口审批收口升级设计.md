## 2. 批次设计

### 批 A · 提示面资产化守卫（纯测试，生产 LOC 0）

**目标**：把"提示面"当成受管资产——整面有预算棘轮、段标题单源全量钉住、提示文提及的工具名必须真实存在。措辞漂移从 review 问题变成红灯。

**A1 整面预算棘轮**：新守卫 `tests/unit/context/test_promptSurfaceBudgetRatchet.py`，模仿 `tests/unit/agent/test_agentCoreSizeRatchet.py` 的形态（基线 JSON＋history 单调不升＋waiver 留痕＋goal 不得高于实测）。要点：

- **动态段必须用固定假源注入**（工作区文档、技能目录、工具清单随仓内容漂）——否则基线随仓库内容涨落，棘轮失真。这是本格成败点：收集器走两条装配路径（`build_context` 与 `build_system_prompt`），把工作区/技能/工具注册表替换为 fixture。
- 指标按段 owner 分列：恒定四段（现 1439 字符，`rules_sections.py:27-103`）、soul/personality、宪法、技能目录、工具清单、时间、工作区；另设整面总预算一个数。
- 新增工具/技能属正当增长：走 waiver 留痕并要求同步清理等量旧文案（净预算不升），机制沿用 size-ratchet 的 `METHOD_COUNT_WAIVERS` 形态。
- 与运行时硬顶的边界：`NEUROVA_TOOL_PROMPT_BUDGET_CHARS=18000` 等是"超限降级"的运行时防线，棘轮是更紧的"只降不升"基线，两者不互替，不重复定义同一判据。

> **实施偏差（2026-11-03，台账 §6-480）**：动态段不做假源注入、整段不入棘轮——工作区/技能目录内容属部署数据（随部署涨落），入棘轮会让基线随部署内容失真；其膨胀由运行时硬顶（`budget_report.SEGMENT_CAPS`）＋目录头尾单源守卫兜住。棘轮指标收敛为仓内自有文案面：恒定四段＋工具清单＋总额。

**A2 段单源扩展＋提及咬合**：扩展现守卫 `test_promptContractSingleSource.py`——①"标题字面量只许一处"从 `BEHAVIOR_RULES_HEADER` 扩到 `rules_sections.py` 全部段标题（现四段）；②提示文恒定段中出现的工具名 token 必须在 `builtin_tools.get_registered_tool_names()`（`neurova/builtin_tools.py:1354`）内，防幽灵路由句。

**与 `test_tool_descriptions.py` 的边界**：该文件管工具描述质量（≤600 字符、路由目标真实、中文三件套），本批管整面预算与段单源；实施时若发现判据重叠，收口进一处不并存（教义第 6 条）。

**红灯判据**：A1 先把基线写成低于实测值证明红；再临时注入超长段证明棘轮咬合。A2 测试内临时注入幽灵工具名/重复段标题证明红。**验收**：全绿并纳入受保护子集分片。

### 批 B · 审批等待收口（重量批，已裁 T2/T3）

**教义第 7 条判定**：链 A（工作流 `exec_approval`）与链 B（治理 ASK）承担同一功能"审批等待"，必须先比后合。对比结论：链 B 的持久化、重启复活、带外重放、跨线程唤醒完整；链 A 独有的是渠道关键词回复体验与四级定向（`builtin.py:2147-2183`）。**合并方向（已裁 T3 真合并）**：ApprovalManager 成为未决/裁决唯一事实源，链 A 只留渠道关键词回复前端；登记/持久化/复活全部下沉，链 B 裁决回调作为唯一回传通道。

分格（B1 可先行，B2/B3 依赖 B1；B3 真合并拆子格逐格红绿）：

- **B1 结构级一次一问＋线程不泄漏**：`_PENDING_APPROVALS` 增加"同一 chat 会话至多一个未决"的结构约束（已裁 T2：串行排队——第二单在前一单终结后自动继续，节点不产生业务失败；队列状态与超时归属随格设计）；等待改造去掉 `run_in_executor` 卡线程（改 asyncio 原生等待或可中断短轮询），`CancelledError` 必须清理 handler 与登记（现 `:2384` `except Exception` 漏接，executor 线程最长泄漏 3600s）。
- **B2 等待语义三件套**：①审批通知未成功投递（`attention_budget.deliver` 返回 held/失败，`builtin.py:2248-2260`）不启动计时或延后计时——"未送达不计时"；②超时返回保持诚实形态（`status=timeout` 已是）；③引擎读面修正：`execution_engine.py:801,807` 现把 pending/timeout 一律当 success，需按内层 status 显式呈现（该格先现查影响面）。
- **B3 持久化与复活（真合并主体，按"存储下沉→回传接通→退役清理"拆子格）**：链 A 未决登记/裁决回传下沉 ApprovalManager（唯一事实源，SQLite 形态复用或并入其表），重启复活＋渠道 handler 重注册＋带外重放路径接通（对照链 B `governance.py:285-298` 的 hasApprovalWaiter→带外重放）。

> **实施偏差（2026-11-03，台账 §6-486）**：工作流实例是进程内状态，重启后 PENDING 行**不假复活**——由 ApprovalManager 的 TTL 惰性到期诚实闭单；登记落库的价值是治理面可见与带外裁决，不是假装工作流还活着。"handler 重注册"随工作流实例同生共死，无独立复活面。

**红灯判据**：B1 同会话第二单未决不再并行等待（修前并行等到超时）；取消等待后线程数不回落修前必红。B2 通知 held 时短 timeout 测试修前走满全程、修后不计时。B3 未决落库→重启→复活→渠道关键词回复能命中，修前蒸发。**live-verify**：真 9527 后端＋真工作流执行单走一遍审批往返。

### 批 C · 出口禁拆与系统文案预算（已裁 T1：仅系统生成文案）

**设计**：`message_chunker.py` 加**拆分策略登记表**——消息类别 → 允许拆分与否。类别初分：agent 正文（允许拆，现状可靠性优先正确）、审批通知（**禁拆**：结构化信息拆散丢上下文）、系统兜底错误文案（**禁拆**）、管理员手动发送（允许拆）。禁拆类超长时**诚实截断**：显式"已截断"标记＋全文落台账/日志，不静默丢字符。配套 C2：系统生成文案（审批通知、兜底文案）的字符预算具名常量，发送层断言，超限走截断＋点名；agent 正文不设词数预算（已裁 T1）。

**红灯判据**：禁拆类超长消息发送后渠道只收到一条（修前收到多条）；截断件带显式标记且台账可查全文。**影响面**：`message_chunker.py`、`manager.py:340-346` 分片决策点、`builtin.py:2238-2242` 审批通知发送侧。

### 批 D · 入站队列不可用的方向修正（已裁 T4：有界直发＋旁路台账）

**设计**：`manager.py:501-502` 的 fail-open 直发改为**有界直发**——强制走同一 `dispatch` 路径（与队列路径完全同一套 handler 链，消灭行为分叉）＋强制落"旁路"台账行＋计数告警并接进面板待办读数。裁定理由（留案）：入站拒绝意味着用户消息无声丢失，比"旁路但可观测"更伤；旁路计数成为常驻读数后，队列可用性本身有了事实判据。旁路计数与批 H2 判定台账、批 F 出口台账同属"出入口可观测单源"族，实施时收口不重复建表。队列去重键（平台消息 id）**不动**——已核实是正确形态。

**红灯判据**：模拟队列不可用→旁路直发必落台账行且计数可见（修前静默）。

### 批 F · 出口失败片归宿（D-8 修正版）

**设计**：`send_message` 的失败片（`manager.py:352-360`）从"只告警"改为显式归宿——落渠道出口台账（与 `channel_router.py:312` 的 `chat_error` 记账同族单源，收口进同一处不造第二份），失败形态点名失败片序号、渠道、原因；同片**重试一次**（有限、具名常量）。**不做**幂等标记——已核实无自动重投路径，幂等标记没有受益场景（教义第 2 条：不为不存在的问题加码）。`outbox_handler` 的"零生产接线"是独立断点，登记台账另议，不混入本批。

**红灯判据**：模拟适配器首次失败→失败片落台账且重试一次成功（修前只告警）；重试仍败→台账行终态失败点名原因。

### 批 H · 指挥资格统一判据（T6 已裁本轮动）

**断点**："这一轮谁能指挥 agent"由两道门分治且无统一读面：渠道准入 `access_policy.py:39-55`（管"谁说话"，渠道身份域）与治理白名单 `security/governance.py:539-561`（管"哪条命令跑"，命令文本域，消费点 `tool_executor.py:1566-1573`、`tool_layers.py:534-551`）。两门各自正确，但没有任何一处能完整回答"渠道发送者 S 指挥 agent A 执行命令 C 的资格"，审计面也只有各自的半张（`channel_router.py:312` 渠道侧、工具执行台账工具侧）。

**设计**：

- **H1 单一判定落点**：新函数（落点建议 `security/command_authority.py`，实施时按单源纪律定稿）`resolveCommandAuthority(senderId, channelType, agentId, command)`，组合两门：渠道准入（复用 `chatAccessDecision`）→ 治理白名单（复用 `match_whitelist`）→ 四态判定（allow／deny(channel)／deny(policy)／not_supported），**缺省 fail-closed**——任一门无法作答即 deny 并点名缺哪道。两个既有消费点全部改指该函数（教义第 7 条：接通后退役各自的分支逻辑），禁止第三处重写判定。
