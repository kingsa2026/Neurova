# 019a 叙述层入库：条目权威从 knowledge.json 换到底座库

**Blocked by**: 019（拆自 019；019b 承接"写方法转调 admit() + 删 JSON 条目路径"）
**阶段**: E3（§4.1 投影层不持写权）

## 目标
`KnowledgeRepository` 的条目权威落到 `knowledge_facts.db` 的 `knowledge_narratives` 表，
`knowledge.json` 退出读路径。**不连带分片索引**——`_rebuild_indexes` 与 `_item_index_docs`
只读 `self._items`，是它的纯函数，喂进去的不变则索引输出不变。

## 涉及层
- [x] 数据：迁移 v4 建 `knowledge_narratives`（id 为 PK，可见性/归属/标题成列，正文与分块进 `payload_json`）
- [x] 逻辑：`_load` / `_save` 两个边界按 `NEUROVA_KB_NARRATIVE_STORE` 换后端，默认关
- [x] 迁移：闸首次打开时把旧 `knowledge.json` 搬入并归档改名，旧文件不再被读到
- [x] 测试：`tests/unit/knowledge/test_narrative_store_019a.py`（19 例）+ 真数据对等核验

## 边界（刻意不做）
- 分块**不立表**：它随条目整篇读写，拆出去就是第二个权威，正是底座要消灭的东西。
- 墓碑与冲突两本旁账仍留 JSON，019b 收编。
- 写方法不转调 `admit()`：那是 019b，两件事混在一起出了错分不清是谁。

外加闸内跑通端点用到的整条写面（改标题/改块/共享/提交/审批/删除/墓碑/重启复现）。

核验脚本是一次性的（临时目录副本 + `:memory:` 评测库），未入库；它的等价物是
`test_narrative_store_019a.py::TestRepositorySwitch::test_indexDocsByteIdenticalAcrossBackends`。
真数据读数只在本次运行留痕，不做常驻用例——那会把生产库内容变成测试依赖。

三条落地时新增的约束（不是原验收项，是过程中撞出来的）：

1. **搬家只发生一次**：`importFromJson` 用 `INSERT OR IGNORE`，随后把旧主文件归档为
   `knowledge.json.pre-narrative-store-*`。若不归档，"删空全部条目后重启"会因为
   库里 0 行而拿快照把已删条目复活——这条有常驻用例守着。
2. **回退不留静默空库**：归档已存在而 `knowledge.json` 不存在时，关闸构造直接抛错并给出
   两条出路（保持开闸 / 手工复原）。这正是 B01"对着空表跑"的同类错误方向。
3. **闸内写失败不吞异常**：JSON 时代 `_save` 把一切异常降级成一条日志；换成全量替换后
   吞掉写失败会让内存与库分叉，下一次成功写入抹平分叉期间的编辑。故闸内直抛。

底座库读损坏同样不复用 JSON 的"隔离后当空库继续"——`migrate()` 抛错即抛错。
