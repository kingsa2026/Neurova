## 补记（2026-09-20 工单 019a 期间）：判据漏洞已补，根因比"少一条判据"更深

011 否证当时登记了一条判据漏洞：对账只让"预测 vs 自己的回放"互相作证，测不到
"两个写入器不一致"（backfill 88 个主体 vs reconcile 87 个，两边都报自洽）。补判据时取证，
发现的根因不是算法而是**装配**：

- `backfill.run()` 造的门是 `KnowledgeAdmissionGate(store, lineageLedger=…, credibility=…)`
  ——**没接 resolver**，身份消解退回精确名+别名，所以那一对近似标题没被合并；
- `FoundationReconciler.reconcile()` 造的门是 `KnowledgeAdmissionGate(store, resolver=…)`
  ——接了 resolver 却**没接血缘与置信**，于是"回放"根本不是生产写入的形状。

同一个"唯一咽喉"被两处各自装配，咽喉就不唯一了。补齐血缘段后还立刻暴露第二件事：
对账的回放此前一直在绕过"无主知识必须拒写"这条硬约束（没断言就 admit 不进去），
也就是说 005 的守卫在对账路径上是空转的。

修法（根因位，不在调用方加守卫）：
1. `admission.productionAdmissionGate(store, toolVersion=…)` 成为唯一造门入口，
   把已接通的四段（消解/冲突/血缘/置信）一次装配齐；未接通的（本体裁决、入索引）由
   `pendingSegments()` 如实报出，不硬凑。
2. 两个写入器都改经工厂造门；`_requestsFromRepository` 成为唯一的"旧行 → 咽喉入参"映射，
   断言合成从 backfill 搬进映射，两处不再各写一份。净效果：backfill `+5/−43`（少 38 行），
   reconcile `+31/−2`（搬进来的那段注释解释了为什么必须在映射里）。
3. 新增常驻判据 `test_backfillAndReconcileAgree`：同一份旧库，两个写入器的
   facts 与 subjects 必须各自相等；并配一条"样本必须锋利"的自检
   （那对近似标题确实只有经消解才合并、精确名不合并），否则这条判据是空的。
4. 另加 `test_factoryGateStillDemandsAnActor`：装配齐了以后无断言的 admit 必须在写入前被拒，
   库保持 0 行——这条不许为了回填方便而放宽。

真数据重跑（只读 knowledge.json，写只落在一次性库；生产回填产物已按 `.pre-20260920-gateparity` 留档）：
