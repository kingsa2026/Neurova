# 019b-1 记录种类进咽喉：条目作为"带载荷的记录" admit

**Blocked by**: 019a
**阶段**: E3（§4.1、§5 第四条硬约束）

## 目标
`admit()` 认识两种记录：`triple`（主体-谓词-客体）与 `narrative`（一条知识文档）。
条目走咽喉后立刻拿到四件它以前没有的东西：内容身份 `content_key`（B03 根因位）、
经消解的 `subject_key`、断言与活动（谁经什么介质写的）、由断言聚合出的 `confidence`（灭 G11 的硬编码 0.7）。

**不产三元组**：本切片不做抽取、不调 LLM。条目正文的唯一副本留在
`knowledge_narratives.payload_json`，事实行只存指纹与治理字段——
在同一个库里复制两份正文，就是这次改造要消灭的那个病。

## 涉及层
- [x] 数据：迁移 v5 给 `knowledge_facts` 加 `record_kind`（默认 `triple`，老行不改写）
- [x] 逻辑：`AdmissionRequest.recordKind`；narrative 段的谓词由咽喉固定为 `documented_as`、
      客体即 `knowledge_id`、正文不落进事实行；`relation_kind='document'`
- [x] 读面：`searchableFacts()` 默认不返回 narrative 事实行（正文在叙述层，
      混进池子就是一池空文本），要读必须显式 `includeNarratives=True`
- [x] 映射：`_requestsFromRepository` 把旧条目按 `record_kind='narrative'` 发（回填与对账共用同一映射）

## 验收标准
- 同一份 130 行旧库，plan / reconcile / backfill 三方仍然同数（本切片是表示法变更，不是行为变更）。
- 条目事实行 `content` 为空但 `content_key` 非空；正文唯一副本在叙述层。
- 匿名条目（无断言）在写入前即拒。
- `record_kind` 默认值不破既有行与既有测试。

## 完成状态

红灯先行 14 例（`tests/unit/knowledge/test_narrative_record_kind.py`）。
**踩回老坑一次并被抓出**：这批用例一开始写成 `def testXxx`（驼峰、漏下划线），
pytest 静默只收 1 条、既不报错也不失败——正是 `test_pytest_collection_hygiene.py`
存在的理由；改回 `test_` 前缀后 14 条全收齐全绿。教训：**新建测试文件后必须连
`tests/unit/core/` 一起跑**，只跑本目录会让这条守卫缺席。

一处设计约束比预想的硬：**迁移链必须单主注册**。
`db_migration.register_migration` 要求同一版本域内版本号按注册序严格递增，而一个库文件只有
一个 `user_version`——所以"一个库 = 一个版本域 = 一条注册序"。v4（叙述表）与 v5（`record_kind`）
分属两个模块时导入期直接 `ValueError`（实测）。修法是新立 `foundation/foundation_schema.py`
做本域链的单主：SQL 仍由各模块持有，注册顺序集中在一处，两个存储改调 `applyTo(conn)`。

被覆盖的是纯派生物（可由 `knowledge.json` 重放得到），现存归档 `*.pre-20260920-recordkind`
是统一装配之后、记录种类之前的那一版。后续脚本应按链版本分 tag，别复用。
