**Blocked by**: 019b-2

## 目标
`knowledge_tombstones.json` 这本旁账搬进底座库 `knowledge_tombstones`（迁移 v6），
闸内条目权威与删除史同一份存储、同一套搬家纪律。

## 为什么墓碑属于治理层
它记的是"这条知识被谁在什么时候收回了、被谁取代"——和 `retracted` 事实行是同一件事的两半：
一半说说法退场，一半说条目原件留在哪儿。留在 JSON 里的代价不是"多一个文件"，而是
**开闸后 restore / list_deleted 读的那份不再等于写的那份**。

## 涉及层
- [x] 数据：v6 建 `knowledge_tombstones`（整份条目快照进 `payload_json`，
      `agent_id` / `deleted_at` / `deleted_by` / `superseded_by` 成列可查）
- [x] 逻辑：只换 `_load` 与 `_save_tombstones` 两个边界，`self._tombstones` 形状一字不改
      （12 个调用点零改动）
- [x] 搬家：首次开闸把旧 JSON 导入后**归档改名**；归档前缀挂在原文件名之后，
      条目与墓碑各自留名（否则两份归档互相顶替，事后认不出谁是谁）
- [x] 闭环：`purge_knowledge` 一并投影，治理行跟着退场，不留"活着却无人认领"的行
- [x] 测试：`tests/unit/knowledge/test_tombstone_store_019b2c.py`（9 例）

## 验收标准
- 闸外逐字旧行为（写 JSON、不建底座库）。
- 闸内不再产生 `knowledge_tombstones.json`；delete/restore/purge/冲突顶替四类写入都在表里。
- 整份条目快照能原样回来（含正文、分块、修订）。
- 清空墓碑后重启不拿快照复活删除史。
