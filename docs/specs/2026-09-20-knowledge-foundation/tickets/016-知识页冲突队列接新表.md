# 016 知识页冲突队列接新表

**Blocked by**: 007, 011
**阶段**: E2

## 目标
治理者在现有冲突队列 UI 上看到五类冲突、严重度与建议策略，并能按依据裁决。

## 涉及层
- [ ] API：`knowledge_sharing.py` 冲突端点切读 `knowledge_conflicts`（保留旧响应字段以不破契约）
- [ ] UI：`NeurUI/src/pages/KnowledgePage.vue:178-196` 队列条目增加 kind / severity / policy_basis；
      `api/modules/knowledge.ts` 契约同步；i18n 补齐 `zh-CN` / `en-US`
- [ ] 测试：`NeurUI/src/pages/__tests__/` 增补队列渲染用例（vitest）

## 验收标准
- 无 `policy_basis` 的项在 UI 上不可被"自动裁决"路径关闭。
- 旧前端契约不破：既有字段仍在，新字段可选。
- `npm run build`（vue-tsc）通过。

## 完成状态（2026-09-20 实施）

**一个队列、两条轴，靠 `axis` 判别而不是混成一种形状**。工单原文写"冲突端点切读
`knowledge_conflicts`"，逐点核实后的口径是：`knowledge_conflicts`（007，成员是**事实行**）
与条目侧账本（019b-4a 收进 `knowledge_entry_conflicts`，成员是**条目** + 相似度）是两个对象，
硬并一张表要么丢相似度要么靠 fact↔entry 来回翻译——所以 016 把两侧都摆到治理者面前，
**语义合一留给 017**（那里给出为什么不能并的判据）。

- **API**（`knowledge_sharing.py`）：`GET /conflicts` 加 `axis=all|entry|fact`，**默认 `entry`**
  ⇒ 旧调用方拿到的响应逐字不变；两侧同用时条目侧字段一字不改、事实侧原名透出
  （`kind/severity/recommended_policy/policy_basis/member_fact_ids`），另加两条纯派生读数
  `subject_label` / `members_summary`——队列上只给 `subj_5fbb…` 等于让人去查数据库。
  `POST /conflicts/{id}/resolve` 按**账本归属**分派（新增 `repository.has_conflict`），
  响应如实回 `data.axis`。
- **裁决要真落地**：事实侧 `supersede_old` 现在要求 `winner_fact_id` 且必须是本冲突成员，
  落库时把败方逐条 `supersede`。只写一个 resolution 字符串＝队列清了而两条矛盾事实同时进
  上下文，那是假干净。`RerankBackendError` 一类后端故障不在这里退化（照 007 的口径上抛）。
- **UI**：`KnowledgeConflict` 改成判别联合（拿错轴的字段在编译期就该红）；队列行显示轴、
  种类、严重度、建议策略与 `policy_basis`；**没有"自动裁决"按钮**——`policy_basis` 为空标红
  "无依据 · 须人工指明胜方"，事实侧"新说法接管"在未选胜方前 `disabled`。
- **i18n**：11 个语言包全量补齐（zh/en + 9 个其他语言各 18 键）。中途被两条守卫教做人：
  ① `zh-CN keys are two-level camelCase` ⇒ 枚举标签必须是**顶层 section**（与
  `personality` / `emotion` 同型），不能嵌在 `knowledge.conflictKind.*` 三层里；
  ② 键段要驼峰，而后端枚举值是蛇形 ⇒ 页面里一张 `CONFLICT_POLICY_KEYS` 映射表就是翻译的一部分
  （`enumLabel` 会把值小写，救不了 `most_recent`，只能自己映射 `mostRecent`）。

**判据**：

  `axis` 过滤、按归属分派且不串账、非管理员 403 与未知 id 404、resolved 历史、
  **`supersede_old` 缺胜方 400 / 胜方非成员 400 / 有胜方则败方真的变 superseded**。

  `winner_fact_id` 发出（含"轴标签必须是文案不是键名"这条，防止 i18n 断链静默通过）。
