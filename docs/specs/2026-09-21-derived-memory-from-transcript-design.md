# 从会话历史派生记忆：写侧凭据、派生引擎与跨进程可见性

日期：2026-09-21 · 状态：待审 · 上游设计：`2026-09-20-external-agent-ingest-design.md`

## 1. 为什么做这件事

外部 agent 导入今天面临一个不对称：会话历史家家都有，记忆索引却不是（八族里只有
`openclaw_transcript` 能从源库直读记忆）。产品判断是：**既然会话已经能落地，就该能从会话
把记忆长出来**，而不是等每家源都给出可取证的记忆表。

同一句话在运行期还有一层意义：Neurova 本来就该有一条"记忆没写成功就补上"的兜底。它今天
存在但从未生效过。这两件事共用一个引擎——**兜底与派生是同一条产线的两个触发口**。

### 非目标

- 不做 LLM 逐轮提炼（成本高、依赖模型可用，会把"确定性转换"变成"可失败的处理"）。留口子但不在本期。
- 不改运行期正常对话的写记忆语义（仍逐条 `remember()`），只加凭据。
- 不动反思→教训那条链（链A/链B 已闭环，见 `2026-09-19-reflection-feedback-loop-audit.md`）。
- 不修 MoE 专家覆盖不到 `category=general` 这个既有缺口（§9 另立）。

### 范围更正

`2026-09-20` 设计定的触达面是"只做包内模块 + 薄 CLI，本轮不开 HTTP 端点、不做前端向导"。
本设计**取代**该条中关于端点的部分：可检索性断点只能在服务端进程内根治（§6），因此开一条
导入端点并接智能体管理页入口。

## 3. 判据：写侧意图账本

要满足"只写差异"和"时机门控（确定写失败才补）"，必须把判据从**时间窗**换成**凭据有无**。
`crash_time` 的语义是"此后消息可能未落库"，不是"确实未落库"，拿前者当后者用就是要杜绝的全量灌入。

- **意图**：运行期每轮双写前记一条 `{agent_id, session_id, message_ts, role, content_digest}`。
- **回执**：`remember()` 返回后记 `{content_digest → memory_id | gated}`。返回 `None`（内容门
  判定重复）算**已了结**，不补。
- **判据**：启动时只有"有意图、无回执"的条目是确认丢失，才进入补写集合。`crash_time` 退化为
  扫描窗口边界，不再决定"写什么"。
- **去重不由账本负责**：补写走 §5 的写入口，重复与否由内容门（§2 那把八元组键）判。账本管
  "该不该补"，门管"会不会重复"，两件事混在一把键上会两头不稳。
- **落盘**：追加式 JSONL，每轮两次小 append（remember 前记 attempt、之后记 receipt），中间崩溃
  正是判据所在——**攒在内存里批量刷会直接毁掉这个能力**，所以不能缓冲。代价与既有行为同量级：
  运行期每轮本就写一次会话文件（`SessionManager` 每段落盘）。路径可注入（沿用"写盘路径必须可
  注入 + conftest 双层隔离"那条教训，严禁落到真实 `data/`）。
- 账本只增不删会无限增长：以"回执已了结"为界做轮转（保留窗口 = sentinel 的崩溃判定窗口）。

## 4. 派生引擎：两个触发口，一条实现

新包 `neurova/memory_derive/`：`ledger.py`（意图/回执）、`engine.py`（选择 + 门控 + 产出
`MemoryRecord`）。`recovery/` 与 `memory_ingest/` 都依赖它，谁也不拥有谁。

**统一输入是已落盘的会话消息**（经 SessionManager 读）。导入落盘的会话与崩溃恢复扫到的
会话是同一种东西，差别只在**选择器**：

- 恢复口：账本里"有意图无回执"的差集；
- 导入口：本次 `ingest_run_id` 覆盖的会话消息。

**门控（默认值待签，均可 CLI/端点覆盖）**：

| 参数 | 默认 | 语义 |
|------|------|------|
| 角色 | 仅 `user` | 对方 agent 的回复不升格为本系统记忆 |
| `--derive-min-chars` | 12 | 短于此（寒暄）不写 |
| `--derive-per-session` | 200 | 单场会话上限 |
| `--derive-total` | 恢复口 200 / 导入口 2000 | 单次总量上限，触顶即申报剩余条数 |

**超限不静默截断**：被门挡掉与因上限被截断的条数一律进报告（沿用导入面的申报口径）。默认姿态
是"派生必须显式开启"（`--derive-memories`），降级路径永不顺手灌全量。

## 5. 写入与索引对齐

派生结果一律走批量咽喉 `import_memories`（单事务、保留历史时间戳、带 `ingest_run_id` 可整批
撤销），**不循环调 `remember()`**（§2 那 18GB 就是这么来的）。

派生行必须逐字复刻运行期参数，否则八元组键撞不上、去重失效：
`content = "用户: {消息正文}"`、`category="general"`、`memory_type="episodic"`、
`origin="owner"`（对方用户发言）/`"agent"`（若将来放开助手侧）。

落库后批末对齐一次：

- 向量：`index_memories(整批, incremental=True)` 一次（矩阵重建与缓存落盘各一次）；
- 关键词：逐条 `upsert_memory_index`（纯内存字典）。**禁用 `build_keyword_index`**——它先
  `clear()`，只喂新批次会抹掉既有索引。

## 6. 跨进程可见性：端点 + 显式刷新

- **A 主路**：新增导入端点（`neurova/api/endpoints/ingest.py`），`apply_bundle` 在服务端进程内
  执行，写的就是本进程 manager 单例 → 快照天然一致，无需失效协议。智能体管理页加导入入口
  （detect 报告 → 确认 → apply → 结果与申报回显；文案改 11 份 locale）。
- **B 补齐通道**：`MemoryManager.reload_memories(agent_id)`——按作用域增量拉缺失行进
  `_memories`，逐条 `upsert_memory_index`，并让内容门索引增量并入。只增量，不得退化成每次
  recall 全量重建（那是审计 P1-D6 刚消掉的开销）。A 完成即调用它；CLI 独立进程导入后由人或
  前端显式触发。
- 前提关系要写明：**没有 B，§3 的"只补差异"在跨进程场景不成立**（门与召回读同一份陈旧快照）。

## 7. 失败与撤销

- 派生批次与导入批次都走同一个批次标签：导入口用 `ingest_run_id`，恢复口用
  `recovery:<启动时间>` 形态的标签（`import_memories` 本就要求非空 run id）。两者都能按标签
  精确撤销，撤销与媒体清理沿用既有单一口径。
- 恢复口除标签外再记一条审计：补写条数、覆盖时间窗、来源=兜底——它不是用户发起的导入，
  事后要能单独查清是谁在什么时候补的。
- 账本写入失败**不阻断**对话（与运行期"索引维护失败不阻断记忆写入"同口径），但必须告警并计入
  降级计数——否则兜底会静默失去判据。

## 8. 验收与测试策略

TDD，红→绿逐行为推进；用例一律 `test_` 前缀且断言 collected 数。

1. 账本：意图/回执配对、`gated` 算已了结、有意图无回执才进补写集、窗口轮转。
2. 引擎门控：只取用户侧、长度门、每会话上限、超限申报不静默。
3. **去重对齐**（本设计最硬的回归防线）：先跑一次运行期 `remember()`，再对同一条消息跑派生
   补写，断言只落一条——断言必须经生产构造点取 manager，不接受测试里手工传 `agent_id`。
4. 索引对齐：批量派生后 `upsert` 生效且既有倒排未被清空；向量索引只重建一次（按调用计数断言，
   不给 3500 次缓存整写开绿灯）。
5. 端点：detect/apply 显式确认、apply 后同进程立刻 recall 得到该条。
6. 崩溃恢复口：目录布局修正的回归（用真实 `sessions/<agent_id>/` 布局建夹具）。
7. 活体验证：对既有真库（opencode 单库）跑一遍"导会话 → 派生 → recall 命中 → undo 归零"。

## 9. 已知缺口（登记，不在本期解决）

- MoE 四专家不覆盖 `category="general"`：运行期自产的对话记忆同样进不了 L0 专家。这是既有
  缺口，且**不能**由派生方单改 category 绕过（会让 §2 那把门键失效、去重崩掉）。
- LLM 提炼档（本期非目标）若要做，须接 `track_llm_call` 与成本门控，失败要申报不得静默降级。
- 六族仍只导会话；`dsh_session` 仍只有指纹。
- 只有记忆索引、无会话事件表的源库仍 detect 不出（指纹按会话表立）。

## 10. 对上一份 spec 的更正

`2026-09-20-external-agent-ingest-design.md` §4 原文"不触发……由启动扫描与后续召回自然覆盖"
经核实只有半句成立：向量通道在重启后自愈，但**服务不重启就看不见导入行**，而所谓"启动扫描"
指向的正是本 spec §2 那条从未接线的死代码。更正为：导入行的可见性条件是"服务重启"或"显式
`reload_memories`"，兑现手段即本 spec §6-B。

## 11. 交付切片（顺序即依赖，具体工单由计划展开）

本设计横跨运行期写路径、派生引擎、批量咽喉、API 与前端，体量足以拆成四片分别验收，
每片独立可绿、不出现半接线状态：

1. **片一（后端地基）**：账本 + `reload_memories` + 批量咽喉的索引对齐。可单独测死（§8.1/4/5
   的一部分），不改变任何现有行为。
2. **片二（恢复口）**：修通 `ShutdownGuard`（接启动钩子、扫对目录、按判据补写、上限与审计）。
   依赖片一的账本与对齐。做完"崩溃丢写"这条兜底第一次真的生效。
3. **片三（导入口）**：`memory_derive.engine` 接进 intake，CLI `--derive-memories`。依赖片一。
4. **片四（端点与前端）**：导入端点 + 智能体管理页入口 + 11 份 locale。依赖片三，且是 §6-A
   的兑现处。

片一是纯地基、对用户不可见，不能单独当作"做完了"对外说；能力从片二（兜底真的生效）或
片三（导入长得出记忆）起才算到位。
