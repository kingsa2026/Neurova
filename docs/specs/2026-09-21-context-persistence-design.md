## 1. 为什么单独立项

D1 的裁决是"池的**永久归档**必须跨重启为真"。这句话把 P1-3 从"接通或退役"改成了"必须建持久层"，
量级从 bug 修补变成**新增子系统**。审计 §10 对 B4 写明了必须先出的三件设计：

1. 写放大
2. 启动加载策略
3. 零停机迁移版本纪律

本文件就是这三件的答案，外加**实施前必须先钉死的边界**（§4 非目标、§5 契约）。

### 1.1 现状实测（基线脚本 §1，一条命令复现）

生产 `ContextOrchestrator.__init__` 注入 `EvictionLedgerDB` 时**不传** `resident_limit`，
且池的 `ttl_seconds=0`。按此构造面实测：

| 观测 | 读数 |
|---|---|
| `resident_limit` / `ttl_seconds` | `None` / `0` |
| 写入 600 条后常驻 | 600 条（无回收） |
| `cleanup_expired()` | 0 |
| 台账 DB 行数 | **0** |
| `recall_evicted(query=…)` | **0 条** |
| 新进程（模拟重启）侧 | 常驻 0 条、`recall_evicted` **0 条** |

即：**写入口按构造不可达，读入口恒空，池本体没有任何持久化**。模型侧
`recall_history(query=…)` 的子串模式因此是一条恒空出口，而工具文档（`builtin_tools.py`
的 `recall_history` schema）告诉模型"可召回被折叠/驱逐的内容"。

**真跨进程复核**（不只在同一进程里换实例）：进程 A 写入 300 条后退出——
`writer: 常驻 300 台账行数 0`；进程 B 以同库新开池读取——
`reader(新进程): 常驻 0 | recall_evicted = 0`。D1 的验收判据（A1）当前确为红。

### 1.2 与 B2/B3 的关系（不重复、不冲突）

B2 给池的写入咽喉打了 `chat_scope`，B3 让视图截断只产副本。两者都建立在"归档实体是权威原文"
这一前提上。**持久层是这个前提的物理承载**——进程一退，前提就没了。所以 B4 必须满足
B2/B3 立下的隔离与不可变契约，而不是另立一套（§5.3、§6.4）。

## 2. 决定（D7–D13）

沿用审计的 D 编号风格续编，避免与 §10 的 D1–D5 撞号。

### D7 底座：沿用 `EvictionLedgerDB`，单文件单库，收口三件事

审计已裁定"自然底座是已建好却空转的 `context/eviction_ledger_db.py`"。本规格落实为：
**同一张表兼作常驻回收目标 + 冷归档 + 读侧索引预筛**，不新建第二套持久化。

- 库路径：`data/context_ledger/<agent_id>.db`（沿用现路径，不迁移目录）。
- 分区键：`(user_id, agent_id)` + 可选 `session_id`；隔离条件**静态写死在每条查询里**
  （沿用现实现的强制定额，不做 SQL 拼接）。
- **不引入连接池**：库路径随 agent 数增长，进池会让池注册表无界增长——与 ADR 0014
  "动态路径不进池"一致。实施上按"每池一个常驻连接"处理，见 D8。

### D8 写放大：换掉"每行一条 INSERT + 一次 commit + 一次 connect"

**现状形状**（`record()`）：每行一次 `connect` → 两条 `INSERT` → `commit` → `close`。

注意：P1-3 下这条路径**生产不可达**（§1.1），所以下表的"现状形状"是**把现有逐行
`record()` 直接接上写入路径**的代价——即"不做本决定"的代价。

实测（10 万行存量库，24 条/轮，各 20 轮取中位；三次连跑区间，基线脚本 §2）：

| 形态 | 每轮耗时（中位） |
|---|---|
| 每行独立连接 + 提交（现状 `record()` 同形） | **214–318 ms/轮** |
| 常驻连接 + 每轮一次事务 + trigram FTS 影子写 | **0.78–0.91 ms/轮** |
| 常驻连接 + 每轮一次事务 + 不建 FTS | **0.34–0.35 ms/轮** |
| 同一次运行内倍数（现状 / 每轮一事务含 FTS） | **261–420×** |
| FTS 影子写的相对成本（含 / 不含） | **2.2–2.7×** |

**决定**：写入口改为**批量提交**——一次轮次内的全部归档条目共用一个连接、一个事务，
事务边界 = 一次归档调用（`add_context` 的批量调用方）。

- **不做异步/后台缓冲刷盘**：D1 的验收是"重启后取得到旧内容"，攒在内存里批量刷会把
  崩溃窗口内的内容连同"已归档"的承诺一起丢掉。事务边界只能到"写调用返回"为止，
  不能再往后拖。
- **不设 WAL 参数竞赛**：`synchronous=NORMAL` 已在 WAL 下保证进程崩溃不丢已提交事务
  （只可能丢最后若干事务的"断电级"持久性），与归档语义相称；不引 `synchronous=OFF`。
- 事务提交频率 = 归档调用频率（生产为每轮一次，实测中位 <1 ms），不额外引入节流窗口。

### D9 读侧索引：`trigram` 分词器 + 长度 <3 的查询回退 LIKE

审计说"读侧 FTS 预筛"是底座三合一之一。现状用的是 `unicode61`，**对中文等于没有索引**
（unicode61 把连续 CJK 切成一个词，任何短语查询都命中 0）。

实测（5 万行，三次连跑区间，基线脚本 §4）：

| 查询 | unicode61 | trigram | LIKE 真值 |
|---|---|---|---|
| `上下文压缩` | **0** | 4912–4934 | 与 MATCH 相等 |
| `窗口预算` | **0** | 4921–4994 | 与 MATCH 相等 |
| `上下文` | **0** | 16526–16530 | 与 MATCH 相等 |
| `The context window` | 16667 | 16667 | 16667 |

要点不是"命中多少条"（语料是随机生成的），而是**trigram 的命中集合逐条等于 LIKE 真值，
unicode61 对任何中文短语都是 0**。

精确性（CJK 语料，逐长度 120 次抽样，LIKE 作真值；基线脚本 §4b）：

| 查询长度 | 假阳性 | 假阴性 |
|---|---|---|
| 1 | 0 | 14.6–24.0 万条（trigram 无法索引） |
| 2 | 0 | 14.6–17.1 万条 |
| **≥3** | **0** | **0**（长度 3 / 5 / 10 均如此） |

**决定**：

- FTS 分词器换 `trigram`；`unicode61` 的现有 FTS 表在迁移中重建（D12）。
- **查询长度 <3 时不用 MATCH**，直接走现有 LIKE 分支（trigram 对 <3 无索引能力，
  强行 MATCH 会得到假阴性——这是"漏召回"，比慢更糟）。
- **查询串必须转义**：现状 LIKE 分支直接拼 `f"%{query}%"`，`%` 与 `_` 是 LIKE 通配符。
  实测（基线脚本 §8）：库内 3 行时查询 `%` 命中 **3 行**（应为 0），查询 `_` 命中 **3 行**。
  改用 `ESCAPE '\'` 并对 `\` `%` `_` 三字符转义。
- 候选集上限：MATCH 命中数超过阈值（初值 2000）时**降级为按 `id DESC` 取最近 N 条 +
  在候选内做子串过滤**，避免一次查询把整库拉回内存再逐条过滤。阈值需在实施期用真实
  语料校准，不做想当然取值。

### D10 启动加载：只登记，不预载；热集按需回载

"启动加载策略"是审计点名要设计的第一件事。三个候选与实测（10.2 万行库，基线脚本 §5）：

| 候选 | 启动代价（warm，三次区间） | 常驻内存 | 判定 |
|---|---|---|---|
| 只登记 `COUNT(*)` | **4.8–5.1 ms** | 0 | ✅ 采用 |
| 回载最近 500 条 | 0.93–0.96 ms | ~0.13 MB | 按需 |
| 回载最近 2000 条 | 3.9–4.0 ms | ~0.5 MB | 按需 |
| 回载最近 10000 条 | 24.6–25.7 ms | ~2.6 MB | ❌ 不做 |

（`COUNT(*)` 的 5 ms 是**冷读**的首个查询成本；§9 的同一查询在已活跃连接上是 4.7–5.0 ms，
量级一致。启动只发生一次，不做进一步优化。）

**决定**：

- 启动只读一次 `COUNT(*)`（用于 `get_retention_stats` 与 `/metrics`），**不把历史塞回常驻**。
  理由：D1 要的是"取得到"，不是"开局就全在内存"——池的语义本来就是"按需调取"。
- 调取路径（`draw`）**不查 DB**：常驻集是视图的唯一来源，DB 只服务 `recall_evicted`
  的显式召回。这条边界必须写进契约，否则"draw 每轮扫库"会把 B5 的规模问题提前引爆。
- 需要预热时由调用方显式回载（`rehydrate(limit=…)`，工单 005），默认不调用。

### D11 GC：保留策略显式化，`gc_stale` 的节流点搬到有调用方的位置

现状 `_LEDGER_GC_EVERY=20` 的节流计数挂在 `_archive_evicted` 上，而 `_archive_evicted`
在生产不可达 → **GC 也永不触发**。持久层一旦真跑起来，不清理就会单调增长。

**决定**：

- 保留策略两维：`keep_count`（默认 5000 条/`(user, agent)`）+ `keep_days`（默认 30 天）。
  两维都是**默认生效**的，不是"配了才生效"。
- GC 触发点：随归档批量提交同批执行（每 N 次提交一次），N 与环境无关地写死在模块常量。
- FTS 与内容表对齐用**分批删除**（5000/批）。实测 5 万行库删除 2 万行后 FTS 残留
  **50000 行**，全表 `NOT IN` 对齐 388–433 ms、分批（5000/批）310–446 ms——量级相当，
  但分批不长时间持写锁（基线脚本 §7）。**不采用 `delete-all`**：该指令只对
  contentless/external-content 表合法，本表是普通 FTS5，实测直接报 `OperationalError`。

### D12 迁移：`db_migration` 版本域 + 零停机顺序

这是审计点名要设计的第三件事。现状 `eviction_ledger_db.py` 只用 `CREATE TABLE IF NOT EXISTS`，
**没有版本域、没有 `user_version` 纪律**，与 `AGENTS.md` §3 "schema 变更加入
`core/db_migration.py` 注册表"直接冲突。

**决定**：

- 注册版本域 `context_ledger`（`neurova/core/db_migration.py` 的既有机制，`register_migration`）。
  **不新建平行迁移体系**。
- 版本链（每条独立事务，失败回滚并上抛）：

| 版本 | 内容 | 实测代价（5 万行，三次区间，基线脚本 §6） |
|---|---|---|
| **v1** | 加 `content_digest` 列 + 回填 + `uniq_digest(user,agent,digest)` 唯一索引 + `idx_scope_id(user,agent,id)`（索引顺序理由见基线脚本 §8b） | **0.18–0.20 s** |
| **v2** | FTS 重建为 `trigram`（影子表 + 回填 + 原子换名） | **0.84–0.86 s**（一次性事务）/ **1.19–1.33 s**（分批 + 切换） |

索引顺序实测（10 万行热集最近 500 条，基线脚本 §8b）：
无二级索引 0.78–0.95 ms / `(user,agent,session)` **33.9–35.5 ms** / `(user,agent,id)` 0.90–0.91 ms。
按 `session` 收尾会让热集查询慢 37 倍——故 v1 建的是 `(user, agent, id)`。

- **零停机顺序**：v2 的分批重建在迁移窗口内**并发写不停**，实测三次连跑：并发写
  228–267 次，写侧停等 p95 **5.5–18.3 ms**、max **128.7–181.7 ms**（基线脚本 §6）。
  因此 v2 必须走分批路径，**不得**用一次性 `INSERT … SELECT`——那样写侧会被整段阻塞
  （一次性事务 0.84 s 全部持锁）。
  p95 与 max 的差距说明"分批"消掉的是**持续**阻塞，不是单次最坏抖动；实施时判据取 p95。
- 切换窗口补齐增量：分批回填到达末尾后，切换前需把 `id > offset` 的尾批补进影子表，
  再 `DROP` 旧表 + `RENAME` 影子表，三步在同一事务内完成（实测通过）。
- **防降级**：`db_migration.migrate` 自带"库版本高于代码已知最大版本即拒绝打开"，
  沿用即可，不另写校验。
- **旧代码打开新库**（回滚场景）：v1 之后旧代码 `INSERT` 不带 `content_digest` →
  实测插入成功但该行列值为 NULL（基线脚本 §6 的对照），唯一索引对 NULL 不冲突。
  这是**允许的**：旧代码能写、能读自己写的行，新代码读到时按"无摘要"对待（回填兜底）。
  **不做**"旧代码写了就报错"的硬拦——那会让回滚从"功能降级"变成"服务起不来"。

### D13 隔离：召回路径必须过作用域闸口，作用域随归档落库

B2 修好的是**视图路径**的隔离（`orchestrator` 的 `filter_by_scope`）。持久层是**第二条读路径**，
现状完全不过闸口。实测（基线脚本 §8）：

- 群聊归档（`session_id=project_roomB`、`chat_scope=room:project_roomB`）落库后，
  在**单聊池**（`session_id=s_direct`）召回条数 = **0**（恒空，因为库里按 session 精确等值过滤）；
- 在**无会话池**（`session_id=None`）召回条数 = **1**，且没有任何闸口 → **房间内容可见**。

**决定**：

- `recall_evicted` 增加与视图路径**同源**的作用域过滤：调用
  `collaboration.memory_scope.filter_by_scope`，判据是库里存的 `chat_scope`
  （读不出来时按 `session_id` 的 `project_` 前缀回溯，与既有 `scope_from_metadata` 同规则）。
  **不新写第二份作用域判定**。
- `record()` 必须落 `chat_scope`。现状 `evicted_chunks` 表**没有 `metadata` 查询面**：
  `recall_evicted` 从库里构造 `ContextInput` 时只回填 `turn_id/session_id/evicted_at/
  recalled_from`，**丢掉** `chat_scope`——放行之后闸口也无据可判。故 metadata 的
  `chat_scope` 需提升为独立列（工单 002 的 v1 迁移一并加），或保证读侧能解出等价判据。
  **收口（U1，2026-09-21 拍板）**：取"独立列为主 + 读侧解析 metadata 作兼容兜底"——
  v1 迁移加 `chat_scope` 列（读路径高频且可加索引）；旧行（列值为 NULL 或无该列）由
  读侧解析 metadata 的等价判据补齐，两路判据同源（`collaboration/memory_scope`），
  不新写第二份规则。
- 召回是**跨会话**的（这正是 D1 要的"跨重启取得到"），因此过滤只能按作用域，不能按
  session 精确等值。现状"单聊池恒空"的根因就是拿 session 做了等值过滤——**改成
  "session 优先 + 跨 session 兜底 + 作用域闸口"**。

## 3. 容量账（实测，供容量规划）

5 万行库（内容 271 B + metadata 61 B 每行；基线脚本 §3）：

| 配置 | 磁盘 | 5 万行总量 |
|---|---|---|
| 无 FTS | 358 B/行 | 17 MB |
| `unicode61` FTS | 795–796 B/行 | 38 MB |
| **`trigram` FTS** | **968–969 B/行** | **46 MB** |

即：**每约 1.4 KB 归档占 1 KB 磁盘**。10 万行 ≈ 92 MB。trigram 相对 unicode61 的额外
开销是 173 B/行（约 22%）——这是中文可检索的价钱，且**只在 FTS 影子表上**。这个量级是可接受的，但**必须**与
D11 的保留策略同时落地——否则它就是单调增长的磁盘占用。

## 4. 非目标（本批不做，写清以免被当成遗漏）

- **不做池本体的"全量持久化"**：常驻集仍只在内存。持久层承载的是**归档与召回**，
  不是"重启后池里还是那 600 条"。后者是另一件事（会话重建），不在 D1 的判据里。
- **不做 `draw` 的 DB 直查**（见 D10）。B5 的规模问题（P1-4 嵌入缓存 + 批量打分）
  与本批正交，本批不碰。
- **不退役 `_eviction_ledger` 内存台账**：它承载"本进程驱逐"语义，与持久层是双源合并
  （现状 `recall_evicted` 已如此）。删它会把"同进程内更快的一等公民"换成"每次都查库"。
- **不动 `resident_limit` 的默认值**：D1 只要求"取得到"，不要求"常驻有上限"。
  默认仍 `None`；上限是运维开关，本批只保证"开了上限时全文不丢"（现在这条已成立）。
- **不做加密/压缩存储**：`evicted_chunks` 是明文，与现状一致。落到静态加密是独立议题
  （`docs/architecture` 的 memory security 层），不在 D1 范围。
- **不做跨 agent 的库合并/分片**：按 agent 分库是现状与 ADR 0014 的既有形态，不动。

## 5. 契约（实施必须满足，逐条可测）

### 5.1 写入契约

- `record(...)` 返回前，该条必须已完成事务提交。
- 同一次归档调用内的多条**共用一次事务**；`record` 不再每次 `connect/close`。
- `chat_scope` 必须随条目落库且**读得回来**（D13）。
- 写失败必须**显式可见**：现状 `_archive_evicted` 里 `except Exception: logger.warning`
  是"归档失败不影响主流程"的诚实降级，保留；但持久层自身不可用时必须在
  `get_retention_stats()` 里上报（不静默）。

### 5.2 读契约

- `recall_evicted(query, limit)` 在**新进程**里必须能取到上一进程写入的内容（D1 判据）。
- 查询长度 <3 走 LIKE 分支且**转义** `%` `_` `\`。
- 候选集超过阈值时降级为"最近 N 条 + 候选内过滤"，不得整库拉回（D9）。
- 读路径必须过作用域闸口（D13）。

### 5.3 隔离契约

- 群聊（`room:<id>`）归档在单聊轮召回**不可见**；跨房间互不可见；群轮可见 direct + 本群。
- 判据与视图路径**同源**（`collaboration.memory_scope`），不新写阈值/规则。

### 5.4 版本契约

- `context_ledger` 版本域必须注册；`user_version` 与注册链一致。
- 库版本高于代码已知版本 → 拒绝打开（沿用 `db_migration` 既有防护）。
- 迁移每条独立事务；`v2` 必须走分批路径（长事务会阻塞写，实测见 §D12）。

### 5.5 容量契约

- 保留策略（`keep_count`/`keep_days`）默认生效；GC 有生产触发点。
- FTS 与内容表对齐用分批删除；不得依赖 `delete-all`（普通 FTS5 不支持）。

## 7. 已知的坑（实施时必读，均为实测踩到）

1. **`trigram` 对 <3 字符查询无索引能力**，会返回假阴性（不是假阳性）。必须按长度分流。
2. **`delete-all` 只对 contentless/external-content 表合法**，普通 FTS5 直接 `OperationalError`。
3. **长事务持写锁**：一次性 `INSERT … SELECT` 回填 FTS 会把并发写整段阻塞；必须分批 + 短事务。
4. **LIKE 的 `%` `_` 是通配符**：不转义就是把"用户输入"变成"通配模式"，实测 3 行全命中。
5. **`unicode61` 对中文等于无索引**，改造后旧表**必须重建**，只换 tokenize 参数不会改已有索引。
6. **`gc_stale` 的节流点挂在不可达路径上**：接线时必须同时确认 GC 有真调用方，
   否则"加了持久层"会退化成"持久层单调增长"。
7. **`metadata` 里的 `chat_scope` 读不回来**：`evicted_chunks` 只存 `metadata` 字符串，
   而读侧构造 `ContextInput` 时不解析它 → 闸口无据可判。要么提升为列，要么在读侧解析。
8. **内存台账与持久台账是双源**：合并去重按内容 hash 做，改造时不要破坏去重语义
   （同内容在两边各有一份时只能出一条）。
