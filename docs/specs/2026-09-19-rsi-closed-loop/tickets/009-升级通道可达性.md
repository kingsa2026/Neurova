# 009 · 升级通道可达性（发散 → 人工提案）

**Blocked by**: 007, 008

## 目标

让 `SelfImprovementProposer` 这条"自动调整失效时升级人工评审"的通道在真实运行中**能够被触发**。
现在它是一段逻辑上存在、事实上不可达的死码。

## 证据（审计实测）

`orchestrator._escalate_to_proposer_if_needed:309-313`：

```python
needs_escalation = status == "diverging" or (
    status == "oscillating" and isinstance(trend_slope, (int,float)) and trend_slope < 0)
```

而 `diverging` 要求 `mean_gain < -0.05`（`convergence_analyzer.py:104`）。
在 gain 恒 0（度量失明，见 007）或参数已达 setpoint（零候选，见 002）的现实下，
mean_gain 无负值来源。实测 80 轮：status 集合 `{insufficient_data, converged}`，
`diverging/oscillating` **从未出现** → `_escalate_to_proposer_if_needed` 恒返回 `[]`
（`orchestrator.py:250` 的调用点形同虚设）。

第二个门槛：`:322-324` `if performance is None or performance >= 0.5: continue` ——
性能取自 `_extract_performance(signals)`，只认
`performance_score/success_rate/avg_success_rate/stability`（`:628`）；
`integration_manager.collect_feedback_signals:139-150` 已强制注入 `performance_score`，
故当四系统都无真实退化信号时 performance 恒 ≥0.5，即便进了发散分支也会逐个 continue。

## 交付内容

1. 发散来源真实化：007 上抛的 `measurement_blind` 与 006 的真 ROI **两者都作为升级触发条件**
   （度量失明即"自动参数调整失效"的准确定义，无需等到数值上出现负增益）。
2. `_escalate_to_proposer_if_needed` 的判据改为消费 `GateVerdict`（003），
   并在**每个被跳过的系统**上记录跳过原因（`performance>=0.5` / `no signals`），
   使其可被 012 的观测面呈现 —— 不允许静默空列表。
3. 提案创建后必须能被 010 的链路消费（走 `persist_synthesized_skill`），
   即：本单产出的提案在 010 完成后是"可批准且批准即生效"的。
4. `_compute_avg_performance:364-381` 与 `self_improvement_proposer` 侧是否存在重复实现，
   一并 grep 收口（本单范围仅限升级判据，若发现重复定义则登记台账不强行删）。
