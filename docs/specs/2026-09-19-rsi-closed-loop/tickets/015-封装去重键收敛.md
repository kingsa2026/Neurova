# 015 · 封装模板去重键收敛

**Blocked by**: 014

## 目标

同一个模式被 observe 两次，不会第二次又产出一个待审模板；
已批准的技能不会每轮被打回"待审"。

## 证据（审计实测，行号待 implement 复核）

`evolution/skill_encapsulation.py` 内并存两套 ID 构造：

- 去重查找键：`:339` `f"skill_{pattern_id}"`，其中 `pattern_id` 为 64 位 hex 全串
- 规范落盘键：`:360` / `:379` `f"skill_{fingerprint[:16]}"`（16 位前缀）

两者**永不相等**（实测 `equal? False`）。后果：`AutoSkillBuilder.observe` 每轮都判"新模板"，
重新封装、把 `is_active` 重置为 False（`:376`）→ 上一轮已批准的模板本轮重回待审队列。
磁盘侧 `skill_service.py:339-343` 因 duplicate 早返回，`enabled` 未被覆盖 ——
即**内存态与磁盘态每次重启/每轮都漂移一次**。

生产者侧是真实的：`creation_governance.finish_task:218-236` 驱动 `builder.observe`，
所以这不是死码，是活着的自噬循环。

## 涉及层

- [x] 逻辑层：`skill_encapsulation.py`（ID 构造单点化）
- [x] 测试：`tests/unit/evolution/test_skill_encapsulation_identity.py`（新）

## 交付内容

1. 抽出单一构造函数 `skillTemplateId(fingerprint) -> str`（命名随 Neurova 风格），
   去重查找与落盘两处**共用它**；`pattern_id` 若语义不同则改名以显式区分，
   不允许两个不同含义的 ID 共用 `skill_` 前缀。
2. `is_active` 在"命中既有模板"分支上**不得被重置**（显式断言）。
3. 复核 `find_skills_for_context`（`:414`）零调用方的判定，登记进 017 删除清单。
4. 放大视角：grep 全仓 `skill_` + fingerprint/pattern_id 的其它拼接点（含
   `creation_governance.py:90-100`），同契约的其它命中点一并收敛或在本单登记。

## 验收标准

- 用例：同一模式连续 `observe` 2 次 → 模板集合大小不变、`is_active` 保持 True、
  第二次不产生 pending 项（当前必红：第二轮重新封装）。
- 用例：`resolve` 后内存模板 id 与 `SkillService` 磁盘 manifest id 逐值相等。
- 静态守卫：`skill_encapsulation.py` 内匹配 `f"skill_{` 的表达式只剩 1 处（grep 计数断言）。
- 回归：`tests/unit/evolution/test_skill_consolidation_structural_and_deadcode_p1p2.py` 仍绿。

净负（两处拼接收敛为一处，且不改外部契约）。

## 执行结果（2026-09-21 落地）

### 落地时读到的现状（与票面行号有出入）

`pattern_id` 已经不是 md5 短串：`_update_pattern:251` 取的是
`fingerprint(tool_sequence, context)` —— **64 位 sha256 全串**，而落盘/建键侧
已由另一处的 "P0 统一命名" 收敛成 `canonical_skill_id()`（`skill_{指纹[:16]}`）。
两者仍**永不相等**，所以自噬循环原样成立，只是错位面从"两处落盘键"缩成
**一处**：`_check_encapsulation:339` 的命中判定。

实测红讯（同一模式第 4、5 次观察）：

```
INFO Encapsulated pattern b3afa314…c22a into skill skill_b3afa314281e9cf8   ← 第一轮
INFO Encapsulated pattern b3afa314…c22a into skill skill_b3afa314281e9cf8   ← 第二轮，同一模板又封装一遍
```

`self._templates[template_id] = template` 是**覆盖写**：新 `SkillTemplate` 带
`is_active=not self._review_gate` ⇒ 评审闸常开（默认）时每轮把人工批准打回 pending。
模板条数不变（键相同），变的是批准态与对象身份 —— 票面"模板集合大小不变"这条
断言在旧实现下**恰好是绿的**，所以真正咬人的断言是 `is_active` 那条。

### 交付

1. **单一构造点**：`pattern_skill_id(pattern_id)`（模块级，`:123`）成为全模块唯一
   的 `f"skill_{` 表达式，只服务两处：旧命名别名登记、空序列兜底。
2. **命中判定与建键共用同一身份**：新增 `_existing_template(pattern)`（`:355`），
   `_check_encapsulation` 改用它。两跳分工：按 `_canonical_template_id()` 直取覆盖
   正常路径；**指纹身份**那一跳（`_pattern_skill_similarity() == 1.0`）兜住
   旧命名模板 —— 老版本存成 `skill_<64 位全串>`，跨重启从落盘态恢复后仍在表里，
   只比规范 ID 会把它当新模板再封一遍。该 helper 此前生产零调用方（只被
   `test_skill_creation_governance.py:335` 直测），本单给它一个真实消费者。
3. **名字不再冒充身份**：`_generate_skill_name` 的单工具/空工具分支原样返回
   `skill_<pattern_id>`（与旧身份串同形），改
   为 `{tool}_skill_{pattern_id}` / `auto_skill_{pattern_id}`。只影响**新**模板名，
   已落盘模板名不动。
4. **`is_active` 命中即不重写**：命中路径直接 `return`，`_encapsulate_pattern`
   不再被调用，覆盖写消失；用例显式断言批准态与对象身份同时保持。
