# 015 · 封装模板去重键收敛

**Blocked by**: 014

## 目标

同一个模式被 observe 两次，不会第二次又产出一个待审模板；
已批准的技能不会每轮被打回"待审"。

## 证据（审计实测，行号待 implement 复核）

`evolution/skill_encapsulation.py` 内并存两套 ID 构造：

- 去重查找键：`:339` `f"skill_{pattern_id}"`，其中 `pattern_id` 为 64 位 hex 全串
- 规范落盘键：`:360` / `:379` `f"skill_{fingerprint[:16]}"`（16 位前缀）

两者**永不相等**（实测 `equal? False`）。后果：`AutoSkillBuilder.observe` 每轮都判"新模板"，
重新封装、把 `is_active` 重置为 False（`:376`）→ 上一轮已批准的模板本轮重回待审队列。
磁盘侧 `skill_service.py:339-343` 因 duplicate 早返回，`enabled` 未被覆盖 ——
即**内存态与磁盘态每次重启/每轮都漂移一次**。

生产者侧是真实的：`creation_governance.finish_task:218-236` 驱动 `builder.observe`，
所以这不是死码，是活着的自噬循环。

## 涉及层

- [x] 逻辑层：`skill_encapsulation.py`（ID 构造单点化）
- [x] 测试：`tests/unit/evolution/test_skill_encapsulation_identity.py`（新）

## 交付内容

1. 抽出单一构造函数 `skillTemplateId(fingerprint) -> str`（命名随 Neurova 风格），
   去重查找与落盘两处**共用它**；`pattern_id` 若语义不同则改名以显式区分，
   不允许两个不同含义的 ID 共用 `skill_` 前缀。
2. `is_active` 在"命中既有模板"分支上**不得被重置**（显式断言）。
3. 复核 `find_skills_for_context`（`:414`）零调用方的判定，登记进 017 删除清单。
4. 放大视角：grep 全仓 `skill_` + fingerprint/pattern_id 的其它拼接点（含
   `creation_governance.py:90-100`），同契约的其它命中点一并收敛或在本单登记。

## 验收标准

- 用例：同一模式连续 `observe` 2 次 → 模板集合大小不变、`is_active` 保持 True、
  第二次不产生 pending 项（当前必红：第二轮重新封装）。
- 用例：`resolve` 后内存模板 id 与 `SkillService` 磁盘 manifest id 逐值相等。
- 静态守卫：`skill_encapsulation.py` 内匹配 `f"skill_{` 的表达式只剩 1 处（grep 计数断言）。
- 回归：`tests/unit/evolution/test_skill_consolidation_structural_and_deadcode_p1p2.py` 仍绿。
