# 010 · 批准即生效（提案落到真实技能加载链）

**Blocked by**: 005

## 目标

管理员点"批准"后，**下一轮对话的技能列表里真的有这个技能**。
这是整条人工通道唯一有意义的验证点。

## 证据（审计实测）

- 写侧：`self_improvement_proposer.py:875-887` 把内容落 `.agents/skills/<t>/manifest.yaml`
  （目录建在 `:355/362-364`，回滚删在 `:888-899`）。
- 读侧：技能真实加载走 `SkillService`（`skills/skill_service.py:119`，
  目录 `data/agents/{id}/skills`，文件名 `manifest.json`，`_load_skills` `:148`）；
  运行时灌回经 `agent_core.py:906` → `skills/market_registry.py:242 restore_market_skills_from_service`；
  轮级经 `agent/chat_pipeline.py:568 → :304 restore_library_skills_for_turn`。
- 结论：`.agents` 后端**零读取方**（grep 仅命中 proposer 自身的写与删），
  且目录名 + 格式（`.agents` vs `data/agents/`、YAML vs JSON）**双双不符**。
  所以 `APPLIED` 状态只是一次文件写入，零运行时效应。
- 实测 `.agents/proposals/` 积压 90 个 JSON 全为 pending。

## 交付内容

1. `approve_and_apply` 的 skill_manifest 分支改调 `persist_synthesized_skill`，
   随后立刻 `restore_market_skills_from_service` 回灌 registry；
   回灌失败不得返回 `APPLIED`（**记账与动作不分家**，同 D5）。
2. action_definition / pr_patch 两类提案：若当前无对应生效通道，
   则 `approve_and_apply` 对其显式返回 `not_supported`（附原因），
   **不得**继续伪报成功。这是"禁止表面抹除"的反向要求——不得伪报成功。
3. 删除 `.agents` 写/删分支（`:355/362-364/866-899`），
   提案台账本体迁至 `data/agents/{agent_id}/proposals/`，并补 `agent_id` 字段
   （现状提案无 agent_id，`:239-256`，多 agent 结果混合不可溯源）。
4. 提案状态机持久化：`PENDING/APPLIED/REJECTED/ROLLED_BACK` 重启不丢
   （现状 `Path(".agents")` 为 CWD 相对 `:355`，换目录启动即"丢"）。
