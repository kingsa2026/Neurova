# 016 · 改进真正生效并跨重启存活

**Blocked by**: 014

## 目标

一次技能改进从"产出"到"下一轮对话真的用它"到"重启后还在"，全程无断点、无静默丢弃。

## 三个断点（前两个行号来自子代理审计，implement 前须复核）

**a. 评审闸默认开 + 有界队列静默丢**（据 spec §1 臂三补入，原 24 故事未单列）
`evolution/skill_review_gate.py:35` 默认开启，于是
`skill_experience.record_experience(source=improver/attribution)` 的产物一律进 `_pending_records`
（`skill_experience.py:121-136`），攒够阈值后才生效；队列有界 50，**溢出静默丢弃**。
后果：改进不回流到技能定义，且丢失不可观测。
→ 修法：溢出必须计数并进告警面（012 的 `/rsi/status`），生效判据走 `GateVerdict`（003）；
不改默认开关（改行为门控属产品决策，登记为待议，不在本单偷偷翻闸）。

**b. `config["improvements"]` 写了没人读**
`skill_improver.apply_improvement` 追加 `config["improvements"]` + 版本递增，
但全仓 grep 无上下文组装侧读取方。
→ 二选一（spec 故事 19 的判据）：让 `chat_pipeline` 的上下文组装真的消费它，或删除该写入。
不接受"写了没人读"的第三态。

**c. 进化史重启归零**
`closed_loop.py:712 bootstrap_evolution_persistence` 只挂 5 件
（tool_weights / pattern_miner / tool_lifecycle / experience_feedback / skill_experience_store）。
`AutoSkillImprover` 无 persistence mixin（仅 `to_dict:753`），builder 的 `_patterns/_templates` 未挂载
→ 改进史、变体、A-B 记录跨重启全清。

## 附带修正（一处一行）

`post_chat_pipeline.py:2578` 调归因未传 `agent_id`，落默认 `"default"`
（`skill_experience.py:506 → skill_attribution.py:152`），
而同函数 `:2572-2574` 的 ledger 按真实 agent_id 建 → 多 agent 下归因恒 0。

## 执行结果（2026-09-21 落地）

### 三断点复核：两真一错位，另长出两处更深的断

票面 a/b/c 逐条核实后，**a、b 成立、c 成立但根因比票面写的更靠后**；
另外在 c 的验证路径上实测抓到两处票面未列的断点（`A'`/`B'`），它们才是
"下一轮对话真的用它"这一目标真正的堵点，已在本单一并修掉。

| 编号 | 断点 | 实测 |
|---|---|---|
| a | 待审队列有界 50 静默截断（`skill_experience.py:132`） | 成立：`del self._pending_records[:-50]` 无计数、无日志、无状态面 |
| b | `config["improvements"]` 写了没人读 | 成立：全仓唯一提到该键的生产代码就是写它的那一处（grep 只剩 `skill_improver` 自身） |
| c | `AutoSkillImprover` 无持久化 ⇒ 改进史/变体/A-B 重启归零 | 成立：类不挂 `PersistedStateMixin`，`bootstrap_evolution_persistence` 只装配五件 |
| `A'` | **人工批准的自动技能落盘即 `enabled=False`** | 实测：`register_to_skill_registry` → `create_automatic_skill` → `_register_metadata` 的 `enabled` 只看"source 是自动产物且评审闸开"，**不看模板是否已过审批面** ⇒ 批准停在内存态，磁盘上那条永远停用，下一轮对话用不到 |
| `B'` | 重启后已批准技能不在 `_templates` ⇒ 同模式再被观察就重封一条待审 | 实测：`AutoSkillBuilder.__init__` 只认领 `builder_pending` 条目；新 builder 观察同一模式 → `list_pending_templates()` 又出现 `skill_952365df111e1763`（人工批准被撤销） |

`A'`/`B'` 与 010 是同一族缺陷的另一条臂：010 修的是"RSI 提案批准即装库"，
这两条修的是"封装臂批准即生效"。

### 交付

1. **a · 溢出不静默**：`PENDING_QUEUE_BOUND = 50` 常量收口 + `_pending_dropped`/
   `_pending_offered`（进队累计）两计数 + 溢出 `logger.warning`；计数随状态落盘，
   读回按 **max 而非覆盖**（旧文件不得把已发生的丢失抹成 0）。
   判据 `pending_pressure_verdict()` 走 `GateVerdict` 三态：`unevidenced`（从未有条目
   进过队 —— 通道有没有压力无从判断，不得报"无压力"）/ `failed`（丢弃 > 0）/ `passed`。
   进告警面：`RSIOrchestrator.get_status()` 新增 `experience_channel`（012 的唯一状态面，
   故 `GET /v1/governance/rsi/status` 一并可见）。
2. **b · 选"删除该写入"**（票面二选一）：`apply_improvement` 不再写
   `config["improvements"]`，改进留痕（type/changes/reason/expected_impact/applied_at）
   **折进 `revisions` 那一份** —— 每条修订既是回滚快照也是审计留痕，而 `revisions`
   本来就有读取方（`revert_last_improvement`）。
   为什么不选"让 `chat_pipeline` 消费它"：行为面已由经验库组合进技能描述承载
   （`apply_improvement` 末尾就写 applied 经验），再加第二个注入口等于把同一句话
   从两条通道灌进上下文 —— 本批一路在拆的就是"两处口径"。
3. **c · 改进史持久化**：`AutoSkillImprover` 挂 `PersistedStateMixin`，快照/读回
   四件（使用记录 / 改进史 / 变体 / 同签名去重集）；`closed_loop` 装配第六件
   （`NEUROVA_EVOLUTION_IMPROVEMENTS` → `data/evolution/skill_improvements.json`），
   关停 flush 同批带上。落盘触发点在 `record_usage` / `create_variant` /
   `apply_improvement` / `revert_last_improvement`，且全部**移到 `self._lock` 之外**
   （C-15 约定：磁盘 IO 期间不得把读路径串行挡住）。
4. **`A'` 修根因**：`human_approved` 沿 `publish_automatic → create_automatic_skill →
   _register_metadata` 单线穿透，只短路"自动产物注册即禁用"这一道门（判重、质量门、
   安全扫描一概不动）—— 与 010 给 `install_skill` 加的通道同构同名，不再造第二套词汇。
5. **`B'` 修在去重口**：`_existing_template()` 加第三跳 `_adopt_disk_template()`，
   按规范身份（014 的 `get_skill_info` 已解别名）从磁盘 manifest 认领并登记进内存表，
   `is_active` 跟随磁盘 `enabled`。选"按身份认领"而不是"放宽 `__init__` 扫描条件"：
   后者要靠 `author`/`source` 猜归属（实测 manifest 里 `author` 根本没落盘），
   而规范 ID 就是结构身份，猜错空间为零。
6. **附带修正**：`_step_rsi_iteration` 的 `agent_id` 上提到函数首行做**单源**
   （原先 SkillService 用真 id、MetaLedger 又现算一遍、归因调用干脆不传 ⇒
   `MetaLedger.list_records` 是 `WHERE agent_id=?`，非默认 agent 归因恒 0）。

### 反掩盖：既有替身把这两个缺陷洗成了绿

- `tests/unit/evolution/test_skill_attribution.py:91` 的 `_FakeLedger.list_records`
  **完全忽略 `agent_id`** ⇒ "调用方没传 agent_id"这类缺陷在该套件里不可能变红。
  本次用按 agent 过滤的台账替身（真语义 `WHERE agent_id=?`）重做断言。
- `_step_rsi_iteration` 的用例改**驱动真实步骤**并用 spy 捕获 kwargs，
  红讯就是 `{'registry': None, 'skill_service': <SkillService>, 'ledger': <MetaLedger>}` ——
  没有 `agent_id` 这一项。

### 票面未列、本单登记的遗留

- `AutoSkillBuilder` 的 `_patterns` **刻意不持久化**：它是证据库的派生缓存
  （`_update_pattern` 每次重读 `evidence_store.task_results()`），再落一份就是两套真相。
  代价如实记下：重启后某模式**必须再被观察一次**才会重算并封装。
- `create_automatic_skill` 的 `human_approved` 目前只有封装臂在用；遗传臂 / NL 合成臂
  的"注册即禁用"仍是无条件生效（它们没有 builder 这样的模板批准态）。
  是否给那两臂接人工批准入口属产品决策，**未擅自翻闸**。
- `data/evolution/skill_improvements.json` 是新增运行时文件（与既有五件同目录同风格），
  备份/清理清单若按文件名枚举需补一条。
