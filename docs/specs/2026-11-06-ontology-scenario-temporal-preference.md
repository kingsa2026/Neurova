# 场景压力测试：时间演变下的偏好追踪与推荐（Agent × Ontology 精准度实例 #2）

> 场景：客户X 于 8月1日 购买 20寸红色接发假发；9月20日 再次购买 16寸金色接发假发；期间剪短头发并染为金色。10月1日 客户再次购买接发假发时，Agent 应推荐什么？
>
> **正确答案：推荐 16寸金色接发**（匹配客户当前发型状态：短发＋金色）——不是 20寸红色（那是历史偏好，已被状态变更淘汰）。
>
> 定位：这是与方案推荐场景（`2026-11-06-ontology-scenario-trace-planB.md`）**互补的第二类压力测试**——上一个考"属性数值匹配＋多跳遍历"，这一个考"**时间序列偏好演变＋状态变更淘汰**"。两者合在一起覆盖 Agent 知识检索精准度的两大核心场景类型。
>
> **推演口径**：以当前 HEAD 代码为事实源（B8–B14 已落格），不假设任何未实现的改进。

---

## §1 为什么这个场景比方案推荐更难

| 维度 | 方案推荐场景（前例） | 本场景 |
|---|---|---|
| 核心能力 | 属性数值匹配（400M vs 200M） | **时间序列偏好演变**（旧偏好过期，新偏好生效） |
| 时间角色 | 静态（方案属性不变） | **动态**（客户发型在两次购买之间发生了变化） |
| 正确答案 | 唯一（方案B） | 唯一（16寸金色）但**理由是"最新状态匹配"而非"属性最大"** |
| 干扰项 | 方案A（属性不匹配） | **20寸红色假发**（属性不匹配且**时间过期**——双重理由淘汰） |
| 隐含前提 | 方案属性已结构化 | **客户发型状态变更**必须被感知——否则不知道旧偏好已过期 |
| 本体能力需求 | qualifier 数值比较＋多跳遍历 | **时间衰减排序＋状态追踪＋属性兼容匹配** |

关键差异：方案推荐场景里，"400M vs 200M"是**空间维度的属性区分**（两个方案同时存在，选哪个）。本场景里，"16寸金色 vs 20寸红色"是**时间维度的偏好演变**（先买A后买B，B代表当前偏好）——**检索系统必须知道时间顺序，并且知道后面的购买覆盖了前面的偏好**。

## §2 数据入库推演

### §2.1 两次购买会变成什么事实？

| 时间 | 事件 | 理想事实 | 现实概率 |
|---|---|---|---|
| 8月1日 | 客户X 购买 20寸红色接发 | `(客户X, purchased, 20寸红色接发假发)` valid_from≈2026-08-01 | ⚠️ 取决于这条信息是从对话、订单系统还是文档进来——对话进来走 graph_bridge LLM 抽取 |
| 9月20日 | 客户X 购买 16寸金色接发 | `(客户X, purchased, 16寸金色接发假发)` valid_from≈2026-09-20 | ⚠️ 同上 |
| 9月20日前后 | **客户X 剪短头发并染为金色** | `(客户X, has_hair_length, "短")`＋`(客户X, has_hair_color, "金色")` valid_from≈2026-09-20 | ❌ **极低**——这是对话中的状态描述，抽取 prompt 不引导提取"客户外观状态变更" |

### §2.2 关键断点（写入面）

| # | 断点 | 影响 |
|---|---|---|
| W-① | **购买记录的 valid_from 取决于摄取时机**——`admission.py` 的 `validFrom` 由调用方传入，但**对话中提到"上个月买了…"时，LLM 抽取的 `validFrom` 是对话时间而非购买时间** | 事实的 valid time 不可靠 |
| W-② | **"剪短头发染金色"这个状态变更没有结构化为事实**——它是对话中的描述，抽取 prompt 不引导提取"客户外观/偏好状态变更" | 系统不知道客户的偏好依据已改变 |
| W-③ | **两次购买之间没有时序关系被记录**——`purchased` 关系没有 `precedes`/`supersedes` 语义，系统不知道 9月的购买"取代"了 8月的偏好 | 无法推断"最新购买＝当前偏好" |

## §3 检索推演

### §3.1 10月1日小红/客户问"推荐接发假发"后检索管线逐步走

**Step 1：查询进入 hybrid_search_knowledge（四路 RRF）**

查询词大概率为"假发 接发 推荐"或"接发假发"。

| 路 | 匹配行为 | 20寸红色命中？ | 16寸金色命中？ |
|---|---|---|---|
| BM25 | "假发"/"接发" token 在两条购买记录/条目中都出现 | ✅ | ✅ |
| FTS5 | 同上 | ✅ | ✅ |
| 向量 | "接发假发推荐"语义与"购买接发假发"相近 | ✅ | ✅ |
| tfidf | 词频匹配 | ✅ | ✅ |

**RRF 融合后**：两条购买记录**排名几乎相同**——因为检索词对它们的匹配度完全一样（都是"客户购买接发假发"）。**没有任何时序信号区分先后。**

**Step 2：排序**

- 采纳先验：两条购买记录都没被采纳/拒绝过 → 中性
- 推导事实过滤：不涉及
- **无时间衰减因子**：`hybrid.py` 无 recency/time_decay（grep 零命中）→ 8月和9月的购买**权重完全相同**
- **无时序排序**：`hybrid.py` 的 ORDER BY 按 relevance/subject，**不按 recorded_at**

**Step 3：LLM 收到什么？**

LLM 收到两条记忆（扁平列表）：

```
[memory 1] "客户X 购买了 20寸红色接发假发"（8月1日的事实）
[memory 2] "客户X 购买了 16寸金色接发假发"（9月20日的事实）
```

**关键问题：LLM 不知道哪条更新。**

payload 里有 `confidence` 但没有 `recorded_at`/`valid_from` 时间戳字段——`_normalize_item` 不透传时间字段（`knowledge_retriever_adapter.py:507-538`）。即使 LLM 从 content 文本中猜到日期，也没有结构化的"这条比那条新"信号。

### §3.2 关键断点（读取面）

| # | 断点 | 对本场景的影响 |
|---|---|---|
| R-① | **无时间衰减因子**——8月和9月的购买在检索排序中权重完全相同 | 20寸红色和16寸金色排名不分先后 |
| R-② | **payload 不透传时间戳**——LLM 看不到哪条更新 | LLM 无法做时序推理（"第二条比第一条新所以选第二条"） |
| R-③ | **无"最新偏好"语义**——检索返回所有匹配事实，没有"只取该主体+谓词的最新一条"的模式 | 两条购买记录并列出现，LLM 自己猜哪条代表当前偏好 |
| R-④ | **客户状态变更不在库**——"剪短头发染金色"没有结构化为事实 | 即使推荐了16寸金色，**理由是"最新购买"而不是"客户当前发型是金色短发"**——推荐缺乏语义依据 |
| R-⑤ | **无产品属性→客户状态匹配**——即使知道客户当前是金色短发，也没有机制把产品属性（16寸/金色）与客户状态做兼容匹配 | 推荐缺乏"为什么这个产品适合你"的语义解释 |

## §4 回答质量评估

### §4.1 当前管线会怎么回答？

| 维度 | 预期表现 | 置信度 |
|---|---|---|
| **推荐 16寸金色还是 20寸红色？** | **不确定**——两条记忆排名相同，LLM 可能推荐任何一个，或者两个都提但不分主次。LLM 如果足够聪明，可能从 content 文本中的日期推断"后面的更代表当前偏好"——但这靠 LLM 的通用推理能力，不是系统保证 | ⭐⭐☆☆☆ 约 50%（等于抛硬币＋LLM 补救） |
| **能解释"为什么不推荐 20寸红色"吗？** | **大概率不能**——系统没有"客户已剪短头发染金色"的结构化事实，LLM 不知道偏好已变更 | ⭐☆☆☆☆ |
| **能说"因为客户现在是金色短发所以推荐16寸金色"吗？** | **不能**——同上，状态变更不在库 | ⭐☆☆☆☆ |
| **能列出客户的购买历史吗？** | 能——两条购买记录都在检索结果中 | ⭐⭐⭐ |

### §4.2 理想回答 vs 现实回答

**理想回答**（改进落地后）：

> 根据客户的购买历史和当前发型状态：
>
> **推荐：16寸金色接发假发**（与客户当前发型状态精确匹配）
>
> 推荐依据：
> - 客户最新购买（9月20日）：**16寸金色接发**——代表客户当前偏好
> - 客户当前发型状态：**短发＋金色**（9月20日后变更）
> - 16寸长度适配短发，金色与已染发色一致
>
> **不再推荐：20寸红色接发**（8月1日购买）——客户已剪短头发并染为金色，该产品的长度和颜色**不再匹配当前发型状态**。
>
> 如需同色系搭配，也可考虑16寸其他深色系接发产品。

**现实回答**（当前管线）：

> 根据知识库，客户之前购买过以下接发假发产品：
> - 20寸红色接发假发
> - 16寸金色接发假发
>
> 您可以考虑根据客户的发长和颜色需求来推荐合适的产品。
>
> （没有时序信号，没有状态变更感知，没有推荐倾向——LLM 只能模糊地"两个都提"）

## §5 针对性改进方案

### 改进 ①：时间衰减排序（检索面，解决 R-①）

**问题**：hybrid.py 四路 RRF 无时间衰减——所有事实按文本相关度平权排序。

**方案**：
1. `hybrid.py` 的 RRF 融合分中增补一个 `recency_boost` 项：`score *= (1 + recency_weight * exp(-days_since / half_life))`
2. `NEUROVA_RECENCY_WEIGHT` env 控制（**默认 0**＝纯 RRF 不变，§13 K-09 TD②"默认 0/关，先测后开"）
3. `NEUROVA_RECENCY_HALF_LIFE_DAYS` 控制半衰期（默认 30 天）
4. 需要 fact 行的 `recorded_at` 透传到检索结果 payload

**落点**：`hybrid.py`（RRF 融合处加乘法项）＋`knowledge_retriever_adapter.py`（payload 透传 recorded_at）

**效果**：9月的购买比8月的排名靠前——**不需要 LLM 推理，系统直接把旧的压下去**。

### 改进 ②：payload 透传时间戳（LLM 面，解决 R-②）

**问题**：`_normalize_item` 不透传 `recorded_at`/`valid_from`——LLM 看不到时间。

**方案**：`_normalize_item` 增加两个字段：`recorded_at`（ISO 字符串）和 `valid_from`。LLM 收到后可以做时序推理。

**落点**：`knowledge_retriever_adapter.py:507-538`（_normalize_item）＋`injector.py`（把时间戳以 `[日期: 2026-09-20]` 前缀注入 prompt）

**效果**：LLM 收到 `[2026-09-20] 客户X购买了16寸金色接发` 和 `[2026-08-01] 客户X购买了20寸红色接发`——能自行判断后者更旧。

### 改进 ③："最新偏好"语义（检索面，解决 R-③）

**问题**：检索返回所有匹配事实并列，没有"只取最新一条"的模式。

**方案**：
1. `KnowledgeFactStore` 增 `latestFactsByPredicate(agentId, predicate, tenantId)` — 按 subject_key 分组取 `recorded_at` 最新的那条
2. `knowledge_retriever_adapter` 增"偏好追踪模式"：当检索词命中"购买/偏好/选择"类谓词时，用 latestFactsByPredicate 替代全量返回
3. 或者在 payload 上标记 `is_latest_for_subject_predicate: true/false`

**落点**：`knowledge_facts.py`（新查询方法）＋`knowledge_retriever_adapter.py`（模式切换）

**效果**：检索"购买"只返回每个客户的**最新一条**购买记录——20寸红色自动消失，16寸金色自动突出。

### 改进 ④：状态变更追踪（写入面＋语义层，解决 R-④/R-⑤）

**问题**：客户"剪短头发染金色"这个状态变更没有结构化为事实——系统不知道偏好依据已改变。

**方案**：
1. **抽取扩展**：LLM 抽取 prompt 增加"客户状态变更"指令——识别外观/偏好/需求的变更描述，提取为 `(客户X, has_hair_state, "短发金色")` 形态的事实
2. **状态关系登记**：`has_hair_state`/`has_hair_length`/`has_hair_color` 等走 B8 候选面 → 审批后成为正式关系
3. **状态覆盖语义**：同一主体的状态类关系（has_hair_state 等）天然是"最新覆盖旧值"——`conflict_judge` 的 `most_recent` 策略天然适用
4. **产品属性结构化**：假发产品也需要属性结构化——`(假发16寸金色, has_length, "16寸")`＋`(假发16寸金色, has_color, "金色")`
5. **属性兼容匹配**：检索命中产品后，按产品属性 vs 客户当前状态做匹配打分——长度匹配＋颜色匹配 → 高分推荐

**落点**：`graph_bridge.py`（抽取 prompt）＋`relation_candidates`（审批）＋新模块 `product_state_matcher.py`（兼容匹配）

**效果**：
- 库里有了 `(客户X, has_hair_state, "短发金色")` ——— 系统知道客户当前状态
- 库里有了 `(假发16寸金色, has_length, "16寸")` + `(假发16寸金色, has_color, "金色")` ——— 产品属性结构化
- 匹配逻辑：产品属性 == 客户状态 → 推荐；不匹配 → 不推荐或降权

### 改进 ⑤：时间线注入（LLM 面）

**问题**：LLM 收到的是无序记忆列表，不是时序叙事。

**方案**：`injector.py` 的知识注入段，对有 `recorded_at` 的条目**按时间倒序排列**并加时间前缀：

```
[2026-09-20] 客户X购买了16寸金色接发假发
[2026-08-01] 客户X购买了20寸红色接发假发
```

LLM 收到倒序时间线后，通用推理能力足以判断"最新的代表当前偏好"——**不需要本体推理，只需要把时间信号透传给 LLM**。

**落点**：`injector.py` 知识注入段＋`knowledge_retriever_adapter.py` payload 透传。

**效果**：LLM 收到倒序时间线，几乎必然推荐16寸金色（最新的）——这一条改动就足以解决本场景的核心推荐问题。

## §6 实施优先级

| 优先级 | 改进 | 改动量 | 效果 |
|---|---|---|---|
| **P0** | ⑤ 时间线注入（payload 透传＋倒序排列＋时间前缀） | **极小**（~20 行） | LLM 收到时间信号 → 大概率推荐正确 |
| **P0** | ② payload 透传时间戳 | 极小（与⑤合并） | 同上 |
| **P1** | ① 时间衰减排序 | 小（~15 行，env 默认 0） | 系统层面压旧升新 |
| **P1** | ③ "最新偏好"查询 | 小（~30 行，新查询方法） | 结构化解决"只取最新" |
| **P2** | ④ 状态变更追踪＋产品属性匹配 | 中（抽取 prompt＋候选审批＋匹配模块） | 语义级推荐（"因为客户是金色短发所以推16寸金色"） |

**最小改动路径**：⑤＋②（~20 行改动）就能让 LLM 收到时间信号，大概率推荐正确。④ 是语义级提升但需要抽取 prompt 和候选审批配合。

## §8 与 K-09（§6-568）的关系

本场景的核心诉求——**时间衰减排序**——就是 K-09 TD② recency 的具体实例。§6-568 登记时说"hybrid.py 无 recency/time_factor（grep 零命中）"——本场景证明了这项缺失的实际影响：**同分排序导致过期偏好与当前偏好并列，Agent 推荐歧义**。

§6-568 已登记"下一步最小动作"——本场景可以做为 recency 改进的红灯判据：

- 红灯：`test_recencyBoostRanking`——同主体两条购买（间隔 50 天），`NEUROVA_RECENCY_WEIGHT=0.5` 时**最新的排名必须高于最旧的**
- 绿灯：hybrid.py 的 RRF 融合加乘法项后判据通过
