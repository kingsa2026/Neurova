# 010 · 三条主经验臂同吃服务端客观票据

**Blocked by**: 002, 003, 004

## 目标

把仓库里唯一真门的证据源接过来：`creation_governance` 的逐工具成败票据
（`:144-155` 失败粘性 `MIN(success)`、`:182-183` ≥3 独立任务成功、
`:209-215` `is_policy_denial` + `result is not None` + `success is True` 三重核验）。
今天结晶器 / `ExperienceFeedback` / EKB 三条臂都不查它。

## 涉及层

- [x] 逻辑层：三条臂的成败来源统一改查票据存储；模型自述与关键词降为"无票据时"的
  `unevidenced` 旁路（D1）
- [x] 装配层：经 `agent_core.py` 生产构造点传递票据句柄（禁止测试内手工注入）
- [x] 观测层：无票据入库条数进 008 指标
- [x] 测试：端到端

## 验收标准

- 伪造一轮"自述成功但无票据" ⇒ 条目落库且标 `unevidenced`，并被 007 降权
  （当前必红：它会被当成成功票）。
- 有票据且含失败 ⇒ 条目不得为成功（002 的跨臂一致性）。
- 反向锁：有票据的正常成功轮不得被误标无证据。

## 开工前置（本轮核查到的三个硬点，逐条附证据）

本轮完成 006/007/008/017 后剩 010/013/009/015/016；010 是其中最早的一张，
但它不是"照着票改三处"就能收口——先记下三个必须一起处理的硬点：

1. **句柄来源不是构造函数**。票据存储的唯一入口是
   `SkillService(agent_id=...).creation_evidence`（`creation_governance.py:226-231` 的
   `finish_task` 就是这么拿的），它按 agent 现取、无全局单例。三条臂
   （`PatternCrystallizer` / `ExperienceFeedback` / `EKB`）目前都不持有它 ⇒
   新增装配点应在 `post_chat_pipeline._step_record_experience`
   （它已经同时握着 `self._agent`、本轮工具记录与 002 的 `tool_success`），
   而不是在 `agent_core.py` 里加形参——`agent_core.py` 有尺寸棘轮
   （基线 2159 行，净增即红），装配逻辑必须落独立模块。
2. **形状对齐是这张票真正的雷**。按结构身份查票据要用
   `structure_key(steps)`，而 `normalize_steps` 要求 `params` 是 **dict**
   （字符串直接 `ValueError: Invalid skill tool/params`）；本轮的 `tool_call`
   记录里 `params` 是 LLM 原始参数**字符串**（`agent/loops/base.py:196-201` 的
   `_tc_arguments`），写入侧 `record_tool_execution(tool_name, params, …)` 收的才是
   解析后的 dict。⇒ 查票据前必须 `json.loads`；且**解析失败不得静默当成"无票据"**
   ——那会把每一轮都标成 `unevidenced`，制造比现状更糟的假象（红测试必须覆盖这条）。
3. **三态语义要重排，不是并排**。接入后：有票据 ⇒ 票据结论覆盖一切自述
   （含 002 从 `tool_result.success` 得到的值，因为票据还额外要求
   `result is not None` 且非 `is_policy_denial`，见 `:196-202` 的三重核验）；
   无票据 ⇒ 002 的 `tool_result` 聚合值降为**旁路证据**，仍标 `unevidenced`
   入库（D1），关键词分类（`experience_feedback.classify_outcome`）退到最后一格，
   且其结果**不得再进 `success_rate` 分母**（005 已经这样处理观察票，口径要一致）。

验收不变（票面四条），另加两条本轮推导出的必测项：
- 参数串解析失败 ⇒ 判"票据不可读"并告警，不得判"无票据"；
- 有票据为 True 但本轮 `tool_result` 含 False ⇒ 取票据还是取记录必须有唯一答案
  （按第 3 点：取票据，因票据口径更严）。

### 关键语义（写给后续工单，别再重推）

- 票据是**该结构在独立任务上的历史聚合**，不是本轮回执的别名：本轮那张票要到
  `chat_pipeline.execute()` 收尾的 `finish_task` 才落库，**晚于 post-chat**。
  所以"票据覆盖本轮"覆盖的是"这条序列此前被服务端确证到什么程度"。
- `lookup ∈ {evidenced, absent, unreadable}` 描述的是**取证过程**；判据三态仍复用
  `GateVerdict(passed/failed/unevidenced)`，符合 D5，没发明第二套三态。
- `unreadable` 落库仍是 `unevidenced`（库里确实没有确证证据），但与 `absent` 在
  观测面（step data + WARNING）分得开。没做成第四种 DB 列值，是因为它会从 008 的
  `unevidenced_ratio` 算式里隐身 —— 那正是 008 刚删掉的假观测面形态。
