# Agent × Ontology 知识检索精准度全面升级方案（统一版）

> 定位：本文整合检索精准度分析（三桥）、方案推荐场景推演、假发推荐场景推演三份前序分析，给出**一份**覆盖全部已识别场景类型的统一改进方案。
> 事实源：`neurova/agent/chat_pipeline.py`、`knowledge_retriever_adapter.py`、`hybrid.py`、`derivation_citation.py`、`context/injector.py`、`foundation/knowledge_facts.py`、本体栈升级计划（B1–B14 已落格 v29–v34）。
> 前序文档（并入本文后退役）：`2026-11-06-ontology-retrieval-precision-plan.md`（三桥分析）、`2026-11-06-ontology-scenario-trace-planB.md`（方案推荐场景）、`2026-11-06-ontology-scenario-temporal-preference.md`（假发推荐场景）。

## §0 一页结论

**Agent 检索本体知识库"能找到"但"找不准、注入'知有但不知其义'"。**

根因不在本体语义栈本身——B8–B14 落格后，写面已完备（类型层级/关系特征/条件类/qualifier schema/双时态/推导账本/形状校验）。根因在**从用户问题到 LLM 上下文之间缺了四层能力**，导致本体的语义能力只在写入时生效（校验/物化），读取时仍然是"纯文本相似度 + 扁平列表 + 无时间信号"。

**四层缺失 → 五项改进 → 三个场景全部覆盖。**

| 层 | 缺什么 | 解决什么 | 核心改动 |
|---|---|---|---|
| L-A 语义桥 | 用户语言→本体术语的映射 | 别名/异写/条件类/类型层级对查询词零影响 | 开闸 5 个默认关＋新增查询扩展模块 |
| L-B 检索策略 | 数值比较/多跳遍历/最新偏好 | "400M 的方案""最新的购买""关联的客户"走不通 | 检索结果后处理＋关系遍历 |
| L-C 时间维度 | 无时间衰减/无时序排序/无状态变更追踪 | 过期偏好与当前偏好同分并列 | recency 权重＋payload 时间戳＋最新覆盖 |
| L-D 注入结构 | LLM 收到扁平文本不是结构化视图 | 推导标注/类型层级/qualifier/时间线在管道里丢失 | 上下文构建器按本体结构组织 |
| L-E 反馈环 | 用户纠正不回流到检索 | 检索 miss 持续 miss | 纠正→候选→审批→命中闭环 |

## §3 各层详设

### §3.1 L-A 语义桥

**目标**：用户语言经过归一/扩展/澄清后，检索词能精确映射到本体术语和事实。

| # | 改进 | 类型 | 落点 | 红灯判据 |
|---|---|---|---|---|
| A-1 | **开闸查询归一**：`NEUROVA_KB_QUERY_NORMALIZE=on` | 开闸 | env | 别名命中测试 |
| A-2 | **开闸歧义澄清**：`NEUROVA_KB_AMBIGUITY_CLARIFY=shadow→on` | 开闸 | env | shadow 读数 |
| A-3 | **本体感知查询扩展**（新模块）：查询词→别名归一→子类展开（`subjectKeysOfType`）→条件类实例注入→关系邻域（`activeFactsForPredicate`）→扩展词追加进 searchQuery | 新增 | `ontology/query_expander.py` | "高风险订单"→扩展出 HighRiskOrder 实例集 |
| A-4 | **概念别名归一**（扩 B8 的 `resolveRelationAlias` 到 concept）：查询词命中 concept 别名→替换为 canonical_label | 扩展 | `term_registry.py` | concept 别名命中 |

### §3.2 L-B 检索策略

**目标**：检索结果不只是"文本最相似的"，还要"语义最相关的、数值最匹配的、路径最短的"。

| # | 改进 | 类型 | 落点 | 红灯判据 |
|---|---|---|---|---|
| B-1 | **qualifier 数值过滤**：hybrid 返回后按查询中的数值条件对 qualifier 值做后过滤 | 新增 | `hybrid.py` 或 `query_expander.py` | "400M"过滤掉"200M"的事实 |
| B-2 | **条件类数值原子**：限制原子从字符串 hasValue 扩展到数值 gte/lte | 扩展 | `rule_engine.py` | `LargeScalePlan = Plan ∩ has_database_size >= 400M` 自动归入 |
| B-3 | **多跳关系遍历**：检索种子→沿关系走 1–2 跳→按 domain/range 剪枝→补充邻域事实 | 新增 | `graph_bridge.py` 或新模块 | 方案B→derived_from→方案A→A 的属性进 context |
| B-4 | **"最新偏好"查询**：`latestFactsByPredicate(agentId, predicate, tenantId)` 按 subject 分组取最新 | 新增 | `knowledge_facts.py` | 两次购买只返回最新一条 |

### §3.3 L-C 时间维度

**目标**：时间成为检索排序和 LLM 注入的一等信号。

| # | 改进 | 类型 | 落点 | 红灯判据 |
|---|---|---|---|---|
| C-1 | **recency 权重**：RRF 融合分乘以 `1 + weight * exp(-days/half_life)` | 扩展 | `hybrid.py` | 同主体两条购买（间隔 50 天），`NEUROVA_RECENCY_WEIGHT=0.5` 时最新的排名 > 最旧的 |
| C-2 | **payload 透传时间戳**：`_normalize_item` 增加 `recorded_at`/`valid_from` 字段 | 扩展 | `knowledge_retriever_adapter.py:507-538` | payload 含时间戳 |
| C-3 | **时间线注入**：injector 知识段按 `recorded_at` 倒序排列＋时间前缀 `[2026-09-20]` | 扩展 | `injector.py` | prompt 含 `[日期]` 前缀且倒序 |

### §3.3 L-D 注入结构

**目标**：LLM 收到的不是扁平文本列表，而是**按本体结构组织的知识视图**。

| # | 改进 | 类型 | 落点 | 红灯判据 |
|---|---|---|---|---|
| D-1 | **类型分层注入**：检索结果按 `category`（本体类型）分组 → prompt 以标题分区（"## 订单事实\n…"） | 新增 | `context/ontology_context_builder.py` | prompt 含类型标题 |
| D-2 | **推导标注可见**：`derivation.derived=True` 的条目在 prompt 中前缀 `[推导:规则 R]` | 消费 | 同上 | prompt 含推导前缀 |
| D-3 | **类型层级上下文**：注入当前查询涉及的类型子树 | 新增 | 同上 | prompt 含 "HighRiskOrder ⊑ Order" |
| D-4 | **解释链可引用**：`premiseCount > 0` 的条目附 `(由规则 R 从 N 条前提推出)` | 消费 | 同上 | prompt 含推理依据 |
| D-5 | **qualifier 透传**：qualifier 业务限定以键值对注入 | 消费 | 同上 | prompt 含 `channel: web` |
| D-6 | **双时态标注**：`valid_from/valid_until` 透传为 `[有效期: 2026-01-01 ~ 2026-06-30]` | 消费 | 同上 | prompt 含有效期 |

### §3.4 L-E 反馈环

| # | 改进 | 类型 | 落点 | 红灯判据 |
|---|---|---|---|---|
| E-1 | **开闸脱靶登记**：`NEUROVA_KB_MISS_CAPTURE=on` | 开闸 | env | 0 命中落候选 |
| E-2 | **采纳先验**：已有 ✓ | — | — | — |

## §4 场景验证（改进前 vs 改进后）

### §4.1 场景一：方案推荐（属性匹配＋多跳）

| 推荐方案 | ⭐⭐⭐ B（BM25 词面＋LLM 推理，约 70%） | ⭐⭐⭐⭐⭐ B（数值过滤确定性命中） | L-B B-1/B-2 |

| 采纳记录 | ⭐⭐ 取决于 adopted 是否落库 | ⭐⭐⭐⭐ 事实在库可引用 | — |

### §4.2 场景二：假发推荐（时间偏好＋状态变更）

> 客户X 8月买20寸红色→9月买16寸金色（剪短染金）→10月再买接发，推什么？

| 维度 | 改进前 | 改进后 | 驱动层 |

## §6 不做什么（边界声明）

| 项 | 理由 |
|---|---|
| 把本体术语向量化（term embedding） | 术语量小（<1000），别名＋层级＋查询扩展已够归一；第四路检索成本>收益 |
| SPARQL 查询引擎 | 评测报告不采纳；策略 B-3 的关系遍历覆盖主用途 |
| LLM 自主规划多跳（ReAct 式） | 需要工具调用循环；策略 B-3 的确定性遍历更可靠 |
| 重开 011 两池交织 | 已否证（recall@5 0.8555→0.7604） |
| 全量 prompt 重写 | 只在本体知识命中时追加结构化段 |
| K-09 时间面四项合并到本方案 | 已登记 §6-568 为待立项；本方案的 L-C 层覆盖其核心诉求（recency＋时间透传），FTS 加列/导出源时间属独立迁移 |
| 一次性翻转全部默认关开关 | §6"不打包全开"纪律：逐项 shadow→on，A/B 确认后逐个翻 |
