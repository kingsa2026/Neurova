## 0. 结论摘要

**适用性判定（先于一切对照）**：该标准第 1 章明示适用范围为"开展**标准数字化活动**中**标准本体的构建**"——它规定的是构建**标准文献领域本体**时应有的实体类型集（第 6 章：标准/相关方/领域类别/要素/层次/信息单元/对象/特性/约束逻辑/行动/外部资源等）、关系类型集（第 8 章）与建模方法（第 5 章），约束对象是**本体的内容**，不是本体建模工具软件。Neurova 是通用 AI Agent 知识平台，本体面服务任意领域建模，不在该标准的强制适用对象之列——**"Neurova 是否符合 GB/T 48000.3-2026"作为合规命题不成立**。

真正可回答的是两个衍生问题，本文档逐一给出读数：

1. **机制对齐**：Neurova 的本体建模机制（类型系统、约束、导出、扩展、构建流程）能否承载"按该标准建模一个标准本体"——**15 项可测对照：9 符合 / 4 部分符合 / 2 差距**（§2 对照表；其中构建流程一项的逐步评测见 §6），流程三阶段全部有机制承载，概念提取 4 步逐条对上。
2. **领域就绪**：若业务要在 Neurova 内承载"标准类知识"（标准数字化场景），缺什么——**5 项差距 G1–G5**，补齐设计见 §3，批次切分见 §4（建议三批：P1 两个数据面缺口、P2 两个导出/扩展面缺口、P3 一个可选领域包）。

一句话读数：**机制层基本够用（SHACL 约束、Turtle/OWL/JSON-LD/PROV 导出、租户分区、数据驱动类型系统、关系候选挖掘都有真实现），差距集中在"本体元数据描述项"（Definition/基本数据类型/等价类/命名空间）四块元层面＋一个可选的领域种子包**。

## 3. 差距与补齐设计（G1–G5＋G6 待核）

设计通则（每项都遵守）：

- **单一事实源**：不新造第二份类型系统/校验/导出——所有新元数据进 `ontology_terms` 现有列族或既有导出面，校验收编进 `validation.py`/`shapes.py` 既有 findings 流，导出进 `export/` 既有函数。
- **零停机迁移**：`ontology_terms` 加列一律新起 `_SCHEMA_Vn`（ALTER TABLE ADD COLUMN，不删不改 v8 SQL 文本），经 `core/db_migration.py` 注册表登记 PRAGMA user_version。
- **保守写入**：沿用注册表哲学——缺元数据不算违规，`unregisteredFindings()` 如实报出；不把"没填 Definition"做成写入阻断。
- **前端对齐**：本体工作台 `StudioTermsSection.vue` 表单与 API 模块同步扩字段；11 语言 i18n 齐补。

### G1 Definition（定义）描述项

- **动机与根因**：表 1/表 2 都把 Definition 列为定义方式的必要描述项（"给出实体含义"）；本仓术语只有 label 无定义，导出的 OWL/Turtle 里类与属性没有 `rdfs:comment`/`skos:definition`，互操作场景（外部本体工具读导出件）拿不到语义。
- **设计**：
  - 数据面：`_SCHEMA_V{n+1}` 加 `definition TEXT NOT NULL DEFAULT ''`（中文定义，单列即可——多语言定义暂不做，Label 的多语言先例 `labels_json` 若有真实需求再演进，避免过度设计）。
  - API 面：`knowledge_ontology.py` 术语 upsert/查询的 DTO 加 `definition` 字段（只增不改，存量缺省 ''）。
  - 导出面：`export/owl.py` 每条类/属性声明行追加 `rdfs:comment "<definition>"@zh`（有值才写）；Turtle 子集语法已支持 `"文本"@lang` 字面量，无需扩语法；jsonld 导出同步加 `rdfs:comment`。
  - 前端面：`StudioTermsSection.vue` 术语表单加"定义"文本域（与 label 并列），列表行可选展示截断。
- **迁移**：一版 ALTER＋存量回填脚本不需要（缺省 ''，未填即"这一维没依据"）。
- **测试口径（先红后绿）**：红——term_registry 单测断言 definition 列存在且 upsert/读回一致（现 schema 无此列即红）；导出单测断言有 definition 的术语导出行含 `rdfs:comment`、无值不输出。绿——两测转绿＋`unregisteredFindings` 不因缺 definition 变红（保守写入回归）。
- **影响面**：`term_registry.py`、`knowledge_ontology.py`、`export/owl.py`、`export/jsonld.py`、`turtle.py`（无需动语法）、`StudioTermsSection.vue`、`api/modules/ontology.ts`。工作量 ≈ 0.5 人日。

### G2 数据属性基本数据类型枚举

- **动机与根因**：5.5 表 3 的 5 类（布尔/日期/数值/文本/URL）是数据属性值域的类型约束；现状 range 只能指向实体类别（range_kinds），"这个 property 的值是日期型"无处声明，导出面也因此无法产出 `rdfs:range xsd:date` 之类断言。
- **设计**：
  - 数据面：新 `_SCHEMA_V{n+1}` 加 `datatype TEXT NOT NULL DEFAULT ''`——**仅对 kind='property' 有意义**，取值闭集 `('boolean','date','number','text','url')`（常量单点定义在 `term_registry.py`，与 `_TERM_KINDS` 并列）。
  - 校验面：`validation.py` 收编一条固定校验——kind='property' 且 datatype 不在闭集 → 写前 finding（violation）；kind≠'property' 且 datatype 非空 → warning（提示填错位置）。同时补上 #10 待核项：**kind='property' 声明 symmetric/transitive/inverse_of → violation**（7.2.2 d) 数据属性不应具三性质）。
  - 导出面：`export/owl.py` 补 kind='property' 分支：`rdf:type owl:DatatypeProperty`＋`rdfs:range xsd:boolean|xsd:date|xsd:decimal|xsd:string`（url→`xsd:anyURI`）；同时修 G6——现有循环缺 property 分支的_declaration_遗漏。
  - 前端面：StudioTermsSection 表单在 kind=property 时显示数据类型下拉（5 项闭集），ontology.ts 类型同步。
- **迁移**：一版 ALTER；存量 property 术语 datatype 缺省 ''（未约束态，不算违规）。
- **测试口径**：红——property 术语带非法 datatype 写入被拒（violation finding）；property 术语带 symmetric 被拒；导出含 `owl:DatatypeProperty`＋`rdfs:range xsd:*` 断言。绿——转绿＋存量无 datatype 的 property 导出不受影响（只增不改契约）。
- **影响面**：`term_registry.py`（列＋闭集常量）、`validation.py`、`export/owl.py`、`StudioTermsSection.vue`、`api/modules/ontology.ts`。工作量 ≈ 1 人日。

### G3 等价类（owl:equivalentClass）语义

- **动机与根因**：表 1 第 8 项 Equivalent Class 要求可声明等价类；现状 `external_iris_json.skos_exactMatch` 是"外部精确匹配"的**导出改写**（owl.py `_iri` 用外部 IRI **替换**本仓 IRI），既不是等价断言、也丢了本仓 IRI——严格说现状导出的是"换名"不是"等价"。
- **设计**：
  - 数据面：不改 schema——`external_iris_json` 的键闭集扩一档：现有 `skos_exactMatch` 语义保留为"同义对齐"，新增键 `equivalentClass`（或统一改造，见待拍板 ①）。
  - 导出面：`export/owl.py` `_iri` 改为**不再替换**、始终输出 `kbg:` 本体 IRI，等价/同义改为独立断言行：`kbg:X owl:equivalentClass <外部IRI>`（类）与 `skos:exactMatch`（属性/关系）——消除"换名丢本体"的语义损失。**这是行为变更**：外部消费方若依赖"导出即外部名"需知悉（契约从替换改附加，见待拍板 ②）。
  - 前端面：StudioTermsSection 的外部 IRI 编辑区按键名区分"等价类/同义匹配"两种映射。
- **测试口径**：红——导出含 `owl:equivalentClass` 断言且本仓 IRI 不被替换；绿——转绿＋`_iri` 反查（knowledge_ontology_iri）往返不回归。
- **影响面**：`export/owl.py`、`export/jsonld.py`、`knowledge_ontology_iri.py`（若有反向假设）、`StudioTermsSection.vue`。工作量 ≈ 0.5 人日。

### G4 IRI 命名空间机制（第 9 章 a)

- **动机与根因**：扩展原则要求扩展词汇用**新命名空间**；现状全仓固定 `kbg:`＋一个 `NAMESPACE` 常量，领域包（G5）的词汇若也压进 `kbg:`，则"标准本体词汇"与"平台内置词汇"在 IRI 层不可区分。
- **设计**：
  - 数据面：不改 `ontology_terms` schema——命名空间是术语的属性：新加列**不需要**，直接复用 `external_iris_json`？不行，那是外部映射。加 `_SCHEMA_V{n+1}` 列 `namespace TEXT NOT NULL DEFAULT ''`——空 = 缺省 `kbg:`（存量不动）；非空 = 术语的 IRI 前缀段（如 `so:` 标准本体包）。前缀到 IRI 的映射表单点放在 term_registry 常量 `NAMESPACE_REGISTRY: dict[str, str]`（代码级单点；若未来需要运行时可配再升数据面）。
  - 校验面：namespace 非空时必须在 `NAMESPACE_REGISTRY` 闭集内，否则写入 finding（violation）——防止任意造前缀。
  - 导出面：`turtle.py`/`export/owl.py` 的前缀行与 IRI 生成函数按 `namespace` 取前缀（`@prefix so: <...>`），`knowledge_ontology_iri.py` 的解析按注册表反查多前缀。
  - 前端面：术语表单命名空间下拉（缺省 kbg:，包导入时自动带）。
- **测试口径**：红——带未注册 namespace 写入被拒；多前缀 Turtle 导出含多行 `@prefix` 且自家解析器读回；kbg: 解析端点对新前缀 IRI 往返。绿——转绿＋存量全部缺省 kbg: 行为逐字节不变。
- **影响面**：`term_registry.py`、`validation.py`、`turtle.py`、`export/owl.py`、`export/jsonld.py`、`knowledge_ontology_iri.py`、`StudioTermsSection.vue`。工作量 ≈ 1 人日。**本项是 G5 的前置**。

### G5 标准本体领域包（可选种子，第 9 章扩展方式的示范载体）

### G6（已核，2026-11-10）OWL 导出的 property kind 分支缺失——登记为导出面潜在坑，不实施

核验结论：**存量零、路径可达、缺口面单点**——按本节原文口径归入"导出面潜在坑"，不单独立项；G2 落地时其导出分支设计已含 property→`owl:DatatypeProperty`，届时自然消除。

- **存量**：`ontology_terms` 实库（`data/knowledge/knowledge_facts.db`，只读查询）各租户 kind 分布仅 `default` 租户 concept 16 行＋relation 20 行——**kind='property' 存量为 0**，今天的导出件没有实际丢数据。
- **路径可达**：kind 闭集 `_TERM_KINDS = ("concept", "relation", "property")`（`term_registry.py:25`），`register()` 对闭集外报 ValueError（:213-214）——'property' 是**合法登记类别**；`POST /ontology/terms`（admin 门，`knowledge_ontology.py:476`）→ `_registerTerm`（:425）透传 `body.kind`，创建 property 术语无任何阻断。
- **缺口面单点**：`export/owl.py` 声明循环仅 concept→Class、relation→ObjectProperty 两分支（:49-56）——property 术语一旦存在，OWL 导出件里无声明显。`export/jsonld.py` **不受影响**（term 行统一 `@type: kbg:Term`＋`kind` 字段直出 :34-39，无 kind 分支即无遗漏）；Turtle 导出走同一声明面（待 G2 时一并核）。
- **触发条件与爆炸半径**：仅当 admin 显式登记 property 术语后，该术语在 OWL 导出（`GET /ontology/export.owl`）中缺失——消费方（外部本体工具）拿到的公理集不完整；本仓自解析往返不受影响（Turtle/JSON-LD 均可见）。

### 6.3 评测结论

1. **流程面判定：✅ 机制符合。** 45256 的构建流程框架（资源准备 → 概念提取 → 本体建模 → 知识提取 → 质量评估）在 Neurova 内**每一阶段都有真实现承载**，概念提取 4 步**逐条实名对上**，且若干环节（候选审批、原子成版闸、逐字可核闸、只追加审计账）比标准文本的流程性要求更严格。
2. **与 G1 的呼应**：quality.py 的质量判据里**已经列了"缺定义"**——即本仓质量面自察到了 Definition 元数据缺口（§2 #4 的 G1 差距），流程与元数据两层互证。
3. **局限（不因结论利好而隐藏）**：14 步中 10 步（本体建模＋知识提取两部分内）未能逐步实名对照，判定粒度是"该阶段全部要求在本仓有明确承载面"，不是逐条核对；正式文本取得后（openstd 在线预览人工阅读或正式渠道文本）应补一版逐步对照，预期只影响表格行数、不影响判定方向。
4. **流程面不新增补齐项**：§3 的 G1–G5 已覆盖流程对照暴露的全部缺口（元数据类），流程机制本身无需立项。
