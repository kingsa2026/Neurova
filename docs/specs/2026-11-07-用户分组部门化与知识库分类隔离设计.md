# 用户分组部门化（含子部门）与知识库分类隔离设计（2026-11-07）

- **来源**：用户点单——知识库分类可自定义、在用户分组中绑定、用户分组承担部门划分（含子部门）；租户A（研发）只见研发分类的本体与知识库，租户B（客服）只见客服分类；**部门名下 agent 同样严格受限**（仅能获取本部门有权限的知识库与本体）；前端 UI 按变化做功能对齐。
- **纪律**：设计先行 → 拍板 → 分批实施（每批独立红绿＋提交＋台账）；单一事实源（不新造第四套组分类学、不新造租户实体）；契约只增不改（存量条目/用户行为不变）。
- **台账**：设计落格随本批办理（§6-52x，落笔时现查尾号）。

## 0. 结论摘要（现状 → 缺口 → 方案）

**现状（全部现场核实，见 §1）**：

1. **"锁已装好"**：`tenant_id` 已是全链数据分区键——知识条目 `can_view`/`visible_items` 租户先行且 admin 不跨租户（`repository.py:1086-1097/1138`）、FTS 强制 `tenant_id=?`（`fts_index.py:224-226`）、facts/subjects/conflicts/baselines 唯一索引含 tenant（v20/v23）、本体 v25 起主键 `(tenant_id, term_id)`、JSON 图谱 per-(agent,tenant) 目录（`manager.py:1222-1261`）、图走查锚点/递归段双键（`graph_walk.py:171-193`）。
2. **"无钥匙"**：tenant 无签发链——登录 JWT 不签 tenant claim（`api/endpoints/auth.py:289-298`）、users 表无 tenant 列、APIKey 无 tenant 字段 → 真实请求恒为 `default`，分区处于休眠态。非 default 只能经渠道 `extra.tenant_id` 配置（`channels/manager.py:150-156`）或手工造 token 产生。
3. **"钥匙坯"已有**：`UserGroupManager`（`/v1/groups` 正主）有持久化（`data/user_groups.json`）、成员管理（`members`）、白名单先例（`allowed_modules`，空=不限制）、admin 门与前端管理页——离部门载体只差三块：**分类注册表、执行点、agent↔分组绑定**。
4. **category 是标注不是边界**：自由字符串（默认 `general`），无注册表无管理端点，仅查询显式传参时等值过滤（`repository.py:1156-1157`）；前端下拉从结果反推且仅首填一次（`KnowledgePage.vue:1379-1382`）。
5. **双通道已收敛**：聊天召回（`KnowledgeRetrieverAdapter`→hybrid→`visible_items`）与用户 API 最终过同一个过滤函数——**服务端按身份加白名单即可同时覆盖两条通道**，agent 隔离不依赖调用方传参。
6. **agent 归属是单人 owner 模型**（`agent_access.py:28-35`），运行时知识过滤用说话人身份（`chat.py:300/312/313` → `knowledge_retriever_adapter.py:242-251`）；kb_builder 落库不传 tenant（`kb_builder_executor.py:127/147` → `repository.py:894` 缺省 default）——既有断点。
7. **死面并存**：`user_group_api.py`（`/v1/user-groups`）是进程内 dict 死端点（零消费方、重启即失、假系统组），与正主 `/v1/groups` 构成双面混淆。

**方案骨架**：**分组即部门，分区停在部门根，子部门用分类收窄**——分类注册表（受控清单）→ 分组模型加 `allowed_categories/default_category/parent_group_id` → 登录签发 tenant claim＝部门根 id（打通休眠的分区键）→ 执行点在 `visible_items`/`can_view` 服务端单点生效（default 部门与 admin 不受限，存量行为不变）→ agent 绑组＋chat 部门根对账＋kb_builder 补 tenant → 前端四页逐一对齐（§3）→ 死端点退役（§2.7）。

## 2. 方案骨架（后端）

### 2.1 分类注册表（"自定义分类"的受控清单）

- 新表 `knowledge_categories`（落 foundation 迁移域，v next）：`category_id`（规范化标识）、`name`（展示名）、`description`、`is_active`、`created_at/updated_at`。admin CRUD 端点 `/v1/knowledge/categories`（列表登录可读——供下拉与导入选择）。
- 写入面第一阶段**不强制**校验（存量自由 category 兼容；管道标签 import/feishu/wecom/kb_builder 不动）；"写入必须注册"登记为后续收紧项。
- 单一事实源：分类清单只有这一处；分组白名单、前端下拉、导入选择器全部引用它。

### 2.2 分组模型扩展（部门载体）

`UserGroup`（`user_group_model.py:121-151`）加三字段（照 `allowed_modules` 同款"空=不限制"语义与 `__post_init__`/`from_dict` 归一模式）：

- `parent_group_id: Optional[str]`——单亲树；**禁环**：create/update 沿链上溯查重（含自指），命中即 400。**部门组＝`group_type=custom` 的组**（五个系统组不是部门）；层级只允许在 custom 组之间挂接。
- `allowed_categories: List[str]`——本组开放的知识库分类（引用注册表 `category_id`）；空=不限制（向后兼容：存量组全分类可见）。
- `default_category: Optional[str]`——本组成员导入/创建条目时的缺省业务分类。

存储沿用 JSON 落盘（`data/user_groups.json`）与既有持久化方法；不加 SQLite 迁移域（存量形态不改介质，避免双源）。

### 2.3 部门归属与层级语义（子部门设计核心）

- **分区停在部门根**：用户的 `tenant_id` claim ＝ 其所属 custom 组沿 `parent_group_id` 上溯到**根**的 `group_id`。子部门不另立分区——facts/本体/图谱/FTS 全部既有 `tenant_id = ?` 等值比较零改动，部门根内共享一套本体与知识图谱。
- **子部门隔离由分类层表达**（拍板 T-F 路径并集）：子组绑专属分类（如"前端文档"），部门根绑共享分类（如"研发制度"）；用户**生效白名单 = 所属组到部门根路径上各组 `allowed_categories` 的并集**（某级空=不限制则跳过该级；整条路径全空=不限制）。效果：前端组成员可见"研发制度＋前端文档"、不可见"后端文档"——子部门间天然互斥专属知识、共享知识人人可见。
- **单主组**（拍板 T-A）：一个用户最多属于一个 custom（部门）组——`add_user_to_group` 落成员前校验目标为 custom 组时用户是否已在其他 custom 组，是即 409（管理面先移后加）；系统组归属不受此限。存量多 custom 组成员（如有）取第一个并留告警日志。
- 解析单源：新增 `resolveUserDepartment(username)`（归属组→部门根→生效白名单，一处实现），身份链、执行点、kb_builder 全部引用它；**分组解析失败一律 fail-closed 回落 default 部门语义**（＝不受限，与今天行为一致，不猜部门）。
- 白名单中引用的 `category_id` 在注册表中被停用/删除时：解析时如实剔除该 id（不报错不编造），组管理面回显"含已停用分类"提示。

### 2.4 身份链（打通"有锁无钥匙"）

- 登录签发（`api/endpoints/auth.py:289-298`）：`identity_claims` 增 `tenant_id`——取 `resolveUserDepartment(username)` 的部门根 id；无部门组 → 不签该 claim（`_user_identity` 既有缺省 default 语义不变，`api/auth.py:676-687`）。
- **改组后重新登录生效**（拍板 T-B）：管理端在成员变更响应与前端提示"分组变更需重新登录后生效"。
- 服务令牌/外部 Agent API key 身份维持 `tenant_id="default"`（`api/auth.py:597/:641`）——机器身份不受部门白名单约束的口子**不开**；确需部门身份走渠道 `extra.tenant_id`（批 D 对账）。

### 2.5 执行点（服务端单点，双通道自动覆盖）

- `can_view`（`repository.py:1086`）：租户相等判定之后追加——`生效白名单非空 ∧ item.category ∉ 白名单 ⇒ False`。admin 同样受白名单约束**但其自身部门根内的**条目不受限（租户先行语义已有：admin 不跨租户 :1088-1091；本条在租户内按其部门白名单过滤）。
  - 修正表述：admin（role=admin）在**自己部门根租户内**不受分类白名单限制（管理面全量语义，与今日 admin 全可见一致）；白名单只约束非 admin。
- `visible_items`（:1138 租户过滤后同位置追加同判据）；`can_modify`（:1099）同口径（写隔离：非 admin 往白名单外分类写/改即拒）。
- FTS 路：`fts_index.py` 查询子句加 `category IN (…)`（白名单非空时）；hybrid/vector 路经 `visible_items` 自动覆盖。
- **default 部门与 admin 行为不变**（反向钉）：无部门组用户与今天完全一致（全分类可见，存量条目全可见）。
- 白名单过滤对**聊天召回自动生效**：召回链收敛于 `visible_items`，无需 `_retrievalMetadata` 传 category——这正是"agent 也被隔离"的机制保证。

### 2.6 agent 通道（部门名下 agent 严格受限）

- `AgentConfig` 加 `group_id`（照 `owner_user_id` 同款落点链：`agent_core.py:273-277` 构造参数→`api/endpoints/agent.py` `_save_agent_config` 序列化＋`CreateAgentRequest/AgentInfo`→`agent_config.py` create/update/登记）；缺省=创建者所属部门组（无部门组则空）。
- chat 对账（拍板 T-D 严格绑定）：chat 端点解析 agent 部门根（沿 `group_id` 上溯）与说话人部门根，不一致且非 admin ⇒ 403（文案点名"跨部门使用智能体被拒绝"）。
- kb_builder 落库补传：`tenant_id`＝说话人部门根 id、`category`＝请求显式指定或创建者部门 `default_category`（修 `kb_builder_executor.py:127/147` 既有断点）。
- 渠道对账：渠道适配器 `extra.tenant_id`（若有）须等于渠道属主部门根，不等即告警并按属主部门根为准（不猜）。

### 2.7 死端点退役（单一事实源收口）

- 删除 `neurova/api/endpoints/user_group_api.py` 与其注册行（`endpoints/__init__.py:280`）及其专属测试（如有，实施时 grep 定位）；`/v1/groups` 正主不动。
- 前端本就只调 `/groups`（零改动受益）；文档同步（`docs/02-api/API_REFERENCE.md` 若有该端点行则移除）。

### 2.8 本体面（零 schema 改动＋三缺口顺手修）

- 本体按租户分区即按部门根分区——"租户A只见研发本体"由 v25 现成机制满足；子部门共享部门根本体（本体写面本就 admin-only），子部门级本体切分登记后续（§6）。
- 顺手修三处既有 tenant 缺口：`term_registry.py` 三查询补 tenant 条件（:650-665/:674-681/:700-709）；`/ontology/validate` 移除 body 传任意 tenantId 的口子（一律取 `_tenantOf`，`knowledge_ontology.py:784/816`）；`rebuildProjectionFromAuthority` 的 `listSubjects`/`projectionDrift` 补 tenantId（`graph_bridge.py:793-794/825`）。

| B | 身份链（登录签发 tenant claim＝部门根 id）＋`resolveUserDepartment` 解析单源＋单主组校验 | 带部门组用户登录 token 含 tenant claim＝根 id；无组用户仍缺省 default；用户已在 A 组再加入 B 组 409 |
| C | 条目面白名单执行（can_view/visible_items/can_modify）＋FTS `category IN`＋kb_builder 补 tenant/category | 跨部门根不可见（条目列表/FTS/聊天召回三路各一格）；白名单外不可见且 404 不泄露；部门共享分类（根组绑定）对子组成员可见；default 用户与 admin 行为不变（反向钉）；kb_builder 条目落说话人部门根 |
| D | agent 绑定（AgentConfig.group_id）＋chat 部门根对账 403＋渠道对账 | 跨部门用户用 agent 403；同部门（含子部门）正常；无组 agent 仅 admin 可用（沿用 owner 门语义不回退） |
| E（可选） | facts/图谱读面按 category 过滤 | facts 读面白名单外 0 命中；图谱走查不跨出白名单条目派生的子图 |
| F1 | GroupPage 树形＋分类绑定＋EnhancedUserPage 所属分组 | vitest 组件测试＋vue-tsc 零错 |
| F2 | KnowledgePage 分类源/导入分类＋AgentFormPage 分组选择 | 同上 |

依赖序：A→B→C→D（→E）→F1/F2。每批独立红绿＋提交＋台账；批量红灯清单共用判据：**存量行为不变是反向钉**（default 部门、admin、无组用户、管道标签条目四类场景逐批复验）。

## 5. 拍板记录（2026-11-07，六项全按推荐裁；备选影响面存档）

| # | 问题 | **裁定** | 备选与代价（存档） |
|---|------|---------|-------------------|
| T-A | 部门归属模型 | **单主组**（add 时校验，与 tenant 分区键单值语义自洽） | 多组并集：灵活但分区键/本体映射复杂，需定义并集空集语义与 claim 多值形态 |
| T-B | 身份携带方式 | **JWT 登录签发 tenant claim**（与既有 claim 链一致；改组重登生效） | 服务端每请求现算：即时生效，但每请求多一次解析＋需定义解析失败语义；claim 链（`_user_identity`）已有接收端，签发改动最小 |
| T-C | 白名单外条目可见性 | **严格不可见**＋导入配套（导入带业务分类、缺省分组缺省分类）；default 部门与 admin 不受限 | 宽松（未分类可见）：隔离有洞、与"仅开放研发分类"表述不符；管道标签收编：需一批数据迁移＋逐组决策，量大 |
| T-D | agent 被跨部门用户使用 | **严格绑定 403**（语义最贴"严格隔离"，可解释） | 以 agent 部门为准：允许跨部门使用但数据面与说话人错位（客服用户用研发 agent 召回全研发内容，泄漏方向混乱）；交集：规则难解释、空集语义另需定义 |
| T-E | 死端点处置 | **退役删除** `/v1/user-groups`（单一事实源，教义第 6 条） | 保留：双面混淆常驻，任何新消费方都可能接错面 |
| T-F | 子部门白名单语义 | **路径并集**（父共享＋子专属；空=不限制跳过；子部门间靠专属分类互斥） | 路径交集（支持"子部门收窄父部门范围"）：父绑大类时交集易算出空集，反直觉；子部门独立分区：四存储层 `tenant_id=?` 全改"self＋祖先链 IN"，改动横扫且"子部门可见父部门共享知识"用分区表达不了 |

## 6. 明确不做（本设计边界外）

- 组织架构多树/DAG（`parent_group_id` 单亲树，不支持一子多父）；
- 跨部门共享分类（白名单只引用本部门路径并集；跨部门协作走 admin 中转或后续共享机制）；
- 子部门级本体独立分区（子部门共享部门根本体；本体写面本就 admin-only）；
- 用户级分类 ACL（分类开放粒度止于组，不做到人）；
- RBAC 激活/桥接（`security/rbac.py` 休眠不动）；`enhanced_user_model` 的 group_type 档位不动；
- 真多实例 SaaS 部署形态（嵌入式单机前提不变，见 `docs/specs/2026-10-23-knowledge-system-upgrade-design.md` D10）；
- 分组配额（`ResourceQuota`）与限流档位语义变更（沿用既有并集最宽口径）；
- 写入面强制分类注册校验（登记为后续收紧项）。
