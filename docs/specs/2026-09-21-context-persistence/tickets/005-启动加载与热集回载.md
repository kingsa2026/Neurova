# 005 启动加载与热集回载

**Blocked by**: 001

## 目标

钉死"启动时对 DB 做什么"这条策略——审计点名要求设计的三件事之一。

## 现状（实测，基线脚本 §5，10.2 万行库）

| 候选 | 启动代价 | 常驻内存 |
|---|---|---|
| 只登记 `COUNT(*)` | 5.2 ms | 0 |
| 回载最近 500 条 | 1.0 ms | ~0.13 MB |
| 回载最近 2000 条 | 4.3 ms | ~0.5 MB |
| 回载最近 10000 条 | 25.5 ms | ~2.6 MB |

## 涉及层

- [x] 逻辑层：启动只读一次 `COUNT(*)`（供 `get_retention_stats` / `/metrics`），
      **不把历史塞回常驻**（D1 要的是"取得到"，不是"开局全在内存"）。
- [x] 逻辑层：显式回载入口 `rehydrate(limit=…)`，默认不调用；
      回载走 `id DESC LIMIT`，顺序稳定（前缀缓存契约）。
- [x] 逻辑层：**`draw` 不查 DB**——常驻集是视图唯一来源；这条边界要有断言锁住，
      否则"draw 每轮扫库"会把 B5 的规模问题提前引爆。
- [x] 测试：`tests/unit/context/test_pool_startup_load.py`
- [x] live-verify：`tests/manual/context_pool_startup_load_90.py`

## 验收标准

- **A9**：启动对 DB 的查询次数为常数（与库内行数无关）；断言只发生登记性查询。
- `rehydrate(limit)` 返回条数与顺序符合契约；默认路径不调用它；重复回载不产生第二份。
- `draw` 路径零 DB 访问（以连接/查询计数或注入探针断言）；`recall_evicted` 是唯一允许查库的读路径（反向锁，防修过头）。
- 登记失败不阻断池构造，但必须是**可见状态**（`registered_at_startup=False` + 点名原因），不得看起来像一个正常的 0。
- 登记读数随本进程写入/GC 同步（不写成一份会过期的启动快照）。
- 物化内存与实测量级一致（约 256 B/条，纯 `ContextInput` 组装；完整对象含索引约 560 B/条）。

## 实施结果

- 红灯 → 绿灯：先把"启动登记"临时摘掉验红（`8 failed, 3 passed`）→ 恢复后
  `12 passed`。红灯文件在转绿前未进 `protected_tests.txt`。
- live-verify（真 `Agent` → 真 `ContextOrchestrator`，真 v0 前像库）：
  - 稳态启动查询次数 **2 / 2 / 2**（库内 0 / 200 / 5000 条）——与规模无关；
  - 启动常驻 **0** 条（只登记，不预载）；
  - 稳态启动代价（开连接 + `COUNT(*)`）**0.4 / 0.4 / 0.8 ms**；
  - 显式回载 10 条，首条为 `id` 最大者（顺序稳定），重复回载常驻仍为 10；
  - `draw` / `query` / `get_contexts` 5 轮 **0 次**查询；`recall_evicted` 期间 206 次（唯一读路径）。
- **旧库首次启动另付 002 的迁移开销**（一次性 schema 升级），live-verify 把两个读数
  分开打印，不把迁移算进稳态启动代价（否则就是拿一次性成本当常态）。
- 登记读数增量为真实落库条数：`record()` 返回"是否真的插入了行"（同内容去重命中
  返回 False），池据此维护 `_ledger_rows`——不靠"自己数调用次数"糊一份可能与库不符的账。
- 指标接线（避免"只写不读"的断点）：新增 gauge
  `neurova_context_pool_ledger_rows`，由 `observe_context_pools()` 读走。

## 不做

- 不做全量预载。
- 不做 `draw` 接 DB（规格 §4 非目标）。
- 不把登记值做成"每次读都查库"（那就是每轮扫库，等于 D10 要防的东西换个位置）。
