# 006 v2 迁移：FTS 重建为 trigram（零停机）

**Blocked by**: 002、004

## 目标

把 FTS 分词器从 `unicode61` 换成 `trigram`，且**迁移窗口内服务不停、写不被长阻塞**。

`unicode61` 对中文等于无索引（004 已实测），而**只改 tokenize 参数不会改已有索引**——
必须重建表。

## 现状（实测，基线脚本 §6/§7）

- 一次性事务重建（5 万行）：**0.88 s**。
- 分批重建（5000/批）+ 切换（5 万行）：**1.34 s**，期间 258 次并发写，
  写侧停等 p95 **16 ms** / max **137 ms**。
- `delete-all` 对普通 FTS5 表**不合法**（实测 `OperationalError`），只能用影子表方案。

## 涉及层

- [x] 数据层：v2 迁移 = 建影子表（trigram）→ 分批回填（短事务）→ 切换前补齐尾批 →
      同事务内 `DROP` 旧表 + `RENAME` 影子表。
- [x] 数据层：`user_version` 推进到 2；迁移失败回滚且上抛。
- [x] 数据层：旧库（v1，unicode61）与新库（v2，trigram）并存期间读写都正确
      （查询侧按 004 的分流规则，不依赖具体分词器行为）。
- [x] 测试：`tests/unit/context/test_context_ledger_fts_migration.py`

## 验收标准

- **A7**：迁移窗口内并发写不停且不长阻塞——断言并发写线程的停等 p95 上界
  （基线 16 ms，实现不得明显劣化）。
- 迁移后中文查询命中对拍 004 的判据（MATCH 命中 == LIKE 真值）。
- 迁移幂等：v2 库重跑 `migrate()` 返回空；伪造 v3 库被拒。
- **不得**用一次性 `INSERT … SELECT` 长事务（实测会整段阻塞写）。

## 实施结果（2026-09-22）

- 交付：`neurova/context/eviction_ledger_db.py`（`_rebuildFtsAsTrigram` +
  `_databasePath` + `_openSideConnection`；常量 `_FTS_REBUILD_BATCH = 5000`、
  `_FTS_SHADOW_TABLE`、`_FTS_TOKENIZE`；`register_migration(2, ...)`）、
  `tests/unit/context/test_context_ledger_fts_migration.py`。
- 红灯 → 绿灯：`5 failed, 5 passed` → `10 passed`。红灯含：迁移后仍是 unicode61 /
  `user_version` 停在 1、迁移提交次数为 0（无分批）、回填读取无 `LIMIT`、
  半成品影子表重入后回填不全。
- live-verify：`PYTHONPATH=. python tests/manual/context_ledger_fts_rebuild_90.py`
  真 v1 库 2 万行 → 迁移 574–627 ms，**期间并发写 36–39 次全部提交成功**
  （停等 p50 1.5–2.2 ms / p95 6.6–184.7 ms），迁移后分词器是 trigram、
  两表行数相等、影子表已清理、中文命中逐条对拍相等、重跑 `migrate()` 返回空。
- **A7 的判据分两半**：结构面（提交次数 = ⌈行数/批大小⌉ + 1、回填读取带 `LIMIT`）
  进单测（与机器速度无关）；停等读数走 live-verify（机时契约）；
  规格 §6 的 `p95 ≤ 16 ms` 上界**未**落成断言（fsync 抖动可差一个量级）。
- 三处实施期踩到的坑写进规格「006 对 D12 的偏离记录」：独立连接的必要性（快照 +
  DDL 锁）、切换段必须与尾批补齐同事务、每批显式 `BEGIN IMMEDIATE`。

## 不做

- 不做 GC/对齐（007）——已由 007 交付。
