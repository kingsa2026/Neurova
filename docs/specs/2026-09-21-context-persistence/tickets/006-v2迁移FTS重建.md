# 006 v2 迁移：FTS 重建为 trigram（零停机）

**Blocked by**: 002、004

## 目标

把 FTS 分词器从 `unicode61` 换成 `trigram`，且**迁移窗口内服务不停、写不被长阻塞**。

`unicode61` 对中文等于无索引（004 已实测），而**只改 tokenize 参数不会改已有索引**——
必须重建表。

## 现状（实测，基线脚本 §6/§7）

- 一次性事务重建（5 万行）：**0.88 s**。
- 分批重建（5000/批）+ 切换（5 万行）：**1.34 s**，期间 258 次并发写，
  写侧停等 p95 **16 ms** / max **137 ms**。
- `delete-all` 对普通 FTS5 表**不合法**（实测 `OperationalError`），只能用影子表方案。

## 涉及层

- [ ] 数据层：v2 迁移 = 建影子表（trigram）→ 分批回填（短事务）→ 切换前补齐尾批 →
      同事务内 `DROP` 旧表 + `RENAME` 影子表。
- [ ] 数据层：`user_version` 推进到 2；迁移失败回滚且上抛。
- [ ] 数据层：旧库（v1，unicode61）与新库（v2，trigram）并存期间读写都正确
      （查询侧按 004 的分流规则，不依赖具体分词器行为）。
- [ ] 测试：`tests/unit/context/test_context_ledger_fts_migration.py`

## 验收标准

- **A7**：迁移窗口内并发写不停且不长阻塞——断言并发写线程的停等 p95 上界
  （基线 16 ms，实现不得明显劣化）。
- 迁移后中文查询命中对拍 004 的判据（MATCH 命中 == LIKE 真值）。
- 迁移幂等：v2 库重跑 `migrate()` 返回空；伪造 v3 库被拒。
- **不得**用一次性 `INSERT … SELECT` 长事务（实测会整段阻塞写）。

## 不做

- 不做 GC/对齐（007）。
