# 003 写侧批量提交（写放大）

**Blocked by**: 001

## 目标

把归档写入从"每行一次 connect + commit + close"改为"一次归档调用一次事务"。

## 现状（实测，基线脚本 §2，10 万行存量库 / 24 条一轮）

| 形态 | 每轮耗时 |
|---|---|
| 每行独立连接 + 提交（现状 `record()` 同形） | 24.0 ms/轮 |
| 常驻连接 + 每轮一次事务 + trigram FTS 影子写 | 2.2 ms/轮 |
| 常驻连接 + 每轮一次事务 + 不建 FTS | 0.33 ms/轮 |

## 涉及层

- [ ] 数据层：`EvictionLedgerDB` 持一个常驻连接（WAL + `synchronous=NORMAL` +
      `busy_timeout`），`record` 不再每次 connect/close。
- [ ] 逻辑层：提供"批量记录 + 一次提交"入口；事务边界 = 一次归档调用，
      **返回前必须已提交**（规格 D8：不做异步/后台缓冲刷盘，那会把崩溃窗口内
      的内容连同"已归档"的承诺一起丢掉）。
- [ ] 生命周期：连接随池关闭释放；连接不可用时降级路径必须显式（不静默丢写）。
- [ ] 测试：`tests/unit/context/test_ledger_write_batching.py`

## 验收标准

- **A2**：24 条/轮的归档耗时 ≤ 现状形状的 **1/3**（同机同存量规模 A/B）。
- 事务语义：一次归档调用内任一条写失败 → 整批回滚或逐条诚实上报（二选一，需在实现里定死并断言）。
- 提交后立即可被另一连接读到（WAL 下读己之写跨连接可见）——防"提交了但别人看不见"。
- 并发：两个写方并发归档不互相长期阻塞（`busy_timeout` 生效）。

## 不做

- 不做 GC（007）。
- 不引入连接池（规格 D7 与 ADR 0014：动态路径不进池）。
