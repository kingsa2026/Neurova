## 1. 问题陈述

**T-09 只解了一半。** 改前的形态是 agent 在电脑操控域结构性失明（结果归一化把 `image_base64`
摘掉、`vision_available` 恒 `False`）。现在槽、闸门、装配三段都已接上并进了 CI，
但整条链的**终点是模型**，而我止于"请求副本带图"这个中间态。按教义第 4 条，
"图进了请求但没人证明模型收到过"就是半接线——它比不接更危险，因为闸门、成本、事件面
都已按"已生效"的假设在跑，而 `capabilities.vision` 在这台机器上今天读的是 `unknown`
（本轮实测原文：`moonshotai/Kimi-K2.6:DashScope 既无实测也无声明——需要跑一次多模态探测才能定`），
门因此一张图也不放。**能力已装好，开关在外部。**

**T-12 的证据有循环性，要说明白。** 契约桩是按我们自己代码里的读点倒推起来的
（`camofox_server_backend.py:295` 读 `data.get("snapshot", "")`，同族读点还有 `tabId`/`targetId`
(255/508)、`refsCount`(317)、`truncated`(312)、`/health`(95/116)）。所以那次真传输跑通，
证明的是**我们对契约的解释自洽**，不是**真容器就返回这个形状**。入库的那批 camofox 判据（`tests/unit/computer_use/test_empty_snapshot_not_success.py::TestCamofoxParity`）
连这一层都覆盖不到——它经 `_make_backend`（`test_camofox_server_backend.py:37`）把
`b._client` **整个换成 MagicMock**，httpx 对象本身都不是真的，所以它只证"给了空串我们会拒绝"。
**"真传输"当时只活在 §13.3 的散文里，探针即用即删、未入库**——这是它最该补的一格，
**已由 U-07 补上**（§27：仓内起桩、真 socket、7 例进 CI）。剩下的循环性问题因此不再是"没验过"，
而是"验的是自家解释"：真容器形状属外部契约，已由 🔒Q-1 划出验收面（§28）。

## 2. 接缝：本方案不新建接缝

四个接缝全部复用既有落点，理想情况下整批收尾只跨 S1/S2 两个：

| 接缝 | 落点 | 为什么是它 |
|---|---|---|
| **S1 能力读数** | `capability_state.reading("vision")`（`capability_state.py:230`） | T-09 的成本闸门读的就是它（`openai_loop.py:594`）。翻闸门与证翻闸门走同一口，不会出现"判据绕过装配点"。 |
| **S2 请求装配** | `openai_loop._attachPerceptionImage`（`openai_loop.py:569`）＋ 三个发送点 | 图进不进模型**唯一**的入口。活体验证取它的出口，不改它内部。 |
| **S3 容器传输** | `CamofoxServerBackend` 的 `base_url`（`camofox_server_backend.py:53`，可注入） | 真容器与契约桩是同一个接缝的两个对端——换对端不换代码，这正是"支路 A/B 都闭合"的结构前提。 |
| **S4 人可观测面** | `GET /api/v1/computer/status?refresh=true`（9527，鉴权后） | 与 S1 同装配点。验收记录取这个口，人复跑得出口一致。 |

## 3. 方案概述

**T-09 是一条活体路线，不是一次改造。** 顺序：先在真配置上把 S1 的读数从 `unknown` 顶到
`available`（零代码，只观察既有探测链），再跑一轮真工具环让 S2 出图并让模型**用画面里独有的
事实**签收，最后同 session 接一轮纯文本做反向锁。只有当中途读数仍翻不过来时，才动 U-05
那个名字收口——因为那时"实测档不可达"才从冗余变成承重缺陷。

**T-12 分两支，其中一支不需要任何授权就能立刻闭合。** 支路 B（默认推荐）：把 §13.3 那个
契约桩从散文**升为入库判据**（真 httpx socket 打到仓内起的最小服务，S3 同形），
把"真传输"变成守卫而不是叙述；然后把口径如实定为"两后端产出侧语义已在真传输上证实，
真容器自身形态不在本仓验收面内（外部服务，需授权）"并落账。支路 A：拿到授权后按 S3 起真容器，
原样复跑 §13.3 那张五态表，字段/错误形态若与我们的读点不符，**当场改产出侧解析并同批补 parity 判据**。
两支共用 U-07 的入库判据：A 只是在同一接缝上多一个真对端。

> **落定（2026-10-01）**：🔒Q-1 拍 **支路 B**。U-07 已入库并进 CI（工单集 §27），
> 终态口径与回潮判据落在工单集 §28；支路 A 的 U-08/U-09 撤下。**登记时按教义第 5 条扫同根因，
> 量到一条没闭合的链**（选路不查能力读数 ⇒ 外部服务仍可能被 agent 自动拉起），
> 已开 **🔒Q-4** 交回拍板，不在本批自行改默认值。

### T-09

**U-01 · vision 读数能翻到 `available`（经声明档或实测档）**
- 判据：在后台激活一个真支持图像输入的模型后，S4 返回的 `capabilities.vision.state == "available"`，
  且 `reason` 点名证据来源（"provider 声明 …"或"实测（学习型缓存）…"）。
- 复跑：`GET /api/v1/computer/status?refresh=true`（token 见本地凭据，**不入库**）；
  无 token 应回 401，用以证实打到的是真装配。
- 否证条件：激活后 `model_metadata[<model>].capabilities` 里没有 `vision` 且读数仍 `unknown`
  ⇒ 触发 U-05；若连 `model_metadata` 都不被 `_persist_probe_result`（`provider_manager.py:1724` 起）
  写回，则这条链的后台探测根本没落地，升级为独立缺陷单，**不在 T-09 里顺手兜**。
- **⏸→✅ 通道已打通（2026-10-01，工单集 §33）**：本条原先记的"本机没有任何可用 vision 通道"
  **一半是我们自己的错**——多模态探测图（内联 base64）签名合法却过不了解码器，严格网关只会回
  `400 invalid image base64 content`，任何模型都探不成。修成 `zlib`+`struct` 现造的 32×32 纯红图后，
  用户给的候选 `sensetime:kimi-k3` 真探测回 **`supported=True / probe_answer="red"`**；
  中途一次限频（429）按 §31 的修法如实**没有**被写成"不支持图"。
  ⇒ U-01 具备条件（切活跃模型即可）；**U-02 仍未跑**：要的是
  `_attachPerceptionImage` 生成的那张副本被真模型读懂，不是探针图。
  其余三个候选的实测（github-models 非 JSON 正文 / aliyun 无 key / volcano coding-plan 不支持）
  仍成立，只是不再等于"没有可用通道"。

**U-02 · 真 vision 模型的一轮工具环签收这张图（承重）**
- 判据：夹具页面把文本事实**刻意做成不可得**（本地 HTML 里用 `<canvas>` 画一段随机短语，
  aria 树取不到 ⇒ `browser_dom_snapshot` 回具名缺口），同轮产图。三条同时成立才算过：
  ① 事件面出现 `perception_image`，`gapTool`/`imageTool` 与真缺口对得上；
  ② 模型答复**说出画布上那段短语**（或引用只可能在图里的事实）；
  ③ 同轮只附一张。
- 复跑：真后端 9527 + 真服务商，经会话页正常发一句话让 agent 操作该页面；
  取证取事件流与助手答复原文，两者进提交说明。
- 否证条件：②答不出但也没报错——**不能把"没报错"当成"收到了"**，这条直接判未合。
  若②成立而①不成立，说明事件面漏报，属真缺陷要修。
- 夹具理由：构造"文本不可得"是为了让"模型只能从图里得到答案"成为唯一解释路径，
  不是自造正对照来省事——正对照已由 §13.3 的"非空成功不误判成故障"承担。

**U-03 · 串台反向锁（同型事故的活体否证）**

**U-04 · 413 防线在真配置上成立**

**U-05 · 能力名收口（条件触发，不是先行动作）**
- 事实：`_probeVision` 实测档问的是 `ModelCapabilityCache.get(key, "vision")`
  （`capability_state.py:251`），而全仓**唯一**的写入方用 `CAP_SUPPORTS_MULTIMODAL = "supports_multimodal"`
  （`model_capability_cache.py:31`；写入点 `provider_manager.py:1757`，另一读点 1785 同用该名）。
  键形状两边一致（`{provider.id}:{default_model}`，取 `get_active_model`）。
  本轮实测佐证：两个名字在这台机器上今天都取到 `null`，`model_metadata` 该模型条目为空 `{}`。
  ⇒ "实测 > 声明"这条**写在 docstring 里的证据次序，实测档今天结构上到不了**。
- 判据：`_probeVision` 的能力名必须与写入方同源（引用常量，不写字面量），
  并加一条判据钉住"两处名字取自同一个符号"，防止第三份口径出现（教义第 6 条）。
- 复跑（先红）：新判据文件替身 `ModelCapabilityCache`，往缓存学 `CAP_SUPPORTS_MULTIMODAL=True`，
  断言 `reading("vision", refresh=True)` 为 `available`；改前该条应红（读 `"vision"` 取不到）。
- 否证条件：若 U-01 已由声明档把门打开，那这条只是**冗余档的命名收口**，按小事做、不排专项；
  若某服务商不返回能力字段（声明档拿不到证据），这条就是唯一能开门的口，必须当场修。
- **✅ 已落地（2026-10-01，🔒Q-2 拍"现在就修"，工单集 §30）**：动手前现场复算把这条的
  **前提否证了**——声明档也读不到东西（`_declaredVision` 按 dict 读 `capabilities`，
  而用户配置里实测 866 条全是 list、0 条 dict；`_persist_probe_result` 又用 `str(member)`
  判定枚举，回枚举成员时恒 False）。所以它**不是一行换名，是同根因的三个命中点**，
  生产净 +20 行、判据 4 条先红（含纠正我原先那条按 dict 造的自证夹具）。
  对 U-01 的影响：修完之后 `capabilities.vision` 才有可能是"实测/声明"任一口点开的 available，
  而不是永远 `unknown`。

**U-06 · Anthropic 环的"未生效"要可读，不能静默**

- 否证条件：若 (a) 复用闸门需要在 `turn_context` 造第二份口径 ⇒ 说明两环请求形状不该硬并，
