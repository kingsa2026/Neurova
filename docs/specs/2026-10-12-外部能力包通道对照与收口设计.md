## 3. 关键实据发现：本仓早有外来能力包通道，而 P2 新造了第二份权限词汇

这一条是本设计的主要结论，也直接改写 P3 的题。

**其一，通道早已存在，只是不叫插件。** 技能侧有完整的四件套：外部来源适配（`skills/market_adapters.py`，七源）→ 远程拉取（`skills/hub_client.py`，937 行，含缓存/超时/重试）→ 导入与声明归一（`skills/market_importer.py:304-306`）→ 安装门（`skills/skill_install_gate.py`：未知能力键拒、`tools.allow` 逐名对表校验、静态扫描 `security/skill_scanner.py` 以 `ScanPolicy.DENY`、注入扫描 `scan_text_for_injection`、信任态 `provisional/trusted` 与上架评审门）。调用面还有真仲裁：`skills/permissions.py` 七类能力键 `tools|network|file|model|system|node|storage`，在 `tool_executor.py:1033`（作用域注入）与 `:1540`（拒绝）处执行，语义写明 fail-closed。

**其二，P2 造成的是双源。** `neurova/plugins/plugin_permissions.py` 的八项 `PluginPermission` 与上面那份是同一件事的两种写法，且**效力更弱**：

| 本仓插件枚举（P2） | 档位 | 技能侧对应键 | 谁真拦得住 |
|---|---|---|---|
| `read:files` | disclosed_only | `file`（`file_read` 族） | **技能那份拦得住**（按工具名仲裁） |
| `write:files` | disclosed_only | `file`（`file_write/create/delete/edit`） | 同上 |
| `network:access` | disclosed_only | `network`（web_*/browser_*/mcp.*） | 同上 |
| `http:request` | disclosed_only | 无（技能不出 HTTP 面） | 都拦不住 |
| `execute:commands` | never_grantable | `system`（`run_code`/`computer_*`/`spawn_subagent`） | 技能那份拦得住 |
| `read:events` / `emit:events` | framework_enforced | 无（技能不接事件总线） | 插件那份在拦 |
| `admin` | never_grantable | 无 | — |

按 AGENTS.md 教义第 6 条「发现第二份定义时，收口到一份并删掉另一份」与第 7 条「同功能先比后合」，P2 这一刀**当时没有与技能侧比**（我扫的是 `neurova/plugins/` 包内，没扫 `neurova/skills/`）。这是我自己造成的双源，登记在此并按下面 §5 的三条路处置，不改历史。

**其三，插件通道真正独有的只有三件事**：常驻对象与生命周期（`BasePlugin.initialize/start/stop/destroy`）、对外 HTTP 面挂载（`plugin_route_mount.py` 的命名空间＋身份门＋逐插件人工授予）、事件总线订阅/发布。技能侧三者皆无（`grep -rn "APIRouter|add_api_route|include_router" neurova/skills/ neurova/skill_system/` 零命中；`skill_system/core.py` 不碰 `event_bus`）。所以收口的方向不是"合并两套体系"，而是**能力词汇与安装门用同一份，独有那三件留在插件侧**。

## 4. 真缺项（按本仓自有理由立项，与"对方有"无关）

1. **构件完整性未固定（两条通道共有，且今天就在开放路径上）**：`grep -rn "sha256|hashlib|digest|checksum|signature"` 在 `skills/hub_client.py`、`skills/market_importer.py`、`skills/market_adapters.py`、`api/endpoints/marketplace.py` **全部零命中**——七个外部来源下载到磁盘并登记成技能，中间没有任何内容哈希固定或签名校验；安装门做的是**内容静态扫描**，不是**来源与完整性**。这是本仓自己的 P0 级暴露面（"扫过的那份"和"跑起来的那份"可以是两份）。原 P3 记的"哈希/签名校验"因此不是插件独有的新设计，而是这条共有欠账的一部分。
2. **渠道插件登记口断链**：`PluginChannelRegistry.register()` 无生产写侧（§2.1 证据）。要么接上（谁在什么时候登记 spec），要么连读侧一起退役——现在这个样子是"面板永远空着而代码看着在位"。
3. **`PluginType` 七值无分派**：`CORE/SKILL/CHANNEL/TOOL/THEME/FUNCTIONAL/EXTENSION` 只被当读数用（`api/endpoints/plugin.py:132/174` 的 `type` 字段与列表过滤），`base_plugin.py:91` 一处默认值，**没有任何按类型走不同装载/授权的分支**。要么定出分派语义，要么把枚举收到真被分派的那几值。
4. **P2 聚合门的空真通过**：`plugin_route_mount._permissionGate` 判的是「声明 ⊆ 已确认」，`required_permissions` 为空即空真通过（当时刻意的最小权限默认）。一旦引入任何"外来包"形态（无声明面），它就是白捡过门。处置见 §5 丙之外的必修项：**外来/无声明 ⇒ 视同未确认，一律不挂路由**，并把这条做成判据。
5. 插件市场四档壳（`plugin.py:198/208/214/474`）——留到 §4.1 的完整性与来源问题解决之后再定形态，不在今天补假实现。
6. **`frontend_resources` 只写不读**：`plugins/plugin_manifest.py:293,314-315,337,383` 一路把它解析、序列化、读回，**全仓没有任何消费方**（`neurova/api/endpoints/plugin.py` 的视图不暴露它，前端也不读）。这是 P1 取回包体时一起带回来的断点，按 §2「只写不读的配置」必须处置：要么接进前端资源装载那条链（而该链见第 8 项，还不存在），要么连同声明面一起退役。
7. **AGENTS.md:140 的主题契约名实不符**：条款写「全站禁硬编码色值（`themes.test.ts` 契约）」，而该守卫只读 `variables.css` 与 `global.css`（`NeurUI/src/styles/__tests__/themes.test.ts:22,25`），从不扫组件。本设计复算实数：pages 74 个中 45 个、components 58 个中 33 个含 hex 字面量。按本仓 AGENTS §4 已有的口径「规则以实际存在的命令为准，不以规则里写着当作已存在」，处置二选一——把守卫扩到组件侧并清掉存量，或改条款文字承认它守的是令牌面。**不许留着**：这是"文档承诺与实测行为相反、CI 看不见"那一类（`tests/manual/_liveVerifyIsolation.py` 的 docstring 记过一次同形态）。
8. **前端没有"贡献点"这一层**：动态路由（`addRoute`）、设置页注册、产物渲染器注册表、语言包运行时合并（`mergeLocaleMessage`）四样全部零命中（§2.2 证据）。⇒ P4「前端插件页」的真实规模不是"加一个页面＋11 locale"，而是先决定**要不要引入外部贡献点机制**这一层；这一条与第 7 项一样是本仓自有产品决定，与"对方有 UI 插件"无关。

## 6. 本设计明确不做的

1. **不做 DSH/Cordis 兼容层，不引入其结构与命名**，不把 `apply(ctx)`/`cordis.yml` 搬进本仓契约（§2 红线）。
2. **不把任何外来包写进"支持清单"**——沿用本仓 `docs/specs/2026-09-20-external-agent-ingest-design.md` 的纪律：**无 fixture 不写进支持清单**，取证只作背景。
3. **不在收口之前动 P3 的远程下载安装面**：§4.1 未解决前，任何"从远端拉代码执行"都是加宽敞口而不是补功能。
4. 不为"对方有市场/有主题/有语言包"而立项任何一类（memory 里那条口径：「对方有 X」不得作本仓立项理由）。唯一例外是 §2 对照里**本仓自有的断点**（第 2、3、4、5 项），它们的立项理由全部来自本仓实据。

## 7. 裁定后第一批的判据要点（先写形状，不落码）

1. 构件完整性：从来源取回的字节流必须带 `sha256` 固定，且**校验先于落盘**；哈希不符 ⇒ 结构化拒因（不 `return False`），并有一格断"扫过的那份与跑起来的那份是同一份字节"（否则判据自证的是空气）。
2. 空真通过：清单声明为空的插件 ⇒ 挂载必须被拒并点名"无声明≠已确认"；带反向对照格（把规则放宽成"空即放行"时该格必须红）。
3. 词汇单点（乙）：一格按 AST 取两份枚举的成员集合，断"插件侧不再自带 `read:files|write:files|network:access|execute:commands` 的独立判定"，另加变异对照。
4. 登记口断链：要么补生产写侧并断"登记后可被读侧读到"，要么连读侧一起退役并钉"不许再长回壳"。
5. 主题契约（第 7 项）：处置后必须有一格按**真产物**读数——扩守卫时，断"pages/components 里 hex 字面量数 = 0（或降到登记基线）"，并自带反向对照（临时塞一个硬编码色的组件必须被抓到）；改条款时，必须有一格断"AGENTS.md 那句话与实际守卫范围一致"（否则又是规则与行为并存各说各话）。

## 8. 本份取证的限制（别把没扫到的当扫过的）

1. **外部侧只读了三份材料**（宿主 README、`docs/cordis-tutorial/01-first-plugin.md`、`docs/cordis-api/registry.md`）＋**一个真实插件包**的 `package.json`（`Ebony-Vinyl/dsh-our-free-model`）。26 类**不是每类都取了样本**，"对方没有权限声明面"这一条只对"我读到的这份包与那份 registry 文档"成立，不宣称覆盖全部 4040 个链接仓库。要据此立项，必须先补到每类有 fixture 为止（沿用 ingest 设计那条"无 fixture 不写进支持清单"）。
2. **前端色值计数是本设计自己跑的 grep**（正则 `#[0-9a-fA-F]{3,8}`，范围 `src/pages/**/*.vue` 74 个、`src/components/**/*.vue` 58 个），**不是** vitest 读数，也**未**跑 `npm run test`/`vue-tsc` 复核；`.css`/`.scss`/内联 `rgba()`/第三方组件内部的硬编码不在口径内。数字会随口径变，写批次时要把口径钉进判据，而不是引用这一处结论。
3. 两通道权限词汇对照表（§3 中表）里"技能那份拦得住"依据的是 `tool_executor.py:1033/1540` 的调用点存在，**未逐条验证七类能力键在每一类工具上真的拒得掉**（本仓有过"只与同名近邻比、没比服务路上的实现"导致误判的前车，见台账 §6-151）。收口批次的第一格必须是行为读数：拿一个声明外能力的包真调一次工具，断它被拒。
4. 未审 `marketplace.py`/`hub_client.py` 的**下载→落盘→登记**全链是否有绕过安装门的旁路（只核到"无哈希校验"这一条）。§4.1 落批时要把旁路扫干净，否则补了校验也还是漏。
5. 未看 `frontend_resources` 之外是否还有同类"只写不读"的字段散在包体里（第 6 项只核了这一处）。§4 落批时按 AST 扫全包体字段，不靠点名。
