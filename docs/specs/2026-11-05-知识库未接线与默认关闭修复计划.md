## 0. 结论与处置总表

1. 真正零生产消费者的死代码是 **4 个模块/类**：`knowledge/config.py`、`federated_kb.py`、`multi_kb_router.py`、`FoundationReconciler`。`LegacyFactBackfill` 是“已否证、故意不启用”的一次性工具，不应按死码删除。
2. 半接线 **4 处**：`memory_links` 只写不读；`knowledge-integration` 的 gaps/learn 恒 501/空；非飞书远程源同步被端点明确拒绝；`access`/`integration` 的 HTTP 面仓内零消费者。
3. 默认关闭 **21 项**：13 项应保持关（安全/成本/延迟/未评估）；8 项按 D-5 的轨道处理——D-01 查询归一、D-02 歧义澄清走包 A 先行，D-03 限流后开，D-04 并行评估，D-08/D-11/D-16/D-19 单独立项。
4. 最重要的是：联邦 KB 是“能力已写、消费为零”；`FactSurface` **不是死码**，只是窄接线。011 已否证“事实池与叙述池按秩交织”，不要重开；它只承担图走查零锚点种子与治理富化。
5. 建议分四批：**P0 死码卫生**（退役/移脚本）→ **P1 接线闭环**（D-1 已裁 A：远程库进对话；D-3 建议 B 退役；非飞书同步口径）→ **P2 灰度转正（包 A）** → **P3 时间感知**（TD②/FTS 源时间/facts 源钟）。

## 1. 口径与证据边界

- **未接线**：在 `neurova/`、根入口脚本与 `scripts/` 中无生产导入/调用；仅有测试或诊断脚本引用。HTTP 端点即使仓内无前端消费者，只要有路由挂载，按“对外契约”处理，不列入死码。
- **默认关闭**：未设置环境变量时的代码行为；部署环境的 `.env` 可以覆盖，本文只对代码默认值负责。
- **动态导入**：知识包内无 `importlib`/`__import__` 形式的动态加载；端点注册表按字符串挂载，已单独核对。
- **反向守卫**：删除候选必须先看测试是否把它钉住；本文逐项列出需要同步改的测试，不把“测试还绿”当作“可以删”。
- **不能外推**：静态导入图看不到仓外调用方；删除前还要做一次 `git grep` 与发布说明。

## 2. 未接线逐项档案

- **判定**：**退役**（需人裁确认无仓外导入）。删即失去的是“从未实现的配置口径”，不是运行时能力；若产品确实要备份/缓存/加密配置，应另立项实现，不能把死配置当能力。

  2. 删除 `tests/unit/core/test_HomeFamilyLandingsFollowDataRoot.py` 的 `FAMILIES["knowledge/config.py"]` 条目；该守卫只检查文件路径落点，删文件后条目会失效。

  4. 全量回归，确认无新增失败。
- **影响面**：运行时零影响；删除后不再有“可配置备份/缓存/加密”的纸面承诺。
- **判据**：删除后 `grep` 零生产引用；`test_HomeFamilyLandingsFollowDataRoot` 改后仍绿；全量测试无新增失败。
- **风险**：仓外插件可能 import 该模块；发布说明中标注“未公开契约的删除”，并保留一个版本的 changelog 记录。

### 2.2 K-02 联邦 KB `FederatedKBService` + `MultiKBRouter` — 真实能力，零生产消费者

- **原功能**：把用户的 `is_active` 远程库配置装配为适配器清单，解密 API Key，按 `MultiKBRouter` 选择目标库（0/1 库直通，≥2 库 LLM FunctionCall 选库，失败兜底全库），逐库检索并合并，结果带 `kb_id` 溯源；单库故障不影响其余库。
- **关键入口**：`FederatedKBService.search()`（`federated_kb.py:73`）、`MultiKBRouter.route()/search()`（`multi_kb_router.py:58/79`）、`kb_catalog_tool()`（`:23`）。
- **来历**：`a6a24988e`（2026-09-05）“P1-4 远程库联邦检索接通 MultiKBRouter”；`multi_kb_router` 来自并行批次 `8cdbd34f9`。测试 `tests/unit/knowledge/test_federated_kb.py`、`test_multi_kb_router.py` 覆盖了服务本身，但没有生产调用方——它自称修复了 `get_adapter` 的零消费，自己却成了新的零消费。
- **现役替代**：chat 链路**没有**；远程适配器只接 NeurFlow 的 `builtin:knowledge_base` 节点（`neurflow/builtin.py:2010`）；飞书走 `datasource_sync` 拉到本地库后才进 RAG；iFlow/IMA/自定义 REST 不参与自动召回。
- **判定**：**需人裁：接线或退役**。删即永久失去“远程多库联邦检索 + LLM 选库”能力；不删则必须给它一个真实消费者，不能继续留在“测试绿、生产零调用”的状态。
- **方案 A（接线，推荐在需要远程库进对话时采用）**：
  - 在 `KnowledgeRetrieverAdapter.retrieve()` 内接入，不新增第二条知识检索器：先跑本地 hybrid；仅当用户有 `is_active` 远程配置时，调用 `FederatedKBService.search()`；远程结果只填补本地 top-k 的空位（本地优先），避免改变本地排序。
  - 远程结果映射为条目形状：`knowledge_id="remote:<config_id>:<content_hash>"`、`title`、`content`、`source="remote:<source_type>"`、`origin="untrusted"`、`score`；带 `kb_id` 与 `config_id` 溯源；不写回本地仓库、不建 fact lineage。
  - 依赖：`user_id`（检索上下文）、`KnowledgeStorage.get_configs_by_user()`、`NEUROVA_KB_SECRET`（加密 key）、可选 `llm_call`（≥2 库时选库）。
  - 失败方向：无配置/解密失败/远程超时/LLM 路由失败均让路，本地结果不受影响；远程调用加超时与并发上限。
  - 影响文件：`neurova/agent/knowledge_retriever_adapter.py`、`neurova/knowledge/federated_kb.py`（补结果归一与超时）、`neurova/agent/chat_pipeline.py`（如需传 `llm_call`）。
  - 判据：无配置零远程调用；单库直通；多库选库失败兜底全库；跨用户配置不可见；远程故障时本地结果逐字不变；活体用假远程适配器（不依赖外网）验证结果带 `kb_id` 溯源。
  - 代价：每轮多一次配置读取；有活跃配置时多一次远程 HTTP；需要密钥与出网；远程内容进入上下文属于数据外发，必须由用户显式 `is_active` 开启。
- **方案 B（退役）**：删除 `federated_kb.py`、`multi_kb_router.py` 及其测试；保留 `adapters.py`（NeurFlow 与飞书同步仍用）；删除 `kb_catalog_tool`；文档明确“远程库不参与自动 RAG”。
- **推荐**：若产品范围包含“远程库进对话”，选 A；否则选 B。由于是唯一实装且无替代，先按“需人裁”处理，不直接删。

### 2.3 K-03 `FoundationReconciler` — 一次性对账器，类零调用

- **关键入口**：`reconcile.py:86`（类）、`:88` 附近 `plan`、`:151` 附近 `reconcile`。
- **来历**：工单 015（`6ea435219`、`b01350926` 等）；测试 `tests/unit/knowledge/test_foundation_reconcile.py` 5 例全绿。它是迁移期工具，不是运行时能力。

- **修复步骤**：

  4. 文档记录运行方式与数据根隔离要求。
- **影响面**：运行时零影响；运维仍可选择脚本对账。

### 2.4 K-04 `LegacyFactBackfill` — 已否证的回填路径，保持不启用

- **原功能**：把旧 `KnowledgeRepository` 条目经唯一咽喉 `admission` 回填到底座，dry-run/apply，产出旧 id→`fact_id` 映射。
- **关键入口**：`backfill.py:21`（类）、`:22`（`run`）；唯一调用方 `scripts/diagnostics/_kb_backfill_rerun.py:36`。
- **来历**：工单 011；提交 `ee94d7f5d` 明确“回填与底座读面——否证结果，默认不启用”；工单 011 结论“未启用（否证结果，按出口判据回退）”。
- **现役替代**：叙述层权威已默认落底座库；回填不是常规运行路径。011 的否证结论是“读路径两池秩交织”使 recall@5 从 0.855489 降到 0.760371；回填与读面一起按出口判据回退，默认不启用，回填本身保留为一次性迁移工具。
- **判定**：**保持不启用**，按脚本级工具保留；不接产品 API/CLI。删即失去迁移逃生口，且可能让未来旧库迁移重新手写。
- **修复步骤**：
  1. 在 `scripts/diagnostics/` 加一段 usage 注释，写明“一次性、默认不启用、需先读工单 011 否证结论”。
  2. 加一条反向棘轮：`neurova/` 生产包不得 import `LegacyFactBackfill`（测试可 import）。
  3. 不新增 API/CLI 入口。
- **影响面**：运行时零影响；保留迁移工具。
- **判据**：`grep` 生产零引用；棘轮绿；工单 011 的否证读数不被重新解释为“已启用”。

### 2.5 K-05 `memory_links` — 记忆↔知识关联只写不读

- **原功能**：`/v1/knowledge-integration/sync/knowledge-to-memory`、`/sync/memory-to-kb` 记录关联；`/sync/links` 读列表；落 `KnowledgeStorage.memory_links`（JSON 持久化，跨重启保留）。
- **关键入口**：`storage.py:258`（创建）、`:276`（读取）；端点 `knowledge_integration.py:136/163/180`。
- **来历**：2026-09-15 收口，把进程内 `_sync_links` 改成持久化；`test_knowledge_integration_wired.py` 钉住落盘与读取。
- **现役替代**：检索管线不读 `memory_links`；`chat_pipeline` 的记忆合并、`orchestrator` 的注入、`post_chat_pipeline` 的反馈均不消费。全仓第二个读者不存在。
- **判定**：**需人裁：接线或退役**。当前是“写入 → 存储 → 无读取”的断点。
- **方案 A（接线）**：在 `_retrieve_memories()` 拿到最终 `ctx.relevant_memories` 后，对带 `memory_id` 的记忆查 `storage.get_memory_links(memory_id)`；对每条 link 用 `repo.find_item(knowledge_id)` 取条目，按可见性（同 user/agent）过滤，去重后作为补充条目加入上下文；上限 3 条；打 `linked_from_memory` 标记；不改变主排序。
  - 影响文件：`chat_pipeline.py`、`knowledge/storage.py`（已有读口）、`knowledge_retriever_adapter.py`（若把链接条目并入知识载荷）。

  - 代价：每条记忆一次 JSON 读；链接质量依赖人工维护。
- **方案 B（退役）**：删除三个端点、`memory_links` 存储字段与相关测试；文档标注“关联能力未实现”。删即失去“记忆↔知识手工关联”，但当前无人读，实际能力为零。

### 2.6 K-06 非飞书远程源同步 — 端点明确拒绝

- **原功能**：`POST /v1/knowledge/configs/{id}/sync` 触发远程数据源增量同步。

## 7. 待拍板项（按 AGENTS.md 核心原则第 8 条给决策影响面）

### D-1 联邦 KB：A 接入聊天 / B 只开 HTTP 面 / C 退役

> **拍板（2026-11-05）：选 A——远程库进对话。** 以下保留 B/C 作为记录与回退依据。

| 维度 | A 接入聊天自动召回 | B 只开 HTTP 面 | C 退役 |
|---|---|---|---|
| 能力 | 远程库参与每轮 RAG | 远程库可被显式调用，不进聊天 | 远程库只剩 NeurFlow/飞书同步 |
| 每轮成本 | 有活跃配置时多一次远程 HTTP | 只在调用时产生 | 0 |
| 主要风险 | 数据外发、延迟、远程内容不可信 | 仍需密钥；若无外部调用方仍是零消费者 | 永久失去该能力 |
| 不可逆点 | 无（可回退开关）；但已出网内容不可追回 | 无 | 删除唯一实装，只能从 git 恢复 |
| 推荐 | 若“远程库进对话”是产品目标 | 仅当有外部/SDK 调用方 | 若产品范围明确不含远程库进对话 |

**A 接入聊天（做法）**
- 在 `knowledge_retriever_adapter.py:214` 的 `retrieve()` 内补位，不新增第二条检索器。
- 数据流：`user_id` → `KnowledgeStorage.get_configs_by_user()`（`storage.py:182`）→ `_assemble_adapters` 解密 → `MultiKBRouter`（≥2 库才选库）→ `adapter.search()` → 映射为条目 → 本地优先合并。
- 触发条件：仅当用户有 `is_active` 配置，且本地命中不足（`hits < limit` 或 quality 低于阈值）时才调远程；单次超时 3s、并发 ≤2、每轮最多 2 个库。
- 必须处理：
  1. **反馈排除**：远程条目没有本地 fact/entry；`_recordKnowledgeLineage`（`chat_pipeline.py:2251`）会把远程 `knowledge_id` 写进 `knowledge_entry_ids`，随后 `/chat/feedback` 调 `recordEntryAdoption` 找不到条目，产生警告。需要给远程条目打 `external=True` 并在 lineage/反馈侧过滤。
  2. **可见性**：远程结果按配置属主 `user_id` 隔离；`attachGovernance` 对无 fact 的条目原样放行（`read_surface.py:166`），不会误挂本地血缘，但仍要显式标记 `origin="untrusted"`。
  3. **密钥**：`NEUROVA_KB_SECRET` 未设置时 `decrypt_api_key()` 返回 `None`，带密钥的配置会被 `_assemble_adapters` 跳过；无密钥的公开端点仍可用。
- 影响文件：`knowledge_retriever_adapter.py`、`federated_kb.py`（补超时/结果归一）、`chat_pipeline.py`（传 `llm_call`/过滤 remote id）、对应测试。
- 判据：无配置零远程调用；单库直通；多库选库失败兜底全库；跨用户配置不可见；远程故障时本地结果逐字不变；活体用假远程适配器验证 `kb_id` 溯源。

**B 只开 HTTP 面**
- 在 `/v1/knowledge/access/*` 或 `/v1/knowledge-integration` 增加一个显式联邦查询端点，鉴权后按 `user_id` 装配适配器并返回带 `kb_id` 的结果。
- 代价：约 +40~60 行 + 测试；不改变聊天延迟；仍需 `NEUROVA_KB_SECRET`。
- 边界：如果仓外没有调用方，这个端点仍是“零消费者 API”，只能算对外契约，不算真正闭环。

**C 退役**
- 删除 `federated_kb.py`（101 行）、`multi_kb_router.py`（111 行）、`test_federated_kb.py`、`test_multi_kb_router.py` 和 `kb_catalog_tool`。
- 保留 `adapters.py`（NeurFlow 与飞书同步仍用）与 `KnowledgeStorage` 的远程配置管理。
- 文档明确：iFlow/IMA/自定义 REST 不参与自动 RAG，只有飞书会同步进本地库。

**推荐（已按 A 拍板）**：按“本地优先、远程补位、失败让路”实施 A；C 作为退役备选保留在本文，B 只在已有外部调用方时成立。不要保留零消费者状态。

**D-2 `knowledge/config.py`：退役还是实现？**
- 退役：删除纸面配置；零运行时影响；代价是若产品要做备份/缓存/加密配置，需要另立项。
- 实现：把配置接到 `KnowledgeRepository`/`KnowledgeStorage`/备份任务；成本高，且会与现有环境变量形成第二套配置源，违反单一事实源。
- 推荐：退役。

### D-3 `memory_links`：A 接入聊天 / B 退役 / C 保留 API 但收紧

先摆一个已核实的问题：`memory_links` 记录没有 `user_id`/`agent_id`，而 `/sync/links` 对任何已认证用户返回**全部**链接（`knowledge_integration.py:180`）。这不只是“只写不读”，还是跨用户关联元数据泄露面。

| 维度 | A 接入聊天（链接扩展） | B 退役 | C 保留 API 但收紧 |
|---|---|---|---|
| 能力 | 记忆命中带出关联知识 | 删除端点与存储 | 外部仍可读写，聊天不消费 |
| 成本 | 加 owner 字段 + 迁移 + 可见性 + 上限 + 测试 | 删 3 个端点、存储字段、测试 | 加 owner + 过滤，约 +30 行 |
| 风险 | 上下文膨胀、老链接无主、链接质量 | 外部 `/sync/*` 客户端 404 | 仍是旁路 API，无聊天价值 |
| 不可逆点 | 老链接需定归属策略（丢弃或归默认）；否则保留泄露面 | 删数据/端点后只能从备份恢复 | 无 |
| 推荐 | 仅当规划了“记忆↔知识导航”UI | 当前首选 | 仅当确认有外部调用方 |

**A 接入聊天（做法）**
- 每轮一次 `get_memory_links()` 读取，按 `memory_id` 建映射；对每条链接用 `repo.find_item(knowledge_id)` + `repo.can_view(user, item)`（`repository.py:1068`）过滤。
- 去重后作为补充条目加入 `ctx.relevant_memories`，上限 3 条，打 `linked_from_memory=True`；不改主排序。
- 必须先给链接加 `owner_user_id`/`agent_id`，并把 `/sync/links` 改为按当前用户过滤；否则接线等于把泄露面带进上下文。
- 影响文件：`storage.py:258/276`、`knowledge_integration.py:136/163/180`、`chat_pipeline.py`、相关测试。
- 判据：无链接零变化；有链接时条目出现且带溯源；跨用户不可见；预算不超；活体用真存储验证。

**B 退役**
- 删除 `/sync/knowledge-to-memory`、`/sync/memory-to-kb`、`/sync/links`、`memory_links` 存储字段与测试；文档标注“关联能力未实现”。
- 删即失去“记忆↔知识手工关联”，但今天没有任何读取方，实际能力为零；不可逆点是外部客户端可能依赖端点。

**C 保留 API 但收紧**
- 保留端点，但加 `owner_user_id` 与过滤；聊天不消费。适合“外部系统正在用 `/sync/*`，但产品暂不做导航”的情况。

**推荐**：当前没有创建 UI、没有读取方、且存在跨用户读取问题，选 **B 退役**最干净；若确认有外部调用方，选 C。A 要等“导航 UI + 归属模型”一起立项。

**D-4 `FactSurface`：保持窄接线还是重开事实池？**
- 保持窄接线：零排序风险；只影响图走查零锚点种子/富化/注入计数。
- 重开事实池：011 已否证，recall@5 会从 0.855489 降到 0.760371；不建议。
- 推荐：保持窄接线；最多做 shadow 评估。

### D-5 灰度项：先转正哪几项？

| 项 | 收益 | 代价/风险 | 不可逆点 | 建议 |
|---|---|---|---|---|
| D-01 查询归一 | 别名驱动召回，W1 已有活体证据 | 查询过度展开；只读，无外部成本 | 无 | **第一优先**：shadow → on |
| D-02 歧义澄清 | 多口径查询不静默择一，W4 已有活体证据 | 占提示预算；可能啰嗦 | 无 | **第二优先**：shadow → on |
| D-03 脱靶登记 | 收集真实缺口，喂别名审批 | 写 DB；噪声/PII；日增量 | 已写入的候选行不会因关闸消失 | 加日上限/去重/保留期后再开 |
| D-04 FactSurface | 零锚点走查种子；治理富化 | 只读，成本低；收益不确定 | 无 | 可与 D-01/D-02 并行评估 |
| D-08 双向量 | 标题精确实体名不被正文稀释 | embedding 成本翻倍；ANN 旁路不兼容 | 索引多存向量，关闸后需重建/清理 | 单独立项评估 |
| D-11 链级 RRF | 多源并列不再只选最高质量 | 改变合并语义，需黄金集对比 | 无 | 单独立项评估 |
| D-16 事件摘要 | 索引从字面升到事件语义 | 每条一次 LLM 成本；写回并 reindex | 摘要已写入条目不因关闸消失 | 按部署 opt-in，先测成本 |
| D-19 Kreuzberg | 统一解析，减少格式分支 | 主路内容可能变化；失败必须显式 | 主路切换后旧解析结果不可自动还原，需重解析 | 先 shadow，再主路 |

**可选包**

- **包 A（推荐，最小风险）**：D-01 → D-02，各自 shadow→on；只读、无外部成本、可随时回退。随后再评估 D-03。
- **包 B（数据优先）**：D-03 先开（先加日上限/去重），用真实脱靶数据驱动别名审批，再开 D-01/D-02。代价是写入面先动，需要清理策略。
- **包 C（成本/排序类单独立项）**：D-04、D-08、D-11、D-16、D-19 各自独立 shadow 轨道，不打包、不共享默认值。
- **包 D（全部保持关）**：只加 shadow 读数，不改默认；最安全，但没有召回改进。

**推荐**：包 A，先 D-01 查询归一、再 D-02 歧义澄清；D-04 可并行评估；D-03 加限流后再开；D-08/D-11/D-16/D-19 单独立项。这样每一步都能单独归因、单独回退，不会出现“开了五项不知道是哪项起作用”。

**D-6 对账/回填：移脚本还是删除？**
- 移脚本：保留迁移期能力，生产包零死码；测试需迁移。
- 删除：更干净，但失去一次性对账/回填逃生口；不可逆。
- 推荐：移脚本（K-03），回填保持脚本且不启用（K-04）。

**D-7 非飞书同步：文档不支持还是实现？**
- 文档不支持：零成本；用户明确知道只有飞书能同步。
- 实现：需要为每个源写 `list/fetch/cursor` 与游标、增量、幂等；成本高，且没有产品需求证据。
- 推荐：文档不支持；有需求再立项。
