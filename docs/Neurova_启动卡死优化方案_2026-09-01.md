# Neurova 启动卡死优化方案（2026-09-01）

## 背景与现象

后端 `start_server.py` 一启动即出现以下实测现象：

- 启动完成后有 **~2 分钟、约 12.6 核满负荷** 的 CPU 燃烧（每 10s 累计 126s CPU 时间），随后戛然而止；
- 进程常驻内存 **4.5GB**（启动 3GB）；
- 用户感受：启动后整机卡死约 2 分钟。

## 根因（已实测闭环）

1. **MoE 语义索引线程每次启动全量重扫**（`mem_core.py:_background_index_memories`，由 `agent_core.py:450 init_moe_router` 触发）
   - 对 `agent_workspaces/default/memory/neurova_memories_persist.db`（**2,328,619 行 / 757MB**）执行
     `SELECT ... ORDER BY temperature DESC LIMIT 500 OFFSET n` —— temperature 列**无索引**，每页都全表扫描+排序；
   - 每批 500 条走嵌入编码：模型目录 `models/embedding/bge-small-zh-v1.5/` **没有 model.onnx** → ONNX 后端失败 → 回退 sentence-transformers（torch CPU，默认线程=全部核）→ 12.6 核燃烧；
   - 每批还重建 numpy 矩阵并报“向量维度不齐，numpy 加速不可用，回退暴力搜索”（历史向量与新模型维度不一致，矩阵加速永远失效）；
   - 批间仅 `sleep(0.05)`；`UnifiedVectorStore.memory_ids` **纯内存不落盘** → 每次重启从头再烧。

2. **记忆库被测试循环灌爆（共同上游）**
   - persist 库 2,328,619 行中 **2,328,380 行（99.99%）是三条测试消息的回放**：
     `助手: [LLM Error] No client available`（1,164,201 行）、`用户: 检查网页搜索功能`（775,994 行）、`用户: 你好`（388,185 行），
     集中在 2026-07-17 ~ 2026-08-31，由开发期 e2e/mock 聊天循环（LLM 无客户端 → 固定错误回复）灌入；
   - `memory_emotions`（memory.db）62 万行 = 前 62 万个记忆 ID 的情感标注（PK=memory_id 一行一条），
     99.997% 是同一档 joy —— 因为标注器是**关键词规则**（`emotion_module.py` joy 词表含单字“好”/“棒”），
     任何内容命中即机械标注；每次 `MemoryManager` 初始化全量物化 62 万个 EmotionState 对象进 dict。

3. **放大器**
   - `core/logger.py:76` `get_logger` 默认 DEBUG + 子 logger 自带 handler 且向 root 传播 → 每条日志**双写**（启动 85s 写 3765 行）；
   - persist 库 journal_mode=`delete`（无 WAL）。

## 优化措施

| # | 措施 | 文件 | 效果 |
|---|------|------|------|
| 1 | persist 库建 `temperature` 索引（CREATE INDEX IF NOT EXISTS） | `manager.py:_init_persistence_db` | OFFSET 分页由“每页全表排序”降为索引遍历 |
| 2 | MoE 索引完成状态落盘（`data/moe_index_state_<agent>.json`：limit/count/时间），下次启动已达标则跳过后台索引 | `mem_core.py` | **消灭每次启动 2 分钟重扫** |
| 3 | torch 回退限核（`torch.set_num_threads(4)`，可 NEUROVA_TORCH_THREADS 覆盖） | `onnx_embedding.py` | 一次索引时不再吃满全核 |
| 4 | 清理测试数据：删除三巨头 + 其余 count≥2 的测试话术，VACUUM，删除 emotion 孤儿行 | 一次性脚本（库已备份至 `data/backups/`） | 2.33M 行 → ~72 行；62 万 joy → 随记忆存在 |
| 5 | 情感标注语义化：新 `SemanticEmotionClassifier`（嵌入原型句 zero-shot 分类，余弦 argmax + 阈值），规则回退修正（去单字“好/棒”，加否定词“不好/不开心/不高兴”） | 新增 `memory_layer/semantic_emotion.py` + `emotion_module.py` | “你好”不再 joy；语义判断，非关键词匹配 |
| 6 | 日志去双写（`logger.propagate = False`） | `core/logger.py` | 日志 I/O 减半 |

## 验证

1. pytest：语义分类器（原型相似度/阈值/neutral）、“好”字效应回归（“你好”必 neutral）、修正规则、`set_emotion` 落库回读、manager 保存路径打标/不打标；16 个新用例全绿。最终回归与改动前基线一致（7 个既有失败，无新增）。
2. 实机重启后端（2026-09-01 20:17-20:26 实测）：

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 启动后索引燃烧 | ~120 秒 × 12.6 核 | **~56 毫秒**（日志从"每 3s 一批"变为一条完成记录） |
| 静置 CPU | +126 秒/10 秒 | **0**（连续 2 分钟零增长） |
| 常驻内存 | 4,506 MB | **334 MB** |
| 启动日志 | 3,765 行（DEBUG 双写） | 739 行（单写） |
| 记忆库行数 | 2,328,619 行 / 757 MB | 46+2 行 / 0.1 MB |

3. API 端到端（/api/v1/memory/emotion/analyze + /api/v1/memory + 直查 DB 对账）：
   - "我今天特别开心，终于见到了期待已久的演唱会，太棒了！" → `joy / 0.6587`（语义路径强度，规则引擎只会给 0.333）；
   - "我很难过，这次考试考砸了，非常伤心" → `sadness / 0.8522`；
   - "你好，请问现在几点"、"检查网页搜索功能" → `neutral`，且连续两次写入 **0 条 emotion 行**（好字效应根除，回放不再污染表）；
   - 顺带修复：API 传 `category=null` 时 `_persist_memory` 因 `.value` 炸掉导致内容不落库（manager.remember 的 None 解析分支），已修 + 回归测试。

## 遗留项（不在本次范围）

- 测试/回放带来的新污染预防：聊天记忆入库时应跳过 `[LLM Error]` 等错误回复、e2e 用隔离 workspace（另立任务）；
- keyset 分页替换 OFFSET（有温度索引后收益有限，列为后续）；
- `_dream_logs`/`trace_recorder`/`tool_execution_manager._contexts` 无界增长（长期泄漏候选，另立任务）；
- 记忆 ID 计数器重启后来源不一致 → 可能复用旧 id 导致残留情感行错挂（观测到的 2328625 案例），需另立任务核查计数器持久化。

## 第二轮：资源消耗全盘修复（2026-09-01 已实施 + 9 用例防回归）

静置期确认无 CPU/内存异常后，修复"使用中累积型"无界点（全部有界化/淘汰化，回归测试见 tests/unit/core/test_resource_bounding.py）：

| P1-2 | agent/tool_execution_manager.py | 终态上下文每次执行结束触发清理（>5min）+ 硬上限 500 按完成时间淘汰；逻辑提取为 _evict_over_capacity |
| P1-3 | agent/tool_coordinator.py | 后台任务观察完成后移入 _completed 有界留存(200)，活动 _background 不再堆积；get_background_status 兼容留存 |
