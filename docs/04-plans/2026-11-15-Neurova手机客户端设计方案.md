## 1. 目标与结论

**目标**：一部手机，随时随地操作 Neurova——对话、知识库、文件、任务、通知、（管理员的）运维观测；
按**租户（部门根）**隔离登录；服务端无论部署在**内网、有公网固定 IP、还是无固定 IP**，手机都连得上。

**结论先行**：

1. **服务端零新建面**。全部能力复用现有 `/api/v1/*`：对话 SSE（`POST /v1/chat/stream`）、
   移动 WS（`/v1/mobile/ws`）、扫码配对（`/v1/mobile/pairing/*`）、租户身份链（JWT `tenant_id` claim）。
   不新造第二套认证、配对或隧道协议（教义第 6 条）。
2. **三形态网络接入的设施已全部在仓**：内网直连（`NEUROVA_HOST=0.0.0.0`）、
   公网固定 IP（反代 + `NEUROVA_ADVERTISED_BASE_URL` + 代理头已接线）、
   无固定 IP（自研中继 `python -m neurova.relay` + `tunnel/agent` 出站隧道，已实施）。
   剩下的只是**部署配置与客户端侧的连接管理**（§4），不是新协议。
3. **客户端形态已裁"两端"（D1）**：鸿蒙端沿用已存在的 `Mobile/harmony` 工程（60+ 页面，协议已对齐）；
   安卓端新建 **Vue3 + Capacitor** 工程，最大化复用 `NeurUI` 的 30+ API 模块、
   Pinia store 与组件资产；**客户端构建物统一放置于仓库根 `Mobile/`**
   （harmony / android / dist 三层，见 §7）。
4. **三个服务端尾巴**必须随本项目补齐：helm ingress 的 WS 升级注解、CORS 生产白名单配置指引、
   移动离线推送桥（已裁做，D2；现通知只有 SSE，App 退后台即失联）（§10）。

## 2. 现状盘点（事实基线）

### 2.1 服务端能力面（手机端要装进去的功能，全部已有端点）

路由前缀唯一事实源：`ENDPOINT_MODULES` 注册表（`neurova/api/endpoints/__init__.py:211-334`），
实际路径 = `/api` + 表中前缀。手机端核心消费面：

| 功能域 | 端点（省略 `/api` 前缀） | 手机端场景 |
|---|---|---|
| 对话 | `POST /v1/chat`、`POST /v1/chat/stream`（SSE）、`GET /v1/chat/history`、`POST /v1/chat/attachment` | 聊天主界面，流式渲染、历史回看、传图/传文件 |
| 移动 WS | `WS /v1/mobile/ws`（`chat:send/chat:cancel/chat:chunk/chat:done`） | 弱网/后台保活的备用对话通道 |
| 会话 | `GET /v1/console/chat/sessions`、`/v1/sync` | 会话列表、置顶/归档/重命名、跨端续聊 |
| Agent | `GET /v1/agents`（属主过滤） | Agent 列表与切换 |
| 知识库 | `POST /v1/knowledge/search`、`/v1/knowledge/*`、`/v1/knowledge-graph` | 移动检索、条目浏览、图谱速览 |
| 文件/产物 | `POST /v1/files/upload`、`/v1/files/*`、`GET /v1/artifacts/{id}/content`、`/v1/media`、`/v1/image` | 拍照/相册上传、产物预览 |
| 任务 | `/v1/tasks/boards`、`/v1/scheduler`、`/v1/neurflow` | 任务看板速览、进度跟进 |
| 通知 | `GET /v1/notifications`、`/unread-count`、SSE `/stream` | 角标、通知列表 |
| 模型 | `GET /v1/models` | 对话页模型选择 |
| 认证 | `POST /v1/auth/login`、`/v1/auth/refresh`、`GET /v1/auth/me`、`POST /v1/auth/logout` | 登录、续期、登出 |
| 配对 | `/v1/mobile/pairing/*` | 扫码绑定设备（§5.3） |
| 运维观测 | `/v1/health`、`/v1/stats`、`/v1/monitor`、`/v1/logs*` | 管理员的移动巡检（P2） |

### 2.2 移动端既有资产

- **Mobile/harmony（鸿蒙 App，已存在）**：`entry/src/main/ets/pages/` 下 60+ 页面
  （Chat/Login/Pairing/Knowledge/Memory/Task/Collaboration/Model/Monitor/...），
  `libs/api/modules/` 下 20 个 API 模块，`libs/adapters/WebSocketAdapter.ets` 已实现
  Authorization 头/子协议双通道（《中继方案》§6.4）。
- **mobile_pairing 服务端（已实施）**：`neurova/api/endpoints/mobile_pairing.py`（1316 行）——
  扫码配对全生命周期、一次性 `connect_ticket`（60s）+ 长期 `device_secret`、
  续签 `/pairing/refresh`、在册设备持久注册表（`mobile_device_store`，SQLite）。
- **自研中继（已实施）**：`neurova/relay/app.py`（382 行，可独立部署 `python -m neurova.relay`）
  + `neurova/tunnel/agent.py`（359 行，服务端出站隧道）+ `neurova/tunnel/protocol.py`
  （223 行，线格式与状态字面量单源）。
- **NeurUI（Web 端）**：Vue 3.5 + TS + Pinia + vue-router + ant-design-vue + axios
  （`NeurUI/package.json`）；`src/api/modules/` 30+ 接口模块、40+ 页面；
  **无成体系移动适配**（无移动 UI 库、无 rem/vw 方案，仅约 15 处零散 `@media`）。

### 2.3 身份与租户链（现状，直接复用）

- **认证**：JWT HS256（`neurova/api/auth.py:29`），Access 60 分钟 / Refresh 7 天；
  `Authorization: Bearer` 头；`POST /v1/auth/refresh` 续期；登出进内存黑名单；
  失败 5 次锁定；全局鉴权中间件 `NEUROVA_GLOBAL_AUTH=off/shadow/enforce`
  （`neurova/api/global_auth.py:98-156`）。
- **租户 = 部门根组**：`resolveUserDepartment(username)`
  （`neurova/auth/user_group_model.py:1025-1098`）沿 `parent_group_id` 上溯到部门根，
  返回 `tenant_id`（部门根 `group_id`）+ 分类白名单；登录/刷新时经 `buildIdentityClaims`
  写进 JWT（`neurova/api/endpoints/auth.py:330-336`）。
- **隔离四层**（服务端已实现，客户端无须也无法自报身份）：
  ① 知识/本体域 SQL `WHERE tenant_id = ?`（`knowledge_facts`、`ontology_terms` 等表带列）；
  ② 记忆域请求作用域 ContextVar（`deps.get_memory_manager`）；
  ③ chat 部门对账门 `_deptGate`（`chat.py:179-197`，跨部门用 agent 即 403）；
  ④ 组档位限流（`group_rate_quota.py`）。
- **手机端含义**：登录后一切数据的租户边界由服务端按 JWT 裁定；App 不做任何本地租户过滤，
  只**展示**当前租户（部门名）作为上下文提示。

### 2.4 部署现状

- 端口单源：后端 9527、前端 8100（`scripts/config.py:23-24`）；`start_server.py` 默认绑
  `127.0.0.1`，局域网须显式 `NEUROVA_HOST=0.0.0.0`。
- 代理头已接线：`config.proxyUvicornArgs()`（`neurova/core/config.py:510-527`）在两个启动点生效
  （`start_server.py:157`、`neurova/api/app.py:1870`），`forwarded_allow_ips` 默认仅回环，
  经反代须配 `NEUROVA_FORWARDED_ALLOW_IPS`。
- 对外地址单源：`NEUROVA_ADVERTISED_BASE_URL`（`mobile_pairing.py:289-297`），
  优先级 隧道路由 > advertised > 入站请求。
- 容器化：`Dockerfile` + `docker-compose.yml`（默认只发布到宿主回环）+ `helm/neurova/`。
- **无任何 TLS 证书配置**（仓库内仅 helm 示例占位）；CORS 默认白名单只有
  localhost 开发端口与 Tauri 桌面壳（`neurova/api/cors_policy.py:29-38`），公网域名须
  `NEUROVA_CORS_ORIGINS` 或 `config/cors.json` 显式加入。
- helm ingress 注解**缺 WS 升级**（`values-production.yaml:43-47` 无
  `proxy_http_version`/`Upgrade`，与《中继方案》§7 记录一致）。

## 3. 总体架构

```
┌─────────────────────────┐
│ 手机客户端                │
│  呈现层（页面/组件）      │
│  领域层（会话/流式/租户） │
│  接入层（HTTP·SSE·WS·   │
│   服务器档案·凭证仓）     │
└───────────┬─────────────┘
            │ HTTPS / WSS（Bearer JWT 或设备 ticket）
┌───────────▼─────────────┐
│ 接入层（三选一或并存）    │
│  A 内网直连 :9527        │
│  B 反代+TLS（固定公网IP） │
│  C 自研中继 /t/<routeId> │
└───────────┬─────────────┘
            │
┌───────────▼─────────────┐
│ Neurova 服务端 :9527     │
│  /api/v1/*（现有全部面） │
│  mobile_pairing·tunnel  │
└─────────────────────────┘
```

客户端内部分层（两端同构）：

- **接入层**：唯一知道"服务器在哪、用什么凭证"的一层。
  服务器档案（§4.5）、JWT/设备凭证存取（§9.2）、HTTP/SSE/WS 三个通道适配器、
  401 单飞刷新、网络切换重连（复用《中继方案》M3 状态机语义）。
- **领域层**：会话与消息流、租户上下文（只读展示）、通知未读数、上传队列。
  全部状态机与字面量从 `tunnel/protocol.py` 口径取，不各自造词（§5.6 of 中继方案）。
- **呈现层**：页面与组件。禁止出现任何服务器地址、token、状态字面量的第二份定义。

## 4. 网络接入设计（三形态）

### 4.1 总览与选型

| 形态 | 适用 | 入口 | 手机连什么 | 前置条件 |
|---|---|---|---|---|
| A 内网直连 | 家庭/办公室同网段 | `http://<内网IP>:9527` | 直连后端 | `NEUROVA_HOST=0.0.0.0` |
| B 公网固定 IP | 云服务器/有公网 IP 的宽带 | `https://neurova.example.com` | 反代（nginx/caddy）→ 9527 | 域名 + TLS 证书 + 反代 |
| C 无固定 IP | 家宽/CGNAT/无公网 | `https://<中继域名>/t/<routeId>/...` | 自研中继（服务端出站连中继） | 一台有公网地址的 VPS 跑中继 |

三形态**可并存**（《中继方案》§5.2 的 `direct` 与 `via_relay` 并存语义）：
同一台服务端可以在内网直连的同时注册到中继；客户端按服务器档案逐台配置。

### 4.2 形态 B：公网固定 IP + 反向代理（推荐反代样板）

**推荐 nginx**（示例，置于 `/etc/nginx/conf.d/neurova.conf`）：

```nginx
server {
    listen 443 ssl;
    server_name neurova.example.com;

    ssl_certificate     /etc/letsencrypt/live/neurova.example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/neurova.example.com/privkey.pem;

    # 上传大文件（知识库导入、媒体）
    client_max_body_size 100m;

    location / {
        proxy_pass http://127.0.0.1:9527;
        proxy_http_version 1.1;

        # WS 升级（/api/v1/mobile/ws、/api/v1/sync/ws/*）
        proxy_set_header Upgrade    $http_upgrade;
        proxy_set_header Connection $connection_upgrade;   # map 见下

        # 透传真实来源（服务端 proxyUvicornArgs 依赖这两组头）
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Host              $host;

        # SSE 不缓冲（/api/v1/chat/stream、/api/v1/notifications/stream）
        proxy_buffering off;
        proxy_cache off;

        # 长连接超时（SSE 15s 心跳 + 流式回合）
        proxy_read_timeout  3600s;
        proxy_send_timeout  3600s;
    }
}

map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
```

用 Caddy 等价更简（自动 HTTPS）：反代块 `reverse_proxy 127.0.0.1:9527` +
`flush_interval -1`（SSE）即可，WS 自动支持。

**服务端配套（必做三项）**：

1. `NEUROVA_FORWARDED_ALLOW_IPS` = 反代机网段（本机反代即 `127.0.0.1`）——
   否则 `X-Forwarded-*` 不被采信，wss 判定与按真实 IP 限流同时失效（《中继方案》§2.3 的教训）。
2. `NEUROVA_ADVERTISED_BASE_URL=https://neurova.example.com`——配对二维码/回连地址的对外口径。
3. `NEUROVA_CORS_ORIGINS=https://neurova.example.com`（Web 端同域时其实不触发 CORS；
   若 App 用 WebView 壳或浏览器访问才需要；原生 App 的 HTTP 请求不受 CORS 约束，此配置为 Web 面预留）。

### 4.3 形态 C：无固定 IP → 自研中继反向隧道（已实施）

不重复设计，直接沿用《中继方案》。部署侧要点（新提炼）：

- **中继机**：任意有公网地址的 VPS，`python -m neurova.relay`（只依赖仓内已在清单的
  FastAPI/uvicorn/httpx），前置 Caddy/nginx 终结 TLS。
- **服务端侧**（家里的 Neurova）配置两个键：
  `NEUROVA_TUNNEL_RELAY_URL=wss://<中继域名>` 与
  `NEUROVA_TUNNEL_ENROLLMENT_TOKEN=<准入凭据>`（`tunnel/protocol.py:139-140`）。
  enrollment token 是**唯一的注册准入**，泄露即等于别人能把流量路由走（《中继方案》§4.4）。
- **路由形状**：手机连 `https://<中继>/t/<routeId>/api/v1/...`；`routeId` 由
  `HMAC(enrollmentToken, instanceId)` 派生（`relay/app.py:52-56`），不可自选、不可覆盖、
  同 instanceId 幂等——服务端重连/漂移不需要重新配对。
- **CGNAT 边界**：无公网 IPv4（含大运营商 CGNAT）时形态 B 物理不通，必须走本形态
  （《中继方案》§7 已载，用户指南须明示）。
- **已知代价（如实）**：中继终结 TLS，能读到明文；缓解 = 中继只部署在用户自己的 VPS +
  访问日志走 `sensitive_info` 单源脱敏。E2E 加密排后续（中继方案 S3）。

### 4.4 形态 A：内网直连

- 服务端 `NEUROVA_HOST=0.0.0.0`（或 compose 改端口映射）。
- 手机与服务器同网段时客户端直连 `http://<内网IP>:9527`；纯 HTTP 仅限内网，出了内网即须 B/C。
- 配对二维码此时由 `_wsOrigin` 的 fallback 分支给出局域网地址
  （`mobile_pairing.py:331-333`），扫码即可用。

### 4.5 客户端连接管理（新增的客户端子系统）

**服务器档案 `ServerProfile`**（已裁做，D4；两端同构，鸿蒙端已有 `ConfigManager` 雏形）：

```
ServerProfile {
  id, name                      // "家里"、"公司"、"VPS"
  entryMode: direct | relay     // 入口形态
  baseUrl                       // direct: http(s)://host:port；relay: https://<relay>
  routeId?                      // relay 形态的路径前缀
  lastConnectedAt, lastSeenTenant
}
```

- **地址解析优先级**：用户手动档案 > 扫码结果（`ref` → `resolve` 回的 `ws_url` 反解）>
  发现域名默认值。与《中继方案》§3.4 一致：二维码不含 host，地址是 resolve 时现算的。
- **连接健康探测**：登录前先 `GET /api/v1/health`（公开白名单路径）判可达；
  不可达时按档案逐个尝试，不把网络故障渲染成"账号密码错误"。
- **网络切换**：WiFi↔蜂窝、回前台 → 连接状态机进 `reconnecting(0)`（计数清零立即重连）；
  IP 漂移后中继 `routeId` 不变，无需重配对（《中继方案》§5.3 已定义，客户端照实现）。
- **会话内通道选择**：前台聊天走 SSE（`/v1/chat/stream`，Bearer JWT）；SSE 连不上或退后台
  恢复时切 WS（`/v1/mobile/ws`）。两通道事件语义对齐表见 §8.3。

## 5. 登录与租户

### 5.1 登录流程（主通道：账号密码 → JWT）

```
App 启动
  → 读安全存储：有 refresh_token？ ──有──▶ POST /v1/auth/refresh 换新对 → 进主界面
  │                                    └─失败（被踢/改密）→ 清除 → 登录页
  └─无──▶ 登录页：[服务器档案] + 用户名 + 密码
            → POST /v1/auth/login {username, password}
            ← {access_token(60m), refresh_token(7d), expires_in}
            → GET /v1/auth/me → 展示用户与角色
            → 安全存储写入（Keychain/Keystore/HUKS，§9.2）→ 进主界面
```

- 登录页必须先选/填**服务器档案**（§4.5）再输账密——同一台手机可配多台 Neurova。
- 401 处理：单飞刷新后重放原请求（先例 `NeurUI/src/api/index.ts:139-160`）；
  refresh 也 401（登出/改密/被禁用）→ 清凭证回登录页，**不静默重试**。
- 登出：`POST /v1/auth/logout`（token 进服务端黑名单）+ 清本地安全存储。

### 5.2 租户的登录态呈现

- 登录成功后 JWT 已携带 `tenant_id`（部门根），服务端全链隔离（§2.3）。
- App 侧**只读展示**：主界面顶栏或"我的"页显示当前用户 + 所属部门根名
  （`/v1/auth/me` + 组名映射），作为"我现在以哪个租户身份在操作"的上下文提示。
- App **不实现**任何本地租户过滤/切换逻辑；越权尝试由服务端 403 兜底
  （`_deptGate`、分类白名单），App 对 403 的呈现是"无权访问该资源"，不是全局登出。

### 5.3 设备配对（辅助通道：免密绑定）

沿用已实施的扫码配对（《中继方案》全案），在客户端作为**登录的快捷替代**：

- 场景：桌面 Web 已登录属主，在 `MobilePairingPanel` 生成二维码；
  手机 App 扫码 → `resolve` 拿回连地址 → `confirm`（自动，无需手输）→
  拿 `device_secret`（长期设备身份）+ `connect_ticket`（一次性）。
- 配对把设备挂到**属主账号**名下：此后该设备可用 `/pairing/refresh` 续签票据，
  以该属主身份走 WS 通道；属主在面板可随时解除（epoch 失效即断）。
- **与 JWT 的关系**：两条凭证体系并行不混用——账号登录拿 JWT（REST+SSE 主用）；
  设备凭证只走移动 WS 通道。App 内两者可共存（同一账号既登录了又配对了设备），
  凭证分仓存储、互不覆盖。
- 手机上"扫自己手机上的码"无意义，故 App 的配对入口 = 扫**桌面屏幕**上的二维码；
  无桌面在旁时走账号密码登录。

### 5.4 租户切换（已裁 D3：按"退出登录 → 新账户登录"实现）

现状 `resolveUserDepartment` 单向解析：一个用户 → 一个部门根 → JWT 一个 `tenant_id`。
已裁**不做登录时租户选择器**，租户切换的语义落在账号切换上：

- 一个账号登录后，其部门根租户即随 JWT 固定；要换租户 = 「我的」页**退出登录** →
  登录页以**属于目标租户的另一账号**登录。
- 服务端**零改动**：`resolveUserDepartment`、claim 注入、隔离四层全部沿用；
  登出黑名单（`/v1/auth/logout`）保证旧 token 立即失效，换账号不留残余会话。
- App 侧动作：`我的` 页展示当前账号与所属部门（租户），提供「切换账号」入口
  （= 登出 + 回登录页）；服务器档案按 §4.5 各自记忆该服务器下最后登录的账号，
  换档案不串账号。
- 多服务器 × 多账号矩阵：每台服务器档案独立持有自己的凭证与租户上下文；
  切换服务器必经各自的登录/刷新链，互不共享 token。

## 8. 关键流程

### 8.1 登录 + 租户（时序）

```
App            服务端
 │ POST /v1/auth/login ────────▶│ 校验+锁定计数
 │                              │ resolveUserDepartment → 部门根
 │ ◀── TokenResponse(JWT: sub,tenant_id,...)
 │ GET /v1/auth/me (Bearer) ───▶│
 │ ◀── 用户/角色/部门展示数据     │
 │ 此后所有请求自动带租户边界     │（服务端 _deptGate/白名单/tenant_id 裁定）
```

### 8.2 扫码配对（时序，引用《中继方案》§3.4，已实施）

```
桌面面板 POST /v1/mobile/pairing/generate (JWT)
  ← {code(6位), ref(22B), qr_code_url}
手机 App 扫码 neurova://pair?ref=…（不含 host）
  POST /v1/mobile/pairing/resolve {ref} → {ws_url}   （ref 一次性消费）
  POST /v1/mobile/pairing/confirm {ref, device_name} → {connect_ticket(60s), device_secret(长期)}
  WS ws_url（Authorization: Bearer <connect_ticket>）
  … ticket 过期 → POST /v1/mobile/pairing/refresh {pairing_id, device_secret, challenge}
```

### 8.3 对话双通道事件映射

| 语义 | SSE（`POST /v1/chat/stream`，主） | 移动 WS（`/v1/mobile/ws`，备） |
|---|---|---|
| 开始 | `start {request_id, session_id}` | （无独立帧，随首 chunk） |
| 正文增量 | `message {content}` | `chat:chunk {content, session_id, index}` |
| 思考链 | `reasoning {content}` | 并入 `chat:chunk`（现无独立帧，如实标注） |
| 重试/让位 | `retry {phase, wait_seconds, ...}` | 无（WS 通道不透传，前台切 SSE 才有） |
| 挂起 | `parked {run_id, resume_via}` | 无 |
| 取消 | （HTTP 中断） | `chat:cancel` → `chat:cancelled` |
| 结束 | `done {request_id}` | `chat:done {session_id, message_id}` |
| 失败 | `error` | `error {code, message}` |
| 保活 | `: ping`（15s 注释行） | `ping`/`pong` 应用层心跳 |

客户端策略：前台默认 SSE；SSE 建连失败/中断且页面仍在前台 → 自动降级 WS 重发同一消息
（以 `session_id` + 客户端幂等键去重，避免双通道重复回答）。

### 8.4 通知与离线推送（已裁做，D2；**服务端已实施 2026-11-15**：`neurova/notifications/push_store.py`+`push_sender.py`+端点 `/api/v1/mobile/push/*`，token 表走迁移域 mobile_push，扇出挂 notify_user 门面后台线程；App 侧上报/注销接口就绪，端内接入选 M2+/M4 批）

- 前台：SSE `/v1/notifications/stream` + 未读数轮询降级。
- 后台离线推送：新增**推送桥**（唯一新建服务端面）：
  - App 启动/登录后上报设备推送 token → 新表 `mobile_push_tokens`
    （`user_id`、`platform`（harmony/android）、`push_token`、`device_id`、`updated_at`，
    一用户多设备并存，进 `core/db_migration.py` 注册表）；
  - 服务端通知落库后按该用户的设备行扇出：**鸿蒙 = 华为 Push Kit**；
    **安卓 = FCM**（覆盖带 GMS 设备）。国内无 GMS 设备的厂商通道
    （华为/小米/OPPO/vivo/荣耀）列为后续扩展批，不进本期承诺——
    无 GMS 且未接厂商通道的设备，推送能力如实降级为"仅前台可达"，
    App 内连接徽标与设置页明示，不冒充已推送。
  - 推送只带**信令**（通知 id/类型），正文由 App 拉取 `/v1/notifications`，
    避免敏感内容过第三方推送通道。
- 服务端扇出点：`notifications` 落库路径后置 hook（异步、失败重试有限次、
  推送失败不影响 SSE 面读数）；推送凭证（FCM 服务账号 / Push Kit 凭据）
  走 `secret_store`，管理端只显"已配置/未配置"不回显。

## 9. 安全设计

### 9.1 传输与准入

- 三形态 TLS 终结点：A 内网可明文（仅局域网）；B 在反代终结；C 在中继终结（风险已登记）。
  客户端对 B/C 一律 `https/wss`；对 A 允许 `http` 但档案上明示"仅限内网"。
- 准入复用现有闸门：登录失败锁定（5 次）、`confirm/refresh` 每 IP 滑窗限流、
  `resolve` 匿名口限流、单用户 WS 连接上限 5（`protocol.py:37`）。
  经反代后这些按**真实来源 IP** 生效的前提是 §4.2 的 `NEUROVA_FORWARDED_ALLOW_IPS` 配置，部署清单必含。

### 9.2 客户端凭证存储

| 凭证 | 生命周期 | 存储位置 |
|---|---|---|
| access_token | 60 分钟 | 内存 + 安全存储（重启恢复用） |
| refresh_token | 7 天 | 安全存储（iOS Keychain / Android Keystore / 鸿蒙 HUKS），**不落明文 preferences** |
| device_secret（配对设备身份） | 至解除 | 同上，独立键，与 JWT 分仓 |
| connect_ticket | 60 秒一次性 | 仅内存 |

- 禁止把任何凭证写进 URL（含日志/统计）；WS 凭证走 `Authorization` 头或子协议
  （`_ticketFromHandshake`，`mobile_pairing.py:1162-1176`），`?token=` 仅作 legacy 兼容不新用。
- 生物识别（FaceID/指纹）仅用于"解锁已保存的会话"，**不替代**登录凭据（P2 增强）。

### 9.3 数据与隐私

- 本地缓存（会话/知识条目）存应用沙箱，iOS/Android 启用 backups 排除；登出即清。
- 截屏防护、越狱/root 检测列为 P2 可选加固，不进 P0 承诺。

## 13. 不做的事

- 不新建第二套认证/配对/隧道协议；不改 `/api/v1` 既有契约（只消费）。
- 不在 App 侧实现租户过滤或身份推断——租户边界唯一权威在服务端（AGENTS §3 身份单通道）。
- **不做登录时租户选择器**（D3 已裁：租户切换 = 退出登录后以新账户登录，§5.4）。
- **iOS 端不在本期范围**（D1 已裁两端：鸿蒙 + 安卓）。
- 不做服务端 schema 级/库级多租户分片（现行"单库 + 行级 tenant_id + 请求作用域"已覆盖需求）。
- 不做 P2P 打洞/IPv6 直连（中继方案已裁，CGNAT 走中继）。
- 不做附件分片续传（服务端无对应端点，如实不做）。
- 不把 App 做成 NeurUI 的整站搬运：管理面（用户/组/渠道/设置写操作）不进手机端，
  P2 巡检只读。
