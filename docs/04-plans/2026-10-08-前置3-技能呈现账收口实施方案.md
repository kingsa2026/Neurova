# 前置条件 3（呈现与采纳分离计数）实施方案

> **执行须知**：逐步用 `- [ ]` 复选框跟踪；每个 Task 独立红→绿→自证→提交。
> 落地纪律的权威源是 `AGENTS.md`（核心原则 / 修复教义 / §2-§5），本方案只给命令级与代码级细节；
> 与本仓 `neurova-repair-batch-pipeline` 的八段流水线一一对应。

**Goal:** 给"技能进了 prompt 目录但没被派发"这一格补上唯一一份账，并退役它已有的第二份定义，
使 `呈现 → 派发 → 执行 → 完成` 四级同在一份账本上可读、可判、可回写。

**Architecture:** 呈现事件由**目录渲染处**经注入回调上报（skills 层零反向依赖，先例
`pattern_crystallizer.attach_ingestion_gate`），落进 `turn_context` 既有的**轮次技能漏斗账本**
（新增 `stage="presented"` 条目 + 轮级去重），由既有 flush 通道
（`post_chat_pipeline._step_skill_funnel_flush`）经 `compute_skill_funnel_update` 归因后写穿
manifest `usage.presentations`，读侧是一份三态 `GateVerdict`，挂在 RSI 状态面既有格旁。
**不新建第二本账、不新建第二个观测通道、不改淘汰/prune 判据口径**（后者登记为后续批次）。

**Tech Stack:** Python 3.12 / pytest（`.venv/Scripts/python.exe -m pytest`）/ JSON manifest /
ContextVar 轮次账本 / `GateVerdict` 三态契约。

**Spec:** `docs/08-research/designer_rsi_paper_vs_neurova_rsi_comparison_2026-10-08.md`
§8「前置 3」+ §6-4（无写入方）、§6-5（同一份 `unmerged` 两次取锁）。本方案是该条目的落地票面。

| 同上 | `times_presented` | **无** | **无** | Task 5 删净 |

选定的呈现落点是 **manifest 漏斗**，依据四条：唯一有生产咽喉写入、有 flush 归因纪律
（"兜底完成不计功"`skill_service.py:38-39`）、持久化在 manifest、已有 ≥3 个现役读方。
把新格补进 `usage_stats` 等于给一份**零写入零读取**的平行定义再配一条写入路——教义第 6 条禁止的形态。

**去重语义（写死在此，避免实现期漂移）**：一轮内同一技能只记一次呈现。
依据：目录段经 `_skill_catalog_section` 单源 helper 被 `build_context`（`context/orchestrator.py:1222`）
与 `build_system_prompt`（`:2752`）两条路径各渲一次（该函数 docstring `:2654-2655` 自陈"单源 helper，
双路径共用"）；逐次累加会把一轮读成两轮。
**冷臂不计数**：`get_turn_skills_off()` 为真时该函数在 `:2665-2666` 提前返回空串，天然不触发回调——
这条要在测试里钉住，因为 P2-4 的 A/B 语义正依赖"cold 臂 = 目录缺席"。
**截断不计数**：被 `max_lines` 裁掉、只写进"还有 N 个未列出"的技能**没有进 prompt**，不得计呈现
（`:155-157`）。

```python
def record_turn_skill_funnel(
    skill_id: str,
    applied: bool,
    ok: bool,
    pool: str = "agent",
    owner_key: str = "",
    stage: str = "dispatch",
) -> None:
    """记一条本轮技能派发：applied=是否真正进入执行，ok=执行是否成功。

    Wave H-W1 三层库：pool/owner_key 记录命中的副本所在库（agent 库默认，
    与既有调用零差异），flush 据此路由回写各库账本。

    `stage` 区分账本里的两类条目：`dispatch`（执行咽喉记的派发）与
    `presented`（目录渲染记的呈现）。二者同账不同判据——呈现条目不得计入
    selections（它只说明"进了 prompt"，不说明"被点名"）。
    """
    _skill_funnel_ledger().append(
        {
            "skill_id": skill_id,
            "applied": bool(applied),
            "ok": bool(ok),
            "pool": str(pool or "agent"),
            "owner_key": str(owner_key or ""),
            "stage": str(stage or "dispatch"),
        }
    )


def recordTurnSkillPresentation(
    skill_id: str, pool: str = "agent", owner_key: str = ""
) -> None:
    """记一条本轮技能呈现：技能行进进了 prompt 目录即算，与是否被派发无关。

    轮级去重——目录段由 build_context 与 build_system_prompt 两条路径共用
    （`context/orchestrator.py` 的单源 helper），逐次累加会把一轮读成两轮。
    """
    ledger = _skill_funnel_ledger()
    for item in ledger:
        if item.get("stage") == "presented" and item.get("skill_id") == skill_id:
            return
    record_turn_skill_funnel(
        skill_id, applied=False, ok=False, pool=pool, owner_key=owner_key,
        stage="presented",
    )
```

`__all__`（`:589-610`）在 `"record_turn_skill_funnel"` 之后加一行 `"recordTurnSkillPresentation",`。

```python
def presentationFunnelVerdict(usageRows: List[Dict[str, Any]]) -> GateVerdict:
    """呈现→派发漏斗判据（前置 3 的读侧；三态不是布尔，没量到不许报"没压力"）。

    - `unevidenced`：累计呈现 0 —— 目录未注入 / 账本刚上线，无从判断；
    - `failed`：有呈现而零派发 —— 技能进了 prompt 却没人点名；
    - `passed`：呈现与派发都有读数。
    输入是各技能的 manifest usage 读数（含 presentations/selections 两键），
    由调用方取数注入——本函数不碰存储，保持可单测。
    """
    presentations = sum(int(r.get("presentations", 0) or 0) for r in usageRows or [])
    selections = sum(int(r.get("selections", 0) or 0) for r in usageRows or [])
    if presentations == 0:
        return GateVerdict.unevidenced("无呈现读数（技能目录未注入或账本未记录呈现）")
    evidence = {"presentations": presentations, "selections": selections,
                "skills": len(usageRows or [])}
    if selections == 0:
        return GateVerdict.failed(
            f"呈现 {presentations} 次而派发 0 次——漏斗在第一节就断", evidence=evidence
        )
    return GateVerdict.passed(
        f"呈现 {presentations} 次、派发 {selections} 次", evidence=evidence
    )
```
