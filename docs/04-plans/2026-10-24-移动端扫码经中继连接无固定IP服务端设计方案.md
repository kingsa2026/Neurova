## 1. 结论与已裁决策

**结论**：服务端无固定 IP 时，"反向代理"必须由服务端**主动出站**建立长连接（反向隧道）才成立——手机需要一个固定的公网入口，而这台机器自己给不出这个入口。更深一层的障碍不在网络而在**数据形状**：今天那张二维码把「谁在配对」和「服务在哪」写进了同一个字节串，于是地址一变，已发的码与已配的设备一起作废。

本设计的头号原则即由此而来：**凭据与地址彻底分离**。二维码只携带高熵一次性引用，地址在扫码后向发现服务换取。

用户已裁三条：

1. **隧道形态 = 自研中继**（不引入 cloudflared/frp 等第三方二进制；协议、日志、凭据、路由全部落在本仓，符合 AGENTS.md §2 自主性与教义第 6 条单源）。
2. **中继位置 = 终结 TLS**（换取路径前缀路由、免每实例证书；代价见 §4.5，作为已登记风险如实呈现，不含糊）。
3. **二维码载荷 = 高熵一次性 `ref`**（枚举面从 10⁶ 抬到约 2¹³⁰；6 位短码保留作手输，与 `ref` 同属一条配对记录的两个入口，**不建第二套凭据体系**）。

另两则子裁定**也已落**（论证与否掉项见 §10）：④ `scanned` 超时＝**直接 expired、不设宽限计时器**（`ref` 一次性，不可回边）；⑤ 凭证策略＝**设备身份长期 ＋ 接入凭证分钟级可续签**，在册设备**长期保留、超 30 天无活动只提醒不代删**——连带必须先修「解除配对后旧凭证仍连得上」这个今天就存在的洞（§4.8，归 S1a，不等隧道）。

## 2. 现状实测（事实基线）

### 2.1 后端配对链已修通，但地址向入站请求要

链路 `generate → qrcode/{code} → confirm → WS /api/v1/mobile/ws` 在 §6-154／§6-161／§6-172 批 25–29 逐段修通（真二维码、回连路径向路由表要、按码读口上登录门）。

- 二维码渲的是**含 host 的完整 ws 地址**：[neurova/api/endpoints/mobile_pairing.py:633](../../neurova/api/endpoints/mobile_pairing.py#L633) 调 `_build_ws_url(request, code=code)`；该函数 [mobile_pairing.py:184-201](../../neurova/api/endpoints/mobile_pairing.py#L184) 的 scheme 取 `request.url.scheme`、host 取 `request.url_for("mobile_websocket")` 的来处。
- 渲染器全仓一处：[neurova/channels/qrcode_auth.py:75-87](../../neurova/channels/qrcode_auth.py#L75)（segno），本设计继续沿用，不第二份。

### 2.2 两端二维码载荷各说各话

- App 侧声明格式 `neurova://pair?code=XXXXXX`，用正则 `/code=([A-Za-z0-9]{6})/` 抠码：[NeurovaHarmony/entry/src/main/ets/pages/PairingPage.ets:50-51](../../NeurovaHarmony/entry/src/main/ets/pages/PairingPage.ets#L50)。
- 服务端实际渲出的是裸 `ws://<host>/api/v1/mobile/ws?code=…`。
- **两者今天只靠 `code=` 这个子串巧合对上。** 改成 `ref` 形状后这条路直接断——载荷格式必须由 `protocol.py` 单源定义，两端各抄正则即教义第 6 点点名的双源。

### 2.3 代理头缺失 ⇒ 经代理后两件事同时坏

全仓无 `X-Forwarded-*` 处理，uvicorn 启动未开 `proxy_headers`／`forwarded_allow_ips`（[neurova/api/app.py:1643](../../neurova/api/app.py#L1643)、[start_server.py:141](../../start_server.py#L141)）。于是经中继/反代后：

- scheme 判成 `http` → 回连地址给出 `ws://` 而手机需要 `wss://`；
- `request.client.host` 变成代理 IP → `confirm` 那道每 IP 滑窗限流（[mobile_pairing.py:645](../../neurova/api/endpoints/mobile_pairing.py#L645)，常量 `_CONFIRM_RATE_LIMIT=5`／窗口 300s 在 [mobile_pairing.py:112-114](../../neurova/api/endpoints/mobile_pairing.py#L112)）对全体手机合并成一个桶：既形同虚设（可被无限枚举 6 位码），又会因单一代理 IP 互相挤兑（第 6 台设备开始全被 429）。

这不是舒适度问题，是安全后果。

## 3. 架构

### 3.1 组件与事实源落点

```
[手机 App]                  [中继 relay：固定域名]                 [Neurova 服务端：无固定 IP]
  wss 入站 ── 数据面 stream ──▶ 按 routeId 配对 ◀── outbound 控制面/数据面 ── tunnel agent
     │                          │                                        │
     └─ ref → resolve ──────────┘                                        └─ 本机 /api/v1/mobile/*
```

- `neurova/tunnel/protocol.py` — **线格式唯一定义处**：`routeId`/`ref`/`connectTicket` 形状、控制帧类型、错误码、以及 M1/M2 状态枚举字面量（§5.6）。中继、agent、配对端点三方都从这里取。
- `neurova/tunnel/agent.py` — 服务端出站代理。随 FastAPI lifespan 启停，向中继保持一条**控制连接**（outbound WSS，带 `relayEnrollmentToken` + `instanceId`），指数退避重连。
- `neurova/relay/` — 可独立部署的中继（`python -m neurova.relay`），只依赖已在清单里的 FastAPI/uvicorn/httpx。控制面＝注册表＋心跳＋驱逐；数据面＝按 `routeId` 转发。
- App 侧：`libs/pairing/PairingPayload.ets`（载荷解析单源，页面不再放正则）、`libs/state/stores/AuthStore`（凭证权威）、`libs/config/ConfigManager`（服务器档案持久化）。

### 3.2 数据面：一条控制连接 + 按需新开数据连接

每条手机侧连接（HTTP 请求或升级后的 WS）都让 agent **另开一条 outbound 数据连接**：中继在控制连接上发 `open{streamId, method, path, headers}`，agent 回连 `wss://<relay>/agent/data?streamId=`（带 enrollment 凭据），随后双向拷贝。

- **不自研多路复用帧层** ⇒ 没有流间队头阻塞：本仓「大产物 chunk」那条链上，一条长流不该拖住另一条。
- 中继对首包有**小缓冲窗 + 超时**：agent 未在窗口内开出数据连接 ⇒ 显式 503 + `tunnel_not_ready`，不静默重发、不降级成 warning（教义第 2 条）。
- 预热水位（提前开 N 条待租以降低首跳延迟）留作后续优化，不进本期。

### 3.3 路由形状

`https://<relay>/t/<routeId>/api/v1/mobile/ws` — 路径前缀而非子域名。这是「中继终结 TLS」换来的主要简化：不需要泛域名 DNS 与每实例证书。若日后改 TLS 透传，路由粒度只能到子域名，届时一并处理。

### 3.4 配对时序

1. Web 面板 `POST /api/v1/mobile/pairing/generate`（仍带 JWT）→ 落一条 pairing 记录，含 `ref`(22B base62) 与可选 `shortCode`(6 位) → 二维码文本 `neurova://pair?ref=<ref>`，**渲染出去的任何字节都不含 host**。
2. App `PlatformAdapter.scanQRCode()` → 解析 `ref` → `POST https://<discovery>/api/v1/mobile/pairing/resolve {ref}` → 回 `{routeBase, wsPath, expiresAt}`；`ref` 一次性消费，配对记录 `pending → scanned`。App 内置的是**发现域名**（可配置、可持久化），不是某台机器的地址。
3. `POST /pairing/confirm`（带 `ref` 或 `shortCode` + 设备名）→ 回一次性 `connectTicket`（短 TTL、单次消费）与最终 `ws_url`。
4. 建连认证走 `Authorization` 头（Harmony 的 `WebSocketAdapter` 已实现带头，[WebSocketAdapter.ets:123-127](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L123)）或 `Sec-WebSocket-Protocol` 回落；query token 降级为 legacy（§4.2）。
5. 地址漂移（中继重启、route 驱逐后重注册）不影响已配对设备：设备用 ticket 重新换一次地址即可，**不需要重新扫码**。

## 4. 凭据与安全

### 4.1 形状

- `ref`：22 字节 base62，一次性，TTL 300s（沿用现值）。
- `shortCode`：6 位 CSPRNG（现有 `_generate_pairing_code` 已用 `secrets`，[mobile_pairing.py:204-210](../../neurova/api/endpoints/mobile_pairing.py#L204)），手输路径，限流照旧且按真实来源 IP。
- `connectTicket`：一次性，握手时消费并标记 `used`；不重复签名体系，取代今天那串可重放的 HMAC token。**时效短（分钟级）**，过期由 §4.7 的续签路径接续，不需要重扫。

### 4.2 token 出 URL 必须退役

今天 WS 凭证挂在 query：`_build_ws_url(..., token=...)` 拼 `?token=`（[mobile_pairing.py:198](../../neurova/api/endpoints/mobile_pairing.py#L198)），服务端 `websocket.query_params.get("token")` 读取（[mobile_pairing.py:801](../../neurova/api/endpoints/mobile_pairing.py#L801)）；App 侧同样在 `buildUrl` 里附加 `?token=`（[WebSocketAdapter.ets:388-393](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L388)）。**经中继后它必然落进中继访问日志。** 改为一次性 ticket 走 header/子协议；query 形态保留一版兼容并加反挂接守卫，退役与新路径接线同批（教义第 7 条）。

### 4.3 限流与真实来源 IP

中继侧解析受信 `X-Forwarded-For` 链（仅信中继网段），服务端 `proxy_headers` + `forwarded_allow_ips` 打开后，`resolve`/`confirm` 的限流按手机真实来源 IP 计。`resolve` 匿名口自身也要限流（虽有高熵 ref，仍需防中继被当作放大器打）。

### 4.4 中继准入

服务端向中继注册**必须**带 `relayEnrollmentToken`。否则任何人可注册任意 `routeId` 冒充别人的服务端，把手机流量接走——这是本设计新引入的最大攻击面，必须在控制面入口堵死。`routeId` 与 enrollment token 绑定，不可覆盖；同 `instanceId` 幂等重注册。

### 4.5 已登记的已知风险（不作掩盖）

**中继终结 TLS ⇒ 中继位置能读到明文**：对话内容、`agent_id`、`session_id` 对中继可见。本期接受的缓解是「中继只连用户自己的 VPS」＋ 中继访问日志复用 [neurova/security/sensitive_info.py](../../neurova/security/sensitive_info.py) 那台单源脱敏引擎。端到端加密排 S3；UI 上这句风险要以一句话如实呈现（§6.1），不靠"反正是自家机器"当成不存在。

### 4.6 身份链不变

中继只搬运。服务端仍由 `neurova/core/identity_context.py` 的 `neurova_request_user_id` 单点写一次「这一轮是谁」（AGENTS §3），会话可见性照旧走 `meta["session_owner_id"]` 与 `resolveSessionOwner()`。归属只从**发起配对的登录态**出，UI 不提供「这台设备算哪个账号」的选择。

### 4.7 凭证分两层（§10.2 已裁＝丙）

今天只有**一层**：`confirm` 铸一条 24h 绝对期的 HMAC token（[mobile_pairing.py:247-274](../../neurova/api/endpoints/mobile_pairing.py#L247)），且仓内无任何再签发路径——设备离线超窗口即永久失效，只能回屏幕前重扫。本设计拆成两层：

- **设备身份**（长期）：`pairingId` ＋ 设备侧长期密钥。有效期直到用户解除配对——**解除是唯一撤销点**，且撤销即时生效。
- **接入凭证**（短期）：`connectTicket`，分钟级、一次性，用于每次 WS 建连。过期后 App 用设备身份签一条 challenge 换新 ticket（`POST /api/v1/mobile/pairing/refresh`）。

为什么不新建第二套体系：refresh 复用的就是「已配对设备」这层既有关系（`pairingId` ＋ 密钥），不引入独立 token 表、不引入第二个身份概念（教义第 6 条）。设备侧长期密钥落 Harmony 的密钥安全存储，**不入 URL、不入日志、不经中继 query**。

### 4.8 真错修复（与本票选项无关，先行独立交付）

`mobile_websocket` 的 token 认证分支只验签名与时效，**不查在册设备**（[mobile_pairing.py:814-821](../../neurova/api/endpoints/mobile_pairing.py#L814)）；`revoke_pairing` 删设备记录并**会关掉当下那条在流连接**（[mobile_pairing.py:782-788](../../neurova/api/endpoints/mobile_pairing.py#L782)），但那条被删的注册记录在放行判定里**没有任何读者**——即「解除配对」拦得住已经连上的那一条，**拦不住设备随后重连**：旧凭证在剩余 24h 窗口内照样连得上，且连上后照常写回 `is_online=True`（[mobile_pairing.py:837-839](../../neurova/api/endpoints/mobile_pairing.py#L837)），面板上看不出一个已解除的设备正以"在册"的样子在用它。这是 AGENTS §2 点名的「只写不读」断点，也是"24h 绝对期看起来砍不掉"的真实原因：**它在替撤销值班**。

三条必须一起做，且不等隧道：

1. **放行查在册**：建连前校验 `pairingId` 仍在册且 `tokenEpoch` 匹配。
2. **解除对重连生效**：`revoke` 递增该设备的 `tokenEpoch`；当下那条连接的关闭今天已有，本条补的是"关掉之后再也连不上"（判据必须包含重连，只断在流连接会漏掉真错）。
3. **注册表持久化**：`_paired_devices` 今天全在内存（[mobile_pairing.py:104](../../neurova/api/endpoints/mobile_pairing.py#L104)），进程重启即清空。改落 SQLite——按 AGENTS §3，schema 变更加入 `core/db_migration.py` 注册表（PRAGMA user_version），不能只写 `IF NOT EXISTS`。**不做这条的后果是真实的**：一升级，所有已配设备一夜失联，且失联原因看不见。

### 4.9 在册设备的退役判据（§10.2 已裁）

**长期在册，不自动删**；超 30 天无活动只在面板给属主一条提醒（「这台设备已 30 天未连接，是否解除」），**不代为决定**。

- 今天那条按 24h 静默回收的逻辑（`_WS_TOKEN_TTL_SECONDS`，[mobile_pairing.py:118,726-740](../../neurova/api/endpoints/mobile_pairing.py#L118)）随本批退役；它属于「把用户自己配的东西弄丢」那一类错，与 §2.5 那两格同源。
- 选 7 天自动退役被否：手机/平板的间歇使用是常态，周期性使用的设备会被反复删除并强制重扫，与本票「不必回屏幕前」的目标直接矛盾。
- 提醒要有数据支撑：`last_active` 今天只在消息循环里更新（[mobile_pairing.py:856-857](../../neurova/api/endpoints/mobile_pairing.py#L856)），持久化后即为「最近连接时间」，面板直接显示（§6.1）。

## 5. 状态机设计（Web 与 Harmony 两端）

### 5.0 总原则：分层的状态机不许合并

| 机 | 权威事实源 | 谁投影它 |
|---|---|---|
| **M1 配对生命周期**（一次性码） | 服务端 `_pairing_codes` | Web 面板主体、App 配对页 |
| **M1b 在册设备生命周期**（长期设备） | 服务端在册设备注册表（持久化，§4.8） | Web 设备列表、App 服务器档案 |
| **M2 通道/隧道** | 服务端 `tunnel/agent` | Web 状态徽标、App 连接徽标 |
| **M3 设备连接会话** | App `WebSocketAdapter` | App 输入区、顶栏徽标 |
| **M4 面板视图态** | 各端本地 | 纯渲染 |

**UI 只投影，不推断。** 今天面板里 `statusColor = status==='confirmed' ? 'green' : 'default'`（[MobilePairingPanel.vue:98](../../NeurUI/src/components/MobilePairingPanel.vue#L98)）这类就地拼条件就是将来漂移的地方。落地后每端只允许一个 `project()` 把 M1×M1b×M2 映射成 M4，其余位置一律读 M4。

M1 与 M1b 分开的理由是 §2.5 那两格缺口的共同根因：**配对码一次性、设备长期**，两套寿命混进一台机就必然出现「删了记录却没人读」与「过期了却还在轮询」。

### 5.1 M1 配对生命周期（服务端权威）

**状态集**：`none · issuing · pending · scanned · confirmed · active` ＋ 终态支 `expired · revoked · used · aborted`

迁移（`from --事件[guard]--> to : 副作用`）：

- `none --generate(JWT 有效, M2 ≠ relay_unregistered)--> issuing` : 落 `_pairing_codes`，分配 `issueSeq`、`ref`、`shortCode`，TTL 300s
- `issuing --记录落盘--> pending` : 渲 QR（不含 host）、面板开 2s 轮询
- `pending --resolve(ref)[status==pending 且未过期]--> scanned` : `ref` 置为已消费；记 `scanned_at`；**服务端主动推一条 `pairing:scanned` 给面板**（没有这条，面板在轮询间隙只能显示"等待扫码"，而手机那侧其实已经扫完）
- `scanned --confirm[限流通过]--> confirmed` : 发一次性 ticket，设备入 `_paired_devices`
- `pending --confirm--> confirmed` : 手输短码路径（跳过 `scanned`，合法）
- `confirmed --ticket 被 WS 握手消费--> active` : `is_online=true`，ticket 标 `used`
- `* --TTL 到期--> expired` : 现有 `_prune_expired_pairing_codes` 是**直接 pop**（[mobile_pairing.py:213-223](../../neurova/api/endpoints/mobile_pairing.py#L213)），改前必须让面板先读到终态，否则过期与"码从来没存在过"在面板上同形（都是 404）
- `* --面板点「取消」--> aborted` : 释放 objectURL、停轮询。**今天没有这个动作**，面板只能干等 300 秒
- `active --revoke--> revoked` : **补上 §2.5 缺口** —— `revoke_pairing` 要把对应码写 `revoked` 并保留到 TTL 到期，屏幕上的码显示「已解除」，不是 404
- `pending/scanned --换码--> aborted` ＋ 新码 `issuing`

**计时**：TTL `300s`（现值）· 轮询 `2000ms`（现值 [MobilePairingPanel.vue:79-80](../../NeurUI/src/components/MobilePairingPanel.vue#L79)）。**已裁：`scanned` 不设独立宽限计时器**（§10）——`scanned` 只是观测态，独占性来自「`ref` 已被消费」这一事实而非软锁，所以到 TTL 直接 `expired`；已扫未确认的出路是面板「取消并换码」（`aborted`），**不存在 `scanned → pending` 这条回边**。

**面板不可见时**：`document.hidden` 停轮询，回前台立刻补一次（省电且不丢终态）。

**已知竞态**：`tick()` 无请求序号，慢响应会把新码渲染成旧码状态 ⇒ `issueSeq` 单调递增，响应序号 ≠ 当前值即丢弃。

### 5.1b M1b 在册设备生命周期（服务端权威；与 M1 严格分开）

M1 管的是**一次性配对码**，M1b 管的是**长期在册设备**——两者混在一台机里是今天那两处缺口的来源（§2.5）。设备身份长、票据短，分层见 §4.7。

**状态集**：`unpaired · paired · online · offline · dormant(30d 提醒) · revoked`

- `unpaired --confirm（M1 进 confirmed）--> paired` : 生成设备身份密钥对，公钥/身份登记入册（落 SQLite，§4.8 第 3 条），`tokenEpoch=0`
- `paired --WS 建连成功--> online` : 写 `last_active`
- `online --onClose / 中继 relay_down--> offline` : **不删记录**（今天的 24h 静默回收在此退役，§4.9）
- `offline --last_active 超 30 天--> dormant` : 只在面板给属主一条「是否解除」的提醒，**系统不代删**（§4.9 已裁）
- `dormant --设备回连--> online` : 提醒自动消失，无需人工确认（回连本身就是答复）
- `* --属主点解除--> revoked` : `tokenEpoch++` ＋ 关闭在流连接 ＋ 入册标记；此后旧 ticket / 旧 challenge 一律拒（§5.5 第 8、9 条）
- `revoked` 是终态，**不可回 `paired`**：要再用必须重新扫码，走一条新的 M1 配对

**关键迁移（续签，对应 M3 的 `reauthing`）**：`online/offline --ticket 过期 + challenge 验签通过 + 仍在册 + epoch 匹配--> 同态`，仅换发新 ticket，**状态不变**。这是"不必回屏幕前"的机器判据：若一次续签把设备推离了它原所在的态，就是把它当成新配对，与本票违背。

**判据要点**：「在册」这条读面必须真的被建连路径消费（§4.8 修的就是这条），否则 M1b 又是一台只写不读的机。

### 5.2 M2 通道/隧道（agent 权威）

**状态集**：`disabled · probing · via_relay · relay_down · evicted`，另加与 `via_relay` **可并存**的 `direct` 标记

- `（冷启）--未配 relayUrl--> disabled` : 面板 `blockedByChannel`，发码按钮 disable ＋ 原因
- `disabled --配好 relayUrl 与 enrollment token--> probing`
- `probing --注册被拒(401)--> probing(凭据无效)` : 面板显式「中继拒绝本机注册」，**不许显示成未配置**（两形处置动作不同）
- `probing --注册成功拿到 routeId--> via_relay`
- `via_relay --心跳 3 次失联--> relay_down` : 保留 `routeId` 与已配对设备；退避 `1s→2s→…→30s + jitter`
- `relay_down --重注册成功--> via_relay` ; `relay_down --长时间未恢复--> evicted`（需人工介入）
- `direct` : advertised 或入站 Host 本机可达时成立，**与 `via_relay` 并存不互斥**。主投影取「本次发码实际使用的地址来源」——否则局域网用户手机一切蜂窝，已发的码当场失效。

**Web 徽标映射**：`direct`→「本机直连（同一网络可用）」；`via_relay`→「经中继 · routeId · RTT」；`relay_down`→「中继失联，重连中（第 n 次）」；`disabled`/凭据无效→「中继未注册」。App 顶栏徽标读同一批字面量。

### 5.3 M3 设备连接会话（App 权威）

今天这机是「布尔 ＋ 计数」：`connected: boolean` / `reconnectCount` / `reconnectTimerId`（[WebSocketAdapter.ets:68-76](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L68)），无显式枚举。改为显式状态，事件名沿用已有 `ws:connected` / `ws:disconnected{reason}`（[:16-17](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L16)）。

**状态集**：`idle · reauthing · connecting · authed · streaming · reconnecting(n) · failed · closed(manual)`

- `idle --connect(wsUrl, connectTicket)--> connecting` : **guard：凭证必须是配对下发的 ticket，不是 `accessToken`**。今天 [ChatPage.ets:139-141](../../NeurovaHarmony/entry/src/main/ets/pages/ChatPage.ets#L139) 带的就是 `accessToken` ⇒ guard 不满足直接 `failed(auth_credential_mismatch)`，别等服务端 4001 再猜。
- `connecting --onOpen--> authed` : ticket 已单次消费；`AuthStore.wsUrl/wsToken` 从此有读取方（收掉 §2.4 第 3 项）
- `authed --chat:send--> streaming` : 对应服务端「同连接同时只允许一条在流回复」（[mobile_pairing.py:864-871](../../neurova/api/endpoints/mobile_pairing.py#L864)）⇒ 输入区发送键转「取消」；`chat:done`/`chat:cancelled` 回 `authed`
- `* --onClose(code)--> reconnecting(n)` : `n < MAX_RECONNECT(10)`（[:40](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L40)、判定 `:354`）按 `ws_reconnect_interval`（默认 5000ms，[:42](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L42)、读取 `:362`）重试；**到顶进 `failed` ≠ 要重新扫码**——重扫的唯一入口是 refresh 被拒（设备已解除），网络类失败只到 `failed` ＋「立即重试」
- `reconnecting --onOpen--> authed` : 计数归零（现有 `:211`）
- `* --主动断开--> closed(manual)` : **终态，`reconnecting` 不得覆盖它**。真竞态：manual close（[:163-164](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L163)）之后在途 `onClose`（`:225-236`）仍可能排一次重连 ⇒ 用显式 `closed` 标志双向咬合，写进红灯
- `* --网络切换（蜂窝↔WiFi）/ 回前台--> reconnecting(0)` : 计数重置并立即连。IP 变了旧流必死，中继侧 `routeId` 不变——**隧道场景高频迁移，今天完全没有**
- `idle --ticket 已过期(本地时钟判定)--> reauthing` : 用**设备身份密钥**签 challenge 调 `/pairing/refresh`（§4.7）；成功→ 拿到新 ticket 进 `connecting`；失败按原因分列（见下方关闭码处置）
- `reauthing --refresh 成功--> connecting` : **M1b 状态不变**（`paired`/`offline` 原地续期），这是"不必回屏幕前"的客户端侧证据
- `reauthing --refresh 被拒(不在册 / epoch 不匹配)--> failed(device_deregistered)` : 文案直接指向「这台设备已被解除配对，请重新扫码」，并给配对页入口——**这是唯一需要重扫的路径**
- `* --pong 超时--> reconnecting` : 心跳 `ping` 间隔 30s（[:38](../../NeurovaHarmony/entry/src/main/ets/libs/adapters/WebSocketAdapter.ets#L38)、循环 `:327-334`）；中继上静默断流不会有 close 帧，判死不能只靠 `onClose`
- 关闭码处置分三档（今天一律只回一句 `reason`）：`4001` 且本地 ticket 未过期 → 先 `reauthing` 试一次，再失败才 `failed`；`4001` 且 refresh 也被拒 → `failed(device_deregistered)` → 配对页；`4008`（单用户超限，`MAX_CONNECTIONS_PER_USER=5` 见 [mobile_pairing.py:121](../../neurova/api/endpoints/mobile_pairing.py#L121)）→ 「该账号设备已达上限」＋ 设备列表入口，**不重连**（重连只会把计数打满）

### 5.4 M4 面板视图态

把现有 5 个分散 ref（`generating/pairing/status/devices/errorText/qrUrl`）收成显式态：

`bootstrapping · unauthed · blockedByChannel · idle · issuing · awaitingScan · scannedWaitingConfirm · confirmedFlash · expiredOrRevoked · failed · unknown`

- `bootstrapping` → 拉 `tunnel/status` ＋ 设备列表；读不到即 `unknown`，**整块撤下**（沿用现有纪律 [MobilePairingPanel.vue:152-160](../../NeurUI/src/components/MobilePairingPanel.vue#L152)，不许把网络/权限问题扮成"进行中"）
- `blockedByChannel` → M2 ∈ {`disabled`, 凭据无效}：生成按钮 disable ＋ 原因，QR 区不渲染
- `awaitingScan` → QR ＋ 短码（次要视觉）＋ 倒计时 ＋ 取消动作（对应 M1 `aborted`）
- `scannedWaitingConfirm`（**新**）→「手机已扫，等待其在手机端确认」＋ 撤回；缺这格时那段会被渲染成"等待扫码"
- `confirmedFlash` → 收摊（QR ＋ ref 链接一起消失）＋ 设备列表刷新
- `expiredOrRevoked` → 两形分文案（今天合并成一句「已过期」，[MobilePairingPanel.vue:95](../../NeurUI/src/components/MobilePairingPanel.vue#L95)）
- 设备在线态：让 M4 的 poll 顺带刷设备列表（无活动配对时降频 10s），修掉 §2.5 快照不刷新
- 在册提醒位（M1b=`dormant`）→ 设备行尾一句弱提示「已 30 天未连接，是否解除」，**不是告警态**（`--nr-text-tertiary`，不加 `--nr-warning` 色）；设备回连即自动消失，无需人工确认——提醒是信息，不是待办积压

**M4′ App 配对页视图态**：`idle · scanning · resolving · waitingConfirm · successFlash · failed(分型)`。`resolving` 是 `ref` 形状新增的一格（有网络往返，必须可见）。`failed` 分四型：无效载荷 / 发现服务不可达 / 中继未注册 / 码已过期或已用——不再是一句「无效的配对二维码」（[PairingPage.ets:111](../../NeurovaHarmony/entry/src/main/ets/pages/PairingPage.ets#L111)）或裸 `e.message`（`:160-162`）。

### 5.5 非法迁移矩阵（这些必须红）

1. `expired → confirmed`（重放已过期码）必须拒
2. `confirmed → pending`（同一 `ref` 二次 confirm）必须拒且回 `used`
3. `ref` 二次 `resolve` 必须拒（一次性）
4. `active → revoked` 必须可达，且面板显示「已解除」而非 404
5. `closed(manual)` 之后不得出现 `reconnecting`
6. M2=`disabled` 时 `generate` **必须由后端拒绝**并点名原因——面板 disable 只是 UX，服务端拒绝才是判据（教义第 1 条：不在 consumer 侧兜）
7. `direct` 与 `via_relay` 并存时，已发出的 QR 地址来源不得漂移
8. **`scanned → pending` 这条回边不得存在**（§10.1 已裁）：`ref` 一经 `resolve` 即消费，任何"超时后把码退回待扫"的实现都等于把一次性凭据改成可重放。判据形态=断言该迁移既不发生在数据上、也不出现在状态枚举的合法边集合里
9. **`revoked → paired` 不得存在**：解除后必须重新扫码走一条新的 M1 配对，不许"恢复在册"（否则解除动作不可信）
10. **不在册设备不得建连成功**（§4.8 第 1 条）：`revoke` 之后用旧 ticket／旧 challenge 各试一次，两次都必须被拒——今天这一格是**漏的**（认证路径不查在册）
11. **`tokenEpoch` 变更后该设备所有旧 ticket 立即失效**（§4.8 第 2 条）：在流连接也必须被主动关闭，不许等它自己超时
12. **refresh 成功不得改变 M1b 状态**（§5.1b）：续签是续期，不是重新配对；若实现把 `offline` 推成 `paired`（或反之）即为本条红

### 5.6 状态枚举的跨语言单源

字面量定义在 `neurova/tunnel/protocol.py`；Web 侧 `NeurUI/src/api/modules/mobile.ts` 与 Harmony 侧 `libs/types` 各持一份同名集合。加守卫 `tests/unit/test_tunnelStateEnumSingleSource.py` 断言**三处字面量集合相等**（先例：`tests/unit/test_repair_discipline_guard.py` 的三落点逐条咬合）。不生成代码、不加同步脚本——那是教义第 6 条点名的"两边都留着加个同步脚本"。

## 10. 子裁定记录（两则均已落）

### 10.1 已裁（2026-10-24）· `scanned` 超时处置 ＝ 直接 `expired`，**不设宽限计时器**

用户裁定取「直接 expired，且不设独立宽限」。决定性理由按权重：

1. **回落 `pending` 与 `ref` 的一次性属性冲突**（技术否决点）：`ref` 在 `resolve` 时即消费，这也是它把枚举面从 10⁶ 抬到约 2¹³⁰ 的全部理由。要回 pending 只有两条路——把 `ref` 改成可重放（旁人拍下的那张图在超时后又活了），或给同一配对记录换新 `ref`（已扫码那台手里那条已死，屏上 QR 还得中途重绘，`confirm` 带旧 `ref` 被拒）。两者都比"直接过期"更糟。
2. **少一个计时器**：原先的「宽限」把 `scanned` 当成一把需要有人解锁的软锁；一次性 `ref` 之下没有可解的锁——这张 QR 对所有其他设备已经死了，独占性来自 `ref` 本身。面板因此只有一套倒计时口径。
3. **面板语义更稳**：回 pending 会让倒计时中途从「已扫码，等待其在手机端确认」翻回「等待扫码」而图还是同一张，用户无法判断是不是同一次扫码。直接过期是一句干净的终态。
4. **不新增状态迁移**：`expired` 今天已在产（[mobile_pairing.py:655,709-710](../../neurova/api/endpoints/mobile_pairing.py#L709)），回 pending 要新写一条边并配反证测试（教义第 2 条：净 LOC 默认 ≤ 0）。
5. **误扫有人工出路，不需机器代劳**：属主点「取消」→ `aborted` → 立刻换新码，秒级恢复。

落成的形态：`pending --resolve--> scanned`（`ref` 消费）→ 随 TTL 到点 `expired`；`scanned` 期间任何时候 `confirm` 都可用（只要未过期）；**不存在 `scanned → pending` 回边**（已写进 §5.5 第 8 条，S1 红灯咬合）。

### 10.2 已裁（2026-10-24）· 凭证策略 ＝ 丙（设备身份长期 ＋ 接入凭证可续签）；在册退役 ＝ 长期在册＋30 天提醒

**先说这一票的真问题**：它不是"24h 长还是短"。今天的 24h 绝对期之所以看起来砍不掉，是因为**它在替撤销值班**——认证路径不查在册（§4.8），所以"让凭证自然过期"是全仓唯一真正生效的失效手段。把窗口调长而不补撤销，等于把安全边界直接拉长。因此本票落成两件事，其中撤销那件**不进选项、先行交付**。

**已裁一：凭证分两层（丙）**

- 设备身份长期（`pairingId` ＋ 设备侧密钥），到解除配对为止；接入凭证 `connectTicket` 分钟级一次性，过期后用设备身份签 challenge 走 `/pairing/refresh` 续。
- 否掉甲（维持 24h 绝对期）：服务端在家、手机在网外的场景下，超一天就得回屏幕前重扫——中继隧道的全部价值正好是"人不在家也能连"。而且甲并没有换到撤销能力（旧凭证在剩余窗口内照样连得上）。
- 否掉乙（只在长连期间随帧轮换、不新增端点）：它治"长连"不治"间歇回连"，而关机过夜／飞行模式一天是手机的常态，回来仍要重扫。省一个端点，换来的是主场景没被覆盖。
- 设备身份复用「已配对设备」这层既有关系，**不新建第二套身份/token 体系**（教义第 6 条），见 §11。

**已裁二：在册设备长期保留，超 30 天无活动只提醒不代删**

今天那条「离线且配对超 24h 即静默删除」的回收逻辑（`_WS_TOKEN_TTL_SECONDS`，[mobile_pairing.py:118,726-740](../../neurova/api/endpoints/mobile_pairing.py#L118)）随本批退役——它属于「把用户自己配的东西弄丢」那一类错。7 天自动退役亦否：周期性使用的设备会被反复删除并强制重扫，与已裁一的目标直接矛盾。

**连带必做的三条真错修复（§4.8，归 S1a，不等隧道）**：放行查在册、`tokenEpoch` **使解除对重连生效**（关掉当下连接今天已有，缺的是"关掉之后再也连不上"）、在册注册表从内存落 SQLite（按 AGENTS §3，schema 变更加入 `core/db_migration.py` 注册表 PRAGMA user_version）。第三条不做的后果是实打实的：**一升级所有已配设备一夜失联，且失联原因看不见**。

**代价如实登记**：新增 refresh 端点、认证从纯无状态 HMAC 改为查有状态注册表、设备长期密钥落 Harmony 密钥安全存储（不入 URL／不入日志／不经中继 query）。净 LOC 为正，须在提交说明里逐条列去向（教义第 2 条）。

## 11. 不做的事

- 不引入第三方隧道二进制（已裁自研中继）。
- 不做 P2P／QUIC 打洞／IPv6 直连——CGNAT 场景由中继覆盖，自研打洞的复杂度与可测性不成比例。
- 不把会话记录可见性接到隧道身份上（仍走 `meta["session_owner_id"]` 单点，AGENTS §3）。
- 不在面板上提供设备归属选择（§4.6）。
- 不建第二份二维码渲染器、第二套配对凭据、第二处对外地址定义（教义第 6、7 条）。
- **不新建第二套身份／token 体系**：接入凭证的续签复用的就是「已配对设备」这层既有关系（`pairingId` ＋ 设备身份），不另立一张 token 表、不另加一个身份概念（§4.7）。
- **不代属主删设备**：长期在册 ＋ 30 天无活动只提醒（§4.9）；同时也不许把「延长凭证有效期」当成退役判据的替代——那是 §10.2 已裁掉的旧依赖。

## 11.5 落地时的三处改判（以改规则为准，不以字面为准）

实施（2026-10-24）时有三处发现"文档字面"与"仓库现实"不符。按 AGENTS 的
「规则与行为不一致时，以改规则为准」处理，逐条留在此处，不当没发生过：

1. **§5.5 第 6 条由"disabled 也拒发码"收窄成"配了中继且未注册才拒"**。
   字面照做会当场打死已上线并有在册判据的**局域网配对**（`test_mobile_pairing_endpoints.py` 那一档），
   而 S0 交付的「一台固定域名的反代机 ＋ advertised」那条路也必然一起废掉。
   落地形态：面板 disable 只是 UX，后端 `503 tunnel_not_ready` 只在
   `configured && state != via_relay` 时出，且把 state 一并回出供诊断。
2. **面板保留一个 10 秒空频定时器**，与在册判据 `MobilePairingPanel.test.ts` 里
   `vi.getTimerCount() === 0` 的字面冲突。那条判据本要守的是"凭据面必须全停"
   （注释自己写了：要断的是不再打状态口），而 §2.5 第二格的实测缺口正是
   "面板开着，在线/离线永不变化"。改判后钉的是：状态口调用次数不再增长 ＋ 二维码已撤 ＋
   设备列表确实在刷。字面的 `getTimerCount()===0` 已移除。
3. **中继必须先拿到上游握手结果再 accept 手机**。原设计没写这一步，第一版实现照做就
   把后端的 `4001 device_deregistered` 吞成"手机连上了"（活体 `[5b]` 当场红，红得对）。
   落地形态：agent 先连本机后端，成功才回 `head{status:101}`；中继收到 101 才 accept，
   否则带着上游的状态码关闭手机侧连接。这条补进 §3.2 的实现口径。

②`ConfigManager` 去硬编码默认值 ＋ 补上 `applyServerProfile`（那条"写了没人调"的持久化路）。
