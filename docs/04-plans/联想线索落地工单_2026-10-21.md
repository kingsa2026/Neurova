## 0. 一句话方案

给每条记忆挂若干**只参与检索、永不进提示**的「联想线索」（`associativeCue`），第一批用本仓**既有规则面**零成本派生并并入词法索引，第二批在**已接线的空闲固化窗口**里按批生成前瞻线索、建一份 `cueText→memoryId` 的旁路向量面、以**实测标定**的余弦门把命中 id 并进现有候选集再走原 RRF —— 全程不改排序公式、不做级联替换、失手即回落平路。

基线与目标（TM-1 实测，`tests/performance/memory/test_associativeRecallGate.py`）：

| 子集 | hit@1 | hit@5 | MRR | 目标线 |
|---|---|---|---|---|
| 描述性（词面重合） | 10/10 | 10/10 | 1.000 | 不得下降（地板判据已钉） |
| 联想（词面不相交） | **2/10** | **6/10** | **0.350** | hit@1 ≥ 6/10（现为 strict xfail） |

零中文字面重合的招牌那条今天 rank=99（进不了前 10）。

## 1. 从它代码里核出来的东西：四条能借、五条不能借

**能借（且已想清楚在本仓长什么样）**

1. **两条访问路各自用不同的文本构造**。它的稠密索引用**不重复拼接**（`stage3_index.py:378-407`：content + query_patterns + keywords + temporal + spatial，各一次），BM25 才用**复读加权**（`:65-91`：content×3、query_patterns×2）。⇒ 本仓照此分治：线索进词法面用加权追加，进稠密面只做一次拼接，**不许用复读喂稠密编码器**（bge 系列会把复读读成强调，改变语义向量）。
2. **候选并集 + 存活性过滤**。它把旁路召回的 id 先与真实条目集取交，再并进入选池（`stage6:804-811`），旁路**只加候选不直接给结果**。⇒ 本仓形态：线索通道只返回 `memoryId` 集合，与当期作用域基集取交后并进 `recall` 的候选，排序仍由既有 RRF + origin 信任决定（`manager.py:2104-2115` 不动）。
3. **高置信门是「加法安全」的**。它对查询↔线索余弦取 hard gate，且 docstring 明写高门是为了「additive-safe」（`trigger_recaller.py:138`）：宁可不注入，也不注入噪声。⇒ 本仓必须同样高门，且**阈值数值不抄它的 0.85**（见 §3 标定法）。
4. **每次旁路命中都留结构化读数**。它记录 `fired / top1_cosine / n_recalled / n_valid / n_new / connected_before / connected_after`（`stage6:812-825`）。⇒ 本仓同族读数进 `manager.get_stats()`，该面已被 `GET /v1/memory/stats` 读（`api/endpoints/memory/crud.py:118-125`）——写了就有人读，不留 §2 型断点。

**不能借（每条都写清在本仓会坏在哪）**

| 它的形态 | 出处 | 本仓不采用的理由 |
|---|---|---|
| 逐轮 LLM 判边界 | `stage1:131-173` | ≈1 次调用/轮；本仓写侧显式 $0（`moe_dependency_extractor.py:1-4`） |
| 逐条 LLM 生成线索 | `build_trigger.py:43-63` | 本仓原子单位是「一条消息」，比它的 scene 粒度小 3–5 倍，单位成本再乘失配倍数 |
| 线索去重用 rapidfuzz 线性扫全表 | `trigger_index.py:162-177` | 每条新线索对全部已存线索做 O(n²) 比对；本仓线索随会话线性增长，10 万条即不可用 ⇒ 换**归一键精确命中 + 向量近邻**两相 |
| 主题层为空即整体返空 | `stage6:580-583` | 预过滤失手的用户可见症状是「完全没有记忆」；本仓要的是**放宽而非中止** |
| 每会话一个 pickle 索引、整会话重建 | `stage3_index.py:164-166`、`build_memory.sh:133-160` | 无增量语义；本仓是在线 per-agent SQLite |

另记它自身的一处矛盾，免得连缺点一起搬：`trigger_index.py:185-189` 注释说「丢了全部条目的线索仍要留，其 `activation_patterns` 召回时还可能有用」，而 `trigger_extractor.py:220-222` 又把无条目的线索**删掉**——两处口径相反，且 `activation_patterns` 在查询期从未被读。本仓不引入无读者的字段。

## 2. 设计（数据面 / 写侧 / 读侧 / 渲染面）

### 2.1 数据面：一张新表，同一座库，不新建第六个存储

`memory_cues` 建在既有 per-agent 记忆库 `data/<agent_id>/memory/memory.db`（`core/agent_workspaces.py:159-161`；现 DDL 在 `manager.py:445`），经**迁移注册表**加版本，不写 `IF NOT EXISTS` 就完事（`AGENTS.md` §3）：

```
register_migration(<现读最大版本+1>, _migrateAssociativeCues, domain="memory")
```

注册函数口径已核：版本号严格递增、重复注册幂等忽略（`core/db_migration.py:34-47`）；建新表必须给**可调用步骤**（executescript 会隐式提交，见其 docstring `:79-81`）。

列（命名按 §2 协作红线 camelCase / PascalCase，禁 `data`/`info`/`manager` 类模糊词）：

| 列 | 语义 |
|---|---|
| `cue_id` | 主键 |
| `memory_id` | 归属记忆行（**不复制内容**，检索命中后回源行） |
| `cue_text` | 线索文本（本仓自设生成，只参与检索） |
| `cue_kind` | 闭集枚举：`hypernym`（上位名）/ `situation`（情境）/ `foresight`（前瞻）——**不叫 trigger**，避开 `explainability.py` 的死 trigger-chain 与 `schema.py` 的死 `trigger_chains` 表 |
| `cue_source` | `rule` / `model`，标记这条是零成本派生还是模型生成（预算与审计用） |
| `confidence` | 生成期置信度 |
| `norm_key` | 归一键，去重第一相 |
| `created_at` / `agent_id` / `neuser_id` / `user_id` | 与主表同三元组，**作用域必须一致**（否则跨用户串线索，撞 §6-163 身份单源裁定） |

同批必须做的收口（§7 先比后合）：`memory_layer/schema.py` 那份零 importer 的死 DDL（含 `trigger_chains`/`memory_relations`，活库无此表）**在同批净删**——留着一份「触发器表 DDL」而新表叫 `memory_cues`，就是给下一个读代码的人埋双源。

### 2.2 写侧：两档成本，各走各的门

**TM-2a（零 LLM）**：线索由本仓**已有的三个规则面**派生，不新造提取器（§6 单一事实源）——
`SemanticSearch._extract_keywords` 的 CJK 2–4 字串（`semantic_search.py:102-138`）＋ `MemoryAutoClassifier.classify_category_multi_label` 的上位类别（`auto_classifier.py:332`，**现值内部自用、chat 主路从未调用**，本批正是它的第一个真实消费者）＋ `DependencyGraph` 已抽出的实体名（`moe_dependency_extractor.py:218` 附近）。

**TM-2b（模型生成，默认关）**：走**已接线**的空闲固化窗口，不新起线程、不挂请求路——
`IdleTimeTracker._trigger_consolidation`（`core/idle_tracker.py:209-273`）在 daemon 监控线程上跑，手工/超载入口在 `post_chat_pipeline.py:3251-3260`。模型调用形态复用 `PatternCrystallizer.review_pending_with_llm` 的既有先例：注入 `llm_client`、**一次批量提示覆盖整批候选**、异常则候选留队下次再来（`pattern_crystallizer.py:491-529`；装配点 `post_chat_pipeline.py:3188-3190`）。

⚠ 实测约束（写进判据，不写进希望）：该窗口**当前没有单次工作量上界**——它 `get_all_memories()` 后对**全库**跑 `run_sleep_cycle`（`idle_tracker.py:244-253`）。所以线索生成必须自带三把闸，缺一即不许合：`cueGen.enabled`（默认 false）、`cueGen.maxRowsPerRun`（每轮最多扫 N 条新行）、`cueGen.maxLlmCallsPerRun`（硬上限）。

配置单源落 `MemorySettingsConfig.PARAM_SCHEMAS`（`memory_layer/settings_config.py:37`，持久化 `<data_dir>/memory_settings.json`，读取口 `get(key, default)` `:210`，带 min/max 校验 `:275-278`）。注意：该表里唯一的 bool 行是默认**开**的 `compression.enable_llm_compression`，本批的 `cueGen.enabled` 是这面上第一条默认**关**的 bool——落地时把这条口径写进提交说明，别让人以为开关默认开。

### 2.3 读侧：并进候选，不替换排序

现有两路输入的位置已核实：稠密向量在 `manager.py:2066-2076`（`store.search(query, limit=limit*2)` `:2070`，向量恒为 `encode(mem["content"])` `unified_vector_store.py:696-697`）；词法在 `:2079-2101`（`search_by_keywords` 计分是**命中关键词条数** `semantic_search.py:255-257`）。

- **TM-2a 改词法面**：`upsert_memory_index` 除对 `content` 抽词外（现值 `:224`），再对该行的线索文本抽词，**同一个 `memory_id` 追加进同一份关键词桶**（桶结构 `:226-228` 天然支持一 id 多词）。零新索引、零迁移、零模型调用。
- **TM-2b 加旁路**：新建**一份** `UnifiedVectorStore` 实例专门承线索——payload 装 `{cueText, memoryId, cueKind, confidence}`，`search()` 返回的就是整份 payload（`unified_vector_store.py:802-804`），于是「索引进的是线索、交回的是 memoryId」直接成立。**不要**试图往主实例塞第二条同 id 向量：`index_memories` 在 `incremental=True` 下按 id 跳过已存在项（`:690-692`，实测读到），伪命中会以「加了线索但向量里根本没有它」的形态静默发生。
- 通道结果只在 `enabled && 引擎可用 && 通过门限` 时并集；任何异常/缺线索 → **原平路结果照常返回**，并记一条 `cueChannel.skipped=<原因>`。即「**放宽而非中止**」，与它的 `stage6:580-583` 反向。

### 2.4 渲染面：分离是免费的，但要钉住

`ContextInjector._build_memory_context` 每行只渲染 `f"- {content}"`（`context/injector.py:604`），`metadata` 与任何派生字段都不进提示；预算折叠 `_foldMemoryLineToBudget`（`:978-1010`）。所以「线索只作访问路、不作证据」在本仓**结构上已经成立**——但这是巧合不是契约，必须补一条常驻判据把它钉住：*任何 `cue_kind` 的文本不得出现在渲染出的记忆段里*（防后人把线索当摘要塞进 line）。

## 3. 门限标定（不许抄 0.85 的正式做法）

它的 0.85 是配 `bge-m3`（1024 维、跨语言）调出来的；本仓是 `bge-small-zh-v1.5`（512 维，`models/embedding/bge-small-zh-v1.5/`，已入 git/LFS）。余弦分布不同，抄数即错数。

标定协议（写进 TM-2b 的红灯，随判据入仓）：
1. 在 TM-1 语料上，对每条联想查询算「查询↔正确线索」与「查询↔全部干扰线索」两组余弦；
2. 取**使精确率 ≥0.9 的最低门限**（即注入 10 条至少要 9 条是对的）作为默认值；
3. 门限值、标定语料指纹、标定读数一并进 `docs/05-reports/` 读数档与提交说明，配置键存实测值；
4. 判据形式：门限上调 → 注入率下降可接受；门限下调到精确率 <0.9 → 红。

配套读数（进 `manager.get_stats()`，被 `/v1/memory/stats` 读）：`fired / top1Cosine / nRecalled / nValid / nInjected / skippedReason`。

### 3.1 实测更正（2026-10-22，批 C-1 落地时）

上面第 2 步「取精确率 ≥0.9 的最低门限」**在本仓语料上无可行解**，实标定数据推翻了自己的假设：

| 量 | 读数（66 行干扰集 + 10 条盲写线索，本机 ONNX 现算） |
|---|---|
| 目标线索的最好余弦 | 0.465 – 0.612 |
| **其它记忆的线索**最高余弦 | **0.687**（比多数目标的自身余弦还高） |
| 干扰项正文最高余弦 | 0.631 |
| 门限 0.30/0.35/0.40/0.45 | 点火 10/10，top-1 精确率恒 **7/10** |
| 门限提到 0.50 | 点火掉到 9/10，精确率反而降到 6/9 |

根因不在「线索与查询像不像」，而在**线索与线索之间互相串味**：泛写的线索（「外出就餐点菜」）
对很多查询都相似，抬门限只会把该捞的也一起挡掉。当前取 0.45（该语料的最优点），代价是每 10 次
注入约 3 次是别人的记忆——所以通道**只加分不重排**、权重压在两路主信号之下，把误注的可见代价
限制在「名次」而不是「顶替」。

另两条同期实测：**抄来的 0.85 在本仓等于通道永不点火**（实测 `fired=0 / droppedByGate=152`），
本仓余弦分布整体低于 bge-m3；**词法通道走不通**——把理想线索灌进关键词倒排后 TM-1 联想读数
一字未动，因为那把刀是「连续中文按 2–4 字非重叠切片」，两句不同的话切片几乎对不上。
批 C 的通道因此是向量而非 BM25。

- 乙 **空闲窗口内每轮 ≤25 次、每会话 ≤200 条线索**（批 C 默认值建议）：按 20 行/次批量，摊到每轮 ≈0.05 次调用，是它原始形态（≈2.1 次/轮）的 **1/40**；风险在固化窗口墙钟（该窗口现无预算上界，见 §2.2 ⚠）。
- 丙 **不设上限，段落级全量生成**：最接近论文形态，读数上限最高，但把每轮写入成本抬高一个量级，且与本仓写侧纪律正面冲突。

推荐 **甲先行、拿到批 A 的实测涨幅再按乙设档**——理由：批 A 的涨幅是判断「模型生成的前瞻线索到底值多少」的唯一本地证据，而现在两者都还没有。

## 6. 验收与复核口径

每批走完八段：复核实状 → 红灯（红须落在行为断言）→ 绿灯 → 红自证（带唯一 `-m` tag stash 本次改动面复跑）→ 宽域 A/B（仓外 worktree 建 HEAD 基线，比失败**集合**）→ live-verify（真 `MemoryManager` + 真 `recall` + 真 `/v1/memory/stats` 读数；线索通道的 `fired/nInjected` 必须出**非零读数**才算在路上，全零读数不算通过）→ 单批一 commit → 落库后复取并入 `protected_tests.txt`。
