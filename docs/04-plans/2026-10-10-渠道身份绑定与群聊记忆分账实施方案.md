# 渠道身份绑定与群聊记忆分账 · 实施方案（2026-10-10）

> 台账出处：§6-123（成因）→ §6-127（本方案的裁定）。用户 2026-10-10 拍板四条，本文是它的实施口径。
> 与 `docs/渠道agent隔离改造计划_2026-09-13.md` 不同职：那份做的是"每 agent 各配各的 bot"
> （多实例、会话物理隔离、配置级身份冲突 409），本方案做的是"**渠道发送者 ↔ 平台账号**"的映射与
> 由此产生的记忆分账。两者共用的只有会话 scope 键口径 `{agent_id}:{chat_id}`（沿那份已定的，不另起）。

## 1. 已定的四条（不再讨论，实施照此）

| # | 裁定 | 实施口径 |
|---|---|---|
| ① | 未绑定发送者给**渠道专属隔离空间**，可事后提升 | 键沿用技能库既有口径 `ch:{渠道}:{发送者}`（`skills/skill_visibility.py:138-161`），不再落 `"default"`。绑定成功后**只影响今后写入**：历史留在原命名空间，读侧双读（个人键 + 渠道键）——不做不可逆的合并搬迁 |
| ② | 绑定关系与码**接续既有实现**，不造第二套 | 实装 `neurova/channels/models.py:98` 已声明、管理器从未落地的 `UserIdentity`（补 `UserIdentityManager` + sqlite 表）；绑定码接 `auth/verification_code.py`，新增 `VerificationType.BIND_CHANNEL`（该文件已 sqlite 持久化、有 TTL/次数上限，是"码"的唯一现有实现）。**不接** `mobile_pairing`（设备↔用户、纯内存 dict、重启即丢） |
| ③ | 绑定作用域＝**agent 级**（每 agent 各绑一次） | 唯一键 `(agent_id, channel_type, channel_user_id)` → 平台 `user_id`。∴ 记忆检索键的构成不变（`isolation.py:48-64` 的 `{agent_id}:{neuser_id}:{user_id}` 本就含 agent_id），绑定表多带一个 agent 维度而已。代价如实记：同一渠道用户在 N 个 agent 下要绑 N 次；自助绑定流程必须把 agent 上下文带进码里，否则跨 agent 串用 |

## 2. 开工前实状（逐处 file:line 复算，不是推断）

- 渠道入站：`channel_router.py:126-140` 造的 meta 有 `channel_user_id`/`chat_id`/`chat_type`/
  `source_channel`/`turn_origin`，**没有 `user_id`**；`:180` 另把 request 侧通道设成
  `agent.config.owner_user_id`；`:215` 才 `agent.chat(...)`。
- 轮身份：`chat_pipeline.py:613` 取 `(ctx.metadata or {}).get("user_id")` →
  `turn_context.py:386` 落 `"default"`。⇒ 只读轮身份的那一族（`tool_executor.py:524`/`:5407`、
  `post_chat_pipeline.py:1067`、`swarm.py:626`、`mcp_server.py:153/187`）把**所有**渠道发送者当同一个人。
- 记忆作用域**只从 JWT 写**：`api/deps.py:118-125`、`api/endpoints/memory/base.py:211-212`；
  渠道路径没人调 `set_request_scope`（`memory/manager.py:864`）⇒ 全落 `(default, default)`。
- 已有但不同职的"码/绑定"三面：`mobile_pairing.py:102-104`（设备↔用户，内存态）、
  `qclaw_binding_model.py:109-123`（外部应用凭据↔用户，唯一真持久化的 binding 表）、
  `verification_code.py:28-34`（注册/改密/登录/换邮/2FA 五型）。
- 会话 scope 已有分组：`channels/manager.py:686-703` 按 `chat_id`（群共享）或
  `chat_id:sender_id`（`share_session_in_group` 关）——但**无 `chat_type` 分支**，群与私聊只靠 chat_id 隐含。
- 闭集可复用：`skill_visibility.py:31` `_SYSTEM_IDENTITIES = {"", "default", "system", "anonymous", "unknown"}`
  ——身份"是不是真实主体"的判定已在此一处，本方案不复述它（教义第 6 条）。

## 4. 红线与不做的事

- 不新建第二套"码"实现、不新建第二张绑定表、不复制 `_SYSTEM_IDENTITIES` 判定。
- 不做不可逆的历史记忆搬迁：①的"提升"只改今后写入的归属，历史双读；要合并须另裁。
- 渠道 `user_id` 一律**服务端解析**，不信入站报文自带的同名字段（否则外部可冒充平台账号）。
- `data/` 零写入用指纹自证；每批 live-verify 走 `create_app` + TestClient + `_liveVerifyIsolation`。
- 隐私边界（本方案不解决，只标记）：群共享作用域意味着**同群成员可见彼此沉淀的群记忆**，
  这是 ④ 的直接后果，需在 UI 与文档如实写清，不得只做成技术默认值。
